# 依頼
FMG（Fantasy Map Generator）のパフォーマンス改善の一環として、「海洋レイヤー（Ocean Layers）」の描画システムを、現在のレガシーなD3.js（SVGパス方式）から、GPUアクセラレーションを効かせた **WebGL** での描画へ移行します。

以下の「背景」「設計・実装要件」「注意事項」を厳守し、新しく作成する海洋WebGLレンダラークラスのコード（TypeScript）およびシェーダープログラム（GLSL）のモジュールを生成してください。

---

# 1. 開発背景とターゲット
- **目的**: ズームやパン（ドラッグ移動）のたびに発生する、膨大なSVG海岸線パスの再計算・再レンダリングによるCPUボトルネックを完全に破壊する。
- **スコープ**: 海洋レイヤーは原則として「表示専用（編集を行わない）」ため、依存関係を極限まで排除した疎結合なグラフィックスコンポーネントとして実装する。
- **拡張性の考慮**: 近い将来、平面の2D地図だけでなく、地図データを球体にマッピングする「Globe（地球儀ビュー）」への3D展開が確定している。そのため、描画ロジックと3D/2Dの座標変換（頂点シェーダー）は切り離せる設計にする。

---

# 2. アーキテクチャおよびディレクトリ構造（要件）
現在、プロジェクトはモノレポ構造でリファクタリングを進めています。
今回のコードは、将来的に `packages/@fmg/ocean/src/` 以下に配置されることを想定し、他のドメイン（`burgs`, `rivers`, `states`）のコードや、`window` 直下のグローバル変数に直接依存しないようにしてください。

### 生成してほしいファイル構成
1. `OceanRenderer.ts`: WebGLの初期化、コンテキスト管理、バッファ転送、描画命令（Draw Call）を担当するメインクラス。
2. `ocean.vert.ts`: 頂点シェーダー（GLSLを文字列としてexport）。
3. `ocean.frag.ts`: フラグメントシェーダー（標高データ等をもとにピクセル色を決定するGLSL）。

---

# 3. 技術的制約・実装アプローチ（注意事項）

### ① レガシーDOM・グローバル依存の完全排除（重要）
- `window.grid` や `window.pack` をレンダラーの内部から直接参照することは絶対に禁止します。
- 地形データ（標高マップや海岸線インデックス）は、すべてJavaScriptの **`Float32Array` や `Uint16Array` などの TypedArray** として、初期化時またはデータ更新時に外部から引数（コンストラクタ）経由でインジェクトする設計にしてください。

### ② Globeビュー（地球儀）を見据えたシェーダー設計
- 2D平面と3D球体（Globe）のどちらにも対応できるよう、頂点シェーダー（Vertex Shader）側で「投影行列（Projection Matrix）」および「ビュー行列（View/Model Matrix）」を正しく受け取れる（`uniform mat4`）標準的な3Dグラフィックスパイプラインの構造にしてください。
- データの二重持ちによるメモリ枯渇を防ぐため、グリッドのUV座標、またはグリッドインデックスからシェーダー内で座標をサンプリング（あるいはテクスチャマッピング）できる構造を意識してください。

### ③ メモリアロケーションの最小化
- FMGは数万〜数十万のセルを扱います。毎フレーム `new Float32Array()` が走るようなコードはガベージコレクション（GC）のスパイクを引き起こすため厳禁です。
- WebGLの `gl.bufferData` や `gl.bufferSubData` へのデータ転送は、必要なデータが更新されたタイミング（地図の初回生成・再生成時）のみに限定し、毎フレームの描画ループ内では転送を行わないようにしてください。

### ④ エラーハンドリングとフォールバック
- ユーザーの環境によってWebGLコンテキストの取得に失敗した場合（`canvas.getContext('webgl')` が null の場合）、アプリケーション全体がクラッシュしないよう、エラーを適切にキャッチして安全にハンドリングできるようにしてください。

# 4. 出力コードの期待値
上記要件を満たす、型定義が厳格なTypeScriptコードと、海岸線のグラデーションや波の表現が描画可能なフラグメントシェーダーのプロトタイプを出力してください。
