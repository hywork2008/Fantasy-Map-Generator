Problem. domShim.ts patches document.getElementById to return Zustand store values wrapped as mock HTMLInputElement objects. Generators receive options through DOM-shaped queries — a 30-property mock object pretending to be an HTML form. The seam between the options store and generators exists but runs through the wrong interface: the DOM.

Solution. Delete the shim; have main.ts call useOptionsState.getState() once and pass a typed WorldOptions argument directly to each generator.

  • Locality: options access concentrates in one function call per generation run
  • Leverage: generators become testable with a plain object — no DOM setup, no shim
  • Delete the shim: 117 lines of mock scaffolding, 30+ window property descriptors
  • Interface shrinks from DOM-shaped to a single typed parameter

  Main->>Renderer: drawBurgs(pack.burgs)
  Renderer-->>Main: SVG updated

Problem. burgs-generator.ts imports drawBurgIcon, drawBurgLabel, and drawRoute from the Renderer layer and calls them inside the generation loop — one draw call per burg as it is created. The Generator cannot be run without a live SVG tree and ViewContext. The UI layer predicate layerIsOn("toggleRoutes") is also called inside generation, entangling layer visibility with data production.

Solution. Generators produce only state. main.ts calls Burgs.generate() then drawBurgs(viewContext, pack.burgs) as two sequential steps. The layer-visibility check moves to the Renderer or the orchestrator.

  • Locality: Generator bugs stay in generator; render bugs stay in renderer
  • Leverage: generators become testable without SVG — assert on pack.burgs alone
  • Layer invariant restored: Generator layer has zero imports from Renderer layer
  • UI predicate (layerIsOn) moves out of business logic

3. Eliminate the worldContext / window.* dual-state copies

Strong in-process
src/context/worldContext.ts

Before — same data at two addresses

window.pack  ·  window.grid  ·  window.seed  ·  window.graphWidth  …
↕ main.ts manually syncs: window.pack = worldContext.pack (×20 props)
worldContext.pack  ·  worldContext.grid  ·  worldContext.seed  ·  …

After — one authoritative store, one name

worldContext  ·  single source of truth for all world data
Modules that still need window.* receive worldContext as an explicit argument

Problem. main.ts copies roughly 20 properties from worldContext to window.* after every generation pass. The same data lives at two addresses: worldContext.pack and window.pack. An update to one is invisible to callers reading the other, creating a silent-divergence failure mode.

Solution. Make worldContext the single authoritative store. Assign window.pack, window.grid, etc. as getters that proxy into worldContext, or — better — eliminate the aliases by threading worldContext through the remaining legacy callers as an argument.

  • Locality: world state has one address; divergence bugs become impossible
  • Delete the sync block in main.ts (~20 assignment lines)
  • Leverage: every caller works from the same object — no staleness window
  • Interface to world state shrinks to one import: worldContext

Problem. ViewContext is a flat bag of 50+ D3 Selection references — one per SVG layer. Every renderer module accepts the full ViewContext to access two or three slots. The interface surface area nearly matches the SVG layer count: adding a new layer means changing the type and touching every renderer.

Solution. Group layers by domain concern (EnvironmentLayers, PoliticalLayers, SettlementLayers, etc.). Each renderer declares which group it needs; viewContext composes these groups.

  • Interface each renderer crosses shrinks from 50 to ~5 properties
  • Locality: adding an environment layer touches only EnvironmentLayers, not 25 renderers
  • Leverage: caller intent is explicit — draw-rivers.ts takes EnvironmentLayers, not everything

This is a medium-effort refactor and should follow candidate 2 (severing the Generator→Renderer coupling) to avoid re-touching the same renderer files twice.

Problem. Five functions in utils/index.ts are shallow wrappers that do exactly one thing: append window.* globals to the argument list before calling the pure core. Applying the deletion test: delete the wrappers and complexity doesn't concentrate — it disperses across callers, each of which already has worldContext and can pass the arguments itself. The wrappers hide a dependency, not a behaviour.

Solution. Delete the wrappers. Callers import the pure core functions and pass worldContext.mapCoordinates / worldContext.graphWidth directly. Where callers share the same few arguments, a small local helper inside the caller module is fine — but that's an internal seam, not a public one.

  • Deletion test passes: wrappers were hiding a dependency, not earning their keep
  • Core functions become testable with any coordinate object
  • Locality: no hidden window.* access in the utils layer
  • Interface shrinks: utils/index.ts no longer re-exports window-coupled functions

Low effort — best done alongside candidate 3 (single-state cleanup), which surfaces worldContext as the natural argument source.

Top recommendation

Start with candidate 1 (delete domShim). It is the highest-leverage single change: 117 lines of fake DOM scaffolding disappear, and every generator gains a testable, typed interface to the options it actually needs. It unblocks candidates 2 and 3 — once generators accept explicit arguments rather than querying the DOM, threading worldContext through them and separating generation from rendering become straightforward follow-on steps.

Sequence: C1 (domShim) → C3 (dual state) → C2 (generator/renderer coupling) → C5 (utils wrappers) → C4 (ViewContext groups)
