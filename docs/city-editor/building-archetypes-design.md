# City Editor：建物規模・屋敷・庭・港湾敷地の調査と設計

調査日：2026-09-29。状態：設計案。今回の変更は本書のみで、生成・描画の実装は変更しない。

## 1. 採用する方針

建物を大小の住宅として一律に分割する方式から、**地区 → 用途を持つ敷地 → 主屋・付属棟・屋外空間**の方式へ拡張する。

- `harbor`：倉庫、住居兼商館、港湾作業場を混在させ、岸壁から倉庫・市街路へ続く搬送動線を確保する。大広場を各セルへ一律に置かない。
- `merchant`：住居・店舗・貯蔵を兼ねる家を主体とし、大商人の屋敷を少数混ぜる。
- `craftsmen`：工房兼住宅と作業庭を主体とし、裕福な親方の大きな家も許す。職業から貧富を固定しない。
- `patriciate`：CEの正式なwardとして追加し、日本語では「富裕層街」と表示する。生成側の既存分類を保持する。都市有力者の屋敷が集まる地区として使う。
- 「貴族街」は初期の独立wardにしない。必要な都市では`patriciate`の地区プリセット／表示名として扱い、貴族・大商人・高位聖職者を個々の屋敷の所有者属性で区別する。
- 庭を「富裕層だけの芝生」としない。普通の家の実用的な裏庭、工房の作業庭、邸宅の中庭・庭園を分ける。

大邸宅を置く第一候補は`patriciate`、商業と一体の大商人邸は`merchant`、大きな工房兼住宅は`craftsmen`とする。大きさと地区種別を一対一にしない。

## 2. 歴史的な基準と確度

既定の想定は**1250～1500年ごろの西・北ヨーロッパの都市**。中世全期間・全ヨーロッパの平均モデルとはしない。イタリア都市の商人邸は地域差を示す比較例として扱う。

以下の出典は建物・空間構成の根拠であり、都市全体の建物比率を与える統計ではない。本書の面積帯、抽選重み、幅員はすべて実装用の初期仮説である。保存建築には再建・改変があり、現在の広場や庭をそのまま中世に遡らせない。

### 2.1 港に倉庫や積替え用の広場はあったか

**倉庫・貯蔵機能はあった。積替えのための空間も必要だが、それが独立した大広場だったか、どれほどの面積を占めたかは港ごとに違う。** 調べた資料から「中世港では広場が多い／少ない」という全欧共通の割合は出せない。

| 確認できる事例 | 確認できること | CEへの設計上の解釈 |
| --- | --- | --- |
| ベルゲンのBryggen | 水際から奥へ延びる敷地に住居・事務所、倉庫、後部の共同施設等が組み合わさる | 港を独立した巨大倉庫だけで埋めず、長い商業敷地と通路の反復も表現する |
| グダニスクの港湾クレーン | 木造クレーンの記録は1367年、1442～44年の再建は水門・防御機能も兼ねる | 荷役設備を水際の特定地点に集中させ、その接続を優先する |
| トリーアの旧クレーン | 1413年の建設後、船乗りが周辺へ移り、クレーンへ向かう街路を持つ地区が形成された | 港は住居も含む活動地区。水際施設と市街路の接続を持たせる |
| ロンドンThree Quays | 1290～1424年の期間に船大工の一家が複数の水際区画を使用した記録と考古学的痕跡 | `harbor`には工房・船関連の作業敷地も混ぜる |

出典：[UNESCO：Bryggen](https://whc.unesco.org/en/list/59/)、[National Maritime Museum：History of the Crane](https://nmm.pl/en/crane/historia-obiektu/)、[トリーア市：Alter Krahnen](https://www.trier.de/leben-in-trier/stadtportrait/geschichte/kulturdenkmaeler/11854.Alter-Krahnen.html)、[MOLA：Medieval properties at Three Quays](https://www.mola.org.uk/discoveries/news/medieval-properties-three-quays)。

Bryggenの現在の建物は後世の再建を含む。またUNESCOは後部の一部が1965年に防火用の空地として変更されたことを記している。現在の空地を中世の荷さばき広場の証拠には使わない。

したがって生成では「広場の多寡」より、次の空間を別々に用意する。

1. **岸壁作業帯**：接岸地点に沿う帯状の空間。荷役・通行を兼用しうる。
2. **荷役通路**：岸壁から倉庫・敷地奥へ続く細長い通路。
3. **荷さばき庭**：倉庫に付属する半私的な空地。一時置きや仕分けを想定する。
4. **共同荷さばき場**：クレーン、水門、主要な荷揚げ地点などの局所的な広がり。
5. **市場広場**：売買の場所。荷役と関係する場合もあるが、荷さばき場とは別用途とする。

1～4は上記の事例から組み立てる生成モデルであり、すべての港に五種類が揃っていたという主張ではない。小さな河港では岸への斜路と数棟の商家だけでも成立させる。

### 2.2 大きな家は商人街か職人街か

サウサンプトンのMedieval Merchant's Houseは約1290年に建て始められ、住居・仕事場・店舗を兼ねる。フィレンツェの14世紀のPalazzo Davanzatiは商人・銀行家のDavizzi家が建てた邸宅である。**大邸宅は貴族だけの建物ではない。** [English Heritage](https://www.english-heritage.org.uk/visit/places/medieval-merchants-house/)、[Musei del Bargello](https://bargellomusei.it/en/museum/palazzo-davanzati/)。

設計では「商人／職人」という経済活動と「一般／富裕／都市有力者」という規模・資力を別軸にする。職人街に大きな親方宅を少数許すのは、この区別に基づく設計判断であり、今回の事例調査からその出現率を求めたものではない。

`patriciate`は貴族身分の同義語として使わない。貴族専用地区を全都市に自動配置するより、都市の政治・社会的性格に応じて、屋敷が集中する地区と商業街に点在する屋敷の両方を作れる方がよい。

### 2.3 庭付き住宅は上層だけか

Historic Englandの整理では、中世の都市庭は細長く、食料栽培、家畜、手工業、廃棄物処理などの実用に使われた。一般世帯の庭と、貴族・高位聖職者の大きな都市邸宅に付属する遊楽の庭は区別される。庭の資料自体にも限界がある。[Historic England：Urban Landscapes, §1.1](https://historicengland.org.uk/images-books/publications/drpgsg-urban-landscapes/heag093-urban-landscapes-rpgsg/)。

15世紀末のクリュニー修道院長のパリ邸宅は、中庭と庭を持つ都市の大邸宅の例になる。ただしこれは高位聖職者の特別な住宅であり、普通の家の標準形ではない。[Musée de Cluny：Hôtel des abbés de Cluny](https://billetterie.musee-moyenage.fr/fr/visit/163)。

CEでは次の形を描き分ける。

| 空間 | 用途・形 | 主な配置先 |
| --- | --- | --- |
| 裏庭・菜園 | 道路沿いの家の背後に細長く延びる。小屋等を付属可能 | 一般住宅、職人宅、商人宅。中心部では短縮・欠如も許す |
| 作業庭 | 土・舗装の空地。資材置きや工房の作業用 | 職人宅、港湾作業場 |
| 中庭 | 主屋・翼棟・付属棟が囲む内部空間 | 商館、大商人邸、上層の屋敷 |
| 庭園 | 囲いのあるまとまった植栽空間 | 上層の屋敷。全邸宅に必須とはしない |

街路前面を揃える現在の方針を保ち、家の周囲に均等な空隙を置く代わりに、裏側・内側へ空地をまとめる。密集する商業中心では、富裕な家でも大きな庭を持たず、複数階・中庭型になる余地を残す。

## 3. 現行コードの課題

調査対象はCEの`src/city-editor`。別系統の`src/city-generator`への変更は本設計の初期スコープに含めない。

| 箇所 | 現状 | 必要な変更 |
| --- | --- | --- |
| `core/types.ts` | CEの`WardKind`は8種類で`patriciate`がない | 型、編集UI、保存・読込・検証に追加 |
| `core/gen/types.ts`, `core/gen/wards.ts` | 生成内部には`patriciate`がある。35枠の候補中2枠 | 既存候補を活用。ただし2/35を歴史的割合と呼ばない |
| `core/generate.ts` | `patriciate`と`administration`を`merchant`へ変換 | `patriciate`の変換を外す。`administration`は別件として維持 |
| `core/gen/housing.ts` | 目標宅地面積は通常80、merchant 110、castle 400 m² | 通常住宅の互換値として残し、新モデルの用途別面積と分離 |
| `core/gen/buildingLots.ts` | 旧分割経路は通常180、merchant 260、harbor 300、castle 1600 m²を目標に分割 | 新経路と旧経路の数値を混同しない。互換ルートとして扱う |
| `core/gen/localInfill.ts`, `blockInfill.ts` | 新しいレイアウトは別経路で街区・建物を生成 | 共通の敷地モデルをこちらへ接続する |
| `core/gen/frontageBuildings.ts` | `lotArea`, `coverage`, `occupancy`で形状を生成し、結果は`Point[][]` | 敷地、建物用途、付属空地を返せる新APIが必要 |
| `core/gen/fabricDistricts.ts` | commercial/residentialを`urban`としてまとめられる | 統合後も元のwardの空間分布を残さないと港と富裕層街が消える |
| `core/gen/localInfill.ts`の`CityFabric` | buildings/lanes/entrances等を保持 | 敷地・私的通路・屋外空間を追加 |
| `render/svg.ts` | 建物と港の桟橋の描画が別。桟橋は海に接するharbor面を参照 | 荷役地点を生成側へ移し、桟橋と搬送動線を同じ計画から描画 |

現行`BuildingLot`は名前に反して建物の輪郭だけを表し、`faceId / polygon / landmark`しか持たない。庭や倉庫を入れるには「敷地と棟」を明確に分ける必要がある。

また`lotArea`は街路・街区寸法の計算にも使われるため、単純に数値を上げると家だけでなく街路網まで変わる。既存道路を尊重して大きな敷地を確保する段階を追加する。

## 4. 地区と敷地タイプ

### 4.1 地区は生成確率と立地条件を与える

`ward`は一棟ごとの用途を固定しない。`merchant`にも小工房、`harbor`にも住宅を許す。候補の確率に加えて、間口・奥行き・実際の搬送路・周囲の用途で採否を決める。

富裕層街は市場・行政・城・主要街路への接続を評価し、荷役の中心や大きな作業庭の直近には負の重みを与える。ただし水辺の商人邸を禁じない。現在の`patriciate`評価（park隣接を優遇、slum隣接を忌避）だけでは十分でない。職人街全体を一律に悪条件にもしない。

独立した貴族街wardは、将来「貴族への入居制限」「特別な警備・権利」「独立した政治効果」などのゲーム上の違いが必要になったときに追加する。外観だけなら地区プリセットで足りる。

### 4.2 初期の敷地カタログ

以下は**生成用の候補範囲で、史実の平均値・法的建蔽率ではない**。敷地面積と、全棟の建築面積合計を分ける。建築面積は上空からの輪郭の面積で、延床面積ではない。

| archetype | 敷地面積の候補 m² | 敷地内の建築面積比 | 代表的な構成 |
| --- | ---: | ---: | --- |
| `small-house` | 60–140 | 55–85% | 小住宅＋小さな裏側の空地 |
| `shop-house` | 100–260 | 50–80% | 道沿いの店舗兼住宅＋裏庭／小倉 |
| `workshop-house` | 140–380 | 40–70% | 工房兼住宅＋作業庭＋物置 |
| `merchant-house` | 220–650 | 45–75% | 商家＋側翼／貯蔵棟＋中庭 |
| `warehouse-compound` | 250–1,000 | 45–75% | 長方形の倉庫1～3棟＋荷さばき庭 |
| `patrician-house` | 450–1,600 | 30–60% | 大きな主屋＋翼棟＋中庭、任意の庭園 |
| `elite-compound` | 900–3,000 | 20–45% | 都市邸宅＋付属棟＋中庭＋囲いのある庭 |
| `port-workyard` | 300–1,200 | 15–40% | 小工房・上屋＋大きな作業空地 |

面積帯と建築面積比は独立抽選後に無理に掛け合わせない。棟の最小厚み、接道、庭の最小幅を満たす組だけを採用する。狭い敷地では一段小さい型に戻す。屋敷を縮小して普通の家と同じ大きさにしながら、名称だけ屋敷にすることは避ける。

`elite-compound`の所有者は`great-merchant / noble / clerical`等の任意メタデータにする。機能と形状は共通で、社会制度を表すデータは後から加えられる。修道院・司教座全体や城郭はこの屋敷モデルで代替しない。

### 4.3 初期の抽選重み

**実装検証用の仮値。敷地候補件数に対する重みであり、棟数比・土地面積比・人口比ではない。** 立地条件で候補を絞ってから再正規化する。倉庫一敷地に複数棟あるため、件数比だけで景観を評価しない。

| ward | small | shop | workshop | merchant | warehouse | patrician | elite | workyard |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| craftsmen | 25 | 20 | 45 | 5 | 2 | 3 | 0 | 0 |
| merchant | 8 | 30 | 10 | 32 | 10 | 9 | 1 | 0 |
| harbor | 10 | 15 | 10 | 15 | 40 | 2 | 0 | 8 |
| patriciate | 5 | 10 | 3 | 17 | 0 | 50 | 15 | 0 |

`patriciate`も全区画を巨大屋敷にはしない。小規模都市は適地がなければ独立地区なしでよく、`merchant`内の有力者宅だけでも成立する。大規模商港では倉庫用の面積予算を別途増やせるようにする。

### 4.4 規模の変化の作り方

型を先に選び、その型の範囲内で間口・奥行きを連動させて抽選する。通常住宅は範囲中央に多く、上端は少なくする。倉庫は細長い棟、大邸宅はまとまった敷地と翼棟・空地で差を出す。

画面の拡大縮小や都市の人口に合わせて家を巨大化しない。同じメートル尺度を使い、大都市では棟数・階数・密集度・大型敷地の選択率が変わる。階数はメタデータで持てるようにするが、現行の平面描画に屋根線や立体影を必須追加しない。

## 5. 港の生成仕様

### 5.1 先に荷役空間を確保する

```mermaid
flowchart LR
  W[接岸・荷揚げ地点] --> Q[岸壁作業帯]
  Q --> Y[局所的な荷さばき場]
  Q --> P[敷地内の荷役通路]
  Y --> H[倉庫・商館]
  P --> H
  Y --> R[市街路・市場への道]
  H --> R
```

これは機能の接続図であり、海岸に平行な一列配置を指定するものではない。

1. 海岸・航行可能な河岸の候補と、道路・水門・既存要素を調べる。river wardだけから航行可能と断定せず、河港は明示設定または港指定を使う。
2. 接岸地点と、既存の門を通る市街路への到達経路を作る。城壁や水路を横断する見かけだけの接続を認めない。
3. 岸壁作業帯と要所の荷さばき場を予約する。
4. 接岸地点からの経路距離・通路幅で倉庫候補地を選ぶ。水際からの直線距離だけで判定しない。
5. 倉庫・商館の敷地と荷役通路を作り、残りへ小住宅・店舗・工房を配置する。

旧来の一律の水際6m後退はそのまま「荷役帯」とは呼べない。安全余白と活動空間を区別し、共有可能な領域を一度だけ予約して二重控除を防ぐ。

### 5.2 初期プリセット

数値は歴史的統計ではなく調整開始値。面積比の分母は水面・主要道路・既存公共施設を除いた港の陸地計画区域。予約した帯・庭・広場の**和集合**で計測し、重複計上しない。

| プリセット | 倉庫の位置づけ | 共同荷さばき場 | 荷役用屋外空間の目安 |
| --- | --- | --- | ---: |
| 小規模な河港・沿岸港 | 商家の貯蔵棟＋少数の倉庫 | 独立広場なしも許可 | 10–20% |
| 密集した商業港（既定） | 長い商館・倉庫群 | 港全体の要所に0～2か所から開始 | 15–25% |
| 倉庫集積型の大商港 | 専用倉庫の敷地面積を増加 | 複数の荷役拠点に対応 | 20–35% |

共同広場が0でも荷役の通路・作業帯は確保する。必要幅を取れない場合は倉庫候補を小型化・棄却し、割合を満たすために狭い通路を潰さない。

初期寸法は岸壁作業帯4～8m、荷役通路2.5～4m、共同荷さばき場150～600m²から試す。これは近代的な物流基準ではなく、地図上の機能的な空間を作る仮値。小港では広場の下限を強制せず帯状空間に統合する。人力搬送主体の通路と荷車通行を想定する通路を区別し、入口の幅だけで通行可能とせず全経路のボトルネックを検査する。

倉庫面積・商館の貯蔵用途も含めた面積・屋外作業面積を別々に測る。「港の建物の40%が倉庫だから適切」といった判断はしない。

## 6. データ構造と生成順序

### 6.1 保存する意図と派生形状を分離する

以下は提案型の概略であり、既存APIへの確定した差分ではない。

```ts
type OpenSpaceKind =
  | "backyard" | "kitchen-garden" | "workyard"
  | "courtyard" | "formal-garden" | "loading-yard";

interface ParcelPlan {
  id: Id;
  faceIds: Id[];                 // 複数セルにまたがる所有・編集範囲
  polygon: Point[];
  archetype: ParcelArchetype;    // §4.2の型
  access: ParcelAccess[];       // 道路/岸壁への接続、用途、有効幅
  buildings: BuildingFootprint[];
  openSpaces: OpenSpace[];
}

interface BuildingFootprint {
  id: Id;
  parcelId: Id;
  faceId: Id;                   // 既存選択・描画との互換用代表セル
  polygon: Point[];
  role: "main" | "wing" | "store" | "workshop" | "stable" | "shed";
  uses: BuildingUse[];          // residential / retail / storage 等の複合用途
  storeys?: number;
  landmark: boolean;           // 大きいことだけを理由にtrueにしない
}
```

`OpenSpace`にはpolygon、kind、所有敷地または共有施設ID、public/shared/privateの区分を持たせる。区画内通路は`ParcelAccess`の形状として管理し、公共道路の`lanes`と混同しない。共同荷さばき場・岸壁作業帯は敷地外の共有施設として扱う。

保存するのは生成バージョン、seed、地区プロファイル、必要なユーザー指定。敷地・棟・庭の形状はキャッシュ可能な派生結果とする。将来の手動敷地編集はoverrideとして保存し、自動再生成で消さない。

既存の`BuildingLot[]`を必要とする描画には、棟をflattenした互換ビューを渡す。L/U形の屋敷は複数棟で表現できる。閉じた中庭は輪郭の穴として無理に一筆化せず、非重複の棟と独立した空地を組み合わせる。

### 6.2 新生成経路

1. 既存メッシュ・主要道路・城・寺院・市場・河川を固定制約として収集。
2. 地区を道路で囲まれる計画区域へまとめる。ただし元のwardポリゴンを用途評価用に保持する。
3. 港の作業帯や荷さばき場、大邸宅候補地を先に予約する。
4. 大型候補地を避けて局所道路を作る。既存の編集済み道路は移動させない。
5. 沿道に敷地を分割。大型敷地は同じ街区の隣接候補を併合し、道路・城壁・水路を跨がない。
6. 各敷地へ主屋、付属棟、庭、アクセスを配置。
7. 面積・衝突・連結性を検査し、不適合なら同一敷地内で簡素化または下位型へ変更。
8. 建物・屋外空間・道路を描画し、集計用メタデータを返す。

街区が用途境界を跨ぐ場合も道路の連続性を保つ。初期実装では、境界を跨ぐ敷地のプロファイルを最大重複面積のwardから選ぶ。大型敷地は同用途側への併合を優先し、港の共有作業帯はward多数決と無関係に保護する。`districtDocument`で代表セルのwardだけへ潰さない。

`coverage`の現行定義は中心部では街区、外縁では宅地で異なる。新モデルの敷地建築面積比を既存`coverage`に黙って上書きせず、`parcelCoverage`として分ける。`occupancy`は空き敷地率を制御し、庭の確保には使わない。

乱数は都市seed・安定した街区ID・敷地ID・用途別のストリームに分ける。棄却で後続の乱数列がずれて都市全体が変わることを防ぐ。局所編集で影響する街区と共有荷役接続の範囲だけを再計算する。輪郭座標だけをIDとすると小編集でも全再抽選になるため避ける。

### 6.3 描画と操作

通常の建物色と細い輪郭を維持する。倉庫は長い棟の反復、邸宅は翼棟と囲まれた空地、庭は淡い地色・少数の植栽で識別する。庭の細部は縮尺に応じて省略可能。荷さばき場は地面として表現し、市場用の記念物を自動設置しない。

Inspectorには「地区の用途」「建物構成（標準／商家中心／倉庫中心／屋敷中心）」「規模のばらつき」「庭・作業庭の量」を基本項目として出す。港では「小港／密集商港／倉庫集積港」を追加する。細かな重み表は詳細設定に置く。

墨線表示と通常表示、SVG書き出しで同じ敷地形状を使用する。選択は敷地を基本とし、付属棟クリックでも所有敷地・元セルを追えるようにする。

## 7. 実装の順序と互換性

| 段階 | 成果 | 主な変更先 |
| --- | --- | --- |
| A | `patriciate`保持、プロファイルと派生敷地型、生成バージョンの導入 | `types.ts`, `generate.ts`, `document.ts`, `fabricDistricts.ts`, UI |
| B | 普通の家・工房・商家・屋敷、私的な裏庭と中庭 | 新規`parcelProfiles.ts`, `parcelPlanner.ts`, `parcelBuildings.ts`、既存infill群 |
| C | 港湾計画、倉庫・作業庭・荷役接続、桟橋の共通化 | 新規`harborFabric.ts`、`blockInfill.ts`, `render/svg.ts` |
| D | 全レイアウトへの接続、編集・保存・性能の確認 | classic/organic/circulade/bram各経路、キャッシュ、テスト |

初回の比較用実装はorganic/classicで行う。circulade/bramは街路パターンを保持したまま同じ敷地生成へ接続し、全対応を確認するまで旧表示を既定にする。通常の家だけが新方式、大邸宅だけ別の無関係な散布方式という二重生成を避ける。

新方式は`fabric.version = 5`等の明示した版で導入する。新規生成には新方式を使い、旧文書は旧版の派生経路で同じ外観を維持する。現在の`upgradeFabricPlan`はv2/v3をv4へ扱うため、新版を無条件に経由させないよう分岐を改める。旧マップの新版への切替は、ユーザーの再生成操作としてUndo可能にする。

以前の保存文書で既に`merchant`へ統合された`patriciate`は、見た目から自動復元しない。元の生成設定がある場合の再生成、または地区の手動変更で指定する。新版はward・寸法単位・プロファイルを保存検証し、未知の値を黙ってcraftsmenへ置き換えない。

新パラメータ、元ward分布、予約空地、港アクセス、生成版をキャッシュキーへ含める。`finishFabric`等が後処理で建物を除去する場合、敷地側の棟リスト・アクセス・空地も整合させる。新配列をマージ・フィルタ・所有セル再割当する箇所も更新する。

## 8. 検証と完成条件

既存回帰テストに加え、同一seedの旧版／新版SVGを作る。最初の固定ケースは「内陸商業都市」「小さな河港」「密集商港」「城のある富裕都市」「細い街区・斜め道路・複数セルの地区」とする。全レイアウトについて最低一つ、港と大型敷地を含むケースを確認する。

| 観点 | 完成条件 |
| --- | --- |
| 地区の意味 | `patriciate`が生成→CE→保存→再読込で保持され、merchantと異なる敷地分布になる |
| 建物の変化 | 各用途の面積分布・中央値・上位10%を記録。小住宅、長い倉庫、大型の屋敷が同じ都市内で判別できる |
| 庭 | 色を塗った余白だけでなく敷地に属し、侵入する自動建物がなく、住宅・門等から到達可能 |
| 港 | 倉庫から荷揚げ地点・市街路への有効幅付きの経路があり、水・城壁・建物で塞がれない |
| 広場 | 共同荷さばき場0の小港でも荷役動線が成立し、大商港では共有空間の面積予算を計測できる |
| 幾何 | 棟は敷地内、棟同士・保護空間と非重複。自己交差、極細棟、閉じ込められた中庭を作らない |
| 密度 | 屋敷増加時は敷地数が減る。倉庫や付属棟を一律に一世帯として人口へ加算しない |
| 再現性 | 同seed・同設定は同結果。地区編集は無関係の街区を再抽選しない |
| 操作 | Undo/Redo、保存再読込、旧版互換、SVG書き出しが整合する |
| 性能 | 固定大規模都市で生成時間・棟数・キャッシュ再利用率を旧版と比較。局所編集で全敷地を再計算しない |

最初に調整すべきは、大型敷地の頻度と面積予算、細い街区での成立率、港の動線幅、庭の縮尺上の見え方。今回の調査だけでは歴史的な最適比率を確定できないため、史例に反しない構成を守りながら、固定ケースの描画と面積集計で調整する。

## 9. 実装レビューと見直し（2026-09-30）

### 確認した問題

初版は `lotArea` を地区全体で拡大し、既存の街区を再分割してから住宅を再生成していた。住宅密度を戻すために旧住宅を後から補う処理も追加され、同じ土地を二通りの方法で処理していた。新しい敷地は郊外も対象にし、既存の門前処理を通した後から建物を追加していた。この構成では門外の大きな建物や、住宅の消失と庭だけが目立つ状態を防げなかった。

前回のテストは棟数や多角形の包含を主に見ており、元の住宅群と新しい主棟・庭の対応、郊外の保持、門前への侵入、方式別の生成成否を十分に検証していなかった。

「庭を既存の空き地だけに置く」という対策も採用しない。従来方式は街区を密に埋めるため、この条件では庭をほぼ生成できない。庭を作るための局所的な再配置は必要であり、大きな主棟と一体で成立させる。

### 現在の処理

1. 既存方式で道路・住宅列・門前空間を確定する。街区サイズを一括拡大せず、元の道路配置を保持する。
2. 城壁内の同じ用途の隣接住宅群を候補にする。郊外、門前広場、城郭、道路、河川に大型敷地を追加しない。
3. 候補を矩形の敷地へまとめ、そこに大きな主棟と庭／中庭／荷捌き場を一体で配置する。主棟は置換対象の最大住宅の2倍以上、かつ90m²以上とする。成立しなければ元の住宅群を残す。棟の斜め切り抜きは行わない。
4. 庭の面積は敷地内で確保する。地区ごとに置換対象の面積と建築面積減少を制限する。既定の減少上限は富裕地区22%、港20%、商業地区12%、職人地区4%。これは史実の比率ではなく、全面的な低密度化を防ぐ調整値である。
5. 倉庫には荷捌き場と幅3mの敷地内通路を組み込み、幅2.5mの通行経路が主棟・他の住宅・壁等を横切らず既存の荷車道路へつながる場合に採用する。小港は私用作業庭、密集商港・倉庫港は共用荷捌き場として扱う。独立した岸壁や荷揚げ接続路は既存住宅を消さず成立する場所に置く。
6. 生成方式による富裕層街のタグ分けは、共通の道路・橋・門・城の生成と検証が完了した後に適用する。

現在、追加する敷地は工房住宅・商人屋敷・富裕住宅／大邸宅・倉庫であり、通常住宅は既存の住宅列を保持する。街区全面を再分割する `parcelPlanner` と寸法抽選用の `parcelProfiles` は削除し、必要な型だけを `parcelTypes` に集約した。各レイアウトに追加していた街区抽出処理も削除した。

### 操作と互換性

City Editorの「従来の住宅」と「中世の敷地（倉庫・屋敷・庭）」で切り替える。文書側の選択は現在の都市、生成設定側は次の生成に適用する。旧文書は従来方式として扱い、保存・共有・Undo/Redoに対応する。富裕層街 `patriciate` と用途構成、規模のばらつき、庭の量、建蔽率の目安、港の構成を設定できる。極端に狭い街区では大きな主棟と庭を同時に作れないため、元の住宅を残す。

### 検証

- 密集住宅列を直接入力し、大きな主棟と庭が同時に生成され、庭が元の住宅用地の再配置から生まれることを確認する。
- 郊外の建物と道路が旧方式と同一であること、門前に追加建物が入らないこと、庭・荷捌き場と完成後の建物が重ならないことを確認する。
- 4レイアウトの出力、保存・共有・Undo/Redo、SVG、UI、地区編集の再現性を検証する。
- 5サイズ×4レイアウト×内陸／湾岸の40条件で、同一seedを旧方式と比較する。旧方式でも不採用になる門・道路のケースは、住宅方式の変更で検証を緩めて通さない。

計測スクリプトと比較画像は `temp/housing-review/` に保存している。生成失敗と、生成後の建物計算の遅延は区別して記録する。全体の型検査には変更前からの別箇所のエラーが残る。

実測結果（ローカル単回計測）: 40条件すべてで旧方式と生成成否・不採用理由が一致し、双方38成功／2失敗。残る失敗は Small/Bram/湾岸 と Medium/Bram/内陸の固定seedで、門への接続・交差条件によるもの。住宅描画の失敗として扱わず、未解決の生成条件として残す。

建物計算の所要時間は、Large/Classic/湾岸で見直し前36.0秒→修正版4.7秒（同時に測った従来方式4.2秒）。Large/Organic/内陸は21.5秒→13.7秒（従来方式12.9秒）。修正版は各方式の計測に新しいキャッシュを使い、既存方式の直後に実行したキャッシュ再利用だけで速く見せないようにした。描画DOMや画像出力の時間は含まない。計測値は環境・seedで変わる。

関連7ファイル120テストが通過し、最後の変更後に敷地生成とUI切替の18テストも再実行した。比較画像は `temp/housing-review/compounds.png`（検証用の商港・富裕層街を同じ位置で拡大）と `temp/housing-review/visual-final.png`（生成した4レイアウト）を参照。
