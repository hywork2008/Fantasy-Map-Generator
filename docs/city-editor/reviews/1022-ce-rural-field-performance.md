# CE耕作地の工程別性能計測（2026-10-22）

## 結論

最優先の調査対象は境界再構成内の凸分割・重なり検証、次が農地候補探索時の障害物判定。比較用保存都市1件では、この2工程が耕作地生成計算の約87%を占めた。畝の生成・SVGパス化は小さく、最初の削減対象にはしない。

今回は計測点と再実行用ツールを追加した。耕区アルゴリズムのチューニングは行っていない。通常の生成は計測を無効とし、既定の手動方式・Workerの2秒制限を維持する。診断用APIを明示的に呼んだ場合だけ、最大60秒まで完了を待つ。

## 対象と条件

- 前回の速度比較に使用した保存都市 `phase7`。表示範囲1,200m、建物6,171棟、農地568区画。ユーザー提示URLの都市そのものの計測ではない。
- v2、Historical period=`ageOfExploration`、耕作方式は自動判定で`planned`（都市近傍には園芸）。範囲・方角・面積割合は未指定。利用可能範囲全体を処理する従来比較条件で、UIで新たに指定する既定70%とは異なる。
- 適地332 face、予約地7,982ポリゴン、探索ノード61,330、管理群40、農道611。境界頂点28,108→2,871、畝41,576本／83,152点。
- 同じ入力をNode v22.23.1（arm64）とローカルVite上のChromiumで計測。ブラウザのUser Agent・viewportは生データに記録した。基準コードは`654484f26`に本計測差分を適用した状態。
- 少数の手動計測であり、統計的な中央値・全都市の性能保証ではない。JIT、GC、開発サーバー、時計分解能で変動する。

## 再実行と生データ

保存したCEのJSONを指定する。通常UIの2秒制限を経由せず、生成計算を最後まで測り、同じ入力で計測なしの比較も1回行う。

```sh
node --import tsx scripts/profileCeRuralFields.mts /path/to/city.json /tmp/rural-report.json
```

出力は`elapsedMs`（子を含む）、`selfMs`（直接の子を差し引く）、`calls`、件数、入力SHA-256、生成条件、形状一致確認。自己時間で並べているため、親子を二重加算せず対象を絞れる。

ブラウザでは開発サーバーから`city-editor/services/analysis/ruralFieldPerformance.ts`をimportし、`profileRuralFieldWorker(document, buildBlockFabric(document))`でWorkerの生成・転送を取得する。戻り値の`overlay`を`storeRuralFieldOverlay(document, documentFabricFingerprint(document), overlay)`で登録した後、`profileRuralFieldRendering(document, () => renderEditorSvg(...), host)`でSVGと接続・レイアウトを測る。後者は測定用ホストの子を置換するため、実画面とは別のホストを使う。

## 同日追記: タイムアウトの矛盾を修正

上記は最適化前の記録。生成に約3.2秒かかる対象に旧2秒上限を適用していたため、通常操作では完了できなかった。上限を5秒へ変更し、日本語・英語の表示も更新した。診断用60秒経路だけでなく、通常の`startRuralFields(document, fabric)`をブラウザで実行し、**約2,448msで568区画が返ること**を確認した。通常Workerは引き続き有限時間で打ち切る。

境界再構成の重なり検証では、相手側ポリゴンを三角分割した結果をキャッシュし、凸片への統合を省いた。さらに各片の境界箱が交わらない組合せを除外してから面積交差を求める。候補側のクリアランス検証用の凸分割は維持した。比較用都市の農地・畝・農道JSONは最適化前と完全一致（SHA-256=`98368bf09ae5197c83dcdbf706db803fe6e51109aef9b0ff1bf3d6e8a715e8ed`）。

同じ入力のブラウザ診断では生成計算2,367ms、Worker往復2,468ms。Nodeの計測なし生成は2,940ms（前記4,905msから短縮）。単一入力・単発の計測であり、他の都市や端末での5秒以内の完了を保証する値ではない。

## 同日追記: 直線のあぜ道と耕作帯へ変更

伝統型の群境界をVoronoi半平面、耕作帯を平行な直線で定義する方式へ変更した。農道に触れる格子セルを丸ごと除外してから境界を修復する処理を外し、道路予約地を幾何的に差し引いた利用帯を到達可能セルにclipする。農道幅は1.2 m。セル間の内部辺を消すため、探索格子を粗くしても内部の道幅に反映されない。水域・予約地などに接する外縁は安全側の格子輪郭を維持する。

探索粒度は `RuralFieldSettings.targetAccessCells` とし、既定25,000、整数1,000〜1,000,000を許可。値を増やすと外縁の精度と探索負荷が上がる。機械化型は従来方式を維持する。

同じ保存都市 `phase7` を今回の変更直前・直後に再計測。Nodeの計測なし生成は3,234 ms→680 ms、計測ありは3,412 ms→813 ms。探索幅4 m→8 m、到達ノード61,330→15,173、区画568→672、農道611→169。アルゴリズムと探索粒度を同時に変えた結果であり、直線化だけの寄与は分離していない。単一入力の少数計測で、暖機・GC・同時処理・端末負荷の影響を含む。旧粒度を指定した `targetAccessCells=100000` の新方式も単発で約2,301 msで完了した。配置は意図的に変わる。各版の計測あり／なしでは形状が一致した。

確認: 関連23件（領域の穴・分断と面積保全、農道予約地との非重複、輪作・面積上限、設定保存、Worker、計測）、TypeScript、変更ファイルのBiome。保存都市の農地・農道・建物から作ったSVGプレビューも確認した。CE画面のボタン操作を通した確認ではない。

## 同日追記: 都市側に残る格子外周を直線化

直線化した群境界とは別に、都市側の外周には到達可能セルの階段が残っていた。同一直線上の頂点だけを削除していたため、交互に水平・垂直へ進む輪郭を斜めの弦へ置き換える工程がなかった。

`ruralFieldMargins.ts` を追加。凸な利用帯との接点を固定し、その間の外周を始点・終点の直線へ置換する。元の輪郭からの偏差上限は探索幅の1.25倍。候補polygonの三角分割に土地被覆・障害物判定を適用し、同じ包絡領域から得た別成分との重複も検証する。置換できない場合は局所的に分割する。群や帯の間の非重複は包絡領域で保証し、旧方式の全区画間の境界再構成は戻さない。

同じ保存都市 `phase7` の今回のNode計測は、計測あり663 ms／なし516 ms、672区画。境界頂点は3,236→2,985。前回との時間差には暖機・端末負荷などを含み、直線化が高速化したという意味ではない。計測あり／なしの形状は一致した。上記Node生データに `marginStraightening` を追記した。

保存都市の簡易SVGで都市側の外周が斜めの直線に変わることを確認した。ユーザー提示画像の都市そのものの再現・CEボタン操作の確認ではない。関連19件（新規2件は外周の直線化と予約領域での局所分割）、TypeScript、Biome、architecture lintを確認。
