# 外縁部の小道と密集住宅の生成方針

2026-09-18。`temp/redline` の Stonewind / Wolfrise Cliffs と City Editor を比較した検討。下記の実装状況を除き、原因分析は変更前の実装について記載している。

## 実装状況

Grid evolutionの `localInfill.ts` と新設した `frontageBuildings.ts` に、直線の小道と沿道建物列を実装した。

- 地区の全周へ小道を引く処理を廃止し、入口から入る小道と、それへ接続する街区分割を生成する。小道は粗い分割だけに使い、宅地ごとの分割には追加しない。
- 接道辺ごとに建物帯を作り、辺からの距離の二等分線で角地の所有範囲を決める。向かい合う列や角地の建物を重ねない。
- 同じ接道辺に対する前面は一律0.15m後退させ、各戸の前後のoffsetを加えない。隣棟間隔は0.16m。coverageは前面を固定したまま裏側を調整する。
- 住宅形状は矩形・L字・コの字を敷地へクリップする。L字の向きは列内で交互にし、後方を中庭側へ開く。狭い角地では凹形状より接道幅と棟厚を優先する。
- 外縁部の幹線から45mという棄却条件を廃止。小道沿いも配置対象にし、建物帯の奥行きとoccupancyで外縁の空地を残す。
- Inspectorの向き指定は `Local street direction (°)` とし、小道の軸を指定する。住宅は一律の地区角度ではなく実際の接道辺へ揃える。
- 建物描画は細い均一な輪郭のみ。屋根線、片側の太い黒線、影は追加しない。

今回の小道は直線で生成する。円弧への置換、道路グラフとしての交点ID、扉・中庭への出入口の明示的なモデルは含めない。既存のセル・featureを保持し、建物と小道は地区単位の派生結果として再計算する。

検証は前面の整列、coverage変更時の前面保持、斜め・逆向きの輪郭、角地と凹形状の非重複・自己交差、外縁部の小道沿い住宅、地区キャッシュ・保存・Undo、河川・海岸シナリオを対象とする。描画確認用SVGは `temp/residential-infill/` に出力した。

## 現段階の目標と参照スタイル（追加指定を反映）

**目標は `roofs=plain` と `processing=none` に相当する、建物の平面輪郭だけで接道前面が揃う配置。**

| 参照ファイル（`temp/redline/`） | 用途 |
| --- | --- |
| `blackfall_ford-roof-plain.svg` | 屋根線・立体表現を持たない建物輪郭の描画基準。ただし配置のoffsetは目標に含めない。 |
| `blackfall_ford-processing-none.svg` | 道路に面した前面が揃う建物配置の主参照。 |
| `blackfall_ford-roof-raised.svg` | 黒い側面による立体表現を見分けるための比較資料。目標には含めない。 |

ユーザーの指定によれば、従来のStonewind / Wolfriseの屋根線は `roofs=gable` に由来し、建物列の細かな前後のずれは `processing=offset` に由来する。そのずれを配置アルゴリズムの必須要素として再現しない。

追加SVGのXMLでも、plainにない黒塗り・黒輪郭のpathがraisedでは230本追加されている。建物色 `#A5A095` のpath数はplainとraisedが各179、processing-noneが177（住宅以外も含む色別集計）。processing比較は建物数も異なるため、pathの順番による一対一の対応を前提にしない。

同じ道路辺に接する建物は共通の前面線と後退距離を使い、各棟を道路法線方向へランダムにずらさない。変化は間口、奥行き、宅地分割、中庭の形で作る。曲がる道路は局所的な接線・オフセット境界に沿わせる。密集度と接触の検証は屋根線・側面・影を除いた平面輪郭で行う。

## 結論

**接道する辺から小道を成長させ、その道路沿いに建物列を詰める方式を採る。街区を分ける小道と、住宅を分ける宅地境界は別に生成する。**

セルの辺に対する平行・直角を基本にする案は適切。ただし、任意の辺を毎回選ぶよりも、実際に道路に接する辺・既存の小道の接線を基準にする。曲線は一律の放物線ではなく、直線を主体に、必要な接続部へ円弧または接線を合わせた曲線を加える。

密集感を改善する第一手は L 字・コの字の種類を増やすことだけではない。建物の前面を道路へ揃え、側面を接触可能にし、余白を各戸の周囲ではなく中庭や裏庭へまとめることが先になる。

### 対象の位置とpathの意味

| ファイル | ファイル内の実際のグループ | 細い小道のpath | 独立したsubpath | うち1線分だけのもの |
| --- | --- | --- | ---: | ---: |
| `stonewind-redline-edited.svg` | `ward-lines > g19`（label: `g19-trails`） | `path18` | 246 | 142 |
| `wolfrise_cliffs-redline-edited.svg` | `g41`（label: `g41-trails`）`> g23` | `path22` | 564 | 386 |

Wolfrise の親グループの名前は、指定の `g21-trails` と異なり、手元のファイルでは上表の通り。対象はその中の細い線をまとめた `path22` として特定した。

両方とも、この細線pathの頂点列は `-edited` のない `*-redline.svg` 内の対応pathと一致する。全subpathの頂点数が同じで、絶対座標に戻した差は 1e-7 未満。元から存在する線であり、編集で新しく追加された小道ではない。

- 元のSVGは `M … L … M … L …`。編集済みは主に `m … 座標列 … m …` へ書き換わっている。
- `m` の最初の組は移動で、続く座標の組は暗黙の相対 `l`。次の `m` は新しい独立線の始点への移動なので、その間をつながない。
- 細線pathには `Q`、`C`、`A` がない。曲線に見える部分も短い直線の列。
- `<g>` は描画・変換・表示のまとまりであり、生成順序、道路グラフ、セルの親子関係を示す証拠にはならない。
- `M 0,0` だけのpathは線分を描かない。道路数へ数えない。

### 曲がり方は円弧に近い部分が多い

連続する6線分の長さと5回の旋回角を調べると、長さの変動係数が0.1%未満、旋回角の標準偏差が0.04度未満になる曲線部分が、Stonewindの31 subpath、Wolfriseの95 subpathにある。全曲線の分類ではなく、円弧に近い連続部分が見つかった本数。

例として Stonewind の `path18` の5番目のsubpathでは、線分長約5.445 SVG単位、旋回角約−3.160度（標準偏差約0.0085度）の部分がある。等長・等角度の折れ線は円弧の近似と整合する。したがって、**放物線を標準にする根拠はこのSVGにはない**。ただし、出力だけから元の生成アルゴリズムや乱数分布は断定できない。

この細線の `stroke-width` は Stonewind が0.374、Wolfriseが0.562。同じファイルの建物輪郭と同じ太さで、道路の実幅を表しているとは限らない。線の形は経路の参考にできるが、描画幅をそのまま通行幅・建物の後退距離へ使わない。

### 密集感には実際の接触と描画上の厚みがある

元の `stonewind.svg` / `wolfrise_cliffs.svg` を描画すると、道路に面した建物列が中庭を囲み、外縁部では建物の背後にまとまった空地が残る。全建物が均等に離れている配置ではない。

建物色 `#a5a095` のpathには長方形に近いものだけでなく、凹頂点を持つ輪郭もある。ただし色による抽出は住宅以外も含むため、住宅の L 字・コの字の比率とはみなさない。また、コの字に見える建物群が一棟のpathとは限らない。

別々の建物色pathが同じ頂点を持つ例も確認できる（座標はSVG内部座標、0.001単位で照合）。

- Stonewind: `path71` と `path75` は `(-15.672, -25.807)` を共有。
- Wolfrise: `path65` と `path67` は `(12.570, 12.174)` を共有。

少なくとも一部では表示された建物色の輪郭同士が接している。さらに黒い側面のpathがあり、Stonewindの例では `v 0.6` による厚みが描かれている。ただしこれらは屋根・立体表現を含むサンプルの観測であり、平面の建物配置の証拠としては追加されたplain / processing-noneを優先する。これらから敷地面積の重複を一般に許す必要があるとは言えない。

## Grid evolutionが疎に見える理由

実際の建物生成経路は [buildingLots.ts](../../src/city-editor/core/gen/buildingLots.ts) → [blockInfill.ts](../../src/city-editor/core/gen/blockInfill.ts) → [localInfill.ts](../../src/city-editor/core/gen/localInfill.ts)。`gridEvolution.ts` 自体はセル形成の途中経過を生成している。

1. **細かな宅地分割まで小道にしている。** `fillPart` の再帰分割は成功するたびに `addLane` する。既定の道路幅3mに対し、小さな分割でも1.8mの道が入る。左右の0.4mの余白と各建物の0.45mの後退を足すと、単純な平行辺同士でも建物間は約3.5m空く。長方形化・縮小があればさらに広がる。
2. **建物を重心中心の内接長方形にする。** districtパラメータがある経路では全てが対象。台形や斜めの外周で余白が増え、道路前面も後退する。L 字・コの字にはならない。
3. **coverageは上限として働く。** 既定値は0.75。内接長方形が敷地の75%より小さくても、`Math.min(1, …)` のため拡大されない。値を上げるだけでは狭い内接長方形を救えない。
4. **地区を一つの角度へ揃える。** 初期角度は `longestFrame`。小道も建物もその角度へ寄せるため、曲がった道路や複数の接道方向への追従が弱い。
5. **外縁部は幹線から45mで打ち切る。** 判定は `roadFrontages` との距離で、小道は対象外。奥へ到達する小道を作っても、その沿道の住宅を棄却しうる。
6. **地区の全周に小道を引く。** district経路の `addLane(boundary(polygon), laneWidth)` は道路でない背面にも空間を確保する。さらに接道条件・最小面積・細長さの検査やoccupancyによる欠落が加わる。

既定値は [fabricDistricts.ts](../../src/city-editor/core/gen/fabricDistricts.ts) にあり、occupancyは中心部0.965、外縁部0.82。単純にoccupancyを1へ上げても、上記の幾何学的な隙間は残る。

## 採用する生成方法

### 1. 道路への入口から、小道を必要な分だけ伸ばす

道路・水際・城壁等で区切られた地区を生成範囲とする。編集用セルの境界全部を道路にはしない。現行のdistrict統合と、局所的な生成結果をmeshから分離する構成は維持できる。

- 始点は既存道路に接する辺や小道上で選ぶ。長い接道辺を選びやすくし、端に偏る細切れ分割を避ける。
- 基本方向は始点の道路接線に平行／直角。district全体の角度は接道方向が得られない場合の補助にする。
- 分割比率は制限付きの乱数とし、両側に住宅の間口・奥行きを確保できる場合に採用する。現行の0.4〜0.6は初期候補にできるが、参照SVGから推定した分布ではない。
- 長さは一様乱数だけで決めず、確保したい沿道宅地数、地区の奥行き、接続先から決めて揺らす。
- 既存小道へ達したら最初の交点で止め、交差する線もそこで分割してT字接続にする。近接はスナップし、ほぼ並行な重複線は棄却する。
- 水域・城壁・建築禁止地では止める。地区境界は通行可能な入口のときだけ接続する。終端が地区内部なら、短い行き止まりとして明示的に許可する。
- 建物のない奥地まで伸びる線は外縁部に残してよいが、それだけで道路沿い全てを建物で埋めない。

単に「ランダム長で止める」だけだと接続先直前に隙間が生じる。「必ず反対側まで貫通」だけだと格子が過剰になる。接続を目指す線と行き止まりを分け、必要な接道面を増やすために成長させる。

### 2. 曲線は限定的に使う

直線の枝を基本にし、幹となる小道や角度の異なる道路への接続に、円弧・接線を合わせた曲線を使う。半径は建物奥行きに対して十分大きくし、急な曲線の両側へ細長い敷地を作らない。

内部の衝突・接道計算では誤差を制御して折れ線化する。曲線化後にも道幅を含む衝突判定を行い、建物を配置した後で道路だけを滑らかにして住宅へ食い込ませない。建物自体は曲げず、間口位置の接線に沿う直線的な輪郭にする。

### 3. 小道で街区を分け、その後は道路なしで宅地を分ける

街区生成と建物生成で再帰を分離する。街区内では道路から一定の奥行きの「建物を置く帯」を取り、接道長をランダムな間口に分ける。各分割線は宅地境界であり、道路として描画しない。

帯が角で衝突したら先に角地の領域を確定し、両側から建物を無制限に重ねない。帯の裏側はまとめて庭・中庭へ残し、袋地には必要な場合だけ細い通路を追加する。

外縁部は、接続された小道も住宅配置の基準へ含める。そのうえで幹線からの経路距離や成長深さによって建物列の長さ・占有率を減らす。全住宅を均等に小さくするより、密な建物列と広い裏庭の組み合わせを優先する。

### 4. 建物は前面を固定し、側面と裏側を調整する

長方形の前棟を基本にし、敷地に余裕があれば片側の側棟で L 字、両側の側棟でコの字にする。隣接する二つの L 字は同じ中庭の領域を参照して向かい合わせ、出入口を残す。形状を独立に抽選してから衝突棄却する方式は空白を増やすため避ける。

- 道路側: 小さな前面後退を揃える。coverage調整でも前面は動かさない。
- 隣棟側: 接触・共有壁・狭い隙間を許す。道路幅を加算しない。
- 裏側: 奥行き、側棟の長さ、中庭面積でcoverageを調整する。
- 密な建物群: 各棟の平面輪郭と細い境界線で識別する。屋根線・片側の太い黒線・影は追加しない。

初期調整案として、密集する建物列の隣棟間隔は0〜0.6m程度から試す。これはSVGから換算した実測値ではない。通行用の小道幅と分け、共有境界の接触は認めても、建物内部の面積重複は原則認めない。

凹多角形を扱う際は、現在の `insetConvexKernel` を L 字・コの字へそのまま適用しない。前棟・側棟の矩形結合から単純な凹輪郭を作り、棟厚と通路幅を検査する。完全に囲んだ中庭を一棟で表すなら穴の表現が必要だが、第一段階はコの字や複数棟で表現できる。

## SVG出力の方針

小道の複数線は `M … L … M … L …` としてまとめてよい。ただし接続関係は生成データ側に保持する。SVG文字列の並び順を道路グラフの代わりにしない。

建物は選択・編集単位ごとに独立した閉じたpathを出す。L 字・コの字は凹多角形の `M … L … Z` で表せる。幾何形状が適切なら `<g>` の増減自体で密集感は変わらない。

```xml
<!-- 概念例。小道の座標は別途生成した道路グラフに由来する。 -->
<g class="ce-infill-lanes" fill="none">
  <path d="M 0 0 L 40 0 M 20 0 L 20 18" />
</g>
<g class="ce-buildings">
  <!-- L字の一棟。棟同士の共有境界は配置段階で決める。 -->
  <path d="M 0 2 L 12 2 L 12 6 L 5 6 L 5 14 L 0 14 Z" />
</g>
```

参照SVGの細線は線画として露出するが、CEの小道は背景色の道路幅を持つpathとして出力される（[render/svg.ts](../../src/city-editor/render/svg.ts)）。参照と同じ黒い線を足すだけでは建物配置は改善しない。

## 実装の優先順位と評価

1. 宅地分割から `addLane` を分離し、前面固定・側面接触可能な建物列を作る。小道に沿った外縁住宅も許可する。
2. 任意の全周道路を減らし、実際の接道方向へ建物を追従させる。三角形・台形の余白を角地の形状として利用する。
3. 共通の中庭を使った L 字・コの字・向かい合う L 字を導入する。
4. 円弧状の枝・接続部と平面輪郭の線幅を調整する。屋根線・側面表現は現段階の対象外。

比較時は同じseed・同じ地区境界・同じ縮尺を使い、屋根・立体表現なし、processing=none相当の条件へ揃える。住宅の道路側後退と同じ道路辺に対する前面のずれ、隣棟間隔、地区面積に対する建物面積、住宅が連続して面する道路長、空地のまとまり、小道の総延長を測る。中心部と外縁部は別集計にする。まずは現状値を記録し、SVGから未測定の密度を目標値として断定しない。

回帰検証は、建物内部の重複がないこと、住宅から実道路へアクセスできること、曲線化後も水域・城壁・建物へ侵入しないこと、中庭への入口が塞がらないこと、同じseedで結果が一致すること、無関係な地区の編集で再抽選されないことを対象とする。

解析用スクリプトと数値は `temp/redline-analysis/analyze.py` / `metrics.json`。PNGによる目視確認は元SVG2枚と編集済みStonewindで実施。編集済みWolfriseについてはXMLの頂点列を解析した。
