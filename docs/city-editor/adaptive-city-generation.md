# Grid evolution を使う完成都市生成の設計案

2026-09-17。調査・設計案。第1段階の実装結果は [generation-phase1.md](generation-phase1.md) を参照。以下の現状計測は実装前の調査値。

## 結論

推奨は「粗いグリッドの辺で河川・城壁・主要街道を作り、各面の内部では建物生成器が路地と建物を一緒に作る二層構造」。街区内の路地・敷地境界は編集用グリッドの辺に追加しない。Grid evolution の中心をHexagonal / Voronoiで細分化する必要はなく、そこで得られていた建物配置の品質を街区内の生成器へ引き継ぐ。骨格の接続検証と編集用メッシュは共用する。

セルごとに座標の縮尺を変える方法は採用しない。座標は全域でメートルに統一し、場所によって変えるのは「街区内の建物・路地の細かさ」「建蔽率」「敷地の目標面積」。共有頂点のある格子に異なる座標倍率を適用すると、道幅、河川幅、隣接面の接続まで不整合になる。

## 現状の確認と survey.md の補足

`core/document.ts` の Small / Medium / Large は地図の一辺を 1,200 / 2,400 / 4,800m にする。Voronoi の点間隔は44.8m、Hexagonal の既定辺長は50mで固定されるため、面数はおおむね1:4:16になる。`buildingTarget` は定義されているが、現在の建物生成からは参照されていない。

Node + tsx、seed=`analysis-grid`、既定パラメータの単発計測：

| 格子 | Small面数 | Medium面数 | Large面数 | Large格子作成時間 |
| --- | ---: | ---: | ---: | ---: |
| Hexagonal | 247 | 941 | 3,673 | 30ms |
| Voronoi | 584 | 2,302 | 8,890 | 225ms |
| Grid evolution | 116 | 116 | 116 | 1ms |

計測対象は `createGridDocument` のみ。完成都市生成・建物生成・ブラウザ描画の時間ではなく、性能保証でもない。ブラウザの長時間停止の支配要因は未特定。

同じSmallのGrid evolutionは、セル面積の最小279m²、中央値11,388m²、最大46,119m²。`classifyUrban` に半径396×0.92m、海・河川・道路誘引なしを与えると、市街地34面の合計165,620m²に対し、円からの目標は416,981m²。全体平均からセル数を決めると、中心の細かい面を過少に選ぶ問題を確認できた。ただし survey.md の「数セル」「中心数m」などは全設定での実測値ではない。

確認した問題：

- `gen/classifyUrban.ts` はセル数で成長を止める。非均一格子には面積予算が必要。
- `core/generate.ts` の `prepareRun` は evolution にも単一の `frame.blockSizeMeters` を渡す。格子の局所形状を表す量と、河川・道路の実寸を分離する必要がある。
- 道・壁・河川は既存メッシュに依存する。粗い外周では、重みや平滑化を調整しても通行経路自体が増えない。
- `rectifyVoronoiBlocks` は非Hex格子にも適用される。ただし尺度は全地図の中央値ではなく、障壁で分かれた市街地成分ごと。survey.md の説明より局所的で、どの補正が見た目を崩すかは段階画像による確認が必要。
- `gen/buildingLots.ts` は最小65m²、境界後退3m以上、地区別の目標面積を使う。地図サイズによる密度制御はない。凹面には凸カーネルを取るため、大きな凹街区を渡すだけでは有効面積が消える可能性もある。
- `wards.ts` に farm 判定はあるが、CEへの変換で farm は empty になる。農地表現は粗い格子を残すだけでは完成せず、用途と描画の追加が必要。

参照サイト <https://watabou.github.io/city-generator/> の本文取得では動的な生成結果を検証できなかった。「Largeは主に建物密度で表現する」はユーザーの観察を設計上の参考とし、現行サイトの内部アルゴリズムを確認した事実とは区別する。

## 方式の比較

| 方式 | 効果 | 残る問題・コスト | 判断 |
| --- | --- | --- | --- |
| 局所尺度だけを追加 | 面積判定・補正量の改善。変更が比較的小さい | 粗い格子に存在しない道路や接続は作れない | 基礎修正として必要だが単独では不足 |
| 中心だけ均一格子、外周は粗い格子 | 現行の街区補正を流用しやすい | 路地をグリッドで表現しない前提では、中心の細分化と境界接続のコストが不要 | 採用しない |
| 粗い骨格グリッド＋面内の路地・建物生成 | 骨格の面数を増やさず建物密度を上げられる。農地も大きな面で扱える | 面内で通れる隙間を作る分割と、主要街道への接続が必要 | 採用する方針 |
| evolution専用の生成器を丸ごと作る | 個別の調整は容易 | 門・橋・水際・保存などの改善が再び分岐する | 避ける |

## 推奨する生成手順

1. **地形と市街地の範囲を決める。** 海岸・河川の概形、市街地の目標面積、中心、港などの制約を先に計画する。都市成長は連結性を保った面積累積で制御する。巨大面一枚で予算を超える場合は境界付近だけを分割し、過伸長や細い触手も制限する。海岸や利用可能な土地の不足時は達成不能な面積を無理に埋めない。
2. **骨格を作る。** 城壁、門、橋の候補、広場、主要街路、城外への街道を計画する。粗い面の既存辺だけに拘束せず、必要な面を横切る線を挿入する。門・橋は線を描いてから近傍へ吸着するのではなく、交差点の接続方向と通行条件を先に確保する。
3. **骨格で囲まれた地区を確定する。** Grid evolution の中心から外周への疎密を地区配置の初期案として使う。骨格に合わない既存の境界は非固定部分に限って再構成する。川沿いや街道沿いの城外市街地も領域に含める。
4. **各街区に建築可能領域を作る。** 面の境界から、壁・川・主要街道の幅に応じて後退させる。大きな凹面を単一の凸カーネルへ縮めず、必要なら面内の作業用ポリゴンへ分解する。この分解は編集用メッシュへ反映しない。
5. **建物生成器が路地と建物を一緒に作る。** 主要街道に接する入口から面内へ通路を延ばし、その周囲を再帰分割して建物群を配置する。分割時に残す帯状の隙間を路地とし、深さに応じて通路幅や建物間隔を変える。出力は建物ポリゴンと必要に応じた路地の描画形状であり、`Mesh.edges` や道路の `FeatureGroup` は増やさない。面内の接続は作業用の分割木や入口情報で保ち、全域の経路探索には参加させない。
6. **外側は農地として処理する。** 農地は大きな区画と畝などの表示を基本にし、道路・川との境界だけを共有する。畝をすべて編集用メッシュの辺へ変換する必要はない。

既存の `FeatureGroup` は `EdgeRef` / 頂点IDを持つため、自由な骨格線を表示だけ追加する設計では編集や検証と食い違う。計画用の線は一時データにとどめ、最終的には交差点で分割し、共有された平面メッシュに組み込む。この制約が対象とするのは壁・川・主要街道のみ。既存辺で骨格が成立する場合はそのまま使い、門・橋や不自然な迂回の解消に必要な箇所だけ局所的にメッシュを修正する。内部の路地を扱うための汎用的な線挿入・再メッシュ処理は導入しない。

`openGeneratedPassages` や `validGeneratedCrossings` は共用候補だが、現在の格子形状を前提とする箇所をテストする。制約に合わない地域を再試行する際も、完成した骨格や手編集領域を動かさない。

## Largeの扱い

「地図の広さ」「市街地の広さ」「建物密度」「骨格の複雑さ」を別の入力にする。現在のSmall/Medium/Largeの実寸を保ったまま、地区数・主要交差点数には独立した上限を設ける。建物数は敷地面積、接道、建蔽率、空地率で調整し、目標値を満たすために最小建物サイズや河川との離隔を破らない。

一定面積で密度だけを増やす方式にも収容限界がある。限界に達した場合は市街地面積を増やすか、要求する建物数を制限する。「同程度の地区数」は可能でも、実際に14,000棟を描けば建物生成・描画にはその件数に応じた負荷がある。

骨格用メッシュの面数と地区内の詳細量を別に制御する。路地・敷地・畝は面から導出する描画形状であり、全域経路探索には参加させない。密度や面形状の変更ではその面の路地と建物だけを再計算し、骨格の経路探索をやり直さない。

## 実装順序

### 第1段階：現行処理の診断と共通基盤

- 完成都市生成を、地形・市街地・交差点・経路・補正・建物・SVG描画に分けて時間、面数、辺数、建物数、再試行回数を記録する。
- Small / Medium / Large、3格子、内陸・河川・海岸の固定シードで工程画像を保存する。見た目の評価に加えて、空街区率、道路の迂回率、門の到達性、実市街地面積を測る。
- `classifyUrban` の既定停止条件を面積へ移す。明示的な `urbanNPatches` は診断用途として維持し、従来格子の面積回帰を確認する。
- 現在は `stages.push({ urban: [...urban] })` が市街地面数Uに対してO(U²)の記録を行う。完成生成では記録を省略し、診断時も追加セル順から必要なステップを復元する。
- `edgeBetween` / `incidentEdges` などの全走査を隣接索引へ置換する候補を計測する。メッシュ変更に伴う索引の失効・再構築を明示する。
- Worker化、キャンセル、進捗表示を追加する。これは操作停止対策であり、演算量を減らす対策とは区別する。

### 第2段階：evolutionで骨格の成立を先に実証

- 地区程度の粗いメッシュに、門・橋と城外道路を局所挿入できるようにする。
- まず内陸・河川なし、次に河川と橋、海岸と港へ進める。骨格の妥当性を確認してから面内の路地・建物を生成する。
- `buildingLots.ts` の再帰分割と隙間生成を起点に、主要街道に接続する路地と建物群を生成する。内部で分割しても元の面数・辺数を変えない。既存の隙間生成だけで接続が保証されるとは扱わず、入口からの連続性を確認する。
- 細かな均一格子のための `rectifyVoronoiBlocks` を粗い面へ一律適用せず、骨格の形状補正と面内の建物方向の調整を分離する。道幅や河川幅は実寸のまま保持する。

### 第3段階：密度・郊外・編集への統合

- 地区ごとの建蔽率、敷地規模、路地幅、農地の描画を調整する。
- 地区単位の路地・建物キャッシュと、関連する河川・道路・境界の編集による失効を実装する。低倍率時の表示簡略化も検討する。
- 生成入力、アルゴリズム版、骨格と地区の対応を保存する。現状のDocumentには格子種別さえ保存されないため、形状判定だけで新旧の生成方針を切り替えない。
- 手編集・ロック領域は制約として維持する。新規生成と既存図面の更新を区別し、再構成対象外の面ID・feature参照を保つ。元の入力からの再生成、Undo / Redo、JSON読込を一体で検証する。

## 完了の判定

- Hexagonal / Voronoi の既存テストと代表画像に重大な回帰がない。
- evolutionで実市街地面積が目標から大幅に外れず、残差は境界街区の粒度と利用可能な土地で説明できる。
- 全陸上門が城外道路と城内道路に接続し、橋以外の水上道路、壁・川との不正な共有辺、自己交差がない。
- 建物が水面や壁へ侵入せず、街区の奥の建物にも路地から到達できる。農地へ都市用の細分化が漏れない。
- 建物密度や路地の詳細量を増やしても、骨格メッシュの面数・辺数は増えない。Largeの建物生成と描画は骨格と別の予算で測定される。
- 同じ入力で再現可能。局所編集が無関係な地区の建物配置を変更せず、ロック・保存・履歴が維持される。

まず第1・第2段階で「少ない地区数でも、線の構成が妥当な都市を作れる」ことを確認する。それを通過条件として密度表現へ進むのが、過去のアンチパターンを再び補正パスだけで追いかけない移行方法になる。
