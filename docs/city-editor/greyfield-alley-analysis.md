# Greyfield：城壁内の住宅街区・小道の形態分析

2026-09-23。対象は [`greyfield_with_alleys.svg`](../../temp/samples/greyfield_with_alleys.svg)。緑線に隠れる形状を [`greyfield.svg`](../../temp/samples/greyfield.svg) と照合し、[抽出スクリプト](../../scripts/extract-alleys.ts) と現在のCE実装も確認した。上下左右の記述はSVG表示上の方向。元の都市生成アルゴリズムを特定するものではなく、この一都市を再現するための観察と設計提案である。住宅の用途情報はSVGにないため、以下の「住宅」は住宅地に見える小規模建物を指す。

**中心となる規則は、主要な境界に沿って住宅列を確保し、向かい合う2列を一つの街区として、街区間だけに小道を通すこと。** 街区の短辺は住宅奥行きで制御し、長辺は複数戸の連続 frontage（道路に面する建物列）として残す。長辺を適度な間隔で横道により分割すると、局所的には整った格子、都市全体では方向の異なる格子の組み合わせになる。

## 1. 緑線をそのまま道路の正解データにはできない

抽出は「既存の建物群の間の空地」をボロノイで骨格化する処理。元の都市がボロノイで生成されたという意味ではない。

| 確認事項 | 分析への影響 |
| --- | --- |
| 建物色 `#A5A095` のpathは2,418個。抽出器と同じ城壁内判定では2,149個、共有頂点による連結群は216個 | 住宅だけの戸数・街区数ではない。点接触による連結、離れた建物による群の分裂もある |
| 緑線は531個のpolylineを660本の直線pathとして出力 | 660本の独立した道路があるという意味ではない |
| 全緑線の `stroke-width` は5（SVG表示座標） | 幹線と小道の実幅の差を消している。幅は原図の建物間の空間で判断する |
| 異なる建物群の間だけを対象にする | 建物と城壁・川岸との間の道は抽出されにくい。同一群に囲まれた中庭の通路も欠落しうる |
| 障害物判定は建物だけ。河川は障害物に含まない | 川の上の緑線を橋や道路と解釈しない |
| `maxGap=16`、短い枝の除去、簡略化などがある | 広場の途切れ、行き止まり、細かな折れ、枝の数には抽出条件の影響がある |
| 最初の城壁pathの座標を中心からの角度で並べ直して内外判定する | 門・河川開口を含む元の境界そのものではなく、城郭の別の城壁も忠実には扱っていない |

緑線には幹線・広場の骨格も含まれる。特に広場と水辺では、緑線より原図の空地・橋・建物前面を優先する。中庭へ向かう短い緑線があっても、公道なのか抽出上の枝なのかは別途判断が必要。

![川の上にも緑線が出る例。橋の細い帯と緑線は必ずしも一致しない](assets/greyfield-alley-analysis/river-alleys.png)

## 2. 観察できる描画・配置の規則

### A. 城壁・川岸との間に細い余白がある

城壁内側では、壁と建物の間に壁に沿う細い空間が見える。横道はその空間まで届き、城壁自体を突き抜けない。川岸でも川の曲がりに沿って建物前面が並び、細い帯状の余白が残る。

したがって、住宅を障害物の線まで充填せず、**壁・岸に沿った通行帯を先に予約する**方式が合う。ただし、SVGだけでは全周で同じ通行幅が保証されることや、全ての水際の余白が公道であることまでは確認できない。塔・門・橋・広い河畔空地は別処理が必要。

### B. 門―中心広場の幹線が骨格になっている

上・右・下などの門から、曲がりながら中心広場へ向かう比較的広い街路を追える。全ての門が広場へ独立した直線で結ばれるわけではなく、途中の街路への合流や、左側の大きな空地へ開く経路がある。

実装規則は「各門から中心の道路網へ到達できる幹線を確保する」。全ての門から中心点へ直線を引く規則にはしない。⑧では既存幹線を住宅で狭めず、その両側の建物列を形成する。

### C. 幹線沿いは建物が連続し、小道の入口は複数戸おき

幹線・広場に面する建物の前面は道路の線形に沿って並ぶ。隣棟の境界は細い黒線として現れるが、毎戸の間に道路幅の空間はない。横道の入口が、長く連続する建物列をところどころで切っている。

「幹線が一等地」はこの配置を作る設計上の動機として自然だが、地価そのものはSVGから観測できない。再現に必要なのは、**幹線 frontage の連続性を高くし、宅地分割のたびに小道を追加しない**という幾何的な規則である。幹線沿いに中庭の開口がある例もあり、全面を必ず閉じるわけではない。

### D. 街区の基本断面は2列。余裕があれば内側に中庭ができる

次の形が併存する。

1. **背中合わせ型**：道／住宅列／背面境界／住宅列／道。街区の短辺を横断すると約2棟。
2. **中庭型**：道／住宅列／中庭／住宅列／道。両端の建物列も回り込み、口の字・コの字になる。
3. **端部・変形型**：角地の横向きの家、奥行きの深い家、凹形の建物が混ざり、断面が3棟になる場所がある。

「住宅3軒分の幅」を、道路からアクセスできない第3列を常に中央へ詰める指示にはしない。**2列＋中庭、または端部の回り込みによって3軒程度の厚みになる**と解釈する方が、原図の接道と整合する。大きな中庭の街区は3軒分を超えるため、2〜3軒は全街区の上限ではない。

![南側。背中合わせの細長い街区、中庭型、横道のずれが併存する](assets/greyfield-alley-analysis/south.png)

簡易計測でもこの観察を確認した。抽出器と同じ共有頂点連結群から、6棟以上・最小面積外接長方形の長短比1.4以上の105群を選び、その長辺中央を短辺方向に横断する線と交わる建物pathを数えた。

| 横断線が通る建物数 | 群数 |
| --- | ---: |
| 1棟 | 3 |
| 2棟 | 86 |
| 3棟 | 15 |
| 4棟 | 1 |

105群中101群で2〜3棟。ただしこれは**細長い連結建物群を選んだ断面計測**であり、住宅街区全体の構成比でも、厳密な住宅列数でもない。中庭も横断し、点接触した建物群も対象になる。計測コードは [`measure.py`](../../temp/greyfield-analysis/measure.py)、個別の群・座標は [`metrics.json`](../../temp/greyfield-analysis/metrics.json)。

### E. 長い道と短い横道による、局所的な帯状構造がある

左上では、壁やそこから内側へ走る道路に沿う住宅帯を、短い横道が何回も横切る。右上では、壁の折れに合わせて帯の向きが変わる。南側では、縦に続く道の間を短い横道が分ける。都市全体を一つの角度で分割した形ではない。

長辺を2分割・3分割したようなまとまりはある。ただし出力からは、厳密な等分、分割順序、再帰の有無を確定できない。**住宅の奥行きに応じたほぼ一定の街区厚みと、近い間隔で入る横道**は支持できるが、「必ずn等分を再帰する」は生成仮説として扱う。

![左上。壁と幹線に沿う帯、短い横道、中庭への小さな開口](assets/greyfield-alley-analysis/northwest.png)

### F. T字接続・食い違いがあるが、十字路も残る

横道が長い道に突き当たるT字、向かい側の横道と位置がずれる接続、連続して横断する十字路が混在する。一律に十字路を禁止する必要はない。一方で、全ての帯の切断位置を一致させると、原図より均一な格子になる。

幹線側への入口数と位置を先に決め、裏側の細分化で入口が際限なく増えないようにする。横道の位置は隣の帯とある程度ずらすが、橋・門や重要な接続先があれば揃える。

### G. 不規則さは境界の曲がりと接続の調整から生じる

街区の内部は直線主体で、隣り合う建物は辺の方向を共有する。道路が曲がる場所では、前面列も緩く曲がり、台形・扇状の敷地になる。異なる方向の帯が合流する場所には三角形や台形の街区が残る。

ランダムに全頂点を動かすより、**壁・幹線・川岸の局所方向に従う区画を作り、その方向が衝突する場所だけ調整する**方が近い。交差角を全て90度へ固定する必要もない。

![右上。城壁の向きが変わるにつれて、住宅列と小道の向きも変わる](assets/greyfield-alley-analysis/northeast.png)

### H. 街区内部の空地は道路網と分ける

小道は複数の街区を回れる網を作る一方、中庭はその内部にまとまった空地として残る。中庭への狭い開口や行き止まりを、全て通り抜け道路へ変換しない。中心広場、大きな建物、左側の河畔空地も、住宅の反復分割から外す。

## 3. ⑧へ落とし込む生成モデル案

以下は観察に基づく提案であり、元のMFCGの実装を示すものではない。

### 先に確保するもの

1. 城壁内の建築可能領域から、河川・城郭・広場・公共施設の予約地を除く。
2. 門―広場の既存幹線と必要な橋を固定する。壁・川岸の通行帯も確保する。
3. それらで囲まれた領域に、基準になる長い frontage を選ぶ。幹線、壁沿いの道、川沿いの道を優先し、編集メッシュの任意の辺を自動的に道路扱いしない。

### 住宅奥行きで帯を作り、長さに応じて横道を入れる

住宅の代表奥行きを `d`、中庭の奥行きを `c`、左右の道幅を `w1, w2` とすると、目標は次のように表せる。

```text
街区の建物側外周間の厚み B ≈ 2d + c
道路中心線間隔 P ≈ B + (w1 + w2) / 2 + 道路前面の後退分

背中合わせ型：c ≈ 0
小中庭型：    c は 0〜d 程度を初期候補にする
大中庭型：    別の型として c > d を許す
```

`c` の範囲は初期調整用の提案値。参照全体から推定した確率分布ではない。住宅の「幅」は間口ではなく、この断面では奥行きを意味する。道路沿いの長さは別の値として扱う。

基準線に沿って `B` の帯を確保し、その背面側へ小道を置く。帯の長さ `L` と目標街区長 `Ltarget` から `n ≈ round(L / Ltarget)` を選び、ほぼ等しい長さの `n` 区画へ分ける。乱数は等分位置の小さな調整に使い、最低間口・残りの厚み・接続先を満たさない分割はしない。帯を深くするだけで住宅のない巨大な内部を作ることも避ける。

ただし、いつも長辺を先にn等分し、その後で奥へ進める必要はない。**奥行きと間口の両方を満たす区画を作る制約**を主にし、分割順序は領域の形に応じて選べる。曲がった境界では局所接線に沿わせ、向かい側からの帯が衝突したら停止・接続・残余街区化する。

### 小道の後に、道路を増やさず宅地を割る

街区外周の接道辺ごとに一列ずつ宅地を配置する。隣り合う辺の角地は所有範囲を調整し、重複を避ける。向かい合う住宅の背面を合わせるか、余剰を中庭へ集める。宅地の境界線と公道を明確に分離する。

住宅の前面は同じ道路境界へ揃え、間口・背面・中庭で変化を出す。孤立した中間列の住宅を作る場合はアクセスの説明が必要であり、単に「3列まで詰める」処理にはしない。

### 接続を先に成立させ、描画へ渡す

- 小道の交点と端点は共有するグラフとして保持する。見た目だけ近接した未接続の端点を作らない。
- 横道は既存道・境界沿いの道へ接続させ、壁や水面で不自然に終わらせない。壁の通過は門、川の横断は橋に限定する。
- 住宅地の道路網は幹線へ到達可能にする。ただし全てを木構造にせず、街区を回れる経路も残す。
- 道路を平滑化するなら、その後の道路幅を含む領域を基準に住宅前面を生成する。建物配置後の線の移動で接道や空間を壊さない。

## 4. 現在のコードとの対応

ユーザーが指す「⑧ 街区・小道」のラベルは [`src/city-editor/core/generate.ts`](../../src/city-editor/core/generate.ts) にある。今回の主な変更対象は `src/city-generator` ではなくCE側。

現在の描画用生成経路は、`buildBlockFabric()` → `buildLocalFabric()` → `buildPerimeterBlocks()`。ただしレイアウトに分岐があり、全てが同じボロノイ処理ではない。

| 箇所 | 現状と今回の分析との関係 |
| --- | --- |
| [`blockInfill.ts`](../../src/city-editor/core/gen/blockInfill.ts) | 地区をまとめ、レイアウト別に生成を振り分ける。`bram` / `circulade` は別経路 |
| [`localInfill.ts`](../../src/city-editor/core/gen/localInfill.ts) | 道路・障害物・後退距離を渡す。城壁内住宅地と外縁部・城郭の経路が異なる |
| [`perimeterBlocks.ts`](../../src/city-editor/core/gen/perimeterBlocks.ts) の `classicStreetBlocks()` | 境界沿いと内部に母点を置き、Delaunay隣接の二等分線で領域を切る。ボロノイの置き換え対象 |
| 同ファイルの非 `classic` 側 | 既に帯状分割と、隣の帯とずらした横道がある。新方式と近いが、領域の共通軸と数値の間隔が主で、局所 frontage・住宅奥行きとの結びつきを強める余地がある |
| [`housing.ts`](../../src/city-editor/core/gen/housing.ts) | `intramuralBlockSpan()` に2列＋道＋中庭の考えが既にある。住宅奥行きと街区厚みを共通の寸法モデルにする足場になる |
| [`frontageBuildings.ts`](../../src/city-editor/core/gen/frontageBuildings.ts) | 沿道建物生成の既存部品。街区生成との寸法共有・接道維持が必要 |

コメントやキャッシュ名に `voronoi` が残っていても、実際の分岐を確認する必要がある。さらに現行の⑧・⑨は、完全に独立した幾何生成とは限らない。`generate.ts` の7以降の処理は完成形を生成して段階別に返し、描画でも `buildBlockFabric()` を利用する。⑧で決めた道路・街区と⑨の住宅が同じ計画を使う構造を維持する。

## 5. 置き換え後の評価項目

1. **断面**：細長い住宅街区の多くが2列、または2列＋中庭になる。大中庭・角地は別集計する。
2. **幹線 frontage**：幹線の両脇に複数戸の連続列があり、宅地ごとに小道が割り込まない。
3. **方向**：壁・川岸・幹線に沿う列ができ、方向の切り替わりは接続部分へ集まる。
4. **道路網**：T字・食い違い・十字路・環状経路が混在し、各住宅地から幹線へ到達できる。
5. **境界**：壁・岸の余白を確保し、門・橋以外の横断を作らない。壁沿い・岸沿いの通行帯の連続性は明示的に確認する。
6. **空地**：余白が各戸の全周へ分散せず、中庭・広場・河畔へまとまる。

住宅だけの識別、各種道幅、横道間隔、T字路の構成比などは今回のSVGだけで確定した値として扱わない。緑線の総数や線幅への一致よりも、上記の構造の一致を優先する。別都市への一般化や具体的なパラメータの確定は追加サンプルで検証する。

今回の成果物は分析のみ。都市生成コード・抽出スクリプト・元SVGは変更していない。
