# CE アーキテクチャ規約

作成日: 2026-10-13

本書は City Editor（CE）の新規実装と段階的リファクタリングの設計規約である。既存コードは移行対象であり、目標構成への一括移動を要求しない。工程と完了条件は [リファクタリング・ロードマップ](plan/architecture-refactoring-roadmap.md) に定める。

参考: FMG upstream の `docs/architecture/architecture.md`（参照元: `fmg-upstream/docs/architecture/architecture.md`、2026-10-13確認）。本書はその責務分離、依存方向、決定論、状態とリソースの所有、段階的移行の原則をCEへ適用する。upstreamの将来構想すべてをCEの必須実装とはしない。

本書の対象範囲では、[初期設計](design.md) の `core/`・`ui/`・`render/` 構成を以下の目標構成で更新する。リポジトリの `AGENTS.md` と橋の共通規約を優先する。廃止予定の `src/city-generator/` は参照・編集・依存追加の対象にしない。

## 1. 目的と分割基準

- 一つのモジュールに一つの明確な責務を与える。
- 地図データ、生成、操作、描画、IOを分離し、依存方向を固定する。
- 同じ入力・設定・seedから同じ生成結果を再現する。
- 既存の公開API、保存データ、FMG連携、編集結果を維持しながら移行する。
- 長時間利用でも、閉じたUIや置換された文書を保持し続けない。

ファイルは数百〜1000行程度を目安とする。1000行を超えたら責務の混在と巨大関数を点検するが、行数だけを理由に分割しない。`part1.ts`、巨大な共有コンテキスト、用途不明の `helpers.ts` で見かけの行数だけを減らさない。関数にも意味のある工程名を与え、単に長い関数を別ファイルへ移して完了としない。

## 2. 目標構成と責務

すべて `src/city-editor/` 内に配置する。FMG本体への統合やMPA境界の変更は本リファクタリングに含めない。

| ディレクトリ | 責務 | 含めないもの |
| --- | --- | --- |
| `state/` | 文書状態、地図設定、状態の所有・採用 | DOM、SVG、生成アルゴリズム |
| `types/` | 層をまたぐデータ型・契約 | 実行処理、可変な共有状態 |
| `generators/` | 手続き生成、ドメイン計算、整合性を保つ編集処理 | DOM参照、描画、パネル操作 |
| `controllers/` | パネル、ツール、生成・編集操作の調停 | 都市生成アルゴリズム、地図描画 |
| `components/` | 常設画面、表示状態、共通UI部品 | 正本となる地図データの複製 |
| `renderers/` | 地図データからの描画、描画専用形状計算 | 都市の存在・接続・用途の決定 |
| `renderers/overlays/` | 選択、ホバー、計測、操作プレビュー | 永続的な都市情報 |
| `services/io/` | 文書の読込・保存・出力、形式変換 | 文書の暗黙的な編集 |
| `services/` | Worker通信、ブラウザー設定、外部受け渡し | 都市の生成判断、現文書の暗黙参照 |
| `data/` | 静的な一覧、テンプレート、参照値 | 状態変更、アルゴリズム |
| `utils/` | 明示的引数だけで動く汎用処理 | UI・現文書・グローバル状態への依存 |

共有型以外の内部型は担当モジュールの近くに置く。単一用途の形状処理は担当する生成・描画モジュールに置き、`utils/` へ無条件に集めない。静的な小さな表も、責務を隠さない限り同居できる。

## 3. 依存方向

原則として許可する依存は以下とする。

| 呼び出し側 | 参照できる層 |
| --- | --- |
| controllers / components | services、renderers、generators、state、types、data、utils |
| services | 基盤処理と明示的な通信契約。IOは受け取った文書と形式変換を扱う |
| renderers | generatorsの読み取り専用計算、state、types、data、utils |
| generators | state、types、data、utils |
| state | types、data、utils |
| types / data / utils | 同じ下位群。循環参照は禁止 |

上位層への逆向きimport、循環import、`window.*` を経由する隠れた依存を新設しない。下位層は状態を明示的に受け取り、現文書をグローバルから取得しない。Workerの生成処理本体はgeneratorsに置き、servicesは送受信・キャンセル・エラー変換を担当する。

型専用importも依存として点検する。進捗、診断、失敗理由はデータまたは明示的なobserver契約で返し、生成側からUIを呼ばない。移行用の再export窓口を新モジュールが逆にimportしてはならない。

## 4. 状態と編集

正本は `CityDocument` とその地図設定であり、SVGやフォーム値を正本にしない。保存対象の文書、生成要求、ブラウザー設定、選択・ツール状態、派生キャッシュを区別する。

- 文書の確定変更は既存の履歴・undo/redo経路へ渡す。ドラッグ中のプレビューと確定編集を分ける。
- controllerは操作の意図・入力を解釈し、ドメイン処理はgenerator側の編集APIへ委譲する。
- UIの入力検証とは別に、橋・城壁・道路接続等のドメイン制約は生成・手動編集で共有する。
- stateを万能な処理集にせず、各ドメインの処理が担当する整合性を保つ。
- 派生データを保存へ追加する場合は、必要性、読込との対称性、既存形式の移行を別途定める。
- 文書の複製は、再試行の分離、履歴、プレビュー等の目的を明示する。処理分割を理由に工程ごとの全体cloneを追加しない。

## 5. 生成の分割契約

Phase 6で旧`generate.ts`の利用者を所有APIへ移行し、窓口を撤去した。完全生成の入口は`generators/generation/generateCity.ts`、段階生成は`previews.ts`、設定は`settings.ts`を直接利用する。目標の内部構成は以下を基本とし、空の階層や不要なフレームワークは作らない。

```text
generators/generation/
  settings.ts           # 設定の初期値・正規化
  stages.ts             # 生成段階の定義・選択
  contracts.ts          # 計画・結果・進捗・診断の内部契約
  pipeline.ts           # 実行順序、工程間の受け渡し
  generateCity.ts       # 試行、再試行、最終成功判定
  previews.ts           # 逐次表示のための生成データ
  planning/             # 地形、都市域、城壁、道路の計画
  assembly/             # 計画からCityDocumentへの反映
  routing/              # 道路接続の完成・修復
```

`runPlan` と `applyPlan` の内部も意味のある工程へ分ける。工程は必要な入力と出力、変更する対象、前提条件を明示する。巨大な `Plan` をすべての工程へ渡すのではなく、地形結果・都市域・城壁・道路などの限定された契約へ段階的に整理する。

RNGは既存の初期化と消費順序を維持し、抽出先で再seedしない。処理順、Set/Mapの走査順、ID発行順、再試行条件を無意識に変更しない。時刻・UIの存在を生成結果の隠れた入力にしない。乱数seedの新規選択は実行要求を作る境界で行い、確定seedを生成へ渡す。

橋の基準値と判定は `src/utils/bridgeSkewPolicy.ts` に一本化する。歴史時代・国家技術による上限、河川法線への接近、最短通過、折れ曲がり禁止を維持し、抽出先に独自の閾値を作らない。根拠は [橋の斜交規約](../plan/bridge-skew-policy.md) を参照する。

## 6. 描画の境界

描画は読み取り専用で、同じ文書・表示設定から同じ出力を作り、再描画で要素を蓄積させない。

- 建物配置、渡し船接続、水車配置など「都市に何が存在するか」は生成・ドメイン計算に属する。
- SVG輪郭、装飾、表示品質など「どう見せるか」はrenderersに属する。
- 描画専用の座標・パス計算とDOM書込を分離する。
- generator関数の呼出し自体を禁止せず、読み取り専用か、世界の事実を決めていないかで判定する。
- 正本と再計算可能な派生結果を区別する。派生結果は必要に応じて生成時または読み取り専用の準備工程で作り、文書の世代に対応したキャッシュへ置ける。
- 地図レイヤーの順序・可視性と、操作overlayを分ける。文書読込や出力で順序が変わらないようにする。

SVGエクスポートはservices/ioが調停し、SVG構築はrenderersが担当する。DOM構築方法の全面変更は構造分割と別の性能改善として扱う。

## 7. UIとリソースの所有

`CityEditorPage.ts` は画面の組立てと接続の入口へ縮小する。各パネル・ツールは必要な操作APIと表示データだけを受け取り、ページ内の全ローカル変数を共有しない。

一時UIは開く時に構築し、閉じる時に生成DOM、listener、timer、observer、非同期処理、文書参照を解放する。常設画面はmount/unmount単位で同じ責任を持つ。折り畳みと破棄を区別し、UIを破棄しても設定は失わない。

すべての長寿命参照について所有者と解除地点を定める。キャッシュは文書の置換・関連変更で無効化し、前文書を保持しない。Workerの遅延結果は要求IDや世代で確認し、終了済み画面や置換済み文書へ反映しない。履歴・ログ・キャッシュは無制限に増やさない。

遅延ロードはCEの既存入口を維持して必要な箇所へ導入する。upstreamのregistry、一モジュール一object export、FMGのglobal登録を内部モジュールへ一律に導入しない。

## 8. 互換性と検証

ファイル移動・工程抽出と、アルゴリズム改善・保存形式変更・性能最適化を分ける。移行用API窓口は期限と利用者を記録し、利用者の移行後に削除する。

変更範囲に対応する既存テスト、型検査、代表都市fixtureで検証する。生成結果は同じ入力・設定・seedで比較し、順序に意味のある配列やIDを無条件に正規化しない。保存・読込、固定要素、FMG由来の地形・道路・橋、段階プレビュー、Worker、undo/redo、SVG出力の互換性を確認する。

新しい境界テストは、決定論、読み取り専用、保存の往復、破棄後の非同期反映禁止など実際の契約を検証する。単なる関数移動を写したテストは増やさない。性能は代表ケースで計測し、分割によりclone・再計算・DOM・listenerが増えていないことを確認する。

完了の基準は行数ではなく、責務の単一性、依存方向、明示的な入出力、互換性、リソース解放である。

## 9. Phase 6の機械検査と残る互換性

`npm run lint:architecture` は `scripts/city-editor/architecture.ts` を通してCEの役割別配置、層の方向、旧パス、下位層のブラウザーglobal/DOM型、実行時循環を検査する。静的import、再export、型専用import、`import("...").Type`、文字列の遅延import、`new URL("...", import.meta.url)`を含む。計算された動的importは依存を検査できないため拒否する。CE外の現行利用者とテストにも旧パスの検査を行う。廃止予定CGは参照・編集せず、検査走査から除外する。

componentsとcontrollersは画面組立て・controlの接続のため相互参照できる。servicesは明示的な入力を受け取り、IO・CLI・Workerの調停としてgenerators/renderersを利用できる。generatorsはCEのservices/UI/renderersを参照しない。既存のFMG共通幾何・橋規約・i18n契約は引き続き外部依存であり、検査はその外部graphまで再帰走査しない。

型参照も層の制約を受ける。`CityDocument`と生成recipe等、同じtypes層内の再帰データ契約は許可し、実行時の循環importと区別する。SVG・JSONの参照資産と`assets/catalog.ts`は静的dataとして扱い、assets配下に新しい実行モジュールは許可しない。

唯一の旧配置例外は`core/document.ts`。廃止予定CGの既存文書利用者を壊さず、CGソースへ触れないため、文書作成APIとnative parserを再exportする。CEと現行FMG利用者は新APIを使用し、この旧パスへの新規importは検査で拒否する。CG撤去時に窓口も削除する。過去のreviews・基準manifestは履歴として旧パスを維持する。
