# CE・FMG連携改善 設計書

作成日: 2026-10-05  
状態: P0〜P4の初期実装を追加。[実装・計測記録](1005-fmg-integration-results.md)参照。
要件: [1005.md](1005.md)

## 1. 目的と採用方針

FMGのBurg Editorで大都市のプレビューを速く表示し、CEでは中心市街地とFMG由来の郊外景観を別レイヤーとして扱う。

最初の成果物は、**詳細住宅の生成を省略した簡略プレビュー**とする。初版では通常画像への自動置換を行わず、都市の構造生成は1回だけ実行する。次に、FMG連携時の郊外をセルに依存しないSVG地物へ移行する。通常画像への段階的な置換は、計測結果を踏まえた後続工程とする。

対象はFMGのBurg Editor、FMG→CEの入力契約、CEの生成・描画・保存処理。廃止予定の `src/city-generator` は調査・変更対象に含めない。

本書のAPI名・追加型・性能目標は提案であり、実装済みの機能や計測結果ではない。

## 2. 現行実装から分かったこと

| 項目 | 現状 | 設計への影響 |
| --- | --- | --- |
| Burg Editorプレビュー | `src/ui/components/BurgCityPreview.tsx` が入力生成、Worker実行、`serializeCitySvg()`、Blob URL作成を行う | 簡略化の入口はこのコンポーネントとSVG生成経路 |
| 都市生成 | `core/generate.ts` の `generateCityOnDocument()` は構造生成・検証を行い、失敗時は別seedで再試行する | 簡略表示のために人口・都市規模・試行条件を変えない |
| 詳細住宅 | `render/svg.ts` が `buildBlockFabric()` または `buildCityBuildings()` を呼ぶ | Workerが返った後もメインスレッドで詳細処理が発生する |
| 既存描画品質 | `light` は住宅をまとめて描き、`minimal` は表示を間引く。いずれも住宅形状生成後の処理 | 既存品質設定だけでは住宅生成コストを取り除けない |
| Worker通信 | `progress` は複数回送信し、`complete` でPromiseを解決してWorkerを終了する | 「1要求で複数通知」は可能。現行APIの最終結果が1回という制約と区別する |
| 固定河川・橋 | `importedFixedCrossings` と `fixedDocumentGeometry.ts` でセルとは独立した形状を描画する | 郊外用に河川・橋を新しく推測する必要はない |
| メッシュ外街道 | `core/frameRoads.ts`、`CityDocument.frameRoads` が既に存在する | 線による郊外描画を、この延長として整理できる |
| 都市の範囲 | `frame.extentMeters` と `settlementExtentMeters`、`cityRadiusMeters` がある | 表示範囲と生成範囲を区別する既存の考え方を拡張する |
| 周辺都市 | `roads[].nextBurg` はID・人口・距離などを持つが、描画用座標や市街地輪郭は持たない | 周辺都市を正しい位置に描くにはFMG側からの追加情報が必要 |

現行経路は次のとおり。

```text
BurgCityPreview
  → getBurgSiteDescriptor → shareFromDescriptor → createGridDocument
  → startCityGeneration / Worker
      → generateCityOnDocument → complete(CityDocument)
  → serializeCitySvg → renderStandaloneCitySvg → renderEditorSvg
      → buildBlockFabric / buildCityBuildings
  → SVGのBlob URL → 画像表示
```

調査時点では性能計測を実施していない。住宅生成、構造生成、入力構築のどれが支配的かは都市ごとの計測で確定する。

## 3. 用語と必須条件

### 3.1 中心部・郊外の区分

- **中心部レイヤー**: CEで生成・編集する連続した市街地。城壁内だけに限定せず、必要な城外居住帯・城門への接続区間も含む。
- **郊外レイヤー**: 中心部生成範囲の外側にある、FMG由来の都市・河川・街道。Voronoiセルの境界にスナップさせない。
- **表示範囲**: 中心部・郊外を含むSVGのviewBox。遠い河岸を表示するために広げても、中心部のセル密度や住宅数は増やさない。

既存の `settlement: "core" | "outskirts"` は市街地内部の用途分類であり、本書のレイヤー区分とは別概念である。`outskirts` のセルを一律に削除すると城外居住・城門接続を失うため、その方法は採用しない。

### 3.2 橋・地物の不変条件

1. FMG・CEともに橋は局所的な河川進行方向に直角とし、対岸まで最短の横断区間とする。道路に合わせて斜めに橋を描かない。
2. FMGの検証済み固定橋は、その位置・向き・橋面端点を保持する。必要な曲がりは乾いた陸上の取付道路側で処理する。
3. 簡略化、クリッピング、品質切替で河川・橋・城門の位置を変えない。橋を途中で切って別の端点を作らない。
4. 不正または検証不能な橋は描かず、該当する接続を未成立として診断する。未検証の横断を通常道路で覆って隠さない。
5. 簡略表示の住宅記号数は、人口・必要住戸数・実際の生成住宅数として利用しない。

## 4. 改善A: Burg Editorの簡略プレビュー

### 4.1 初版の処理

既存の入力と構造生成は維持し、Workerの返却した `CityDocument` を簡略専用の描画経路に渡す。

```text
入力スナップショット
  → 構造生成・既存の検証・既存の再試行
  → CityDocument
  → 簡略描画（詳細住宅・敷地分割を呼ばない）
  → 画像表示
```

新設候補は `render/previewSvg.ts` の `renderCityPreviewSvg(document, options)` とする。SVGの枠、共通スタイル、固定地物、主要構造の描画部品を既存レンダラーから共有する。通常レンダラー全体を複製しない。

`renderStandaloneCitySvg()` / `serializeCitySvg()` の既定動作は詳細出力のままとし、Burg Editorだけを新しい入口へ接続する。CEの既存 `RenderQuality` は操作時の表示調整として残す。

### 4.2 描画内容と生成予算

| 要素 | 簡略版 |
| --- | --- |
| 河川・海岸・固定橋 | 検証済みの元形状を使用する |
| 城壁・城門・主要街道 | 構造生成の結果を使用する |
| 城郭・寺院等の主要施設 | 既存の配置結果から輪郭を描く。装飾は省略可能 |
| 住宅街区 | 建築可能部分の塗りと少数の住宅記号で密度を表現する |
| 個別住宅・付属建物 | 詳細な区画分割・敷地充填を実行しない |
| 路地・畑・装飾 | 既に得られた構造だけを使い、詳細fabricを要求する部分は省略する |

住宅記号の初期予算案は、街区あたり最大3個、都市全体最大300個。全住宅を生成してから先頭300個を取る処理は禁止する。生成済みの街区と予約領域から直接配置し、安定した街区IDとseedで決定的に選ぶ。

記号が水面・道路・主要施設の予約領域に入る場合は省略する。複雑な街区の縮小・分割が高コストになる場合も塗りだけへ退避し、必ず記号を置くための探索は行わない。予算は人口や表示範囲に比例して増やさない。

`buildBlockFabric()` や `buildCityBuildings()` だけでなく、それらを内部から呼ぶ補助処理も対象とする。港・水車・公園の描画が詳細fabricを必要とする場合は、簡略版では既存の構造情報で表せる輪郭に限定する。

### 4.3 状態・取消・キャッシュ

状態は `loading → ready-preview | failed` を基本とし、都市切替・閉じる操作・再試行時には既存Workerを取消する。要求IDまたは同等の世代管理で、古い完了通知が現在の都市画像を上書きすることを防ぐ。

現在のeffectは `burgData` オブジェクトを依存値にしている。改善時には、生成に関係するdescriptor・settings・seed・生成器版・プレビュー版から安定した入力キーを作る。同じ都市IDでも河川・街道・人口・時代・frame等が変われば再生成する。都市IDだけをキャッシュキーにしない。

初版で永続キャッシュは導入しない。必要なら後続で上限付きメモリキャッシュを設ける。差し替え・取消・破棄時のBlob URL解放を保証する。

### 4.4 失敗を早く知るための設計

簡略描画が短縮するのは主に構造生成後の処理である。構造生成中の失敗は詳細住宅生成より前に発生するため、住宅省略だけでその失敗時刻が早くなるとは限らない。

そこで、Burg Editorで現在捨てている `progress` を利用し、段階・試行番号・失敗理由を収集する。試行中の失敗は「再試行中」、全試行終了時は「生成失敗」と区別する。内部の詳細診断はログに残し、画面には短い状態と再試行操作を出す。

開発用には既存の `debugFailure` による最初の棄却で停止する経路を利用できる。ただし、通常生成とは試行条件が違うことを診断結果に明記し、本番プレビューの成功率比較や通常の監査結果と混ぜない。

簡略版の成功が保証するのは構造生成と簡略描画までであり、省略した詳細住宅生成の成功ではない。住宅品質・住戸数監査は引き続き詳細経路で実施する。

### 4.5 将来の詳細画像への置換

初版の受入後、表示ニーズと計測結果から採否を判断する。同じ `CityDocument` から詳細fabricを追加生成すればよく、都市構造の生成をもう一度行う必要はない。

詳細生成が重い場合はDOMに依存しない形状計算を別Workerへ移し、返却された形状からSVGを組み立てる。レンダラー側で再度fabricを作らないよう、計算済み形状を渡す契約も必要になる。

単一Worker内で段階返却する場合は、新たに `preview-ready` と最終 `complete` を区別し、前者でWorkerを終了しないようクライアントを拡張する。これは複数のPromise解決ではなく、中間イベントと最終結果の設計である。詳細化の失敗時は簡略画像を維持し、古い要求による差し替えとBlob URLの漏れを防ぐ。

## 5. 改善B: 中心部と郊外のレイヤー分離

### 5.1 データの責務

郊外地物はSVG文字列として保存せず、IDとローカル座標を持つ構造化データとして保持する。SVGはそこから生成する。中心部の `mesh` と、郊外の線・輪郭を別々に所有する。

追加データの概念案:

```ts
interface RegionalContext {
  version: 1;
  sourceRevision: string; // 描画対象入力の改訂を識別するハッシュ等
  coverageBounds: Bounds;
  settlements: Array<{
    burgId: number;
    name: string;
    center: Point;
    outline?: Point[];   // FMGに実形状がある場合のみ
    radiusMeters?: number; // 規模表示用。実市街地輪郭とは区別する
  }>;
  roads: RegionalRoad[];
  // 河川・固定橋は既存の検証済みpayloadを参照・再利用する。
}

interface CitySceneRegions {
  version: 1;
  coreBoundary: Point[]; // 生成・編集する市街地の範囲
  regionalContext: RegionalContext;
  connectors: RegionConnector[];
}
```

上記の `Bounds`、`RegionalRoad`、`RegionConnector` は本設計で定義する新規型の概念名である。道路はroute ID、branch ID、点列、幅、交差施設IDを持つ。コネクターはroute/branch ID、境界交点、中心部側の接続先、検証状態を持つ。

FMG側の `services/burgSiteDescriptor.ts` とCE側の同名契約型を同時に更新し、`io/incomingCity.ts` の検証・共有経路にも追加する。新規契約はdescriptorの新バージョンとして扱い、現行version 2を読み込めるアダプターを残す。

中心部の原点は対象burg。座標変換は既存と同じく `x=(mapX-originX)*metersPerMapUnit`、`y=(originY-mapY)*metersPerMapUnit` とする。SVGへのY反転は描画境界で一度だけ行う。

### 5.2 周辺都市の入力

FMG側で表示範囲内のburgから位置・名称・規模を収集する。`nextBurg` の距離だけから座標を逆算しない。FMGに市街地輪郭がない都市は、規模に応じた輪郭記号とラベルで表し、推定された表示であることをデータ上で区別する。

対象burg自身は中心部レイヤーが描くため重複表示しない。表示範囲外の接続先都市は、既存のBeyond情報を用いる境界ラベルに留め、周辺都市を見せるためだけに表示範囲を無制限に拡張しない。

### 5.3 SVGレイヤー構成

論理的には中心部と郊外の2レイヤーとし、描画順に必要な下位グループを設ける。

| 下から上への順序 | 内容 |
| --- | --- |
| 背景 | 陸地・海域の基底 |
| 共通水系 | FMG由来の検証済み河川・水域。中心部との境界で途切れさせない |
| 郊外地物 | 街道の乾いた区間、周辺都市の輪郭・記号 |
| 中心部 | 街区、住宅、内部街路、施設、城壁 |
| 横断施設 | 検証済み橋と必要な取付部 |
| 注記・操作 | ラベル、選択、編集ハンドル |

「SVGの線だけで描く」は、セル面を郊外地物の基準にしないという要件として具体化する。街道・都市輪郭はstroke主体のpathを使う。河川は実際の川幅と水面判定を守るため、既存の河岸・水面pathを再利用し、一本の一定幅の線へ置換しない。

中心部・郊外の表示切替は独立させるが、水系と橋の整合性は共通処理で維持する。非表示にしても衝突判定に使う水域・予約領域は残す。郊外地物は初版では参照・選択のみとし、セルの塗り・頂点移動の対象にしない。

### 5.4 境界の決定と道路接続

初期移行では既存の市街地メッシュ範囲と `frameRoadLegs(..., "beyond-mesh")` を利用する。次段階で、生成対象の市街地・城外居住帯・主要施設・城門の取付区間を包含する `coreBoundary` を明示する。

郊外から入る街道と境界の交点を、route IDとbranch IDを保持したコネクターにする。中心部側の経路はこの接続点に到達させる。接続点が水中、橋面上、城壁の門以外に来る場合は、境界または陸上の取付区間を調整する。固定橋を移動して帳尻を合わせない。

橋面と取付区間を境界で分断しない。境界調整が成立しなければ不成立を返し、途切れを隠す短絡線を描かない。共有橋・分岐路は施設IDとroute/branch IDで重複除去する。クリップ後の中心部と郊外の道路端点は同一座標を参照させる。

### 5.5 メッシュ依存の縮小

最初に表示上の分離を完成させ、その後に郊外生成処理を削減する。表示グループを分けただけでは生成の高速化を達成したと判定しない。

FMG連携の新モードでは、郊外の表示だけに必要だったセル生成・水域分類・街道経路探索・住宅充填を行わない。中心部の境界接続と予約領域は先に確定し、既存の経路探索・防御施設・河川検証が郊外セルを必要としていないかを確認しながら依存を外す。

[`suburban-landuse-redesign.md`](suburban-landuse-redesign.md) の沿道住宅・農地設計は、中心部生成範囲に含める城外居住帯および単独CEで維持する。新しい郊外レイヤーには初版で沿道住宅・農地を追加しない。将来追加する場合もセル全面の充填へ戻さず、街道に沿う独立形状として設計する。

### 5.6 橋の検証

固定橋は `validFixedBurgCrossings()` と既存の物理水面検証を再利用する。局所接線と橋方向の内積、河岸交点、橋面・取付区間、水域内の障害を検証する。直角判定の許容差は既存の厳密な数値許容差を継承し、簡略表示のために緩和しない。

最短横断は、選定された局所河川断面で、法線上の対応する両岸を結ぶ区間として検証する。蛇行河川の別の枝を横切る長い区間や、道路の元の斜め線分を橋として採用しない。河岸に必要な支持部は既存ルールに従う。

簡略表示・通常表示・CE編集表示・SVG出力の全経路で同じ検証済み形状を使用する。

## 6. 保存・互換性・移行

新しい地域データを含むCEドキュメントには新バージョンを設ける。`CityDocument` の型だけでなく、`core/document.ts` のparse/serialize、`io/cityEditorFile.ts`、共有データ、履歴の複製・復元も更新対象とする。

既存version 1〜3のドキュメントは従来表示を維持して読み込む。固定河川・`frameRoads` が存在する場合は再利用できる範囲だけを移行し、存在しない周辺都市の座標や輪郭を捏造しない。新レイヤー化のために既存の手編集セルを自動削除しない。

新規FMG連携でのみ新しい地域モードを有効化し、単独CEは従来生成を既定とする。地域データが欠けた旧入力は従来経路へ戻す。一方、地域データが存在しても壊れている場合は入力エラーを示し、不正な橋を別経路で描かない。

保存した地域形状は入力時点のスナップショットとする。読み込み時にFMGの最新状態へ暗黙更新しない。FMGから再取得した場合はsource revisionを変更し、橋・接続点を再検証する。

プレビュー品質と住宅記号は表示用派生物として扱い、正式な住宅データや住戸数へ保存しない。

## 7. 実装順序と完了条件

| 段階 | 作業 | 主な変更先 | 完了条件 |
| --- | --- | --- | --- |
| P0 計測 | 入力・グリッド・Worker・住宅生成・SVG・画像表示を分離計測 | `BurgCityPreview.tsx`、`generationDiagnostics.ts`、ベンチ用スクリプト | 同一入力で成功・失敗時間、形状数、SVGサイズを比較できる |
| P1 簡略版 | 専用描画、記号上限、失敗進捗、取消・世代管理 | `render/previewSvg.ts` 新設、`render/svg.ts` の共通化、`BurgCityPreview.tsx` | 詳細住宅生成を実行せずBurg Editorに簡略画像が出る |
| P2 地域契約 | 周辺都市・道路・境界・接続点の契約と旧入力互換 | FMG/CE両descriptor、`incomingCity.ts`、`types.ts`、`document.ts` | 新旧入力と保存往復が成立する |
| P3 描画分離 | 郊外path、共通水系、独立表示、境界接続 | `frameRoads.ts`、固定地物描画、`svg.ts`、`CityEditorPage.ts` | セル形状に依存しない郊外が簡略・詳細・出力で一致する |
| P4 生成削減 | 郊外だけのメッシュ処理を除去 | `document.ts`、`generate.ts`、`gen/blockInfill.ts` 周辺 | 郊外表示範囲だけを広げても中心部のセル・住宅数が増えない |
| P5 任意の詳細化 | 同じ生成済み都市から詳細画像へ置換 | Worker契約、計算済みfabric入力、プレビューUI | 構造再生成なしで差し替えでき、失敗・取消時も簡略版を維持する |

P1を最初のリリース単位とする。P2〜P4は順番に導入し、P5は必須完了条件に含めない。P1はP2以降に依存させない。

## 8. 検証計画と受入基準

### 8.1 機能・幾何検証

- 簡略描画で詳細住宅生成関数と同等の充填処理を呼ばない。住宅記号数が予算内で、同じ入力から同じSVGになる。
- 簡略・詳細で河川、橋、城壁、城門、主要道路の構造座標が一致する。表示品質で人口・必要住戸数・生成seedが変わらない。
- 河川に対して斜めの入力街道、蛇行、複数河川、合流点、共有橋を含め、非直角の橋が一本も出力されない。
- 郊外レイヤーにセル境界・住宅充填結果が漏れない。橋・街道・水系の重複、境界の隙間、Y反転の二重適用がない。
- 都市切替・閉じる・再試行・連続更新で古い結果が出ず、WorkerとBlob URLが解放される。
- 旧CEドキュメント、新地域データの保存再読込、undo/redo、共有入力、SVG出力で形状と検証状態を保持する。
- 詳細住宅を必要とする住戸数監査は、簡略描画を使わず従来の計数を維持する。

追加テストは簡略レンダラー、Burgプレビューの非同期制御、地域入力検証、境界コネクターに置く。回帰対象は `render/renderQuality.test.ts`、`core/frameRoads.test.ts`、`core/generationWorkerClient.test.ts`、`io/incomingCity.test.ts`、`services/burgSiteDescriptor.test.ts`、`renderers/registeredLandRouteScene.test.ts` を中心とする。

### 8.2 性能計測

小都市・中都市・大都市、内陸・河川横断・港湾・遠い河岸を含む入力を固定し、成功例と失敗例を分ける。既存fixturesと `ce:audit` の入力を再利用する。構造生成のバッチ監査だけではブラウザ描画時間を測れないため、Burg Editor相当のブラウザ計測を別に行う。

記録する値:

- descriptor構築、グリッド構築、Worker構造生成、結果転送、住宅関連計算、SVG作成・シリアライズ、画像表示までの各時間。
- 初回表示までの時間、最初の失敗通知までの時間、全試行失敗の確定時間。
- セル数、住宅形状数・記号数、SVG要素数・バイト数、利用可能ならメモリ指標。

実行機・ブラウザ・コミット・入力・seedを固定し、初回ロードとウォーム実行を区別する。各ケース10回以上測り、中央値とp95を記録する。CIでは壁時計の短い閾値だけを合否判定にせず、詳細生成を呼ばないことと形状予算を安定した条件として検証する。

初期性能目標案は、詳細版で住宅・SVG処理が支配的な大都市について、Worker完了後から画像表示までの中央値を50%以上削減、初回表示までの中央値を30%以上削減とする。未計測の仮目標であり、P0で基準を記録してから確定する。構造生成が支配的なケースは別集計にし、P4や生成本体の次の改善候補を判断する。

同じ失敗入力・同じ試行条件で、既存の失敗理由が失われず、最初の失敗通知と最終確定の時間が悪化しないことも確認する。最初の棄却で停止する診断モードは別集計にする。

### 8.3 全体の完了判定

P1で「Burg Editorが詳細住宅を作らず簡略画像を返す」を達成し、P4までで「中心部は編集可能な市街地、郊外はFMG由来のセル非依存形状」という構成にする。表示速度、入力互換性、道路接続、橋の直角・最短横断をすべて満たした時点で本改善の必須範囲を完了とする。

## 9. 主なリスクと対応

| リスク | 対応 |
| --- | --- |
| 住宅生成より構造生成が遅い | P0で段階別に計測し、簡略化の効果と生成本体の課題を分けて評価する |
| 簡略レンダラーが詳細処理を間接的に呼ぶ | 呼出経路のテストと段階別計測で検出し、構造描画部品へ責務を分離する |
| 郊外セル削除で門・城外居住・経路検証が壊れる | 表示分離を先行し、接続点と予約領域を確立してから生成範囲を縮める |
| 広域の表示で入力サイズが増える | coverageと表示範囲を限定し、地物件数・座標数に検証上限を設ける。橋・河岸を粗くして上限を回避しない |
| 固定地物と旧経路が二重描画される | 入力モードと地物IDで所有者を一意にし、描画経路を統合する |
| 簡略画像が住宅配置の確定結果に見える | UIに簡略表示と示し、住戸数監査・正式な詳細出力と用途を分ける |
