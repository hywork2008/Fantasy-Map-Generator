# 骨格先行生成（Skeleton-first）設計書

作成日: 2026-10-14
状態: Phase S0完了（2026-10-14、[調査・基準記録](../reviews/1014-skeleton-first-s0.md)）。Phase S1完了（2026-10-14、[実装・計測記録](../reviews/1014-skeleton-first-s1.md)）。S2以降は未実装

CEの都市生成に、現行方式と並ぶ新しい生成方法「骨格先行（skeleton-first）」を追加する。現行の生成オプション・生成方法・保存済みrecipeは変更しない。利用者は生成パネルで方法を選び、未指定時は現行方式のまま動く。

- [生成の失敗条件と試行結果](../generation-failure-cases.md) — 現行の不採用理由の集計

## 1. 背景: 現行方式が抱える構造的な取り合い

現行方式（以下「メッシュ先行」）は、文書パネルで作った1枚のメッシュの上で、海岸→河川→市街地→城壁→門→街道→街区の順に決める（`generators/generation/pipeline.ts` の `runPlan`）。

- 河川はメッシュの辺を辿る（`planning/rivers.ts`）。
- 城壁は市街地セル群の外周の辺そのものである（`assembly/outerWalls.ts`、`wallGeometry.ts`）。
- 門は城壁の辺と道路の辺の交点である。

この構成から次の問題が生じる。

1. **形の制約**: 城壁の形は必ずボロノイの塊の輪郭になる。四角・多角形・星型（稜堡式）は作れない。Bram の多角形核（`polygonalCirculadeLayout.ts`）だけが例外で、ベクトルで先に形を決めて周囲のメッシュとつなぐ。
2. **辺の取り合い**: 川・壁・道が同じ辺と頂点を奪い合う。後から直す処理として `generators/` の `meshDeformation.ts`、`riverWallRouting.ts`、`passages.ts`（`straightenBridges` / `straightenGateCrossings`）、`resolveRiverOverlaps.ts` などが積み重なっている。
3. **遅い失敗**: 不採用の判定は全工程の後、あるいは途中の重い工程の後に出る。失敗した試行は最初からやり直し、最大8回試す（`generators/generation/generateCity.ts` の `COMPLETE_CITY_ATTEMPTS`）。2026-10-02の集計では、不採用理由の上位が `unconnected-gates` 91、`invalid-crossings` 33、`too-few-external-roads` 13、`self-intersecting-faces` 5 だった。どれもメッシュ上での取り合いか、メッシュの変形に由来する。

## 2. 方針: 線を先に決め、メッシュを後から合わせる

都市の構造を三つの層に分ける。

| 層 | 内容 | 表現 | 決める時期 |
| --- | --- | --- | --- |
| L-外周 | FMGまたは合成地形の海岸線・河川・街道 | 固定のポリライン/ポリゴン | 最初（入力） |
| L-骨格 | 都市核、市域、城壁の形、門、橋、壁と川の交差 | ベクトルの幾何 | メッシュより前 |
| L-街区 | 住宅・街区・街路のボロノイ | メッシュ（`CityDocument.mesh`） | 骨格の後。骨格の線に沿わせる |

要点は次の三つである。

- 交差（壁×川、道×川、道×壁）は**線分どうしの交点**として一度だけ計算し、そこで角度の規約を満たすように幾何を調整する。
- メッシュは骨格の線を**必ず辺として含む**ように作る（§5）。そのため後から頂点を押し動かす必要がない。
- 検証はメッシュを作る前の骨格段階で行い、失敗した骨格は安く捨てる。

当初案の「FMG入力は地図の端、都市形状は中心に置いて空間で分ける」は、川が市内を貫く都市・港町・門まで入る街道では成り立たない。本方式は空間ではなく**決定順序と線の所有権**で分ける。入力が端にしか無い場合は、その特殊ケースとして自然に扱える。

## 3. 選択方式とUI

### 3.1 設定

`types/generation.ts` の `GenerationSettings` に以下を追加する。

```ts
/** 未指定 = "mesh-first"（現行）。 */
generationMethod?: "mesh-first" | "skeleton-first";
/** skeleton-first のみ有効。未指定 = "auto"。 */
wallShape?: "auto" | "organic" | "round" | "oval" | "square" | "polygon" | "bastioned";
/** wallShape = "polygon" | "bastioned" の辺数。未指定は都市規模から決める（5〜8）。 */
wallSides?: number;
```

- 現行の設定項目と既存のrecipeは意味を変えない。`generationMethod` が無いrecipeは現行方式で再生する。
- `generators/generation/settings.ts` に `resolveGenerationMethod` と `resolveWallShape` を追加する。`wallShape: "auto"` の解決は §4.3 の時代規則に従い、seedに名前空間を付けたRNG（`${seed}:wall-shape`）で決める。

### 3.2 生成パネル

`components/generationPanel.ts` に「生成方法」の選択欄を追加する。`skeleton-first` を選んだ時だけ「外壁の形」と「辺の数」を表示する。

`skeleton-first` で未対応の設定（§7のv1範囲外）は**黙って無視しない**。選択欄を無効にし、理由をツールチップに示す。FMG連携で起動した場合も、同じ規則で方法を選べるようにする。

### 3.3 メッシュの所有

現行方式は文書のメッシュを作り直さない（グリッドは文書パネルの責務）。骨格先行は**自分でメッシュを作る**。これは grid evolution の採用（`controllers/gridPreview.ts` の `adoptGridEvo`）と同じ種類の文書置換である。

- 生成するメッシュは evolution と同じ粗さ（1区画≒1セル）とし、`document.gridKind` は `"evolution"` のままにする。`"evolution"` は生成・描画の約15箇所で粗いメッシュ用の処理（街区・建物の fabric、平滑化の強さ、通路、広い川の橋など）を切り替えているためである。新しい値を足すとそれら全てを更新する必要がある（S0記録§1.4）。保存形式は変更しない。
- 文書パネルのグリッド選択は、この方法では生成に使わない。パネルにその旨を表示する。
- 生成後の手動編集は現行と同じメッシュ・featureGroup の経路で行う。骨格はメッシュの辺の並びとして保存し、特別な固定は追加しない。

### 3.4 recipeと決定論

- 成功した文書の `fabric.generation.algorithm` は `"skeleton-city-v1"` とする。`settings` に `generationMethod` と `wallShape` を含めて再生できるようにする。
- RNGは工程ごとに名前空間を分ける（`${seed}:skeleton:<k>:<工程>`）。骨格の再試行番号 `k` を含めることで、再試行が後段の乱数を消費順序で汚さない。
- Set/Mapの走査順とID発行順は、現行と同じく生成の入力として扱い、意図せず変えない。

## 4. 生成工程

段階プレビューのために、`stages.ts` に骨格先行用の段階一覧 `SKELETON_STAGE_DEFINITIONS` を別に定義する。現行の `GENERATION_STAGE_DEFINITIONS` は変更しない。

| 段階 | id | 内容 | メッシュ |
| --- | --- | --- | --- |
| K1 | `skeletonInputs` | 外周入力の正規化 | なし |
| K2 | `skeletonCore` | 都市核と市域 | なし |
| K3 | `skeletonWall` | 外壁の形 | なし |
| K4 | `skeletonCrossings` | 門・橋・壁と川の交差 | なし |
| K5 | `skeletonCheck` | 骨格検証（失敗なら K2 へ戻る） | なし |
| K6 | `conformingMesh` | 骨格に沿うメッシュの生成 | 作る |
| K7以降 | `wards` 〜 `conceal` | 現行の後段工程を再利用 | 使う |

### 4.1 K1 外周入力

- 入力は現行と同じく `prepareRun.ts` から得る。`siteToGeography`（FMG descriptor）または `synthSite`（単独生成）を使うが、`cellsFromMesh` は呼ばない。
- 海岸は陸と水のポリゴン、河川は中心線と川幅（両岸のポリゴン）、街道は外部の端点を持つポリラインとして保持する。
- FMG連携の固定交差（`importedFixedCrossings`）と固定道路は**変更しない入力**として扱う。これは既存の制約を引き継ぐ。

### 4.2 K2 都市核と市域

- 都市核の位置は、FMGの都市位置または合成地形の中心とする。陸上にあり、河川帯の外にあることを条件にする。
- 市域の半径は現行と同じく `params.cityRadiusMeters` と住居数から決める（Lot occupancy guide による半径を流用する）。
- 市域のポリゴンは「円を陸のポリゴンで切り取り、核を含む連結成分を残したもの」とする。海に食われて市域が下限（現行の `urban-area-too-small` と同じ πR² の45%）を切れば、この時点で不採用とする。

### 4.3 K3 外壁の形

外壁は市域と核から作るパラメトリックな多角形である。

| wallShape | 作り方 | 時代の制約 |
| --- | --- | --- |
| `organic` | 市域の外形を平滑化し、低周波の揺らぎを加える | なし |
| `round` / `oval` | 楕円に弱い調和成分を加える（`circuladeLayout.ts` の `RingHarmonic` を流用） | なし |
| `square` | 回転した長方形。角の丸めと辺のわずかな揺らぎを加える | なし（ローマ式の方形都市、バスティード） |
| `polygon` | N角形。各頂点に塔を置く | なし |
| `bastioned` | N角形の各頂点に稜堡（面2本・側面2本）を付ける。半月堡は後続で扱う | `ageOfExploration` 以降のみ |

- `auto` の解決: `bastioned` は `ageOfExploration` 以降に限り候補とする。それより前の時代では `organic` / `round` / `oval` / `polygon` から選び、方形は `classicalAntiquity` で重みを上げる。具体的な重みは実装時に計測を見て決め、ここでは固定しない。
- 水との関係:
  - 海: 外壁から海側を切り取る。海岸沿いの区間は「海壁」として扱うか、壁なしの区間とする。現行の `seaOpeningEdgeIds` に相当する区分を、ベクトルの段階で決める。
  - 川: 川が外壁と交わる場合、その交点の周りで壁を局所的に作り直し、壁が川を**川の法線方向に**横切るようにする（交点の前後に頂点を2つ挿入する）。川と平行に近い壁の区間が生じる形は不採用とし、形のパラメータを引き直す。
- 外壁の形は、城壁の多角形が単純（自己交差なし）で、核を内包し、市域面積の所定割合（`walledAreaShare`）に収まることを満たす必要がある。

### 4.4 K4 門・橋・交差

- **門**: 街道のポリラインと外壁の交点を門とする。交差角が大きく斜めなら、街道の最後の区間を曲げて壁にほぼ直角に入れる。`bastioned` では門を稜堡の間の幕壁（カーテン）の中央付近へ寄せる。
- **門数**: 外部街道が足りない場合（現行の `too-few-external-roads` の下限）は、外壁の向きに沿って補助の街道を枠まで伸ばす。枠まで乾いた陸がつながらなければ、ここで不採用とする。
- **橋**: 街道や城内の幹線が川を渡る地点は、`bridgeSkewDegrees(axis, riverTangent)` と `resolveBridgeSkewLimit(period, transport, structure)` で判定する。上限を超える地点には架けない。AGENTS.md の原則に従い、道を曲げて直角に入れる、別の地点を探す、渡し船にする、のいずれかとする。橋は折れ曲がらない1本の線分とし、最短距離で渡す。
- **壁と川の交点**: 水門の位置として記録する。現行の `riverWallPassage.ts` が作る通路の情報は、ここで線分として決まる。

### 4.5 K5 骨格検証

メッシュを作る前に、ベクトルだけで次を判定する。

| 判定 | 対応する現行の不採用理由 |
| --- | --- |
| 各門から核へ、壁内の乾いた陸を通る経路がある。各門から枠へ、壁外の乾いた陸を通る経路がある | `unconnected-gates` |
| 壁×川、道×川の交差がすべて一点で十字に交わり、橋の角度が上限内である | `invalid-crossings` |
| 外部街道の本数が規模の下限以上である | `too-few-external-roads` |
| 外壁が単純多角形で、骨格の線どうしが近接の下限（ブロック寸法の半分）より離れている | `invalid-mesh`（予防） |

- 経路の判定は、骨格を粗いラスタ（ブロック寸法の1/2程度）に焼いた上での連結判定で行う。精密な道路の経路探索は後段の工程の責務として残す。
- 失敗した場合はK2へ戻り、`k` を増やして骨格を引き直す。骨格の試行回数の上限は別に設ける（初期値16）。骨格の段階の費用はメッシュ工程より桁違いに小さいと想定するが、実測で確かめる（§8）。
- 骨格の不採用理由は現行と同じ `generationDiagnostics` の observer 契約で返し、生成ログパネルに表示する。

### 4.6 K6 骨格に沿うメッシュ

骨格の線（外壁、川岸、海岸、街道の幹線）を辺として含むボロノイを作る。

1. **境界の標本化**: 骨格の各線を、ブロック寸法に応じた間隔で標本化する。稜堡の短い面や壁と川の交点の付近では、間隔を局所的に縮める。
2. **鏡像の種点の対**: 各標本点について、線の法線方向に ±d だけ離した2つの種点を置く。対になる2つの種点の間のボロノイ境界は、ちょうど骨格の線の上に乗る。
3. **内部の種点**: 骨格で区切られた各領域（城内、城外、川の帯、海）の内部に、現行の `grid.ts` と同じ可変半径のポアソンディスクで種点を撒く。骨格の線からの距離が d の2倍未満の内部種点は捨てる。
4. **ボロノイと仕上げ**: `computeVoronoiCells` で一括して計算し、地図の枠で切り取る。骨格の角（凸・凹）の付近で線から許容値（ブロック寸法の5%）以内にずれた頂点は、線の上へ吸着させる。許容値を超えるずれがあれば、その付近の標本間隔を縮めて**その領域だけ**作り直す（全体のやり直しはしない）。
5. **対応表**: 骨格の各線について、それを構成するメッシュの辺の並びを記録する。外壁・川・街道のfeatureGroupは、この対応表から直接作る。メッシュの辺を経路探索で辿る処理は不要になる。
6. **検証**: 全ての面が単純多角形であること、各骨格の線が辺の並びで途切れずに表現されていることを確認する。

この方法は、現行の `polygonalCirculadeLayout.ts` が多角形核の外周に `outerAnchorNodes` を置いて周囲のボロノイとつなぐやり方を、全ての骨格の線に一般化したものである。

### 4.7 K7以降 現行の後段工程の再利用

街区の割り当て（`planning/wards.ts`）以降、すなわち城内街路・街区・建物・隠蔽（`conceal`）は現行の実装を再利用する。

- 骨格先行は `runPlan` の `planCoast`〜`planDefenses` の4工程を置き換え、それらと同じ出力（`Plan` に無い中間値 `coast`、`classified`、`coastalWater`、`genBorders`、`canPlaceTownGate`、`streetHub`、`residentialOutskirts` などを含む）を骨格から作る。`planRoads` と `planWards` は現行の関数をそのまま呼ぶ（S0記録§1.2）。
- 文書への反映は現行の `applyPlan` を使う。`applyGates` の門配置の前処理のうち、壁輪郭の平滑化（`finishCityGeometry(next, "boundaries")`）、`openWallRiverMouths`、`repairRiverWalls` は骨格先行では呼ばない。`clipSurveyedRiverWalls` は残し、何も変えないことを診断で確認する（S0記録§1.3）。
- 完成後の `finishCityGeometry` 全体は、壁の頂点を一時的に固定して呼ぶ。そのほかの後段の修復処理（`straightenBridges`、`straightenGateCrossings` など）は最初は現行のまま通し、何も変更しないことを診断で確認してから外す。

## 5. 配置

規約§2・§5に従い、`generators/generation/skeleton/` に置く。

```text
generators/generation/
  generateCity.ts         # settings.generationMethod で分岐（試行・最終判定は共通）
  stages.ts               # SKELETON_STAGE_DEFINITIONS を追加
  settings.ts             # resolveGenerationMethod / resolveWallShape
  skeleton/
    contracts.ts          # Skeleton, SkeletonFailure, 工程ごとの入出力
    pipeline.ts           # K1〜K6 の順序、骨格の再試行
    inputs.ts             # K1
    cityCore.ts           # K2
    wallShapes.ts         # K3（形の族ごとの生成関数）
    crossings.ts          # K4（橋は bridgeSkewPolicy のみを使う）
    checkSkeleton.ts      # K5
    conformingMesh.ts     # K6
    toPlan.ts             # K7 へのアダプタ（planCoast〜planDefenses と同じ出力を作る）
```

- `skeleton/` の各モジュールはDOMとUIに依存しない。`generators/geom.ts`、`generators/voronoi.ts`、`src/utils/bridgeSkewPolicy.ts` を使う。
- 橋の角度の閾値を `skeleton/` 内に独自に持たない。
- 比較用のCLIは `services/analysis/` に置く（既存の `wallRingLab.ts`、`cityGenerationAudit.ts` と同じ層）。

## 8. 評価と未確定事項

### 8.1 評価指標

数値目標は計測の前に決めない。調整定数は推定ではなく実測で較正する。次の指標で現行方式と比較する。

- 成功率と、成功までの試行回数（骨格の試行と完全な試行を分けて数える）
- `generationMs` の中央値と分布、工程ごとの内訳（`docs/tools/ce-performance.md` の階層付き内訳）
- 不採用理由の分布
- 外壁の形の族ごとの成功率

S0の基準では、FMG連携は96都市すべてが1回目で成功し、時間の46%が住宅の当てはめ（`fit-housing`）だった。FMG連携では速度の改善を目標にせず、失敗率を下げないこと（退行なし）と形の自由度を評価する。単独生成では不採用の68%が `wall-river-routing-failed` で、時間の19%が不採用の試行に費やされていた。速度と失敗率の比較はこちらに重点を置く。

骨格先行を既定の方法へ切り替えるかどうかは、この比較の後に別途決める。本設計の範囲では既定を変えない。

### 8.2 想定するリスク

- **有機的な市街地**: 歴史的には、街が先に育ち、その輪郭に壁が付くことが多い。`organic` の外壁は市域の推定に依存するので、現行方式の有機的な見た目を再現できるかは比較して確かめる。
- **鏡像の種点の角の処理**: 鋭い角（稜堡の先端、壁と川の交点）では、標本点を細かくしても小さな面や細い面ができやすい。最小の面積と辺の長さの下限を検証に含める。
- **後段の暗黙の前提**: 後段の工程が、現行のメッシュの性質（セルの大きさの分布、市街地の境界の形）を暗黙に前提としている可能性がある。Phase S0の調査とPhase S3の診断で洗い出す。
- **FMG連携の固定交差**: FMGが決めた橋の位置を変えられないため、外壁や門の位置はそれに合わせる必要がある。固定交差が外壁の近くにある場合の扱いはPhase S1のテストで具体化する。

### 8.3 未確定事項

- 外壁の形の `auto` の重み（実測後に決める）
- 骨格の試行回数の上限（初期値16は仮）
- 海岸沿いの区間を海壁にするか壁なしにするかの規則（時代と港の有無で決める案がある）
