# Grid evolutionの実装に関する調査

City Editorにおいて、**Hexagonal** や **Voronoi** では妥当な見た目で都市が生成されるのに対し、**Grid evolution** を選ぶと過去に修正してきた様々な見た目のアンチパターンが再発してしまう最大の理由は、**「都市生成や補正の各アルゴリズムが、均質なセルサイズ（1セル約45〜50m）の均一格子（Uniform Grid）を前提として調整されてきたため」**です。

`Grid evolution` はその前提（不変条件）から根本的に外れた幾何構造を持っているため、これまでのセッションで追加してきた安全弁や補正フィルターが意図通りに作動しなくなっています。

具体的にどのようなメカニズムでアンチパターンが表出しているのか、コードと処理の観点から解説します。

---

### 1. メッシュ構造の根本的な違い

| 項目 | Hexagonal / 通常 Voronoi | Grid evolution (`buildPatchCells`) |
| :--- | :--- | :--- |
| **格子の性質** | **均一格子（Uniform）**<br>青色ノイズ（ポアソンディスク）または正六角形 | **密度勾配格子（Scale-variant）**<br>中心が超高密度、外周が超低密度のスパイラルスキャッター |
| **セル総数 (Small時)** | **約 600 〜 800 セル** | **約 100 〜 120 セル** (nPatches 15 × 8) |
| **セルサイズ・エッジ長** | 全域で **40〜50m 前後** でほぼ一定 | 中心部は **数m〜10m**、外周部は **150m〜200m超**（20倍以上の開き） |

---

### 2. 各生成・補正ステップで発生している破綻

これまで様々なセッションで修正してきたロジックが、`Grid evolution` の極端な疎密勾配によって次々と誤作動を起こしています。

#### ① 市街地コア面積の極端な歪み (`classifyUrban.ts`)

コミット `a72426e62`（*ボロノイとヘックスでの都市のランダム生成面積を揃えた*）で、市街地セル数をセルの平均面積から自動計算するロジックが導入されました。

```ts
function autoPatchCount(cells: Cell[], cityRadiusMeters: number, cellSizeMeters: number): number {
  const meanArea = meanCellArea(cells);
  const cellArea = meanArea > 0 ? meanArea : Math.max(1, cellSizeMeters) ** 2;
  return Math.max(1, Math.round((Math.PI * cityRadiusMeters * cityRadiusMeters) / cellArea));
}
```

- **均一格子の場合**: どのセルも約 $50 \times 50\text{m}$ なので、面積から逆算した目標セル数（`targetN`）は実際の市街地ディスクをぴったり埋めます。
- **Grid evolution の場合**: 外周部の数個の超巨大セル（数万 $\text{m}^2$）が `meanArea` を極端に引き上げます。その結果、**目標セル数 `targetN` が数セル〜十数セル程度と極端に少なく算出**されてしまいます。
- 中心部のセルは数メートル規模の極小セルなので、わずか十数セル塗っただけで終了すると **市街地が米粒のように極小になる** か、逆に1つでも巨大セルを巻き込むと **都市の半分が1つの巨大なブロックになってしまう** という歪みが生じます。

#### ② 道路の鋭角ジグザグ・大回りの再発 (`buildStreets.ts` / A*ルーティング)

- 道路（Approach roads / 幹線道路）は、メッシュのエッジ上を A* 探索で辿ります。
- 均一格子であれば密な網の目があるため、目的の方向へほぼ直線の滑らかな経路が見つかります。
- しかし Grid evolution の外周部は **1辺が100〜200mもある長大なエッジが数本あるだけ** です。選択肢が物理的に存在しないため、道路が「極端に不自然な大回り」をしたり「城壁に沿って不自然にカクカク折れ曲がる」という、かつて修正したルーティングのアンチパターンが強制的に発生します。
- 外周エッジが粗すぎることで、城壁外の区画（extramural wards）と門の接続が断絶しやすくなります（コミット `3114fd02b` の前提が崩れる）。

#### ③ 街区整形アルゴリズムのスケール破綻 (`rectifyVoronoiBlocks.ts`)

コミット `2980f9582` で導入された `rectifyVoronoiBlocks` は、Hex 以外のメッシュに対して自動実行されます。

```ts
// rectifyVoronoiBlocks.ts
const scale = median(lengths);
const weight = distance(a, b) / (scale * scale * 4 + distance(p, midpoint) ** 2);
const wave = Math.sin((origin[0] * Math.cos(pair.axis) + ...) / (pair.scale * 3) + pair.phase);
```

- この整形処理は **「均一なサイズのボロノイセルが並んでいること」** を前提としており、エッジ長の中央値（`median`）を基準に直交化や波打ちの補正を行っています。
- Grid evolution のようにエッジ長が数m〜200mまで激しくばらついていると、`scale` の基準が壊れます。その結果、中心部の密集した微小セルではエッジが潰れて不正な形状（自己交差判定で弾かれて原形維持）になり、中規模セルでは不自然に引き伸ばされて歪な多角形が生まれます。

#### ④ 橋梁・河川交差の不整合 (`straightenBridges.ts` / `walkRiver.ts`)

- 川のエッジ探索（`walkRiver`）や橋の直線化（`straightenBridges`）、川と建物のクリアランス判定（コミット `d94a53756`）は、いずれも `cellSizeMeters`（約50m）を基準にした距離・角度・オフセット計算を行っています。
- エッジが極端に長い場所を川が横切ると **橋が極端に長大・斜め架橋** になり、中心部の極小セルでは **川幅（10〜20m）がセルそのものより広くなって街区を飲み込んでしまう** 現象が起きます。

#### ⑤ 建物ロットの消失と巨大区画 (`buildingLots.ts`)

- 建物ロットの生成では、道路・水際からのセットバック（3〜6m）や最小敷地面積（65 $\text{m}^2$）が固定メートル単位で定義されています。
- 中心部の極小セル（数十〜100 $\text{m}^2$）にセットバックを適用すると **内側の有効領域が消滅して建物が建たない（空き地だらけになる）** 一方、外周寄りの巨大セルでは **道路もない広大なセル内に建物が延々と再帰分割で敷き詰められる** 現象が発生します。

---

### まとめ：設計思想のインピーダンスミスマッチ

- **TownGeneratorTS 本来の思想（Grid evolution）**:
  「**メッシュの段階で都市の形そのものを表現する**（中心だけ細分化し、外周はただの余白・外郭とする）」
- **City Editor の現在の思想（Hex / 通常 Voronoi）**:
  「**均一でフラットなキャンバス（メッシュ）を用意し、その上に後から動的に市街地・道路・城壁をプロットし、整形の各パスで見た目を洗練させる**」

これまでの多くの改善セッションは、後者の「均一キャンバス」を前提として各フェーズ（市街地判定、道路探索、街区整形、橋梁補正など）の幾何学的閾値やフィルターを最適化してきました。そのため、前者の思想で作られた不均一な `Grid evolution` メッシュを流し込むと、各補正レイヤーの前提条件が次々と崩れ、過去に潰したはずの見た目の破綻が一斉に噴出してしまう、というのが根本的な原因です。
