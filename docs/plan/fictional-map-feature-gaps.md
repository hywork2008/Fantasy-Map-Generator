# フィクション地図として欠けている要素 — 概要と掘り下げポイント

## 状態

**未実装の調査・ブレインストーミング・ドキュメント。** 2026-09-05 時点の `master`(`72ac6e7aa`)を
対象に、ゲーム/フィクション作品の地図と比較したときに本プロジェクトの地図表現に欠けている要素を
洗い出したもの。実装計画ではなく、各項目を個別に深掘りする際の起点として書いている。

対象は「地図に描かれる/描かれ得るもの」に限定する。経済・軍事・人口動態などのシミュレーション
ロジックそのものの精度や結合度は対象外(それらは `economy-coupling-audit.md` など既存ドキュメント
の領域)。ここで扱うのは、**シミュレーションの結果であれ静的な地理情報であれ、地図上の視覚要素・
命名・ナラティブ装置として何が足りないか**という observation。

各項目は独立して着手できる。優先順位は末尾の「掘り下げ優先度」節を参照。

## 1. 地形・地物の自動命名とラベル

### 現状

`features.ts` はグリッド/パック両方で地物を海・湖・島に分類し(`features.ts:124`, `features.ts:208`)、
さらに ocean / sea / gulf / continent / island / isle / lake_island / freshwater lake / salt lake まで
グループ分けしている(`features.ts:461-516`)。しかし `feature.name` に値を入れているのは
`lakes.ts:33`(`getName()` は `lakes.ts:37`)と `river-generator.ts:562`(`getName()` は
`river-generator.ts:567`)、街道の `routes-generator.ts:1891`(`getRouteName()`、命名できない場合は
"Unnamed route" を返す `routes-generator.ts:1910`)のみ。

海・湾・海峡・大陸・諸島には名前も、曲線パスに沿ったラベル描画も存在しない。山脈・森・砂漠・平原・
高原も同様で、`draw-relief-icons.ts` は個々のアイコンを配置するだけで、連結成分としてまとめて
命名する処理がない。

### 掘り下げる際の論点

1. 命名対象の単位をどう区切るか: `feature.group` の粒度(既存の island/sea 分類)をそのまま地名の
  単位にできるか、それとも大陸級は複数 group にまたがる別集計が要るか。
2. バイオーム連結成分(森・砂漠・荒野)の命名は `biomes.ts` の biome id と地形の起伏
  (`draw-relief-icons.ts` が既に持つデータ)のどちらを主軸にするか。
3. 文化圏との整合: 地物が複数文化の版図をまたぐ場合、文化ごとに別名を持たせるか(=多言語地名、
  項目7と接続)、代表文化1つの命名で妥協するか。
4. ラベル配置: 既存の `draw-burg-labels.ts` や河川ラベル(`draw-rivers.ts` 内)のパス追従ロジックを
  流用できるか、湾曲した海域名には新規の曲線テキスト配置が要るか。
5. 峠・海峡・岬などの微地形トポニムは `landRouteGraph.ts` / `seaRouteGraph.ts` のチョークポイント
  判定を流用できる可能性がある。

## 2. 歴史の奥行き(前史・国境変遷)

### 現状

現在の世界は「現在時点のスナップショット + `advanceTime` による前進」のみで、生成時点より過去の
状態を持たない。`markers-generator.ts` の `ruins`(`markers-generator.ts:327`)や
`battlefields`(`markers-generator.ts:208`)はランダムな点配置で、どの国がいつ滅びたか、
どの戦役の跡かという因果とは結びついていない。

`technologyPrehistory.ts` は古代ローマ〜中世相当の前史技術ノードを18個持つが未接続で、
実行時の効果を持たない(データ層のみ、`docs/plan/technology-prehistory-rome-medieval.md` 参照)。

`DiplomacyHistoryDialog.tsx` は国家間の外交関係史(誰と誰がいつ何をしたか)を保持しているが、
版図(国境ポリゴン)そのものの履歴は保存していない。年代を遡って国境の変遷を見ることはできない。

### 掘り下げる際の論点

1. 前史生成を「現在の版図を1〜2代逆算する」方式にするか、「生成時に軽量な因果シミュレーションを
  1本走らせて結果だけ残す」方式にするか。
2. 遺跡・廃道・廃坑を前史の結果として配置し直す場合、既存のランダム配置ロジック
  (`markers-generator.ts`, `dungeons-generator.ts`)とどう共存させるか(完全置換 vs 前史由来のものを
  追加する2階建て)。
3. 国境変遷の年代スライダーは、`DiplomacyHistoryDialog` が持つ関係史イベントから逆算描画するのか、
  国境ポリゴンのスナップショットを別途保存する必要があるのか。ストレージコスト(save/export への
  影響、`io/save.ts`)を検討する必要がある。
4. `technologyPrehistory.ts` を接続する場合、現行の技術進行(`technologyProgress.ts`)との整合。

## 3. 土地利用の時間変化の可視化(小項目)

### 現状

当初「資源レイヤーが不可視」として指摘したが、これは誤りだった。実際には経済拡張機能が
`toggleMineralDeposits` を含む9レイヤーを動的登録しており(`src/extensions/economy/index.tsx:427-473`:
Goods / Markets / Trade / Mineral Deposits / Dams / Levees / Water Supply / Sewerage / Power Grid)、
`drawMineralDeposits.ts:33-64` は主要産出物ごとの色・アイコン、稼働/休止/枯渇の3段階を透明度で
描き分け、深度・richness・産出物一覧をツールチップに出している。未発見鉱床を意図的に隠す設計は
「Prospect mines」という探鉱ゲーム性のためのもので(`drawMineralDeposits.ts` コメント)、
項目5で挙げる「未探索領域」の思想の先行実装と言える。`draw-goods.ts` もセル単位の資源アイコンと
バーグの生産プレートを描画済み。

残る狭いギャップは、`forestStock.ts` と `agriculturalLandUse.ts` に**専用レンダラが存在しない**点。
Goods レイヤーは「どのセルが何を産するか」の静的な地理情報を示すが、森林ストックの減少や
耕地/休閑比率という**時間変化する土地利用の状態**は地図に出ない。

### 掘り下げる際の論点

1. これは新規レイヤーの追加ではなく、既存 Goods レイヤーへのオーバーレイ(彩度・ハッチングで
  枯渇度を示す等)で足りるか、独立レイヤーが要るか。
2. 優先度は他の7項目より低い(シミュレーション可視化の穴であり、地図のナラティブ要素の欠落ではない)。

## 4. 超自然の地理(面としての魔法圏・種族領域)

### 現状

`markers-generator.ts` には `portals`(`markers-generator.ts:418`)、`rifts`(`markers-generator.ts:428`)、
`sacred-mountains` / `sacred-forests` / `sacred-pineries` / `sacred-palm-groves`
(`markers-generator.ts:259-289`)などの**点マーカー**があるが、面としての魔法地理は存在しない。
リポジトリ全体で `leyline` は0ヒット。レイライン網、荒魔法地帯、呪われた土地、常闇/永冬の領域と
いった面的な超自然地理がまるごと欠けている。

`dangerField.ts` は面のスカラー場を生成しセル単位で危険度を持たせ、対応する
`renderers/danger-renderer.ts` で色分け表示する仕組みを既に持っている。同じ「セル単位スカラー場 +
専用レンダラ」というパターンが流用できる先行実装として存在する。

種族の地理も同様に薄い。種族はキャラクター属性(`Character` の race)としては存在するが、
エルフの森・ドワーフの山中都市・竜の縄張りといった非人間の居住域が地図上の面として表現されない。
`giantHighlandOikoumene.ts` が「巨人族の高地居住域」という方向性の唯一の先例。

### 掘り下げる際の論点

1. 魔法場を `dangerField.ts` と同様の「セルごとスカラー値 + 生成ロジック + 専用レンダラ」で作るか、
  danger と統合(危険度の一因として魔法濃度を混ぜる)するか、完全に独立させるか。
2. 種族領域は文化(`cultures-generator.ts`)の版図決定ロジックを種族に転用できるか、それとも
  文化とは独立した「オクメーネ」レイヤー(`giantHighlandOikoumene.ts` 方式)を種族ごとに増やすか。
3. 魔法圏・種族領域が政治的国境(`states-generator.ts`)、danger field、biome とどう相互作用するか
  (魔法濃度が高い土地は入植されにくい、種族領域は国家の実効支配と別、等)の因果を設計する必要。
4. Fantasy 以外のカルチャーセット(Playwright テストで避けるべきとされている "Dark Fantasy"/
  "High Fantasy" 以外、`feedback_playwright_culture_set` 参照)でこのレイヤーがどう振る舞うべきか
  (非表示 or 空)。

## 5. 「作中の物体としての地図」的装置

### 現状

1. **未探索領域**: `fogging` というスタイル要素(`styleElementGroups.ts` の `OVERLAYS_ELEMENTS`)は
  あるが手動トグルで、「誰にとっての既知の世界か」というゲーム的な概念(探索によって開示される)
  ではない。
2. **意図的な誤り**: 古地図的な歪み、伝説の島、"Here be dragons" の類の仕掛けは存在しない。
  現在の地図は常に全知の航空写真であり、作中人物が描いた紙という体裁を取っていない。
3. **凡例・カルトゥーシュ**: `editors.ts:337-341` の `view.legend` は `data` 属性に手で値を詰める
  方式で、自動生成されたテーマ性のある凡例(コンパスローズ、装飾枠)ではない。
4. **縮尺の断絶**: 大陸マップ → 地方(submap)→ 都市(`/city/` 独立 Vite MPA、
  `project_city_generator_mpa` 参照)までは繋がっているが、村・砦・宿場の平面図と
  ダンジョン内部図が空白。`dungeons-generator.ts:5` のコメントに "No interior simulation" と
  明記されている。

### 掘り下げる際の論点

1. 未探索領域はプレイヤー(または特定文化/勢力)視点の「既知セル集合」を新規に持つ必要があり、
  `WorldContext` への状態追加が要る。探索条件(距離、burg からの視認、斥候ユニット等)の設計が先。
  項目4で挙げた鉱床の discovered フラグ(`drawMineralDeposits.ts`)と統合的に設計できる可能性。
2. 意図的な誤りは「見た目だけの飾り」で済むか、ゲームプレイに影響させるか(誤った地図を頼りに
  移動すると実際の地形と食い違う、等)で実装規模が大きく変わる。
3. 凡例自動化は既存の `view.legend` API を壊さずに、テーマ(ジャンル/カルチャーセット)に応じた
  装飾を差し込む形が現実的か。
4. 縮尺連続性は `/city/` MPA(`project_city_generator_mpa`)のスコープ拡張として村落・砦レベルの
  簡易平面図を作るか、ダンジョン内部を含めて別の生成器を新設するか、スコープの線引きが必要。

## 6. 自然地理の残り(地質・風・海の危険・地下世界)

### 現状

1. **地質・プレート**: `mineralResources.ts:163` 自身が「将来のテクトニクスモデルが残りを置き換える」
  とコメントしており、山脈の走向・火山弧・地震帯・鉱床分布を一貫させるプレート境界モデルが無い。
2. **風**: `main.ts:212` の緯度帯6値固定配列(`winds: [225, 45, 225, 315, 135, 315]`)が
  降水計算(`precipitationModel.ts`)の入力に使われるのみで、専用の可視化レイヤーがない
  (コンパスローズ的な `toggleCompass` は現在の風向とは無関係)。
3. **海の地形**: 浅瀬・岩礁・渦・海溝・漁場の概念がない。`oceanCurrents.ts` と `ice.ts` はあるが、
  航路の物理的危険(座礁・遭難ポイント)が地図情報として存在しない。
4. **地下世界**: 洞窟系・Underdark 相当はほぼ皆無(`cavern` 1ヒット、`underdark` 2ヒットのみで
  いずれも直接関係しない箇所)。

### 掘り下げる際の論点

1. プレートモデルは既存の heightmap 生成(`heightmap-generator.ts`)と後付けで整合させるのが困難な
  可能性が高い。生成順序の先頭(プレート境界 → 隆起 → biome)に組み込み直す設計変更になるか、
  既存の地形を説明変数として逆算する軽量モデルで妥協するかを検討する必要。
2. 風の可視化は `draw-precipitation.ts` が既に風向データ(`windDirections`)を扱っているので、
  それを流用した矢羽根オーバーレイが最も安価。
3. 海の危険地形は `seaRouteGraph.ts` の航路コスト計算に接続できると、単なる飾りでなく
  ゲームプレイ上の意味(航海日数・遭難リスク)を持たせられる。
4. 地下世界は完全新規領域。スコープが city generator 並みに大きくなる可能性が高く、
  最初は「ダンジョン内部平面図」(項目5)との統合検討から始めるのが妥当。

## 7. 言語の地理

### 現状

文化ごとに namebase(`names-generator.ts`)は存在するが、言語族・方言境界・征服による地名の
上書き層(古い地層の地名が残る)という概念がない。`dialect` はリポジトリ全体で0ヒット。

### 掘り下げる際の論点

1. 言語圏を文化(`cultures-generator.ts`)の版図と1:1にするか、文化より粗い/細かい独立の言語圏
  レイヤーを持たせるか。歴史上征服された地域では言語圏と文化圏がずれるのが本来の姿。
2. 項目1(地形の自動命名)と統合設計するのが効率的: 地物の名付け言語を「現在その土地を支配する
  文化」ではなく「その土地の言語層」から引くことで、征服の痕跡を地名に残せる。
3. 項目2(歴史の奥行き)とも接続: 言語層の重なりは前史の国境変遷の副産物として自然に生成できる。

## 8. ゲーム的オーバーレイ

### 現状

1. **ヘクス/移動コスト表示**: `docs/plan/cell-to-hex.md` に構想はあるが、現状の `toggleGrid` は
  `pointyHex` パターン(`draw-grid.ts:15`)による装飾グリッドのみで、移動コストや到達可能範囲の
  表示ではない。
2. **旅程の等時線**: `DirectionsDialog.tsx` は2地点間の経路(徒歩/騎乗/馬車、海路+陸路の自動接続)を
  計算するのみで(`project_burg_directions_dialog`)、「ここから3日で行ける範囲」という面表示はない。
3. **補給線・勢力圏(ZOC)**: 要塞(`frontierFortsGenerator.ts`)と軍団(`military-generator.ts`,
  `regimentMovement.ts`)のデータはあるが、その影響圏を面として描く表現がない。
4. **交易路の流量**: キャラバン(`caravans.ts`, `caravanMovement.ts`)のデータはあるが、
  `draw-routes.ts` の線は交易量に応じた太さの変化を持たない(要確認: 現状は固定幅の可能性が高い)。

### 掘り下げる際の論点

1. 等時線は `landRouteGraph.ts` / `seaRouteGraph.ts` の既存コスト計算をダイクストラで面展開すれば
  比較的安価に作れる可能性がある。`DirectionsDialog` のロジックと共有できるか確認が要る。
2. ZOC は政治的国境(`states-generator.ts` の実効支配)と危険度(`dangerField.ts`)のどちらに近い
  概念として実装するかで設計が変わる。
3. 交易路の太さは `draw-routes.ts` の現状実装を先に確認し、データ(キャラバン量)を線幅にマッピング
  するだけで済むか、SVG構造の変更が要るかを見極める必要がある。

## 掘り下げ優先度

1. **項目1(地形・地物の命名)**: 分類ロジックが既に揃っており、命名+ラベル描画の追加だけで
   「フィクション地図らしさ」への影響が最大。次点の投資対効果。
2. **項目4(超自然の地理)**: `dangerField.ts` という直接流用できるパターンがあり、ファンタジー
   ジャンルとしての差別化に直結する。
3. **項目2(歴史の奥行き)**: 効果は大きいが `technologyPrehistory.ts` 接続や国境スナップショット
   保存など前提作業が重く、設計コストが高い。
4. **項目7(言語の地理)**: 単独では小さいが、項目1・2と組み合わせると地名の説得力が跳ね上がる。
   項目1に着手する際に同時検討するのが効率的。
5. **項目5・6・8**: いずれも個別には有用だが、単体の投資対効果は上位4項目より低い。
   項目5の「未探索領域」は項目4(鉱床の discovered フラグ)や探鉱ゲーム性の既存設計と絡めると
   安く作れる可能性がある。

各項目の詳細設計(データモデル、生成アルゴリズム、レンダラ、スタイル/レイヤー登録、テスト方針)は
このドキュメントの対象外。着手する項目が決まった時点で個別の `docs/plan/*.md` を新設する。
