## 1. 目的

[long-distance-merchant-reach-capital.md](long-distance-merchant-reach-capital.md) §17 は、運べない荷の予約と、船のない市場の海路を止めた。取り消しは減ったが、次の 2 点が史実と合わない。

- **陸の車両の数で予約を止めている。** 荷車・荷馬車は、お金があれば近くの村から雇えるか、すぐに造れる。経済の規模に合わない少ない車両は、すぐに解消されるはずである。
- **自分の市場の船がなければ海路をしない。** 史実の商人の多くは、自分の船を持たなかった。他人の船の積荷の枠を借り、港の倉庫で次の便を待った。港では、少ない船に荷を積みたい荷主が順番を待つことがよくあった。

本設計は、次の 3 つを決める。

1. 陸: 車両が足りないときは、予約を止めずに車両を雇い足し、運賃を上げる(§3)。
2. 海: 荷は港の倉庫で船を待つ。どの市場の船でも、運賃を払えば積める。積む順は運賃の高い順。待ちすぎた荷は港で売る。荷の溜まった港には、空いた船が回ってくる(§4)。
3. 港の倉庫: 港を持つ都市に、倉庫の収容力(荷の枠)を持たせる。海の交易の量と荷待ちの量で増え、CE は収容力から倉庫の敷地と形を描く。経済と流通網の恩恵を受ける港ほど、大きな倉庫が見える(§5〜§6)。

### 2.4 都市の中での配置

史料から、港の倉庫の配置は次の 5 つの型に分けられる。どの型でも、**倉庫は荷揚げ場のすぐ背後か、水路を敷地に引き込んだ所にある。** 町の中心や市場の広場の近くに大倉庫を置く例はなく、水辺から離れた倉庫は小さく、地元の市場に供する。

| 型 | 内容 | 例 | 水辺からの距離 |
| :--- | :--- | :--- | :--- |
| A 商人の家の倉 | 商人の家の上階・奥・地下を倉庫に使う。港から市場への通りに並ぶ | リューベックの Dielenhaus、アムステルダムの運河沿いの家(破風の巻き上げ梁) | 岸に面するか、岸から市場への通り沿い |
| B 岸の倉庫の列 | 岸の背後に倉庫の棟を並べる。棟は岸に妻(短辺)を向け、奥へ細長く延びることが多い。品目ごとに岸が分かれることがある | Bryggen、Salzspeicher、キングズ・リン、日本橋の河岸 | 岸に接する(0〜数十 m) |
| C 商館(囲い地) | 外国商人や同業の組合が、岸に面した囲い地に倉庫・計量所・宿・会館をまとめる | Fondaco dei Tedeschi、Steelyard、Bryggen | 岸に接し、自前の荷揚げ場を持つ |
| D 国・会社・領主の大倉庫 | 穀物・年貢・会社の荷を集める大きな囲い地。堀割を引き込むか、造船所に接する | Horrea Galbae、浅草御蔵、大坂の蔵屋敷、VOC の海の倉庫 | 岸に接するか、堀割を敷地に引き込む |
| E 囲い込みの船渠 | 船渠を掘り、その岸に多層の倉庫の列を建てる。塀で囲み、税関が見張る | West India Docks | 船渠の岸に接する |

型の出方には次の傾向がある。

- **規模と時代**: 小さな港は A だけ。交易が増えると B が岸に並ぶ。外国商人が集まる港に C ができる。国の穀物や年貢、会社の荷が集まる都市に D ができる。E は 19 世紀の工業化の後。
- **はしけ(艀)**: 大きな船が岸に着けない港では、沖に泊まった船からはしけで荷を運んだ(ロンドンの Pool、江戸の沖の大船と河岸)。倉庫は、深い水の泊地ではなく、はしけが着く内側の川岸・運河の岸(河岸)に並ぶ。
- **陸揚げの規制**: 税関が陸揚げを決まった岸に限ると(Legal Quays)、倉庫はそこに集まり、混み合う。
- **品目**: 穀物は多層の倉、樽物(ワイン・油)は地下か 1 階、材木・石は屋根のない置き場(既存の §5.3 の `timberYard`・`stoneYard`)。

## 3. 陸: 車両を雇い足す

### 3.1 今の仕組み

§17.1 は、出発地の市場の車両の積載 × 30 日を 1 か月の枠・日とし、それを超える予約を `noTransport` で止める。車両の補充は、修理で抜けた分の注文(`queueSimulationReplenishment`)と、計測した輸出量からの補充(`estimateMarketAnnualExportCargoSlots`)による。

### 3.2 変更

| 項目 | 内容 |
| :--- | :--- |
| 雇い足し | 陸の枠・日が足りないときは、足りない分を「雇った車両」として予約する。雇える量は、自前の積載の `LAND_HIRE_SHARE` 倍(案 1.0)まで。雇った分の運賃は、自前の車両の運賃の `LAND_HIRE_FREIGHT_MULTIPLIER` 倍(案 1.5)。照合の利益で運賃の上がった分を見るので、利の薄い嵩物は自然に止まる |
| 雇った車両の扱い | 隊商は、雇った分の積載を自前の車両と同じ種類で持つ。到着したら消える(市場の車両には加えない)。運賃は出発地の都市の運送業者の収入にする(既存の運賃の扱い `freightUnitCost` と同じ) |
| 車両の注文 | 雇った枠・日を市場ごとに記録し、生産の周期の初めに、その分の車両を注文する(修理の分の注文と同じ流れ)。雇い続けるより自前で持つ方が安いので、恒常的な不足は数周期で自前の車両になる |
| 上限を超えた分 | 自前 + 雇える量を超える分は、今と同じく `noTransport` で止める。1 回の照合で何か月分もの嵩物を予約することはなくなる(§16.2 の 398 台分の予約は、自前の積載の 2 倍で止まる) |

### 3.3 収穫月(任意)

収穫月は、雇える量を `LAND_HIRE_SHARE × HARVEST_HIRE_FACTOR`(案 0.5)にする。牽く家畜と人手が農作業に取られることを表す。収穫月の判定は、作物暦([farm-labour-calibration.md](farm-labour-calibration.md))の収穫月を使う。初めの実装では入れず、計測で穀物の流れが偏るときに足す。§10.27 で、作物暦の収穫の重みから 0.5〜1 倍として入れた。

## 4. 海: 港で船を待つ

### 4.1 港の荷待ちの台帳

海の区間がある荷は、出発地の市場の港(§17.2 の `merchantHullHomePort` と同じ選び方。港を独立した存在にした後は [fmg-harbour-model.md](fmg-harbour-model.md) の Harbour)で船を待つものとして数える。

- 初めの段階(P2)では、荷は今のまま市場の倉庫(`ExportStagingLot`)にあり、港の都市 `portBurgId` を記録するだけにする。隊商は今のまま、陸と海の区間を 1 つの隊商で進む。
- 後の段階(P4)で、隊商を港で分ける。陸の区間の隊商が港の倉庫に荷を降ろし、海の区間は港の倉庫から船に積む。§5 の倉庫の収容力が、荷の行き場として実際に効くのはこの段階から。

### 4.2 どの船でも積める(運賃積み)

| 項目 | 内容 |
| :--- | :--- |
| 船の持ち主 | 船は今のまま市場の船(造船の拡張の船体、母港あり)。持ち主は変えない |
| 他の市場の荷 | 港に泊まっている船は、持ち主の市場の荷を積んだ後の空きに、ほかの市場の荷を積める。運賃は船の持ち主の市場の運送業者の収入にする |
| 予約の上限 | §17.1 の海の上限を、「自前の船の積載」から「その港に泊まる船と、30 日以内に着く船の積載」にする。持ち主の市場の荷を先に数える |
| 船のない市場 | 港に他の市場の船が来るなら、海路を予約できる。どの船も来ない港だけ、今と同じく止める(`noTransport`) |

### 4.3 積む順

港で船の空きより荷が多いとき、荷の運賃の申し出(枠あたりの価値 × 運賃率)の高い順に積む。同じなら、港に着いた順(浅草御蔵の着いた順の陸揚げ)。高額品が先に積まれ、嵩物が待つ。§17.4 の「嵩物の予約が先に枠を使うと、同じ周期の高額品が止まる」も、これで解く。

### 4.4 待つ間の費用と期限

| 項目 | 内容 |
| :--- | :--- |
| 倉敷料 | 港で待つ荷は、枠・日あたり `PORT_STORAGE_FEE` を港の都市に払う(倉庫の持ち主の収入)。§5 の収容力を超えた荷(岸に積んだ荷、はしけに載せたままの荷)は、倍の倉敷料を払う |
| 傷み | 食料は既存の鮮度と穀物の傷み([grain-storage-life.md](grain-storage-life.md))で傷む。収容力を超えた荷は、傷みを早める(案 1.5 倍)。§10.29 で、港で待つ主食に穀倉の傷みを入れ、収容力を超えた割合の分を 1.5 倍にした |
| 期限 | 今の上限(荷待ちの最大 + 往復 + 30 日、`getStaleLotDays`)を使う。期限を過ぎた荷は出発地に戻さず、港の都市の市場で売る(地元の価格の `STALE_SALE_DISCOUNT` 倍、案 0.7)。差額は商会の損になる |

### 4.5 空いた船の回航

生産の周期の初めに、港ごとの荷待ちの量(枠)と、船の空き(枠)を比べる。持ち主の市場に積む荷のない船は、荷待ちの多い港へ空船で回る(不定期船)。

- 回る先は、荷待ちの枠 ÷ 泊まっている船の積載の大きい港。回航の日数で割り引く。
- 船の持ち主と母港は変えない。回った先で荷を積み、着いた港で次の荷を探す。
- 1 周期に回る船は、港ごとに空いた船の半分まで(全部の船が同じ港に集まらないように)。

### 4.6 季節(任意)

冬の休航は、今の出港日(`tradeSailSchedule.ts`)に休航の月を足す形で後から入れる。初めの実装では入れない。§10.27 で、港ごとの休航の日付(`seaSeason.ts`)として入れた。

### 4.7 船の注文

§17.2 の注文は残すが、きっかけを「自前の船がない」から「港の荷待ちが、泊まる船と着く船の積載の `HULL_ORDER_BACKLOG_MONTHS`(案 2)か月分を超える状態が続く」に変える。回ってくる船で足りる港は、船を注文しない。

## 5. 港の倉庫の収容力

### 5.1 持たせる値

港を持つ都市(`burg.port`。Harbour の実装の後は Harbour)に、倉庫の状態を持たせる。経済の拡張の状態に保存する。

```ts
export interface PortWarehouseState {
  burgId: number;
  /** Cargo slots the port's warehouses hold. Buildings stay when trade falls. */
  capacitySlots: number;
  /** Highest smoothed need seen (slots). Drives expansion. */
  needSlots: number;
  /** Who built the largest share. Picks the CE layout type (§2.4). */
  owner: "merchants" | "merchantHouse" | "state";
  /** Year the last building step finished. */
  lastBuiltYear: number;
}
```

### 5.2 増え方

| 項目 | 内容 |
| :--- | :--- |
| 必要な量 | `need = 港の年間の海の取扱量(積み出し + 陸揚げの枠)× 平均の滞留日数 ÷ 365 + 直近 12 か月の荷待ちの最大`。滞留日数は案 30 日。指数平滑(年 0.3)で `needSlots` に入れる |
| 建てる | `needSlots` が `capacitySlots` を 1 年続けて超えたら、1 棟分(§5.3 の 1 棟の枠)を建てる。費用は枠あたり `PORT_WAREHOUSE_COST_PER_SLOT` で、港の市場の商会の資本から払う。払えなければ建てない(§10.30 で実装) |
| 建てる期間 | 1 棟 1 年(案)。建てている間は収容力に数えない |
| 減り方 | 建物は残る。取り扱いが減っても `capacitySlots` は下げない。100 年使われない分だけ、年 1% ずつ減らす(倉庫が住宅や作業場に変わる) |
| 初めの値 | 地図の作成時に、港の都市の人口と市場の中心かどうかから決める(既存の車両の初期値 `landFleetCountsFromBurgScale` と同じ考え方) |
| 持ち主 | 商会の本拠(`merchantHouse: major`)がある都市は `merchantHouse`、外国の商会の支店(外地の商館)が多い都市も `merchantHouse`。国の公共穀倉(`publicWorks.granary`)が大きい首都の港は `state`。ほかは `merchants` |

収容力は、§4.4 の倉敷料の倍額と傷みを避ける量として効く。荷待ちの多い港ほど早く倉庫が増える。

### 5.3 収容力から床と敷地へ

- 床面積 = `capacitySlots × PORT_WAREHOUSE_FLOOR_M2_PER_SLOT`(案 0.8。§5.3 の `warehouse` の 0.8 m²/lot にそろえる)。
- 階数は時代で決める。古代・中世 2〜3 階、近世 3〜4 階、工業化の後 5〜6 階(§2.3 の Bryggen、Fondaco、Zeemagazijn、West India Docks)。
- 敷地 = 床面積 ÷ 階数。1 棟の大きさは型で変える。

| 型 | 1 棟(区画)の敷地の目安 | 根拠 |
| :--- | :--- | :--- |
| B 岸の倉庫の列 | 100〜600 m²(細長い棟) | Bryggen・Salzspeicher の棟。数字は目安で校正の対象 |
| C 商館 | 2,000〜6,000 m²(囲い地全体) | Fondaco(延べ 9,000 m²、4 層)、Steelyard 5,250 m² |
| D 大倉庫 | 5,000 m²〜12 ha(囲い地全体) | Horrea Galbae 21,000 m²、浅草御蔵 約 12 ha |
| E 船渠の倉庫 | 1 棟 2,000〜2,500 m² の列 | West India Docks 約 2,400 m² / 棟 |

### 5.4 型の選び方

| 条件 | 型 |
| :--- | :--- |
| 収容力が 1 棟(B)の最小に満たない | A のみ(港の倉庫は描かない。商人の家の倉で持つ) |
| それ以上 | B |
| 持ち主 `merchantHouse` で、収容力が C の最小以上 | B + C(1 か所) |
| 持ち主 `state` で、収容力が D の最小以上 | B + D(1 か所) |
| 蒸気船の技術を習得し、収容力が E の最小以上 | E(B を置き換える) |

収容力の順位は世界の中で比べ、大きな港の上位ほど C・D が出やすいようにする(交易の恩恵を受ける港に大きな倉庫が見える)。

## 6. CE への受け渡しと配置

### 6.1 データ

`BurgSiteEconomy` に任意のフィールドを足す。任意フィールドの追加なので `DESCRIPTOR_VERSION` は変えない。CE 側の型のコピーも同時に直す。

```ts
export interface SitePortWarehouse {
  capacitySlots: number;
  /** Ground area after storeys (m²). Capped like storage[] (§5.3 of fmg-economy-to-city-editor.md). */
  groundAreaM2: number;
  storeys: number;
  layout: "merchantHouses" | "quayRow" | "compound" | "stateStore" | "dock";
  /** World rank 0..1 of capacitySlots among ports. */
  rank: number;
  /** Slots waiting for a ship now. CE may show stacked goods on the quay when this exceeds capacity. */
  queuedSlots: number;
  /** Top goods by slots through the port (labels). */
  mainGoods: string[];
}
// BurgSiteEconomy.portWarehouse?: SitePortWarehouse
```

在庫から決める今の置き場(`storage[]` の `warehouse`・`granary`)との関係:

- 港の倉庫は建物の量(在庫が空でも残る)、`storage[]` は今の在庫の量。
- 水運で入る(`waterborne`)`warehouse`・`granary` の面積は、港の倉庫の敷地の分だけ差し引く(ギルドの置き場を差し引く `guildCover` と同じ扱い)。残った分だけ今の場所に置く。

### 6.2 配置(今の CE の課題)

今の CE は、港の倉庫を水辺に寄せない。

- `storageYardPlacement.ts` は `harbor` の区画を置き場に使わない(`BLOCKED_WARDS`)。
- `waterborne` の置き場は、川からの距離だけで寄せる。海岸には寄せない。
- `warehouse` は城壁内で町の中心に寄せる(`Math.hypot(spot.centre) * 0.012`)。

§2.4 のとおり、港の倉庫は岸の背後に置く。

| 型 | 置き方 |
| :--- | :--- |
| A | 置かない。岸から市場への通り沿いの商人の家を大きくする(既存の [approach-commerce-quarters.md](approach-commerce-quarters.md) R5) |
| B | `harborFabric.ts` の岸の帯(`quay`)と荷さばき場(`loading-yard`)の背後、岸から 0〜40 m の帯に、岸に妻を向けた細長い棟を並べる。岸の長さに沿って、荷の多い岸から順に埋める |
| C | 岸に面した 1 区画を囲い地にし、中庭を囲む棟と、岸に面した自前の荷揚げ場を持たせる。町の市場の広場に近い岸を選ぶ |
| D | 岸に接する広い区画を選ぶ。城壁の内外は問わない(浅草御蔵は町の外れ)。堀割を引き込む表現は後の段階(P6) |
| E | 産業時代の船渠の表現ができるまで描かない |

- 川の港では、深い水の岸ではなく、はしけが着く内側の河岸に寄せる。
- `harborPreset` は、型 C 以上のとき `warehouse` を既定にする(岸の帯と荷さばき場が広くなる)。
- `queuedSlots` が収容力を超えるときは、荷さばき場に積んだ荷(樽・俵の山)を描く(任意)。

## 8. 計測

province-101(5 年)、world-101・world-102(3 年)、1 か月の刻みで、§17.3 と同じ表を取り、次を足す。

- 港ごとの荷待ちの枠と待ちの日数の分布(中央値・90%)。
- 船の積み荷の比(自分の市場の荷 / ほかの市場の荷)、回航した船の数。
- 陸の雇った枠・日と、そこから注文した車両の数。
- 期限を過ぎて港で売った荷の件数と原価。
- 港の倉庫の収容力の分布と型(A〜D)の数。CE で上位の港を 3 つ開き、岸の背後に倉庫が並ぶことを目で確かめる。

目標: 取り消しと港での売却の合計が §17 の後を超えない。高額品の取引(24 日以上を含む)が §17 の前の水準に戻る。船のない市場の海路が、船の完成を待たずに始まる。

## 9. 未決

- 回航で船が集まる港と、集まらない港の差が大きすぎないか(回航の割合の上限で足りるか)。
- 倉庫の初めの値を、地図の作成時の人口で決めてよいか。古い地図を読み込んだときも同じ式で作る。
- 運賃積みの運賃を、持ち主の市場の運送業者に払うか、船の持分を持つ商会に払うか([corporation.md](corporation.md) の持分の扱いとの関係)。
- §5.3 の 1 棟の大きさ(B 型)と、枠あたりの床面積は、CE で描いた大きさを Bryggen・日本橋の河岸の図と比べて決める。

## 10. 実装(2026-10-19)

### 10.1 実装したこと

| 段階 | 内容 | 場所 |
| :--- | :--- | :--- |
| P1 陸の雇い足し | 陸の予約の枠・日を、自前の積載 × (1 + `LAND_HIRE_SHARE`)(1.0)にした。自前の枠を超える分の運賃は `LAND_HIRE_FREIGHT_MULTIPLIER`(1.5)倍で、超える割合だけ掛ける。割増で利益が出ない品は、自前の枠まで減らす。出発の予約は、自前の車両が足りなければ、種類ごとに自前の台数 × 雇い足しの割合まで雇う(`TransportAllocation.hiredUnits`、`MerchantLandAssetBalance.hired`)。雇った車両は市場の台帳に入らず、到着・取り消し・損失で帰る(損失でも修理に回らない)。積み込みの判定(`getLargestAvailableLandCapacity`)も、雇える種類を空きとして数える | `merchantTransportAssets.ts`、`tradeTransportRoom.ts`、`markets-generator.ts` |
| P1 車両の注文 | 雇った車両・日を数え(`hiredDays`)、生産の周期の初めに、平均の台数を修理の分と合わせて注文する | `transportAssetOrders.ts queueSimulationReplenishment` |
| P2 運賃積み | 船の台帳に、泊まっている港(`berthBurgId`、造船の拡張の `currentBurgId`)を写した。自前の船で足りないとき、その市場の港に泊まるほかの市場の空いた船を借りる。海の予約の枠も、借りられる船の積載を足す。着いた船は着いた港に泊まる。持ち主と母港は変えない | `merchantTransportAssets.ts`、`tradeTransportRoom.ts` |
| P2 積む順 | 積み込み中の隊商は、陸の隊商を先に今の順で、海の隊商を枠あたりの価値の高い順に出発させる | `caravans.ts loadingOrder` |
| P3 回航 | 生産の周期の初めに、市場ごとの海の荷待ち(海の区間のある積み込み中の隊商の枠 + 船がなく予約できなかった枠)から、泊まっている船の積載を引いた残りを求める。荷待ちのない市場の空いた船(泊まっている港が分かるもの)の半分まで(切り上げ)を、残りの大きい市場のいちばん大きい港へ回す。回航の日数は §10.5 | `merchantTransportAssets.ts repositionIdleHulls`、`portWarehouses.ts`、`shipyardQueue.ts` |
| P4 港の倉庫の収容力 | 市場のいちばん大きい港に `PortWarehouseState` を持たせた(拡張の状態 `portWarehouses` に保存)。海の区間のある隊商が出発すると、出発地と行き先の市場の港の取扱量に積荷の枠を足す。毎月、年の取扱量(月 11/12 の減衰)× 30 日 ÷ 365 + 荷待ちの最大(同じ減衰)を必要量とし、月 0.1 で平滑する。必要量が収容力を 12 か月続けて超えたら、差(100 枠以上)の倉庫を建て、1 年で収容力に加える。1,200 か月使われなければ年 1% ずつ減らす。初めの値は港の人口 × 40 枠(市場の中心は 2 倍) | `portWarehouses.ts`、`production-generator.ts` |
| P5 CE への受け渡し | `BurgSiteEconomy.portWarehouse`(収容力、延べ床 = 枠 × 0.8 m²、型、順位、荷待ち、海の主な品)。型は §5.4 のとおりで、商館は商会の本拠の都市、大倉庫は首都、船渠は沿岸の蒸気航行を採用した国の港 | `burgSiteEconomy.ts`(拡張と services) |
| P5 CE の配置 | 新しい `quayWarehouses`(空撮の施設)。階数は時代(古代・中世前期 2、中世盛期・後期 3、近世 4、蒸気以降 5)、地上の面積は延べ床 ÷ 階数で、町の面積の 12% まで。水まで 45 m 以内の土地の区画から、水に近く町の内側のものを先に選び、岸から 6 m の荷揚げ場を残して建物を並べる。建物の前(水側)の帯が水に届かなければ置かない(岸が曲がって離れる所で列を止める)。岸の倉庫の列は 10 × 24 m の棟を岸に妻を向けて並べ、大倉庫(40 × 14 m)と船渠の倉庫(68 × 35 m)は岸に沿わせ、商館は中庭を持つ 1 区画にする。置いた面積の分だけ、水運の倉庫・穀倉の置き場を減らす。商館・大倉庫・船渠の港では、岸の帯の既定を `warehouse` にする | `quayWarehousePlacement.ts`、`aerialLandmarks.ts`、`aerialLandmarksSvg.ts`、`harborFabric.ts` |

### 10.2 設計から変えたこと、実装しなかったこと

- 運賃積みの運賃は、今の運賃と同じく出発地の運送業者の収入のまま(§9 の未決のとおり、船の持ち主に払う形にはしていない)。
- 倉敷料、収容力を超えた荷の傷みの割増、期限を過ぎた荷を港で売ること(§4.4)は入れていない。荷は今のまま出発地の市場の倉庫にあり、期限を過ぎれば出発地の市場に戻る(港はその市場の中にあるので、出発地に戻すことは、港の市場に戻すことと同じ)。
- 倉庫を建てる費用は払わない(お金の校正に影響するため。§7.2 の指標を見てから足す)。
- 船の注文のきっかけは §17.2 のまま。予約できなかった枠は、自前の船も借りられる船もない市場だけに残るので、回ってくる船で足りる港は船を注文しない。
- 隊商を港で分けること(§4.1 の後の段階)、大倉庫の堀割、収穫月(§3.3)、季節の休航(§4.6)、荷さばき場に積んだ荷の描画は入れていない。

### 10.10 荷の見込みへの回航と、母港での係船(2026-10-20)

### 10.23 小さな町の生産の手順(2026-10-20)

[port-freight-remaining-tasks.md](port-freight-remaining-tasks.md) の T28。§10.22 で見つけた、小さな町が生産の手順(`Math.ceil(population)`)を労働の少ない手で使い切る問題を直した。

#### 調べたこと

生産の周期の終わりに手順が残っていた町は、province-101・world-102 とも 1 つもなかった(12 か月、すべての町)。使われた労働は町の人口の 19% ほど。手を使い切る原因は 3 つあった。

| 原因 | 内容 |
| :--- | :--- |
| 注文が下限の大きさに切られる | 調整の表の品の 1 手の労働は、職の分野の見込みの人手 × 品の割合(`getCalibratedLaborBudget`)で切られる。この上限は、調べるとすべての品・町の大きさで月の量の下限の労働とちょうど同じだった。下限は 1 手で造れるが、上に足した注文(§10.12 の車両、§10.18・§10.22 の国)は下限の大きさの手に分かれ、手を重ねる |
| 造り終えた品を試す | 月の量を造り終えた品も次の手で選ばれ、何も造らずに手を 1 つ使ってから外れる |
| 材料のない目標を試し続ける | 目標の品の材料(下ごしらえ)が造れないと、その材料だけが外され、目標は残る。次の手でまた同じ目標が別の、あるいは同じ失敗を選び、手を使う。動いている目標(`activeGoalGoodId`)は候補から外しても計画される |

### 10.29 休航の間の倉庫の荷の日数と、収容力を超えた荷の傷み(2026-10-21)

[port-freight-remaining-tasks.md](port-freight-remaining-tasks.md) の T32・T2。どちらも `fmg-long-distance-trade` が `on` のときだけ効く(`off` の結果と node の golden は変わらない)。

#### 調べたこと

- 倉庫の荷(`ExportStagingLot`)は経路を持たず、隊商を作るときに経路を引き直す。休航の判定に要る出る港は、照合の段(`markets-generator.ts`)でしか分からなかった。
- 港で待つ隊商の荷は、今まで傷まなかった。§4.4 は「食料は既存の鮮度と穀物の傷みで傷む」としていたが、穀物の傷み([grain-storage-life.md](grain-storage-life.md))は市場の在庫(年齢の組)だけに掛かり、隊商の荷には掛かっていない。生の食料は隊商に積めない(鮮度で捨てる)。そのため、収容力を超えた分の割増(1.5 倍)の前に、倉庫の中の傷みを入れる必要があった。

#### 変えたこと

| 項目 | 内容 | 場所 |
| :--- | :--- | :--- |
| 倉庫の荷の出る港 | 予約のとき、経路の海の区間の出る港(`seaDeparturePortBurgId`)を荷に書く(`seaPortBurgId`)。同じ荷に積み足すときは上書きする。前からの荷と、初めの倉庫の荷は持たない(今のまま数える) | `exportStaging.ts bookFromRetail`、`markets-generator.ts`、`marketTypes.ts` |
| 休航の間の日数 | 出る港が閉じている日(嵐の休航・氷)は、倉庫の荷の待ちの日数(`waitedDays`)を数えない。港で待つ隊商(§10.27)とそろう | `exportStaging.ts cancelStaleLots` |
| 港の荷の傷み | 港で待つ隊商の主食(`stapleFood` の品。食料の相乗り `isFoodCoLoad` は除く)は、港の気候の穀倉の傷み(四半期 1.5% × 気候の係数、`getQuarterlyStorageLoss` の `fresh`)で傷む | `portWarehouses.ts accruePortSpoilage` |
| 収容力を超えた分の割増 | 港の荷待ちのうち収容力を超えた割合の分は、傷みを 1.5 倍(`OVERFLOW_SPOILAGE_MULTIPLIER`)にする。倉敷料の倍額と同じく、港の荷のすべてに割合で掛ける | `portWarehouses.ts` |
| 精算 | 傷んだ量は待つ間に隊商に溜め(`portSpoiledUnits`)、船が出るとき・港で売るときに荷から引く。引いた分の資本は商会の損(`settleLoss`)、エスクローは買い手に戻し、`spoilage` として記録する | `caravans.ts takePortSpoilage` |

傷みを日ごとに荷から引くと、小さな荷では 1 日の量が 0.01 単位に満たず、荷の単位の丸め(小数 2 桁)で消える。待つ間は丸めずに溜め、港を出るときに一度だけ引く。

#### 計測

地図での計測はしていない。T32 は §10.27 の計測で倉庫の荷の取り消しが 0 件だったものの直しで、T2 の傷みは温帯の港で一季節(90 日)約 1.5%、収容力を超えた分で約 2.2% と小さい。§7.2 の指標で確かめるのは、T31・T6(倉敷料の見込みと倉庫の費用)の計測とあわせる。

#### 残る課題

- 主食のほかの食料(保存食・チーズ・干し魚)は港で傷まない。保存食の傷みの速さは決めていない。
- 倉庫の荷の `seaPortBurgId` は予約の時の経路のもので、隊商を作るときに経路が変わっても書き直さない。

### 10.32 荷待ちと照合の数え方・最初から港で積む荷の大きさ(2026-10-21)

[port-freight-remaining-tasks.md](port-freight-remaining-tasks.md) の T9・T30。§10.25 の回航の需要はすでに「1 組に 1 隻」で数えていたが、照合は荷の枠だけを引いていた。また、最初から海へ出る荷は、海の先の陸の車両 1 台の大きさで詰めていた。

#### 決めたこと・変えたこと

- **船不足の荷待ちと、船を呼ぶ需要を分ける(T9)**。`collectSeaBacklogSlots` は、出発の判断が出たのに船の容量が足りない積み込み中の荷と、照合で船を予約できなかった枠を数える。満載・出港日を待つ荷、港まで運んでいる荷は荷待ちから外す。`collectSeaDemandSlots` はそれらも引き続き数える。回航は、荷が出る日までに船を呼ぶ必要があるので、出発が遅れてから呼ぶ方式にはしない。いつもの月の出港量を下限にする扱いも残す。
- **照合は商会・出港市場・届け先ごとに船を確保する(T9)**。`getSeaRoomHulls` で予約できる実在の船と容量を取り、`tradeTransportRoom` の中で船 ID を共有する。10 枠を予約した 100 枠の船の残り 90 枠は、同じ商会の同じ届け先への積み足しに使える。別の届け先や別の商会には使えない。荷が増えたときは、空いた大きな船に載せ替えてから、必要なら 2 隻目を確保する。この割り当ては照合中の予算で、実際の船の予約は従来どおり出発時に行う。出港済みの荷は海の枠を持たない。
- **港の倉庫の荷の枠は、実際にそこにある荷だけにする(T9)**。照合で予約できず買わなかった分は船の需要に残すが、港の倉庫の `queuedSlots`・必要量には足さない。
- **最初から港で積む荷にも、港の積み替えを使う(T30)**。最初の区間が海なら、距離 0・到着済みの `portTransfer` を持たせる。荷の詰め方と積み足しの目標は船の大きさで決め、海の先の陸・川は複数台・隻で運ぶ。出発時には、その台数と実在の船を予約できることを従来どおり確かめる。保存済みの積み込み中の荷も読み出し時にこの扱いへ移す。出発地での食料の積み足しと交通の記録は残す。
- **積み足しで空き枠を超えないようにする**。`buildCargoManifests` は、選んだ船・車両の容量に加えて、呼び出し元が渡す空き枠も上限にする。最小の船が 100 枠でも、残り 30 枠の積み足しに 100 枠詰めない。

#### レビュー後の修正: 港の荷を利用可能な車両で運ぶ(同日)

上の実装は、船の大きさにまとめた荷に対して、容量だけで陸の車種を選んでいた。例えば、荷駄しかない市場の 60 枠の荷に、保有も雇用もできない荷車を要求し、荷駄 2 隊なら運べても出発できなかった。

港から出発する際は `MerchantTransportAssets.getAvailableLandConvoy` で、実際に空いている車両を先に、足りない分を残る雇用枠から割り当てる。同じ車種の複数台に加え、荷車と荷駄のような異なる車種も組み合わせる。牽く家畜の容量と季節の雇用上限を守り、運べなければ車両や船を予約せず待つ。複数車種の容量は陸の中で足し、その合計と海・川の容量の小さい方を全体の上限にする。

検証: `caravans.test.ts`、`merchantTransportAssets.test.ts`、`tradeCargo.test.ts` の 58 件が成功。レビューの再現ケース(荷駄のみ・60 枠・100 枠の船)が荷駄 2 隊で出発し、実在の船を予約すること、異なる車種と雇用分の組み合わせ、輸送力不足時に予約を変更しないことを確認した。`npx tsc --noEmit` も成功。上の 3 年計測はこの追記の修正前の値で、再計測はしていない。

#### 残る課題

- 薄い荷を 1 隻で複数の港へ運ぶ寄港(T33)は入れていない。別の商会・届け先への積み荷も混載しない。
- 海の先の陸・川の車両は、従来の港の積み替えと同じく、出発地の市場で全行程の分を予約する。着いた港で別の運送人を雇う段には分けていない。
- 回航の需要は従来どおり予定の船の容量で数える。照合が選ぶ最小の空き船と、積み込みが目標にする最大の船の大きさは常に一致するわけではない。
