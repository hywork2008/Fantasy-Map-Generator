# CEの手動都市作成: 描画・仕上げ・共有の調査と設計

作成日: 2026-10-22
状態: 調査・設計。製品コードの変更は未実施。

## 1. 目的と受入例

白紙の都市に城を1セル、道路をその辺に1本置き、2D・3D・保存・共有で同じ内容を保つ。その上で、住宅街・市場・寺院・港・城壁などを手動配置し、指定した区域の建物や細街路だけを既存の生成器で仕上げ、ランダム生成都市と同じ表現品質に到達できるようにする。

「手動配置をそのまま表示する」「選択区域を補完する」「都市全体を再計画する」を別の操作として扱う。城と道路の2つを置いただけでは住宅街や城壁を自動追加しない。

## 2. 現状で起きていること

### 2.1 編集直後の3Dに出るセル境界

関連実装:

- `src/city-editor/generators/mesh.ts`: 初期faceは `ward: null`, `buildable: true`。
- `src/city-editor/controllers/tools/brushes.ts`: Castleブラシは `properties.ward` を変更する。`CastlePlan` を作る操作ではない。
- `src/city-editor/renderers/cityView.ts`: 3Dを開くと現在文書の `buildBlockFabric` と、その `lanes` を渡した `collectTownRoads` を呼ぶ。
- `src/city-editor/generators/localInfill.ts`: 道路沿いを根とした到達探索が、未指定でもbuildableな陸セルへ広がる。
- `src/city-editor/generators/organicBlocks.ts`: `buildOrganicBlocks` は `build` がfalseでも、判定より前に区画周囲の細街路を追加する。Classic側の `perimeterBlocks.ts` も建物生成の早期returnより先に境界の細街路を追加する。

したがって、未指定セルに住宅は建たなくても、区画周囲には道が生じ得る。3Dはそれを道路面として正しく描いてしまう。観察された線は、3Dの編集用メッシュ線というより、メッシュ境界から導出された細街路である。`showBlockMesh` や3D側の線の色だけを変えても原因は残る。

### 2.2 Generate from current edits後に枠まで道が出る

`controllers/generation.ts::generateFromEdits` は現文書をcloneし、`appearance = "town"`、`createFabricPlan` と `resolveDistricts` によるfabricを設定し、`generateRuralFieldStage(..., {preserveLandUse: true})` を実行する。通常の都市計画工程は再実行しない。

`fabricDistricts.ts` は、道路などの境界条件と土地用途が同じ隣接セルを描画用の区画にまとめる。そのため、多くの細かい境界線が消える。一方、未指定の土地も区画として残り、2.1の処理がその大きな区画の外周へ細街路を作る。短い手描きの道の周囲から、表示枠近くまで道が出る原因になり得る。

ここは `featureGroups` のroadが延長されたことと区別する必要がある。手描きのroadが1本のままでも、導出された `fabric.lanes` は増える。`frameRoads` や農道も別の道路供給元である。

農地工程は独立した追加要因である。`preserveLandUse` が守るのはセルの土地用途であり、描画される細街路・農道を手描きの本数に限定する契約ではない。farmセルがあれば `ruralFields.ts` などは農道を追加できる。ただし、今回の白紙の例ではfarmセルがなくても問題を再現したため、農道生成だけを止めても解消しない。

### 2.3 Copy shareable linkでフルセットの都市になる

`controllers/documentIO.ts::currentShare` は、次の順で入力を選び、fabricを除いて共有する。

1. セッションの `completeSource`
2. 保存された `fabric.generation.input`
3. 現在の文書

`CityEditorShare.input` は存在するが、意味は生成器への入力であり、開いた時にそのまま表示するスナップショットではない。`applyShare` は入力を復元した後、`share.stage` があれば該当の生成工程、なければ `runCompleteGeneration` を実行する。

仕上げ後はconceal段階が共有され得るが、新しいセッションでは `completeResult` がnullである。`generation.ts::runGenerationStage` は既に仕上がった結果を再利用できず、`generateStageOnDocument` へ進む。段階指定は「手動編集のまま開く」という指示にはならない。

さらに、ランダム生成都市を後から編集した場合には、優先された古い `completeSource` に最新の編集が含まれない可能性がある。単に `input` に現文書を入れる修正だけでは、開いた後の再生成が残る。

## 3. 検証と限界

一時診断用Vitestで、small/voronoi、seed `manual-city-investigation`、原点に最も近いセルをcastle、その `boundary[0]` の1辺を幅6mのroadとした。仕上げは現行処理と同じfabric作成と土地用途保持の農地工程を呼び、建物パターンはmedievalとした。

確認できたこと:

- 仕上げの前後でmeshと `featureGroups` は同一。
- 仕上げ前より仕上げ後の導出lane数が減る。
- 仕上げ後のlaneにも、座標の最大絶対値が590mを超える点がある。表示枠は±600m。手描きの1辺とは別に、枠付近の道が生じた。
- farmを指定していない状態でも再現した。

関連既存テスト:

| テスト | 結果 |
| --- | --- |
| `controllers/generationFromEdits.test.ts` | 1件成功。土地用途・道路保持、Undo/Redo、段階再表示 |
| `services/io/incomingCity.test.ts` | 30件成功。既存の共有形式の処理 |
| 一時診断 `generators/manualCityInvestigation.test.ts` | 1件成功。調査後に削除 |

一時診断は初回に構文エラーで収集に失敗し、修正後に成功した。上記の既存2ファイルは成功後に再実行していない。

ユーザーが操作した文書・URLは未取得であり、ブラウザでの見た目の照合は未実施。「全ての境界」や追加道路の個々の経路を当該文書で確定したものではない。今回は1つの小規模な決定的入力と実装経路の確認であり、多数seedの検証は行っていない。

## 4. 文書と派生形状の契約

### 4.1 編集内容を正本にする

引き続き `CityDocument` のmesh、用途、道路・壁・川、門、城計画、ランドマークなどを正本とする。描画時に作る全建物・全道路面を新たに文書へ複製保存する方式は採らない。

文書に任意の手動作成ポリシーを追加する案:

```ts
authoring?: {
  mode: "manual";
  localStreets: "explicit" | "district";
  ruralAccess: "explicit" | "generated";
};
```

新しい「白紙から作成」は `manual / explicit / explicit` を保存する。既存文書でフィールドがない場合は従来の生成規則を維持する。スキーマ、codec、fingerprint、共有、履歴も同時に対応する。生成方式・fabric有無・外観設定から手動モードを推測しない。

未指定の `ward: null` と明示的なemptyは、手動モードで都市内街路の自動生成対象にしない。park・cemetery・plazaの園路や参道・広場周囲の通行帯は別の用途として扱い、一律に全laneを消す修正は避ける。

### 4.2 細街路の生成責務を明示する

`localInfill` の到達探索と区画街路生成の入口で、手動ポリシーと対象区域を解決する。2D、3D、SVG出力が同じ判定結果を使う。

- `explicit`: 描いたroadと明示的に承認した施設アクセスだけを道路にする。住宅生成器が細街路を必要とする場合、道路なしで成立する沿道配置を用いるか、補完を選ぶよう診断する。生成後のlaneを単純に隠すと、その道に依存した住宅だけが残るので不可。
- `district`: 指定した居住・商業・工業区域内の区画分割と細街路を許可する。未指定の土地や別区域へ拡張しない。
- 明示的な道路のない孤立区域は表示できる。到達不能を診断し、接続路の追加は別の提案にする。
- 同じ道路区間は共通索引で重複排除する。既存の `physicalRoadRuns` と [道路網整理設計](ce-road-network-normalization.md) に合わせる。

### 4.3 城の用途と城計画を分ける

Castleブラシは現状「城用途のセル」であり、ランダム生成の `CastlePlan`、防御回路、門、進入路の全てを指定したことにはならない。

手動でも城用途だけで最低限の建物を表示できるようにし、詳細な城が必要なら選択区域から城計画を作る操作を用意する。既存 `CastlePlan.siteFaceIds`, `parts`, `accesses`, `provenance` と城の形状生成を再利用する。外周壁・門・進入路を追加する前に追加内容をプレビューし、承認した形状を文書へ反映する。門から既存roadへの接続がない時に、地図端まで道路を勝手に追加しない。

## 5. 操作の設計

| 操作 | 地図に許される変更 |
| --- | --- |
| 白紙から作成 | メッシュと手動ポリシーを作る。用途・道路・施設は未配置 |
| 2D / 3D切替 | 地図を変更しない。同じ正本と補完規則から表示 |
| 現在の編集を仕上げる | 指定済み区域の建物・施設詳細を決定的に導出。未指定区域への道路・施設追加なし |
| 選択区域を補完 | 細街路、住宅、城の詳細、農道などを選択してプレビュー。1操作として確定・Undo |
| 都市全体を生成 | 既存のランダム生成。編集を置き換える操作であることを明示 |
| 現在の地図を共有 | 最新文書を開く。生成工程は実行しない |
| 生成条件を共有 | seed・入力・設定・段階から従来の再生成を行う |

手動でフルセットを作る流れは、地形・水面と縮尺を決める→城などの核を置く→主要道を引く→住宅・市場・工房・公共施設の用途を塗る→必要な城壁・門を置く→選択区域の細街路・建物を補完→2D/3Dで確認→保存・共有とする。既存のdistrict parametersで密度・敷地面積・向きを調整する。

農地の追加・再生成も明示的な操作にし、仕上げから無条件に呼ばない。手動ポリシーでは、ポリシーと対象区域を農地生成にも渡す。3Dの初回表示から仕上げ後まで同じ規則を適用し、ボタンを押した時だけ境界線の意味が変わる状態をなくす。

## 6. 共有・保存の設計

新しい共有形式は `kind` とversionを検証し、次の2用途を判別可能にする。具体的にはversion 2の判別共用体を追加し、既存version 1は再生成用途として読み続ける。

- `intent: "document"`: 最新の出力用文書を完全に含む。`completeSource` を優先しない。読込時に検証と必要な互換変換だけを行い、生成worker・stage再生・農地再生成を呼ばない。保存済みのsnapshotも保持する。
- `intent: "generation"`: 従来のseed、設定、入力、段階を含み、従来通り再生成する。失敗再現リンクもこちらを使う。

共有文書の採用とファイルimportで共通の状態初期化処理を設ける。ただし、既存 `applyImportedMap` はfabricのrecipeを生成UIへ戻すので、そのまま呼ぶだけで手動仕上げのセッションが復元されるとはしない。手動文書は「完成文書の参照」と「再生成の入力」を区別し、段階スライダーの操作で自動的にランダム生成へ戻らないようにする。

Undo/Redoには手動ポリシー、補完内容、表示工程に必要な状態を含める。派生キャッシュは採用時に無効化する。最後に編集した後でも、共有には必ずその最新状態を使う。

URLは現行のgzip形式を拡張できるが、任意サイズの都市を常に実用的な長さにできる保証はない。サイズを測定し、大きい文書にはJSON保存を案内する。無断で生成条件だけのリンクへ切り替えない。サーバー保存は別案件とする。

既存のJSON export/importは `serializeDocument` / `parseDocument` で文書を扱い、通常のimportは全都市生成を自動実行しない。現時点の編集内容の持ち運びには共有URLよりこちらが適する。ただし、現在の導出街路問題はJSON保存だけでは直らない。

## 7. 実装順序と完了条件

### M1: 白紙からの最小例を安定させる

対象: document型・codec、白紙作成、`localInfill`、区画街路生成、fingerprint、`generation.ts`。

- 手動ポリシーを保存し、未指定土地の街路補完を止める。
- 仕上げでmesh・用途・roadの区間・幅・城の対象セルを保持する。
- 仕上げ前後、2D/3Dとも城1セルとroad1辺だけの例に余計な道が出ない。
- OrganicとClassic、実際の白紙既定Voronoiで確認する。必要な分だけhex/evolutionにも同じ契約を当てる。

### M2: 編集結果を失わない共有

対象: `incomingCity.ts`, `documentIO.ts`, `shareRequest.ts`、import状態初期化。

- document/generationを分離し、編集後・仕上げ後・生成都市の後編集の3状態を往復できる。
- documentリンク読込では生成controllerが呼ばれないことをテストする。
- v1リンク、FMG引継ぎ、生成失敗再現リンクは従来の再生成経路を維持する。
- JSONと共有の双方で手動ポリシー・施設・道路・seed・縮尺を保持する。

### M3: ランダム生成と同じ詳細表現を手動で組み立てる

対象: 既存のdistrict設定・施設生成・城計画・選択UI。

- 選択した用途区域だけ住宅や細街路を補完し、区域外の手動指定は変更しない。
- 再補完はseedと設定から決定的に行い、同じ操作の繰返しで施設や道を累積追加しない。
- 城・城壁・門・港・墓地などの所有関係とアクセスを診断する。橋は必ず `src/utils/bridgeSkewPolicy.ts` の上限を守り、成立しない接続は未接続として提示する。
- 補完後の編集、消去、再仕上げ、Undo/Redo、共有で内容を維持する。

### M4: 表示と検証の統一

2D・3D・SVGの道路供給元を手描きroad、区域内補完街路、農道、FMG由来の外部道路に分けて内部診断できるようにする。道路がなぜ存在するかを調査可能にし、編集ガイドは道路面と別の表示レイヤーに置く。

回帰テストは上記の最小例、対象区域からの逸脱、共有時の生成呼出禁止、旧形式互換、Undo/Redoに絞る。UI確認では「白紙→城1セル→road1辺→3D→仕上げ→3D→共有URLを新規に開く」を通す。実装後の検証は関連ファイルのみを実行し、今回の設計段階では全件テストを要求しない。
