## 1. 目的と採用方針

**市壁の外側には、門から延びる街道沿いの列、宗教・公共施設の周りの小集落、水辺の用途別のまとまりを作る。これらの間には庭・畑・空地の楔を残す。** 建物数を満たすために外周全体を住宅地に変える処理は採用しない。

順序は「推定都市史 → 壁の拡張と旧郊外の取り込み → 壁内の住宅容量 → 残余人口と独立施設の城外配分 → 街路と敷地」である。人口は住戸数へ、住戸数は階数・床面積を通して建物へ変換する。必要住戸数をそのまま建物の必要棟数にしない。

経済拡張の有効化やAdvance Timeの事前実行は不要。`Route.traffic`、`trafficRank`、`TradeCorridor`、貨物量、取引先、価格、資金、税収、産業生産量、経済施設台帳を一切入力しない。道の接続、近隣都市人口、外交、地形、文化・宗教、国家の人口と領域、時代・技術だけを用いる。「国力」は財力でなく、人口と領域から作る動員・統治能力の代理値とする。

年号、過去人口、増築、施設成立の来歴は不足時に創作する。実際に記録された出来事と混ざらないよう、すべて出典区分を持つ。現在の地図に整合する都市の来歴を作ることが目的であり、過去の世界を正確に復元するシミュレーションではない。

## 2. レビューの「足りない要素」への対応

| 指摘 | この設計で決めること |
| --- | --- |
| 市壁の段階モデル | 創設・初回囲郭・郊外形成・拡張・拡張後の再成長を生成。旧郊外の取り込みは面積だけでなく敷地群で保持する（§5） |
| 人口成長履歴 | 現在人口に接続する推定人口の節点を作り、以後の実測人口は別系列で蓄積する（§4） |
| 壁内密度・階数 | 棟数と住戸数を分離し、城外人口比の上限と容量不足時の処理を定める（§6） |
| 交易以外の要因 | 宗教施設、墓地、施療院、水車、川下の工房、定期市、橋頭の小集落を立地条件から配置する（§8） |
| CE出力の受入基準 | 沿道集中、空地の楔、敷地接道、人口容量、保存安定性、Leighの比較を検証する（§11） |

元の交易観測計画は別目的の計画として残す。本設計の前提や実装待ち条件にはしない。

## 4. 推定都市史を作る

### 4.1 入力の優先順位と出典

各値・出来事に`source: explicit | observed | estimated`を持つ。

1. ユーザーが指定した創設年、壁、施設、建物、保護領域は`explicit`として優先する。
2. 本モデル導入後の年次人口・建設イベントは`observed`。記録開始前を実測済みにしない。
3. 旧セーブの生成時刻らしい創設年、Relations historyの生成された年表、人口からの推定年代は`estimated`。旧フィールド自体は書き換えず、新しい都市史に採用値と理由を記録する。

一律の創設年は初期生成の年として保持し、`estimatedFoundedYear`を別に作る。最近の実プレイ中に新設された都市まで一律に古くしない。新設イベントが確認できる都市はその年を採用し、判別不能なら推定理由を残して手動修正可能にする。

### 4.2 Est. polity ageの利用

`src/data/polityAgeEstimate.ts`の`estimatePolityAgeForRace()`を再利用する。UIのEst. polity ageは現在の国家人口、主要文化の種族、出生間隔と世代長から得る推定であり、保存された確定建国年ではない。本モデル初期化時に結果を固定する。

Searenについて§3の人口と保存されたHumanの出生条件を同じ式へ入れると約178年、推定建国年は341 − 178 = 163年となる。これは本設計の計算例であり、セーブ内に163年の建国記録があるわけではない。

- 都市と現在の国家は別の歴史を持てる。都市は国家より古くてもよく、国家交代で都市年齢をリセットしない。
- 年代指定がない都市の初期年齢は、首都なら`A = clamp(round(E × (1.0 + 0.8u)), 60, 3000)`、その他は`clamp(round(E × (0.35 + 1.0u)), 20, 3000)`を初期案とする。Eは推定国家年齢、uは都市専用seedからの0〜1乱数。
- Eがnull・0・不正、無所属なら、主要種族の世代長Tから`clamp(round(4T), 40, 600)`を仮のEとして使う。`near_replacement`を0歳扱いしない。
- 3000年は初期生成の上限であり長命種の史実上限ではない。長命種では別設定や明示年齢で上書きでき、国家年齢そのものを3000年に切り詰めない。
- High Fantasy等でもこの経路を使い、文化セット名だけから全国家を同じ年齢にしない。本セーブのCultures set名は確認できていないためHigh Fantasyだとは断定しない。
- 紀元より古い都市は負の内部年を許し、表示では「紀元前相当」または「創設から○年」とする。暦年から技術時代を推測しない。

### 4.3 過去人口と成長局面

最初から年ごとの数百点を創作せず、4〜8個の節点を作る。最低限、創設・初回囲郭・直近の壁拡張・現在の節点を持つ。創設人口は現在以下の小集団、各人口は正値、最後の節点は現在人口へ厳密に接続する。記録済みの人口点は上書きしない。

既定の推定系列は、創設時0.02〜0.08N、初回囲郭0.15〜0.35N、直近拡張0.65〜0.85N、現在Nを目安に、年代順に生成する。小集落では人口最低値を現在人口で抑え、段階を省略する。節点間は対数補間し、年増減率の上限を超える場合は移住・避難等の明示した推定イベントを置くか、節点の年代を広げる。

系列の型は「緩増」「拡張後安定」「急増」「縮小」からseed付きで選ぶ。現在の敵対圧力は急増（避難民）にも縮小にもなり得るので、敵国があるだけで必ず人口増にしない。縮小型は過去人口が現在を上回ってよく、壁内の空地と城外の廃絶敷地を残す。無理に現在人口まで全区画を再充填しない。

新たな年次人口記録は経済拡張の外へ置く。通常進行・早送り・歴史モード共通で、処理した年境界の確定人口を保存し、CEを開く回数に依存させない。年境界を飛ばすモードでは取得可能な節点だけを記録し、補間を`observed`にしない。初期版は推定系列だけで動作可能とし、年次記録は後続段階にする。

## 5. 市壁の段階・容量・旧郊外の取り込み

### 5.1 現在の勢力から作る二つの指標

国力Qと防御圧力Dを分ける。初期案では、Qを`0.65 × log人口の世界内百分位 + 0.35 × log領域面積の世界内百分位`とする（0〜1、同順位は中間順位）。単独国家は0.5、欠測項目は残る項目に重みを振り直し、両方欠測なら0.5。財政値と経済出力は参照しない。

Dは敵対・競合国の接近度と相対規模で算出する。外交係数はEnemy 1、Rival 0.6、Suspicion 0.3、Neutral/Unknown 0.15、Friendly/Ally/同国0を暫定値とする。国境までの陸路距離減衰と`clamp(Q_neighbor − Q_self + 0.5, 0.2, 1)`を掛け、近隣国について最大値を取る。無接続の敵国があるだけで全門を危険にしない。宗主・属国は単純な敵として扱わず、保護側の組織力を壁建設の補助に使う。

現在のDから数百年ずっと戦争していたとはしない。推定史では「過去に似た防御上の動機があった」という出来事を1回生成する程度に留め、初期化に使った外交スナップショットを保存する。

### 5.2 壁拡張の判定

都市が有壁なら、初回囲郭の後、人口節点ごとに旧壁の住戸容量と人口を比較する。次の二条件が満たされた節点を拡張候補にする。

- 壁内目標人口が、その時代の階数上限での旧壁容量の85%を超える。
- 準備期間`round(15 + 45 × (1 − Q))`年以上、旧壁の成立から経過している。

Qが高いほど拡張が早く、次期人口への余裕を取りやすい。Dが高いほど城外人口の許容を小さくするが、低Qなら拡張が必ず成功するわけではない。高D・低Qでは密度増、城外建築の制限、計画未達という状態も認める。現在人口に必ず合わせるための無根拠な大城壁を作らない。

建設時の壁内収容目標は`H_at_build × (1 + reserve)`、`reserve = 0.10 + 0.25Q`（Hは住戸需要）を初期値とする。§6の密度から候補面積を求め、実地形へ置いた後に再計測する。未来人口を実測したような説明はせず、余裕のある囲郭計画とする。

自動生成は最大2つの可視市壁を基本とし、それ以前は撤去壁跡・道路・地区年齢として残す。既存の`DefenseCircuit.ring/state`を利用する。無壁都市にはこの処理で勝手に市壁を追加しない。

### 5.3 囲む形を先に決め、面積比は結果にする

1. 初回の中心核と初期の施設・街道沿い敷地を作る。
2. 拡張直前までの旧郊外を、§7〜8の規則で配置する。
3. 旧郊外の候補群を、人口容量、中心からの接続、既存幹線、施設、乾いた建築可能地の順に評価する。
4. 旧市街を含む連結領域を拡張し、壁の周長増加に罰点を与える。細い沿道帯の先端を一戸ずつ壁で追わず、近い集落群をまとめる境界にする。
5. 河川・崖・禁止域を避け、門と道路を接続し、壁形状・防御余地を検証する。最終壁の内部に入った敷地だけを「取り込み済み」とする。
6. 取り込まれた地区は`core`/`wallRing`へ移すが、旧街道、敷地向き、施設、成立年代は保持する。壁間を均一な新しい格子で塗り替えない。
7. その後の人口増だけを、新しい外門からの城外成長として作る。

`walledAreaShare`はフレーム幅から決めない。新モデルは壁ポリゴンと段階別容量を一次情報とし、「計画された市街地区画面積のうち外壁内にある比」を診断として計算する。水面は分母・分子から除外し、全体が0ならnull。建物屋根面積比・人口比と混同しない。

現行二重モードでは`walledAreaShare`が内壁の割合、`outerWalledAreaShare()`が1になる。この意味を破壊しないよう、新モデルの`outerEnclosedUrbanAreaShare`と`innerEnclosedAreaShare`を別フィールドにする。生成時は新モデルの壁領域を直接使い、旧`splitUrbanCore()`へ比率を渡して外周住宅リングを再生成しない。旧設定はlegacyモードに残す。

## 6. 壁内の階数と城外人口の上限

### 6.1 棟数、住戸、人口を分離

既存の`BuildingLot.storeys`は利用できるが、`fitImportedHousing.ts`は住宅棟数を数えて需要住戸と比較する。新モデルでは全生成方式が使える`residentialCapacity()`を共通化し、住宅fit、レポート、表示が同じ値を使う。

各建物の住戸容量を次で計算する。

```text
住戸容量 = floor(建物床面積 × 階数 × 居住床比率 × 有効床率 / 住戸当たり床面積)
人口容量 = 住戸容量 × 4.5
```

ここで建物床面積は地上のfootprint面積（m²）、有効床率は階段・壁等を除く割合。住宅用途だけを算入し、倉庫、墓地、厩、宗教建築の屋根を住宅として数えない。用途が混在する場合は居住床比率を下げる。小さすぎて容量0の建物を自動で1戸へ切り上げず、付属屋として扱う。階数の上限と用途条件は種族・文化で上書き可能だが、魔法による無限容量を既定にしない。

暫定プロファイル: 有効床率0.75、住戸当たり40m²、住宅の居住床比率0.85、混合用途0.55。例として80m²・3階の住宅は3戸、同面積2階は2戸、1階は1戸となる。値は歴史統計でなく本生成器の初期較正値である。

| 時代設定 | 旧市街の標準階数 / 自動上限 | 壁間地区 | 城外住宅 |
| --- | --- | --- | --- |
| earlyMedieval / highMedieval | 1〜2 / 3 | 1〜2 | 1〜2 |
| lateMedieval | 2〜3 / 4 | 2〜3 | 1〜2 |
| ageOfExploration / maritimeEra / preIndustrialEra | 2〜4 / 5 | 2〜3 | 1〜2 |
| steamEra以降 | 別プロファイルを要求 | 同左 | 中世型の城外比上限を自動適用しない |

初期実装の自動対象はpreIndustrialEraまで。後期時代は明示設定またはlegacy生成へfallbackし、対応済みと表示しない。住戸密度に合わせて`occupancyRadiusMeters()`の「一戸＝一棟」前提も同時に見直す。半径だけを小さくしたり、fitだけを変更したりしない。

### 6.2 城外に住む人口の予算

城外の割合は棟数でなく、都市人口／居住住戸数に対する割合。施設だけが城外にあるケースは住民が0でもよい。

```text
g = clamp((N_now − N_last_wall) / max(N_last_wall, 1), 0, 1)
q_cap = clamp(0.10 + 0.15g − 0.10D, 0.05, 0.25)
H_total = ceil(N_now / 4.5)
H_anchor = 条件を満たす城外施設に付属する住戸需要（最大0.03H_total）
H_out_required = max(H_anchor, H_total − C_inside)
H_out_budget = min(H_out_required, floor(q_cap × H_total))
```

C_insideは選択した密度と壁形状での実測容量。q_capは上限であり最低限城外に5〜25%を出す指示ではない。壁内に収まれば城外住宅0を許す。旧壁以来の増加gは推定系列から取り、人口減少は0とする。無壁都市・廃壁都市にはこの式を適用せず、中心と街路・施設からの配置規則だけを使う。

不足時は、(1) 壁内の未使用敷地、(2) 時代上限内の階数、(3) 推定史に根拠を持つ外壁拡張の候補再選択、(4) 支道を持つ小街区による城外予算の収容、の順に調整する。再試行は最大3回。壁・建物の手動固定は動かさない。なお不足なら`unplacedDwellings`を出し、人口を減らしたり、空地の楔を埋めたり、沿道を無限に伸ばしたりしない。

占有率は敷地が使われる割合、階数は建物の垂直容量、居住率は住戸に実際に配分された世帯の割合として区別する。容量が需要を超えた分は空室として扱い、人口の重複計上をしない。

## 7. 門ごとの配分と建物の並び

### 7.1 出入口の識別と経済に依存しない重み

道路は「路線ID」だけでなく、都市から外へ出る接続ごとに分ける。同じroute 0の両端を区別し、同じ橋・門まで共有する複数路線は共通区間を1回だけ計上する。`nextBurgs`から採用するのは人口・首都・所属国・外交のみであり、経済由来の役割や用途ラベルを読まない。

初期の門重みは次の積とする。

```text
w = R × (0.5 + 0.5S) × A × B
R: roads = 1.0、trails = 0.55（searoutesは除外）
S: その枝で最初に到達する都市人口の log(1+人口) を近隣候補内で0〜1に正規化
A: 同国/Ally/Friendly = 1、Neutral/Unknown = 0.8、Rival = 0.55、Enemy = 0.25
B: 有効沿道の建築可能面積 / 沿道候補面積（0〜1）
```

相手都市がない場合S=0.25、全候補が同人口ならS=0.5。複数相手が共通区間を通る場合、その区間は最大重みを採用し、枝別予算を合計しても門全体の予算を超えない。距離は必要なら道路長で減衰させ、海路のみの接続は架空の陸上門に変換しない。これは交通量推計とは呼ばず「配置上の接続重み」とする。

施設付属のH_anchorを先に確保し、残る城外住戸予算を有効門へwに比例して配分する。整数配分は最大剰余法を使い、同値は安定ID順。受入面積のない門への配分は再分配する。全w=0なら施設以外は未配置とし、全周への均等散布にfallbackしない。

### 7.2 形状の規則

- 城外道路に沿った弧長sと垂直距離dを使う。曲がる道路で門からの直線距離を沿道距離の代用にしない。
- 防御空地・門前広場の外側から列を開始する。空地の寸法は既存`defenseClearance.ts`で時代・実際の外郭施設から計算し、強い制約を優先する。
- 初期案では主要枝の沿道長150〜500m、弱い枝50〜180m、住宅は道路片側につき1〜2列、通常の奥行20〜60m。これはフレーム幅に比例させない。
- 正面幅6〜12m、敷地奥行15〜35mを基礎とし、同じ街路区間では正面線と軒の向きを揃える。建物正面は道路接線から原則15°以内。敷地ごとの微変化はseed付きにする。
- 門に近い部分は連続率0.75程度、末端は0.25程度へ減衰。列の切れ目には庭・畑を置く。独立乱数で家を点散布せず、数戸の列を生成単位にする。
- 1列で予算を受けられない場合、主要枝に限って長さ40〜100mの支道と小街区を追加する。裏側の建物も接道または明示された通路を必要とし、街道との間に家があるのに道路へ直接接続した扱いにしない。
- 500mを超える連続帯、奥行100mを超える塊を自動fitの逃げ道にしない。例外は離れた施設を中心にした別集落として分離する。
- 隣接する成長軸の間に最低30mの未建築の通り抜けを予約する。成長区域同士が近すぎる場合は低優先側を縮小する。施設や水面で既に分断されている場合も分断を保持する。

城外を単一の`suburb: true`で制約免除しない。各建物を`approachRibbon`、`anchorCluster`、`ruralHolding`のいずれかの領域へ所属させ、全敷地が領域内・建築可能地・防御空地外に収まることを検査する。中心点だけの判定では不十分。郊外の支道は現行`shapeSuburbanFabric()`の「outskirtsのlaneを一律除去」から除外し、道路接続を残す。

## 8. 交易以外の施設と小集落

施設は経済拡張から取得しない。既存のCE施設・文化の埋葬設定・宗教と地形を優先し、不足するものは都市史にseed付きで生成する。全部を毎都市へ置くのではなく、§6の予算と立地が許す範囲で小都市0〜1、大都市1〜3拠点を初期値とする。

| 拠点 | 必須条件 | 配置・周辺建物の規則 |
| --- | --- | --- |
| 宗教施設・修道共同体 | 宗教・文化に適合。既存templeは候補を許すだけで城外所在を保証しない | 街道から短い参道を引く。中庭と境界を囲む少数の住居。文化不適合なら修道院を強制せず聖域・集会所等へ置換 |
| 墓地・施療院 | 埋葬文化・公共施設の条件 | 墓地区画は住宅禁止、管理人・施療院付属住戸のみ。参道沿いに限定。Leighは城外衛生墓地の候補に適合 |
| 水車 | 流向と設置可能な岸が確定 | 水際の施設＋接続路＋少数の住戸。水路改変・堰・橋を装飾のために追加しない |
| 皮なめし・染色等の工房 | 確定した流向、取水地より下流、安全な岸 | 細長い作業敷地を岸へ向け、住居は乾いた側へ後退。品目別生産量は使わず用途の表現だけとする |
| 定期市の空地 | 門外広場・街道分岐に十分な地積 | 開放された広場を残し、その縁に宿・住居を少数置く。屋台を恒久住宅容量に算入しない |
| 橋頭の小集落 | 実在する有効な橋・渡し船と対岸の道路接続 | 対岸の接続点から放射状に少数の敷地。橋の両岸を勝手に連続市街にしない |
| 農家群 | 乾いた耕地、通行可能な農道 | 分離した屋敷＋庭・畑。通常は当該都市の人口予算内に含め、周辺別burgの住民を二重計上しない |

Leighでは岸線が未解決なので、河川依存の施設と橋頭集落は保留する。仮の河岸をでっち上げて生成失敗を隠さない。創作してよいのは来歴と配置動機であり、渡れない川を渡れることにする根拠ではない。

新しい渡河が必要になった場合も、FMG・RE・CEの共通`src/utils/bridgeSkewPolicy.ts`へ判定を委譲する。川との直交を基本とし、推奨偏角10°以内、時代・技術の上限（古代・中世の石15°/木20°、近世25°、斜めアーチ以降30°）を超えない。川に平行な橋や川上で屈曲する橋は禁止。適合しない場合は道路を曲げる、別地点・有効な渡し船へ接続する、または拠点を作らない。Historical periodを開始時の下限とし、技術習得を既存共通判定に反映する。

## 9. データ契約・保存・既存実装との接続

新規の概念契約は次の通り。名前は提案であり、既存フィールドがあるという意味ではない。

```ts
type GrowthSource = "explicit" | "observed" | "estimated";
interface UrbanMorphologyProfile {
  version: 1;
  modelVersion: string;
  seed: string;                       // world seed + burgId + modelVersion
  baselineYear: number;
  baselinePopulation: number;        // 人、人口点ではない
  contextRevision: string;           // 非経済入力のみのhash
  estimatedFoundedYear?: number;
  polityAgeAtBaseline?: number;
  populationKnots: Array<{year: number; people: number; source: GrowthSource}>;
  wallPhases: Array<{
    id: string; year: number; source: GrowthSource;
    targetDwellings: number; absorbedClusterIds: string[];
  }>;
  approaches: Array<{id: string; routeIds: number[]; weight: number}>;
  anchors: Array<{id: string; kind: string; year: number; source: GrowthSource}>;
  // 具体的な用途型、制約、欠測理由、入力snapshotは実装時に型を定義する
}
```

FMG側は人口・政治・推定史という意味情報を所有する。CE側は門対応、壁ポリゴン、成長領域、支道、敷地、実測住戸容量、診断を所有する。`absorbedClusterIds`等の参照を保存し、二度開いたときの再乱数化を防ぐ。CE固有の座標をFMGの世界座標と混在させない。

- descriptorにoptionalな`urbanMorphology`を追加。生成元と消費側を同時に対応させる。経済providerのフィールドとは分離し、`contextRevision`へ経済値を含めない。
- FMGの都市史はhost所有の保存領域として追加し、world archiveの検証・ロード・snapshot/rollbackを対応させる。CEを開くだけではFMG乱数ストリームを消費しない。保存が必要な初期profileは明示した初期化処理で確定する。
- 安定IDは世界・都市・道路接続から作る。配列indexや角度丸めだけにしない。道の分割・統合時は対応できる接続だけ引き継ぎ、不明は`stale`として再割当候補を表示する。交易計測用の通過台帳は不要。
- 再読込や外交変更のたびに創設年・過去の壁・家の位置を作り直さない。新しい人口点と現在の配分候補を追加し、既存の土地利用を変えるには成長更新または再生成操作を使う。
- 手動固定壁・区画・施設を優先する。入力衝突は理由付きの未配置容量として残す。
- 旧CE文書は自動移行せず従来表示を維持する。新モデルの再生成は新文書または複製に対して行う。旧descriptorにも非経済情報だけから既定profileを作れるfallbackを用意する。

| 現行箇所 | 必要な変更 |
| --- | --- |
| `src/services/burgSiteDescriptor.ts` | 非経済入力の投影とprofile追加。陸路の両方向と共有区間を識別 |
| `src/data/polityAgeEstimate.ts` | 計算を再利用。毎回の年齢再計算を都市史へ反映しない |
| `src/utils/cultureLotOccupancy.ts` | 住戸容量密度に基づく都市半径へ接続。従来較正との区別 |
| `src/city-editor/core/generate.ts`、`gen/settlementExtent.ts` | 旧市街・取り込み地区・現在の城外領域を段階生成。フレーム幅による壁容量決定を新モードでは使わない |
| `core/gen/fitImportedHousing.ts` | 共通の住戸容量による調整。outskirts全体のsuburb化を禁止 |
| `core/gen/suburbanLanduse.ts` | 新モードでは`roadUse()`を呼ばず接続重みを使用。全生成経路へ領域マスクを適用し、支道を保持 |
| `core/gen/buildingLots.ts`と各fabric生成器 | `storeys`、用途別居住床、領域IDを一貫して出力 |
| `core/housingReport.ts` | 建物数に加え住戸容量、配分人口、城外人口比、未配置住戸、成長領域別集計を出力 |

`fitImportedHousing()`が現在skipするmedieval / fabric v5 / bram / circuladeでも、最終出力の領域制約と容量検査はskipしない。初期実装で対応できないレイアウトは非対応を明示し、通常の住宅fitに入ったケースだけをもって全CEで完了としない。

## 10. Leighの具体的な設計例

以下は**基準セーブの事実に接続した創作例**。自動アルゴリズム実行結果、過去セーブからの実測、CE描画済みの結果ではない。実装時の固定fixtureとして利用できる。

| 年 | 人口 | 出来事 |
| --- | ---: | --- |
| 91 | 1,500 | 渡河路に近い集落の成立。実在の橋は断定しない |
| 151 | 8,000 | 最初の囲郭。中心核と宗教施設を保護 |
| 163 | — | 推定国家年齢と整合するSearen成立。都市の成立はそれ以前 |
| 241 | 18,000 | 街道沿いに旧郊外が形成 |
| 281 | 29,000 | 新市壁へ拡張。旧郊外の住戸の80%を取り込む計画例 |
| 341 | 38,255 | 現在人口へ接続。新門の外に再び少量の成長 |

「80%」は囲郭前の旧郊外住戸に対する例示値であり、全都市の面積比ではない。実際に囲めなかった集落を取り込み済みにしてはいけない。余裕率・時代密度の計算と矛盾する場合は、例示値より生成された有効形状と容量を優先する。

初期fixtureの城外目標を1,020戸（約12%）、壁内を7,482戸とする。合計8,502戸、人口容量38,259人で4人分は丸め余裕。実人口38,255人を増やさず配分する。これは§6の上限を満たすDと容量を選んだfixtureの値であり、本セーブから城外人口12%が観測されたという意味ではない。

たとえば壁内の住宅が平均3戸/棟なら約2,494棟、城外が平均2戸/棟なら約510棟で足りる。実際は敷地床面積・用途・階数ごとに容量を足し上げる。約3,900棟を数本の道路へそのまま移す設計にはしない。

城外は「主街道の複数の門前小街区＋弱い道の短い列＋城外墓地の管理施設」を第一案にする。墓地の存在で周囲に大住宅地を発生させない。各門の方角・住戸数はdescriptorの陸路接続と建築可能面積から決め、route 484の水運は門重みに含めない。河岸不良を解消するまでは川下工房・水車・橋頭集落を必須の構成要素にしない。

## 11. 受入基準

数値はこの設計の初期合格線。完成済みの検証結果ではない。比較は同じ保存世界・人口・都市seed・時代・地形で行い、経済データは与えない。

### 11.1 必須の整合性

1. 建物が水面、壁、濠、防御空地、予約空地、他の建物へ侵入する件数が0。全polygonで検査する。
2. 各城外住宅に成長領域IDがあり、通行可能な道路または通路へ接続している。共有区間の二重配分が0。
3. `H_assigned_inside + H_assigned_outside + H_unplaced = H_total`。容量・配分戸数・棟数を別に出す。受入可能な通常fixtureは未配置0、容量不足fixtureは正しい未配置数と理由を出す。
4. 城外の配分住戸は§6の上限以内。旧郊外の取り込み後に旧・新領域へ二重に人口を数えない。
5. 壁の年代は創設後かつ現在以前、初回→拡張の順序を保ち、領域は入れ子。撤去壁を現在の外壁として使わない。
6. 同じseed・保存profile・地形で再生成し、ID・年表・配分・建物配置が同じ。保存再読込、CEの開閉、無関係な経済値変更で変化しない。
7. 経済ON/OFFで非経済入力を固定したとき、profileと城外の成長領域が一致する。経済をOFFにすることで後日の人口が変化する比較とは区別する。施設・置き場・港の倉庫・舗装の配置は、経済ONでは経済データに従うので一致しない(§13.2、2026-10-21)。
8. 全橋が共通斜交・渡河長制約を満たす。橋頭拠点を置くための例外を設けない。

### 11.2 配置の法則性

- 施設付属住戸を除く城外住戸の80%以上を、主要街道から実接続する成長領域へ置く。「主要」は配分前の重み順で累積80%に達する最小集合と定義し、整数丸めは1戸まで許容する。受入可能容量不足の場合は例外理由を出す。
- 重み上位2門の合計が全体の60%以上で、十分な敷地があるfixtureでは、その2門に沿道住戸の60%以上を置く。一つの有効門しかない都市はその門で評価し、全門同重みの都市には無理な偏りを要求しない。
- 独立した成長軸が2本以上ある通常の陸地fixtureでは、その間に最低30m幅の未建築経路が1本以上残る。両側住宅による閉じた全周帯を検出したら不合格。判定は外郭付近の建築可能な帯状領域で、建物を10m膨張させた占有域が全周を閉鎖するかで補助計測する。
- 沿道住宅の90%以上で正面方向の道路接線からのずれ15°以内。施設の中庭型・地形で制約された敷地は理由付きで別集計する。
- 同じ成長領域の近門部と末端を道路弧長で3等分し、末端の建物被覆率が近門部を上回らない。防御空地は計測区間から除く。
- 表示フレームだけを広げても、壁・人口配分・建物配置を変えない。地形解像度そのものを変更したケースは別比較にする。

### 11.3 基準世界の比較と出力

Leighを主対象、Penorham（約15,990人、川岸配置済み）、Seriemigny（約18,089人）、同世界の無壁小都市を副対象に選ぶ。加えて人工fixtureで長命種・年齢推定null・若い都市・縮小都市・敵向きの門・全門建築不可・固定壁の容量不足・二重壁・単一壁・無壁を検査する。

各ケースで旧生成と新生成の同縮尺画像、壁段階、成長領域、住戸容量、門別配分、空地、未配置理由を出す。Leighでは「全周リングが消えた」だけでなく、旧郊外が壁間に残り、新しい城外建物が門前・拠点周囲に並ぶことを確認する。岸線の既知の問題は別診断として残す。

検証成果物案: `input-summary.json`、`morphology-profile.json`、`capacity-report.json`、`placement-diagnostics.json`、同縮尺の`before.png` / `after.png`。基準セーブは読み取り専用とし、試験後の状態は別名保存する。

## 12. 実装順序と完了条件

1. **非経済入力と固定fixture**: 基準セーブをロードし、population・国家・文化・道路接続を抽出。Leighの推定史fixtureと出典表示を作る。交易台帳や日次決算の改修は含めない。
2. **容量と領域制約**: 共通の住戸容量、密度に対応した半径、城外予算、全生成経路の領域マスクを実装。全周suburb開放を新モードから除き、道路列と空地だけで最低限の配置を成立させる。
3. **壁段階と拠点**: 二重市壁の既存機能に取り込み履歴を接続。宗教・公共施設から開始し、岸が確定したケースにだけ水辺の拠点を追加する。
4. **保存と受入**: profile・敷地所属・診断の往復保存、旧文書互換、Leighほかの目視・定量比較を完了する。
5. **後続**: 年次人口記録と成長更新を追加。未来の実測が蓄積しても、初期化時の推定史を黙って書き換えない。

初期版の完了条件は、経済データなし・時間進行なしで、有壁都市の容量と歴史に整合した城外配置が生成され、建物のまとまりと空地の理由を説明できること。人口を収容できないケースも数値で検出できること。経済の詳細観測や史実の再現は完了条件に含めない。


## 13. 初期実装と検証（2026-10-13）

### 13.1 実装した経路

- FMGの`simulation.burgs[id].urbanMorphology`へ初期profileを保存する。初回のdescriptor取得で、専用の`burg.morphology.initialize`コマンドを通して一度だけ確定する。人口履歴は別の`urbanPopulationHistory`へ年境界で記録し、通常・早送り・歴史モードが共通で呼ぶ。
- 創設年の出典を`initial / observed / explicit`で識別する。一律の旧創設年は保存値を保ち、profile側へ推定年を作る。国家の出生モデル、現在の人口・領域・外交から年代と防御圧力を生成する。
- 推定成長局面は緩増・拡張後安定・急増・縮小をseedで選ぶ。現在人口と過去の壁人口を別に保持し、縮小では過去人口の方が大きくなる。
- ~~対応時代の新しいdescriptorは経済providerを呼ばず、道路交通量・近隣都市の資金／富裕度も投影しない。~~ 2026-10-21 に変更: 経済providerがprofileを返す(Economy拡張機能が有効)ときは、対応時代でも経済profile・道路交通量・近隣都市の資金／富裕度を投影し、CEもそれを使う(§13.2)。無効なときは投影しない。旧descriptorや未対応の後期時代は従来経路を維持する。
- CEは推定壁段階から単一／二重と内側の面積目標を自動選択する。現在の城へ旧壁を伸ばすと間隔を守れない場合は、城を後期の地区に置いたまま旧壁を検証する。生成できなかった旧壁は診断に残す。
- 壁間の旧郊外は幹線付近の実際のface IDで記録し、同じfaceを複数の取り込み地区へ重複登録しない。
- 共通の住戸容量計算を住宅fitとレポート・画面に接続する。階数・床面積・住宅用途を計上し、建物数と住戸数を分ける。密度に応じてdescriptorの住宅半径も調整する。
- 城外は門別の領域へ限定し、道路の弧長、正面の向き、建物列の連続性と末端の疎化を使う。二列目には実際の通路を作り、空地の楔・防御空地・水・施設・他の建物との衝突を避ける。
- 実在する宗教施設・墓地・水車・工房に接続できる箇所を拠点候補とし、条件が合う大都市では定期市の開放区画を予約する。未解決の水辺では水車・川下工房を生成しない。新しい橋を拠点のために作る処理は追加していない。
- hex / voronoi / evolutionとlegacy / medieval双方で最終の領域制約と容量診断を適用する。手動で固定された敷地は保持し、予算超過を診断する。CE文書の保存・再読込でprofileと領域を保持する。

主な実装: [都市史の型](../../src/types/urbanMorphology.ts)、[推定モデル](../../src/utils/urbanMorphology.ts)、[国家からの投影](../../src/services/burgUrbanMorphology.ts)、[城外の領域・建物列](../../src/city-editor/core/gen/urbanGrowth.ts)、[住戸容量](../../src/city-editor/core/gen/residentialCapacity.ts)。

### 13.2 初期モデルでの調整と限界

§4〜8は目標設計として残す。初期モデルの壁拡張は人口の節点と国家の準備期間から選ぶ軽量な推定であり、過去の敷地群を逐年シミュレーションして壁境界を最適化する処理ではない。旧郊外の取り込みを現在の壁間の幹線付近へ投影して記録する。

城外予算は人口増の35%と施設の小さな基礎予算（需要住戸の1%）から開始し、§6の人口比上限で抑える。既存の壁形状で実測した住宅容量を、占有率と時代の上限内の階数で調整する。3回の調整でも足りなければ未配置住戸を返す。容量不足から新しい外壁候補を探索し直す処理は初期版に含めない。余剰容量は空室として扱う。

施設や道路の適地がないときに拠点を強制しない。墓地・宗教施設の周辺住戸は既存の区画と接続路を利用する。離れた施療院や独立した対岸集落を新規施設として作る専用生成器は後続の拡張対象であり、現在の配置の合格をそれらの存在に依存させない。

年次記録は実際に処理された年境界に限定する。開始前・省略された年を実測扱いにせず、200年を超える通常の年次系列は直近200点を保存する。人口や外交が変わっても、保存済みの創設年・過去の壁年を計算し直さない。

### 13.3 再現手順

基準セーブの標準ロード後に、Leigh / Penorham / Seriemignyを生成し、住戸需要の配分・城外上限・全敷地の領域内判定・空地の楔・再読込の同一性・経済profile変更に対する不変性を検査する。

```sh
URBAN_GROWTH_ARCHIVE=temp/000.savdata/Triviers_2026-10-12-18-47.fmg \
URBAN_GROWTH_OUT=temp/urban-growth-validation \
npx vitest run src/city-editor/core/urbanGrowth.archive.test.ts
node scripts/renderUrbanGrowthValidation.mjs
```

生成物は`temp/urban-growth-validation/`のprofile、容量集計、生成診断、CE文書、比較SVG・PNG。通常のロードと同じ河岸・道路修復を行うため、§3の未修復のZIP保存値との違いはロード経路による。比較の旧生成では同じ世界・seedを使い、従来の住宅半径と壁・住宅fitへ戻している。画像は同じメートル尺度へ揃える。

自動試験に加え、[比較画像の描画スクリプト](../../scripts/renderUrbanGrowthValidation.mjs)でLeighの全周住宅帯の解消と旧・新壁、門外の列、間の空地を目視確認する。数値と実際の較正結果は生成時の`summary.json`を参照する。

### 13.2 Economy拡張機能が有効なときの経済データの共有(2026-10-21)

経済に依らない規則は、Economy拡張機能が無効なときに妥当な都市を作るためのものとし、有効なときは経済データを共有して実際の交易・ギルド・在庫に合う都市を作る。

| 場所 | 変更 |
| :--- | :--- |
| `services/burgSiteDescriptor.ts` | 経済providerのprofileがあれば、推定都市史を持つ時代でも`economy`を入れる。道路の`traffic`・`trafficRank`、`nextBurg`の資金・富裕度も、profileがあるときは投影する |
| `city-editor/generators/generation/generateCity.ts` | 推定都市史の経路でdescriptorの`economy`と道路交通量を消さない |
| `city-editor/generators/guildFacilities.ts economyOnDocument` | `urbanMorphology`のある文書でも経済profileを返す(ギルドの会館・置き場・水車の数・港の倉庫・荷さばき場の荷) |
| `city-editor/generators/roadTraffic.ts` | `urbanMorphology`のある文書でも道路交通量を使う(舗装・門前の宿)。キャッシュの鍵に交通量を足す |

変えていないこと:

- profile(`urbanMorphology`)と`contextRevision`は今後も経済値を含まない。壁の段階・城外の領域・空地の楔は経済のON/OFFで変わらない。§11の受入基準7(経済ON/OFFで配置が一致する)は、profileと城外の領域についての基準とし、施設・置き場の配置は経済ONで変わる。
- 城外の街道沿いの成長の重み(§7.1)は、近隣都市の人口と外交のまま。計測した門ごとの交通量で重みを決める`approachGrowthSource: "traffic"`(O4)は、従来どおり明示したときだけ使う。
