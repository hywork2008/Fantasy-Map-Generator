# 河川都市・渡河施設・船舶航路の統合設計

2026-10-03。既存の水域接触フラグを基礎とする段階実装。

実装済み: 都市地点の川幅から川岸候補を求める配置、地点別水深と時代/能力別の固定橋・可動橋・渡し船判定、FMGの陸路横断情報の保存、候補航路→横断解決→河川航路再検証、CEへの橋情報の引き渡しと可動部の表示、実際の水域に応じた船種制限。

未実装: 中洲そのものの地形生成、渡し船の詳細な乗降場・運航表示、建設費とランダム重み付けによる方式選択、季節水位・開閉待ち時間のシミュレーション、全船種ごとの精密な桟橋到達性。現在の能力値・代表船種はゲーム用の既定値であり、測深値や史実の限界値ではない。川岸が元セルを外れる場合も、論理的な政治所属セルは保持する。配置可能な陸地を確認できない不完全な地形では旧配置を維持する。

## 目的

河口幅7kmの川の中央に都市アイコンが浮く問題を、都市地点の物理的な川岸・陸地・航路に基づいて解消する。FMGで決定した地形と渡河方式をCEへ渡す。CEが独自に中洲や橋を発明して両者の地理を変えない。

航行可能な河川に橋があるだけでは跳ね橋を必須としない。対象船舶の喫水、船幅、水面上の高さと、航路水深、橋脚間の有効幅、桁下高を比較する。固定橋で通れない場合に、可動橋、架橋地点変更、渡し船、積み替えを比較する。

## 現状の接続先

- `src/main.ts`: 河川生成後に都市生成。標準配置は国家生成→港配置調整→経路生成。非標準配置は経路生成→国家生成→港配置調整→経路再生成。既存の政治生成用の仮経路を最終航路と混同しない。
- `src/generators/burgs-generator.ts`: 河川セルの都市はセル中心から小さく移動するため、物理的な川岸を保証しない。
- `src/generators/riverHydrology.ts` / `River.cellHydrology`: 地点別の水深・流速推定がある。ただし水深は表示用推定で、測深済みの航路水深ではない。
- `src/generators/riverNavigationGraph.ts`: 流量閾値と河川トポロジーで下流向き航行を作る。船種別水深・橋の通航制約は未接続。
- `src/utils/bridgeCrossingPolicy.ts`: 時代別の総架橋延長を持つ。最大支間、橋脚施工可能水深、通航高、可動部の能力は別途必要。
- `Burg.waterAccess`: 川・海・湖へのセル単位接触と港の水域フラグ。実際の桟橋や船の到達可能性の証明ではない。河川港の排水先が海であることと海港であることを区別する。

## 共通データ案

1. `RiverCitySite`: 都市ID、河川ID、左岸/右岸/中洲、実際の陸地ポリゴン、都市地点の横断面、地域の河口幅、河川中心線、物理的な両岸。都市アイコンは陸地上に置く。
2. `Channel`: 安定ID、左右岸、都市地点の水路幅、低水位時の推定航路水深、高水位時の水面高、流速、推定品質、参照する河川セル。中洲がある場合は水路を別々に持つ。
3. `VesselNavigationProfile`: 船種、河川/湖/海/静穏湾の適性、満載喫水、船幅、水面上高さ、必要余裕、推進方式、遡航条件、マストを倒せるか。川船も帆を持つ場合があるので一律に低い船として扱わない。
4. `NavigationCorridor`: 水路ID、対象船種、進行方向、水深/幅/高さ条件、候補/確定状態、接続する港・航路。海船の河川進入は船種別の条件で判断し、海につながるだけでは許可しない。
5. `Crossing`: 固定橋/跳開橋/旋回橋/渡し船/渡河なし、各水路の横断位置、総延長、最大支間、橋脚施工水深、桁下高、通航開口幅、可動部の形式と開口時条件、開閉時間、道路待ち時間、利用可能季節、根拠となる技術能力。
6. `PortBerth`: 河川/湖/海の実際の水路ID、桟橋位置、水深、許可船種、到達経路。川と海の両方を持つ都市でも、河川桟橋に海船を置く許可にはならない。

長さはメートルで統一する。水面高と橋の標高は共通の基準面にそろえる。未知の水深はゼロや無制限に置き換えず、推定/未知を明示する。

## 生成の順番

1. 河川・海・湖の地形と地点別の幅、水深、流速を生成する。
2. 時代を初期値として、地域/国家の橋梁技術、造船技術と代表船種の能力を解決する。
3. 船種別の自然航行可能区間を作る。橋がなくても浅瀬・急流・外海適性で通れない区間を除く。
4. 都市候補を配置し、川岸または安定した中洲の陸地へ都市を置く。中洲を選ぶならこの時点でFMGの水域形状も確定する。架橋候補を増やす目的だけで全都市に中洲を作らない。
5. 都市と国家・港を確定し、河川と海の航路候補を作る。河口・静穏湾・積み替え港で船種ごとの接続を解決する。両者は共通グラフ上で接続し、単なる「海を先に/川を先に」の上書き処理にしない。
6. 陸路の渡河候補を求め、航路候補と競合する場所で渡河方式を決める。航路の深い主水路には必要な通航開口を確保する。
7. 橋・渡し場を制約として陸路と船種別航路を再評価し、最終航路を確定する。解決しない候補は閉じる/積み替えにし、生成と再生成の無限反復を避ける。
8. 最終の都市立地、水路、渡河施設、航路、桟橋を保存してCEへ渡す。CEは詳細形状を生成するが、通れる船種や渡河方式を変更しない。

既存の国家生成が仮の陸路を必要とする順序は維持する。仮経路と確定経路を分離し、同じseedで段階ごとの再実行が同じ結果になるようにする。

## 橋と船舶の判定

- 水深: 航路の最浅部の低水位水深 >= 満載喫水 + 船底余裕。
- 幅: 橋脚・可動部を除く実際の航行開口幅 >= 船幅 + 側方余裕。
- 高さ: 高い航行可能水位での桁下高 >= 船の水面上高さ + 上方余裕。
- 水深条件は低水位、桁下高条件は高水位で厳しくなる。平均水位一つで両方を判定しない。
- 固定橋が条件を満たすなら可動橋は不要。可動橋は開口時の高さ/幅と運用条件で判定する。
- マストを倒せる船は、倒した場合の高さと作業時間を使う。すべての帆船へ暗黙に適用しない。
- 中洲経由でも各水路の支間・施工水深・通航条件をすべて確認する。主水路に航行開口、他の浅い水路に固定橋という組み合わせを許す。
- 渡し船も水深、流速、船の技術と積載能力が必要。橋が造れない場所なら必ず渡し船を成立させるわけではない。

ランダム選択は成立する候補内でのみ行う。交通需要、建設/維持費、国力、航路を保持する価値、開閉待ち時間で重みを付け、地点IDとseedにより再現する。

## 時代と技術の扱い

史実の初出年とゲームで一般的に建設可能とする時代は分ける。城門・堀の小さな跳ね橋が存在することから、幅広い航路の可動橋の能力を推定しない。

- 中世の段階: 小規模な木造可動部は候補として扱うが、用途、開口幅、地域技術を個別に制限する。一般的な大河の可動橋を自動解禁する根拠にはしない。
- 近世の段階: 小水路の木造跳開・旋回機構を候補にする。サイズや駆動能力の値は史料調査とゲーム調整後に決める。
- 蒸気・産業段階: 鉄/鋼構造、動力と油圧等の機構を持つ大規模な可動橋を別能力として扱う。

上記はゲームの能力段階案であり、世界共通の発明年表ではない。時代は能力の既定値、国家/地域技術は追加の条件とする。総延長、固定支間、可動開口幅、橋脚施工水深を別々に制限する。現行の時代別総延長表をそのまま最大支間として再利用しない。

史料: Rijksmuseumには1660–1680年頃の跳ね橋を描いた作品があるが、これは発明年や大河での能力を示さない。[作品資料](https://www.rijksmuseum.nl/en/collection/object/Wooded-Landscape-with-a-Drawbridge--94089ec76931f782ce113eeef0c8562d?tab=catalogue)。Tower Bridgeは1894年開通で、当初は蒸気と水圧による駆動を使用した大規模可動橋の具体例。[開通記録](https://www.towerbridge.org.uk/stories/timeline-the-construction-of-tower-bridge)、[機構説明](https://www.towerbridge.org.uk/stories/how-does-tower-bridge-work)。これらから中世の大河用可動橋の初出を断定しない。

## 実装段階と検証

1. 地点別の川幅と物理的な陸地に基づく都市位置を確定。既存アイコンの移動に伴う陸路・港座標・CEの原点を同期する。
2. 技術能力と船種別航行条件を追加。既存水深推定を航路用に校正し、数値未確定の間は既存航路を一括削除しない。
3. 渡河候補と航路候補を統合し、固定/可動橋、渡し船、積み替えを保存する。
4. CEの橋形状・可動部表示、桟橋ごとの船種選択へ接続する。
5. 旧セーブは欠けた情報を推定状態として補完し、既存の固定橋を黙って跳ね橋に変えない。再生成時に新しい制約で解決する。

検証例: 河口7kmでも都市地点は狭い川、7kmの主水路と中洲、固定橋を通れる低い川船、桁下を通れない帆船、深さ不足の海船、技術不足で渡し船へ切替、深すぎて橋脚を置けない川、増水時のみ通航不可、海と川の二つの桟橋、複数橋が連続する航路の最も厳しい制約、生成順を変えない再実行での一致。FMGとCEの岸線・中洲・渡河方式が一致することも検証する。

## 河川港の都市内補完

FMGの中洲描画は先送りする。CEでは `burg.port` と `waterAccess.port.river` を根拠に、対応する川が都市近傍から欠落している場合だけ局所的な川を補完する。川幅・岸・流向が残っていれば利用し、形状が全くなければ直線の川岸を都市半径の45%の位置に設ける。幅不明時の初期値は30m。この形状は都市生成用の推定であり、FMGの測量形状を書き換えない。海・湖の錨だけから川を追加しない。

海岸を持たない河川港でも港区画を保持し、河川リボン上に短い桟橋を設ける。短い桟橋は川幅の概ね1/4以内とし、海船用の深い水域としては扱わない。幅7kmの川は既存の水面ポリゴン処理を使って、都市側の岸と桟橋を生成する。入力から港区画・桟橋までの回帰テストを40m/7kmの両方で確認する。

### Ky Cuongの実データへの対応

`Ky Cuong 2026-10-03-14-57.fmg` の都市3（Ilonor）、8（Yethlu）、33（Keathebelse）を入力として生成失敗を再現した。都市中心が川幅の内側に入る入力は都市の陸側を確保して再構成し、居住域に対して幅の大きい河川港は橋の技術上限以下でも水面と岸線で表現する。居住域外の岸セルを港として予約した場合も港の建築・桟橋を生成できるようにする。

水面を横切る港の街道は都市側の陸路を船着き場まで保持し、`sourceRoad.terminal = "riverLanding"` を保存する。城壁内の船着き場には不要な外門を作らず、道路は水面・城・城壁の制約を守って乾いた頂点へ接続する。FMG由来の入口は海岸比率を理由に減らさず、門候補の間隔も必須入口数に合わせる。元の街道のインデックスとrouteIdをすべて保持することを回帰テストで確認する。

実データから切り出した3都市の入力fixtureで、通常のlegacy描画を含む全体生成、川の水面、都市中心の陸地、港区画、桟橋のSVG、全街道の保持を確認する。これらの補完はCE内のもので、FMGの岸線や中洲を描き換えない。

### 岸線と桟橋の描画補正

河川港の補完時に既存の曲線を直線へ置き換えない。位置補正が必要なら曲線と両岸を一緒に平行移動する。形状が欠落または直線の二点だけの場合は、CE内の推定形状として緩い局所的な曲がりを生成する。極端に幅の広い川では曲率を制限し、オフセットした岸が折り返さないようにする。

港の編集セルの水面境界と表示上の岸線は異なることがある。川の水面ポリゴンから実際に表示する岸線を取得し、legacyのSVG、港の区画・桟橋計画、停泊船の桟橋抽出で共有する。Ky Cuongの3都市について、桟橋の根元が表示上の岸線に接し、先端が川の内部にあることをSVG座標で検証する。岸辺の拡大画像でも接続を確認する。

### 両岸の街道の保持

河川港の入力街道を都市側の渡し場まで短縮する場合も、対岸の乾いた街道と両岸の交点を `riverConnections` に保存する。連続水面の幅・深さ・航路・技術条件で橋または渡し船を決め、CEでは対岸から地図端まで描画する。街道の接続先ラベルは対岸側の地図端に置く。深さ不明の航路には既存の判定に従って渡し船を用いる。都市8と、深さ既知の橋・幅制限超過の渡し船を回帰検証する。

### 切り出し範囲外の水理情報

FMGの河川が都市フレーム外でも、接触フラグの河川IDに一致する河川は descriptor に残す。形状配列が空でも都市セル優先の推定水深・流速・水温と船舶の喫水・幅・高さを渡し、CEの形状補完時にも保持する。都市8の保存済み水深1.94mを用いた固定橋と南側街道の生成を確認する。水理情報だけの追加で既存の形状補完方向は変えない。
