# CEの建物の階数と高さの分布

作成: 2026-10-25
状態: H0〜H3を実装。H4は代表ケースの確認を実施（下記§11）。

## 1. 結論と対象

都市全体へ共通の階数を設定する処理を、地区・用途ごとの分布と人口容量の調整へ置き換える。FMG連携と単独CEで同じ規則を使う。通りや街区にはまとまりを残し、都市全体では低層と高層が混在する。階数は人口容量と3D表示で共有し、描画時だけ高さを変えない。

初期対象は欧州の earlyMedieval / highMedieval / lateMedieval と、既存CEで既定に使われる ageOfExploration。その他の時代・文化は従来の階数規則を維持する。高い穀倉・塔状住宅など地域固有の例外は別プロファイルの後続作業とし、今回、住宅の時代別上限は変更しない。CGは調査・変更対象外。

初回調査の後、階数分布・人口調整・互換・操作・3Dの階高差を実装した。全都市の調査や全件E2Eは対象外とし、§11の関連テストと代表ケースで確認する。

## 3. 現行実装の調査

### 3.1 階数が画一的になる経路

| 箇所 | 現行の処理 | 影響 |
| --- | --- | --- |
| `src/utils/urbanMorphology.ts: residentialStoreys` | 初期・盛期中世は標準2/最大3、後期中世は3/4、大航海時代などは3/5 | 時代別の基準値。これ自体は分布を持たない |
| `generators/residentialCapacity.ts: applyResidentialStoreys` | 城内住宅を `urbanGrowth.insideStoreys ?? standard` に一括設定。城外は最大2。lockedセルと集約住宅は除外 | 元のlotの階数があっても城内では上書きされる |

| `generators/populationHousing.ts: detailedHousingFabric` | 城内は `housingFit.storeys ?? standard`、城外は最大2を住宅全棟に設定 | 単独CEの人口生成でも一律になる |
| 同: `populationHousingFabric` | 集約表示も同じhighを使用。約80 m²の住宅を1区画最大8棟と見積もり、同一階数のテンプレートで集約 | 表示単位を変えても画一性が残る |
| `generators/populationHousingFit.ts` | 標準階、最大階、最大階+小さい区画の3候補 | 階数分布を考慮せず、都市全体の階数を切り替える |
| `generators/medievalFabric.ts` | 初期値を patriciate は3階、それ以外は2階とする | 初期値に用途差があっても、その後の処理で揃う |
| `generators/buildingMassing.ts` | lotの階数を採用。住居未設定は容量と同じ1階。非住居はroleで1〜3階 | 現在の3Dは上流の決定を正しく反映している |

表中の省略パスは `src/city-editor/` 以下。これはコードで確認した原因で、ユーザーの全都市に同じ状態が出ることを実測したものではない。

### 3.2 調査用入力による再現

既存関数を `node --import tsx --input-type=module` から直接呼び出した。80 m²の矩形住宅12棟、元の階数は1階と2階が6棟ずつ、全棟core、lockedなし。FMG経路の下流を模した入力で `applyResidentialStoreys` → `assignBuildingMassing` を実行した。

| insideStoreys | 結果 | 軒高 | 合計住戸容量 |
| --- | --- | --- | --- |
| 3 | 12棟すべて3階 | 全棟9.0 m | 36 |
| 4 | 12棟すべて4階 | 全棟11.9 m | 60 |
| 5 | 12棟すべて5階 | 全棟14.8 m | 72 |

別途、同じ12棟を後期中世・人口100人の `populationHousingFabric` に入力した。detailed / cluster-10 / cluster-20 の3モードすべて12棟が3階、容量36住戸、割当23住戸になった。この小さい入力では表示グループも同じになるため、大きな集約区画の同等性までは検証していない。

初回の人口経路の調査呼び出しは、簡略入力に `urbanMorphology.wallPhases` がなく失敗した。空配列と `urbanGrowth.regions` を補って上記3モードを確認した。実アプリの障害ではない。

### 3.3 守る契約

- `residentialCapacity` は原則 `floor(footprint * storeys * residentialShare * 0.75 / 40)`。階数変更は容量変更であり、見た目だけの変更ではない。集約住宅は `capacityDwellings` が正本。
- `buildBlockFabric` は人口処理または `shapeUrbanGrowthFabric` を経て、最後に `assignBuildingMassing` と外観を付ける。ここに二重の乱数割当を入れない。
- `fitMorphologyHousing` は敷地を再利用して階数を再設定する高速経路を持つ。再利用結果と最初から構築した結果が一致する必要がある。
- `documentFabricFingerprint`、局所infillキャッシュ、生成worker、JSON保存、共有リンクの再生が同じ入力を参照する必要がある。
- `populationPlan` の面積見積もりは現在、標準階と1階低い住宅を半分ずつ想定しているが、実生成は一律。この見積もりと実分布を揃える。
- 床の用途配列は `residentialFloorShare` の丸めから作っている。容量の床面積割合と完全一致しているわけではない。今回、用途配分式を同時変更しない。

## 4. 階数のモデル

### 4.1 正本と共通関数

新設候補: `src/city-editor/generators/buildingHeightPolicy.ts`。

1. `resolveHeightContext(document, lot)` が時代、プロファイル、地区種、親区画ID、固定/可変、上限を決める。
2. `sampleResidentialStoreys(context, unitKey)` が初期階数と増階の優先度を返す。人口生成と従来morphology経路が共用する。
3. `fitResidentialHeightCapacity(units, required, constraints)` が、必要な住宅だけ1階ずつ増やす。最終階数で容量を再計算する。
4. 確定階数を `BuildingLot.storeys` または仮想住宅の `storeys` に書く。massingは確定値をそのまま使う。

付属棟は住宅分布の対象外。shed/stable=1階を維持し、workshop/storeは現在のrole規則を維持する。ランドマーク、城、市庁舎、教会、専用の岸壁倉庫、BVモデルの高さは今回変更しない。混合用途のmain棟は住宅として扱い、店舗住宅・商人住宅の分布を使う。

### 4.2 初期分布の仮値

下表は後期中世〜大航海時代の欧州プロファイルに対する初期値。棟数の割合であり、人口や床面積の割合ではない。全都市へ同じ比率を強制するものではない。

| 地区種 | 1階 | 2階 | 3階 | 4階 | 5階 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 城外の住宅・低密度の外縁 | 35% | 65% | 0% | 0% | 0% |
| 一般住宅 | 10% | 60% | 25% | 5% | 0% |
| 市場・商業通りの住宅 | 0% | 30% | 55% | 15% | 0% |
| 有力商人・富裕層の住宅 | 0% | 30% | 50% | 20% | 0% |

初期・盛期中世は1階/2階/3階の一般住宅を30/60/10、市場・商人住宅を10/65/25とする仮案。既存上限3を守る。後期中世の上限は4、大航海時代の上限は5のまま、5階住宅は初期分布に入れず人口圧力下の候補に限る。城外の上限2も維持する。

地区種の優先順位は、城外 → 明示されたparcel archetype → 明示されたward → 一般住宅。大きな都市だから全域を商業地区にしない。主要街路への接道データが得られない棟には、道路種や入口方向を推測で与えず、ward/archetypeまでで決める。住宅文化の外観選択だけで国家の文化・時代を変えない。

### 4.3 通りのまとまりと安定性

- 乱数は共有ストリームを消費せず、`generationSeed / policyVersion / district-or-face ID / parcel ID / unitKey / purpose` をキーとする。配列順や他地区の棟数変更で既存棟を引き直さない。
- 基準は地区の分布。接道の情報がある場合は同じ街路側の連続区間、なければfaceをまとまりの単位とする。同じまとまりには共通の分位値を与える。
- 初期案は、住宅単位の独立キーで15%を個別抽選、85%をまとまりの抽選に従わせる。この混合なら各分布の期待値を保ちつつ、隣棟が似た高さになりやすい。85%は調整用の仮値。
- 隣接する普通住宅の階数差は1以内を目標とする。上限・固定棟・用途を優先し、隣接制約を全都市へ伝播させる反復平滑化はしない。街路をまたぐ棟や特殊建物には強制しない。
- 建物IDが人口処理で `population:...` に変わる前の、元lot/parcel IDを保持する。IDが無い場合はface IDと正規化した元区画形状からキーを作る。表示モード・生成後のグループ番号はキーに使わない。

## 5. 人口容量の調整

### 5.1 方針

低層化で必要な住宅面積を、街区内部の密度ではなく市街地コアのセル数で確保する。通常の敷地寸法、建物の並び、道路・空地の配分を維持する。新ポリシーでは低層化を理由に敷地を小区画化したり、FMGのdistrict occupancyを上げたりしない。

1. 通常の敷地割りで住宅を生成し、地区・用途別の初期階数を割り当てる。
2. 初期分布の実容量と必要住戸数を比較する。80 m²の代表住宅だけでは、実際の小住宅の端数処理や空地・非住宅面積を捉えられないため、生成後にも計測する。
3. 自動生成で不足する場合は `housingAreaScale` を増やしてコアの面積を予約し直す。セルの物理寸法は維持し、必要なら単独CEの自動フレームも広げる。校正は最大3回、1回の面積倍率は最大4、累積最大64。倍率は実容量不足率×1.08を仮値とする。
4. FMGは提供された町の窓内でコアを拡張する。手動フレーム、locked形状、手置きlandmark、輸入地形の外側には自動拡張しない。拡張候補で道路・橋等の検証が失敗した場合は元の有効な都市を残す。
5. 固定外周や拡張上限で残る不足には、必要な住宅だけ選択的に増階する。階数上限・城外予算は守る。残った人口は未配置として報告する。

内部の容量fitは増階候補も計算するが、都市を採用する前に必ず**増階前の初期分布の容量**で面積不足を検査する。増階して帳尻が合ったことだけを理由に、小さいコアを確定しない。

既存都市の「建物の高さ分布を更新」は、保存された街路・敷地・コアを保持する操作とする。コア面積を増やすには都市を再生成する。固定した都市では、人口制約により上限近くの住宅が多くなることを許容する。

### 5.2 既存fitとの接続

旧ポリシーの `insideStoreys` / `housingFit.storeys` と従来の3段階fitは維持する。新ポリシーではこれらを全棟の階数指定として使わず、分布と必要な増階だけを確定する。人口生成の新ポリシーは通常階・増階の2段階で、640→400 m²の小区画化段階を使わない。FMGの新ポリシーもdistrict occupancyを人口合わせで変えない。

階数の増分は実際の `dwellingCapacity` の差分を使う。端数処理で増分0の階を飛ばし、有効な次の増階を候補にする。安定キーと優先度で並べた有限の候補を使うため、必要住戸数が増えても既存棟の階数が下がらない。同じポリシーの再導出で、以前の乱数や増階結果にさらに補正を重ねない。

## 6. 表示モードと面積見積もり

### 6.1 各モードの従来の敷地割りを保つ

詳細表示は、従来の `populationFabricSource` が返す通常の住宅を**そのまま1棟として使う**。高さ分布のために粗い区画へ切り替えたり、矩形を平行線で細分割したりしない。40 m²未満の通常住宅も勝手に物置へ変えない。生成後のcoreの住宅polygon配列が、同じ文書の通常敷地生成と一致することを回帰テストで確認する。

集約表示は既存の粗区画・約80 m²の住宅換算・最大8棟の数え方を維持する。高さは元の区画単位で決める。同じ区画の内部を階数の違いで分割しない。描画グループの分割にも従来の基準階数を使い、高さの抽選だけではグループ形状を変えない。容量は各住宅の切捨て後の住戸数×実棟数で計算する。

詳細表示と集約表示は元から敷地の抽象度が異なる。両者の階数別棟数・容量を厳密一致させるために、詳細表示を粗区画へ変える案は撤回する。各モードについて、従来の形状保持・人口保存・割当が容量を超えないことを保証する。

### 6.2 計画段階の面積

`planPopulation` は初期分布の `E[dwellingCapacity(80, storeys, share)]` を使う。平均階数を容量式へ入れてから丸めない。一般住宅の分布を初期見積もりとし、生成後の実容量で `areaScale` を校正する。`targetAreaM2` と半径、予約するセル数へ反映し、セル内の敷地寸法を補正に使わない。

採用した `housingAreaScale` と `housingAreaPasses` を生成設定・文書・レシピ・共有に残す。人口計画の `areaScale` も保存・検証し、再生時に同じコア面積を使う。校正回数も保存し、再生のたびに上限をリセットして都市が広がり続けることを防ぐ。

## 7. 同じ階数の高さの差

階数分布を先に実装し、階高の差は別段階にする。欧州の対象時代に限り、住宅の固定3.2/2.9 mを基準に、建物ごとに0.95〜1.05倍の共通倍率、各階に追加±0.03 mを適用する仮案。地上階retail/craft等は現在の用途別階高を基準にする。これらの数値も史料校正済みではない。

同じ階の床は水平とし、倍率で地形の基礎高さ・接地・人口容量を変えない。`eaveHeightMeters = sum(floors.heightMeters)` を保ち、窓・木骨・屋根は既存のmassing経路に追従させる。屋根の最高点と軒高を区別して診断する。既存の屋根勾配・最大立上がり4 m・張り出し判定は維持する。屋根勾配のランダム化、屋根裏の住宅化、地下室の容量加算は別作業。

## 8. 保存・互換・操作

- `CityDocument` と生成設定に任意の `buildingHeightPolicy: { version: 1, profile: "european-medieval-v1" }` を追加する案。未指定はlegacy。未知version/profileはcodecで拒否する。
- 新規生成の対象時代・対応欧州文化では新ポリシーを選ぶ。単独CEで文化が不明の場合も初期対象の欧州既定として扱うが、非欧州の明示設定は自動適用しない。外観の地域選択と高さの適用結果を混同しないよう、使用中の高さプロファイルを表示する。
- 新規FMG descriptorからの生成には適用可能な既定を使う。古いJSON・古いCE共有レシピを読むときは未指定をlegacyのままにし、新規生成の既定で補完しない。
- 高さポリシーは文書と共有生成設定の両方へ渡し、両者が矛盾するレシピを拒否する。worker・生成段階表示・Undo/Redo・再生成も同じ値を使う。
- 新ポリシーの面積式を使う `PopulationPlan` に任意の `heightPolicyVersion: 1` を付ける。`planPopulation` / `validPopulationPlan` に対応版の見積もりを持たせ、未指定の既存planは旧式で検証する。文書側のポリシーとの整合も検査する。既存の `profileId: medieval-v1` の意味は変更しない。
- 階数は従来どおり導出し、全棟のmassingを保存しない。集約の報告・テンプレートは各表示モードの元区画と確定階数から再計算する。旧形式では階数が導出値なので、lotに値があることだけで手動指定と判断しない。
- lockedセルは現在の階数・容量を維持する。明示的な建物単位の高さ編集が将来入る場合は、生成値とは別に保存されたoverrideで識別する。
- 旧文書の更新はDocumentパネルの明示操作「建物の高さ分布を更新」で適用する案。人口の再配分と不足量を更新し、Undo可能な1操作にする。旧街路・敷地を保持したまま更新する場合は小区画化を行わず、不足を表示する。
- 新しい設定を `documentFabricFingerprint` と、影響を受ける局所キャッシュ/workerのキーに加える。色・カメラ・表示倍率の変更では階数を再抽選しない。

## 9. 診断・実装順・受入条件

### H0: 入力と互換

共通ポリシー、適用条件、codec、共有、worker、キャッシュ、面積式のversionを追加する。旧文書・旧レシピの導出階数と人口報告が変更前と一致することを確認する。対象外文化・時代も従来のままとする。

### H1: 詳細住宅と従来FMG経路

初期分布と選択的増階を接続する。配列順の入替、別地区編集、キャッシュ再利用で同じ住宅の結果が変わらないこと、上限・locked・外周予算・未配置報告を確認する。容量に余裕がある固定ケースで複数の階数が出ることを受入条件とし、少数棟や過密都市に混在を強制しない。

### H2: 人口生成と集約

detailed / cluster-10 / cluster-20の各モードで、従来の敷地・住宅形状を維持し、人口保存と容量上限を確認する。自動生成で低層化に合わせてコアのセル数が増えること、固定された形状は広げないこと、同じレシピから人口報告を再現できることを確認する。

### H3: 階高・描画確認

階高の微差を追加し、massingと3D・近景窓・木骨・ピッキングの高さの整合、斜面での水平床と接地を確認する。2Dは従来の平面形状を使い、高さ変更で道路・橋の再配置を起こさない。

### H4: 少数の代表ケースで校正

単独CEの余裕ある町、Standard人口設定のFMG連携都市、固定外周の過密都市を各1例。対象時代・文化・seed・人口・外周・policy versionを記録し、変更前後の同じ視点の3D画像を比較する。城外を持つケースと斜面をこの3例内に含める。多数seedの全件試験は行わない。

観測項目:

- core/outskirts別、用途別の1〜5階の棟数と割合。実棟数と描画グループ数を分ける。
- 軒高と屋根最高点の分位値、街路側の隣棟階数差、増階した実棟数、上限到達率。
- 変更前後の容量、割当、未配置人口。人口保存 `assigned + unplaced = target` と各住宅 `assigned <= capacity`。
- 生成時間、fit回数、表示グループ数、3D triangles/buffer bytes。高さ処理単体と都市生成全体を分けて測る。仮の性能予算は高さ計算10 ms/1,000仮想住宅、都市生成時間+15%以内とし、実測前に達成を主張しない。

関連テストの実装時候補は `src/city-editor/generators/` の `urbanGrowth.test.ts`、`population.test.ts`、`populationHousingFit.test.ts`、`buildingMassing.test.ts` と、`src/city-editor/services/io/` の `documentCodec.test.ts`、`incomingCity.test.ts`。新規policyのテストは分布の小数比率そのものの固定ではなく、安定キー・増階の単調性・上限・容量保存を中心にする。近景描画変更時だけ `src/city3d/three/buildingDetails.test.ts` と `src/city3d/core/massingGeometry.test.ts` を追加する。関連成功後の全件拡大はしない。

## 11. 実装・修正記録（2026-10-26）

### 11.1 変更と初版からの修正

`buildingHeightPolicy.ts` に時代・文化の適用条件、地区別分布、安定キー、容量差分による選択的増階を実装した。住宅容量の算式は `residentialCapacityFormula.ts` に分離し、既存APIから再exportする。描画専用の別の階数は作らない。階高の微差は `buildingMassing.ts` で付け、水平な床・屋根・近景の窓・木骨が確定したmassingを共有する。

初版は、表示間の数値一致を優先して詳細表示にも粗い区画を使い、階数別に再分割していた。住宅が細長くなること、元の小住宅を物置へ変えて容量が減ることを確認し、撤回した。§5〜6を修正し、詳細表示では通常の住宅polygonを保持する。集約表示にも階数差による分割を加えない。新ポリシーの人口fitで小区画化を止め、FMGの人口fitでも充填率を上げない。

`generation/heightArea.ts` で、実際の住宅と初期分布から面積不足を検査する。自動生成の不足はコア面積・セル数で補い、単独CEのフレームは必要な場合に広げる。輸入地形や固定形状の制約を越える拡張は行わない。選ばれた面積倍率と校正回数は文書・レシピ・共有に保存する。

旧JSON・旧共有は高さポリシー未指定のまま従来表示にする。Documentパネルに現在の高さプロファイルと「建物の高さ分布を更新」を追加した。更新は既存の街路・住宅の敷地・農地を保持し、Undo/Redoに対応する。コアを広げる場合は都市の再生成を使う。
