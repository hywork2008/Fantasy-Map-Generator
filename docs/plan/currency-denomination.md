# 統一通貨(🟡)の金貨・銀貨・銅貨デノミネーション 設計

## 状態

**フェーズ1実装済み**。内部の金額計算は銀貨基準のまま保持し、`formatPrice()` が金貨・銀貨・銅貨の内訳を表示する。

- 既定レートは **金貨1枚 = 銀貨12枚**、**銀貨1枚 = 銅貨12枚**。
- Options → Simulation Settings → Currency denominations で両方のレートを整数として変更できる。ロックしたレートは他のOptions設定と同様に再読み込み後も復元される。
- `src/utils/currency.ts` が既定値と入力値の検証を、`src/utils/unitUtils.ts` が表示用の `toCoinage()` / `formatCoinage()` を担う。

## 背景・目的

現在この世界の通貨は🟡という単一の抽象単位のみで、`formatPrice()`(`src/utils/unitUtils.ts:105-106`)が `🟡 ${rn(value, 2)}` という小数2桁表示を全経済UIで共通して行っている。[cost-of-living.md](../analytics/cost-of-living.md)で確認した通り、農民一人の年間最低生存費は約0.3〜0.4🟡という値になり、これは「一年分の生活費」としては小さすぎる桁ではないものの、**「住民が普段の買い物で実際に手渡す硬貨」としては小数の抽象単位のままでは物理的なリアリティに欠ける**という指摘がユーザーから出た。

ユーザー指定の要件:

1. 金貨・銀貨の交換レートは史実の金銀比価を参考に、**銀貨11〜13枚 = 金貨1枚**程度をプロンプト用の仮レートとする。
2. 銅貨も用意しないと、現行の統一通貨では住民の日常的な少額決済(パンや雑貨など)を表現できない。
3. 地図上の全ての国は同じ通貨を使うと仮定する(地域ごとの為替・通貨制度の違いは設計しない)。

## 用語衝突についての注意

`src/extensions/economy/generators/goods-generator.ts` には既に **Gold Ingot / Silver Ingot / Copper Ingot(および Gold Ore 等)という交易品(Goods)** が定義されている。これらは🟡通貨で売買される**地金**であり、通貨そのものではない(`goods-generator.ts:1055` に「これは硬貨の物理的供給を二重に表現するものではない」という既存コメントがあり、地金と通貨が意図的に分離されていることが確認できる)。

新しい通貨単位を「Gold」「Silver」「Copper」とだけ呼ぶと、既存の交易品(Gold Ingot 等)と紛らわしい。本設計では通貨側を **Gold Piece / Silver Piece / Copper Piece**(略称 GP/SP/CP)と明確に呼び分け、UI文言でも「〜貨」ではなく「金貨/銀貨/銅貨」(交易品側は「金インゴット」等)で表記を分離する。

## 設計方針: 表示レイヤーのみのデノミネーション(推奨)

「デノミネーション」という言葉から連想される作業は、本来なら国庫・所持金・商品価格などあらゆる金額の**内部保存値そのものを新しい単位系に置き換える**大規模改修に見える。しかし実際に解決すべき課題は「プレイヤーへの表示が硬貨として自然に読めること」であり、内部計算(500件超の既存テスト、`allocateTreasury`、`Taxes.collectTaxes`、`characterStipends.ts` 等の財政ロジック一式)を変更する必要はない。

そこで本設計は次の2フェーズに分割し、**フェーズ1のみを実装対象として推奨**する。

### フェーズ1(推奨・本設計のスコープ): 表示レイヤーの硬貨内訳化

- 内部的に保存されている🟡の数値(`Burg.treasury`, `State.treasury`, `Character.wealth`, `MarketTreasury.balance`, `GuildKnowledgeStock.treasury`, 各Goodの`value`)は**一切変更しない**。
- 現行の🟡単位を、そのまま **「銀貨(Silver Piece)」** として再定義する。つまり `1 old🟡 = 1 SP` — 既存の全ての数値・計算式・テストの期待値はこの1行だけで意味づけが変わり、コード変更が不要になる。
- 金貨・銅貨は、銀貨からの**表示専用の換算(閾値ごとの繰り上げ表示)**として導出する。実際に金庫や所持金の内部表現が「金貨N枚+銀貨N枚+銅貨N枚」の3フィールドに分かれるわけではない。
- リスクが最小(既存のバランス調整・527件のテスト・生成ロジックに触れない)であり、ユーザーの要件「日常決済を表現したい」は銅貨への内訳表示で満たせる。

### フェーズ2(将来・非推奨・本設計の対象外): 内部単位そのものの再スケール

内部保存値自体を銅貨単位の整数に置き換える(例: `Grain.value` や `STARTING_BURG_TREASURY_PER_POPULATION` 等30以上の定数と、その定数を参照する既存テストの期待値をすべて銅貨スケールに書き換える)案。フェーズ1で表示上の課題は解決できるため、追加のゲームプレイ上の恩恵(例えば硬貨単位でのインベントリ管理や、硬貨の重さ・盗難といった新規メカニクス)を具体的に必要とする段になるまでは着手しない。

## 表示アルゴリズム

`src/utils/unitUtils.ts` に `formatPrice()` と並べて新しい `formatCoinage()` を追加し、既存の `formatPrice()` 呼び出し32箇所(後述)を段階的に置き換える。

```ts
export interface Coinage {
  gold: number;
  silver: number;
  copper: number;
}

export function toCoinage(silverAmount: number): Coinage {
  const totalCopper = Math.max(0, Math.round(silverAmount * SILVER_TO_COPPER_RATE));
  const gold = Math.floor(totalCopper / GOLD_TO_COPPER_RATE);
  const remainder = totalCopper % GOLD_TO_COPPER_RATE;
  const silver = Math.floor(remainder / SILVER_TO_COPPER_RATE);
  const copper = remainder % SILVER_TO_COPPER_RATE;
  return { gold, silver, copper };
}

export function formatCoinage(silverAmount: number): string {
  const { gold, silver, copper } = toCoinage(silverAmount);
  const parts: string[] = [];
  if (gold > 0) parts.push(`🟡${gold}`);
  if (silver > 0 || parts.length === 0) parts.push(`⚪${silver}`);
  if (copper > 0) parts.push(`🟤${copper}`);
  return parts.join(" ");
}
```

- アイコン案: 金貨 🟡(既存流用、変更不要)、銀貨 ⚪(白丸)、銅貨 🟤(茶丸)。
- ゼロ額(`silver=0, gold=0, copper=0`)の扱い、負の値(現状マイナス金額があり得るか要確認)、1銀貨未満の端数(現行では0.01〜0.99の小数🟡が存在しうる — `Math.round(silverAmount * 12)`で四捨五入されるため、0.5銀貨未満は0銅貨に切り捨てられる)は、実装時にユニットテストで境界値を固定する。
- `GoodsEditorDialog.tsx:299` の生の `🟡 {good.basePrice}` 直書き箇所は `formatPrice()`/`formatCoinage()` を経由していない唯一の抜け穴として、移行時に必ず同時に直す。

## 少額決済(外食1食など)についての追加検討

上記のサニティチェックは**年間の集計値**で見ており、実際に硬貨を手渡す**1回分の取引**(例: 酒場での1食)を検証すると別の問題が生じることが判明した。

```text
GROSS_FOOD_NEED = 0.43(1人が1年に必要な食料、抽象単位)
1日あたり = 0.43 / 365.2425 ≈ 0.001178 (foodProduction.ts:184 の実装と同じ割り方)
1日分の生穀物コスト(小売1🟡/wain) ≈ 0.001178 🟡/日
→ 本設計のレート(1 old🟡=1銀貨、1銀貨=12銅貨)では ≈ 0.014銅貨/日
3食に分けると1食 ≈ 0.005銅貨 — 銅貨1枚の1%にも届かない
```

**この問題はレート調整では解決しない。** 1日分の生穀物コストを銅貨1枚ちょうどに合わせようとすると、逆算で `1 old🟡 ≈ 金貨5.9枚相当` まで基準単位を引き上げる必要があるが、そうすると連動して他の数値が破綻する。

| 項目 | 現行の新表示(本設計採用レート) | 「1食=銅貨1枚」に合わせた場合 |
| --- | --- | --- |
| 商品価格の最高値(70 old🟡) | 🟡5 ⚪10 🟤0 | 約413金貨相当 |
| 中央官職の所持金の例(350 old🟡) | 🟡29 ⚪2 🟤0 | 約2065金貨相当 |

「1食」と「国庫・高額商品」の間には現行データ上5〜6桁(10万倍以上)の開きがあり、単一の線形な交換レートでは両立できない。原因はレートの選び方ではなく、`GROSS_FOOD_NEED`が「年間の生存必要量」という粗い集計値であり、そもそも外食1食分の価格として使うために設計された定数ではないことにある。

### 採用する解決策: 独立したフレーバー値として定義する

[cost-of-living.md](../analytics/cost-of-living.md)の住宅価格と同じ扱いとし、**「酒場での質素な1食」を`GROSS_FOOD_NEED`から逆算せず、独立したフレーバー値として直接定義する**。

- 生穀物(farmgate価格で農家が売る原材料)が実質ゼロに近いのは経済的に自然で、実際の食堂・酒場の1食には調理・接客・店の取り分といった付加価値が乗る。現実の経済でも「小麦の原価」と「レストランの一食」には数十〜数百倍の価格差があるのが普通であり、「原材料はほぼ0銅貨なのに1食は数銅貨」という開きはむしろ整合的。
- 目安値: **酒場での質素な1食 ≈ 銅貨1〜3枚**。既存の財政ロジック(`allocateTreasury`, `characterStipends.ts`等)には一切接続しない、UI/ドキュメント上のフレーバー値として扱う。
- 参考として、[史実の参考レート](#史実の参考レート)節のビザンツ帝国の例(銀:銅=24:1)のように、`SILVER_TO_COPPER_RATE`をより大きくして銅貨の刻みを細かくする調整も可能だが、それだけでは上記の5〜6桁の開きを埋められないため、根本解決にはならない(粒度をわずかに改善する程度の副次的な調整に留まる)。

### 史実による裏付け(外食産業の原価率・決済通貨)

ユーザーからの追加質問「中世外食産業の原価率や支払いに使われた通貨の史料は存在するか」を調査した結果を記録する。

- **原価率(原材料費に対する販売価格の倍率)を直接示す史料は見つからなかった**。中世の料理店・酒場の帳簿がほとんど現存しないため、「原材料費の何倍で売っていたか」を裏付ける定量的な一次史料は乏しい。一方で、**パンと麦芽酒(エール)については実在する**: イングランドの Assize of Bread and Ale(パンとエールの法、13世紀・ヘンリー3世期に遡る)は、小麦価格が変動しても**パン1個の価格は固定**し、代わりに**パンの重量を小麦相場に応じて改定する**という規制式を定めていた(小麦1クォーターの価格が6ペンス上がるごとに、farthing loaf(1/4ペニーのパン)の重量を規定量ずつ減らす)。エールについても小麦・大麦・オーツ麦の相場に応じて「都市部ではエール1ペニーにつき2ガロン、地方では3ガロン」という換算表が定められていた。これは本設計が既に採用している `FARMGATE_PRICE_SHARE`(farmgate価格=小売の80%)のような「原材料相場→小売価格」の**規制された変換式**の実例であり、根拠のある史実的precedentになる。ただしこれは統治側が定めた**公定価格**であり、酒場・料理店の**自由市場での原価率**とは別物である点に注意。
- **外食(料理店・酒場)の実際の支払い額は具体的な史料が残っている**。12世紀のロンドンを記録したウィリアム・フィッツスティーヴン(FitzStephen)は、テムズ河畔に一日中営業する「cookshop(惣菜屋)」があり、焼き肉・揚げ物・煮物・大小の魚・貧者向けの安い肉から富裕層向けの高級な肉まで扱っていたと記している。1378年のロンドンの価格規制記録には具体的な金額が残っており、**最上級の丸焼き豚 8ペンス、丸焼きガチョウ 7ペンス、丸焼き去勢鶏 6ペンス、卵10個で1ペニー**といった価格が確認できる(1350年制定の法では、客が自分の肉を持ち込んだ場合の調理代を1ペニー以内に制限)。つまり史実でも外食1回分の支払いは「金貨」ではなく「ペニー(銀貨)またはその端数」で行われていたことが裏付けられる。
- **決済通貨は最小額面の銀貨、それでも足りない場合は物理的に硬貨を切って端数を作っていた**。中世イングランドの貨幣体系は 1ポンド=20シリング、1シリング=12ペンス、1ペニー=4ファージング。エドワード1世が1279年にハーフペニー・ファージングを正式な硬貨として鋳造するまで、両替商は**ペニー銀貨そのものを十字の刻印に沿って半分・4分の1に物理的に切断して**端数決済用の小額硬貨を作っていた(1279年に禁止されたが、実際にはその後も慣行として続いた)。これは本設計の「[少額決済(外食1食など)についての追加検討](#少額決済外食1食などについての追加検討)」で見つけた「1食分の価格が最小額面の硬貨よりさらに小さくなる」という粒度問題そのものへの、史実側からの直接的な解決precedentになる — **史実は交換レートの見直しではなく、同じ金属(銀)のままより小さい額面の硬貨を追加(または物理的に切断)することで対処していた**。本設計が銅貨(CP)を独立した最小額面として新設する方針は、この史実の解決パターンと整合する。

まとめると、「原価率」を裏付ける定量史料は乏しいが、「外食の支払いはペニー/ファージング単位の小額決済として実在した」「その決済ニーズには銀貨の細分化・銅貨相当の追加額面で対応していた」という2点は史実として確認できた。前者は本セクションの「採用する解決策」(独立したフレーバー値として1食の価格を定義する)の妥当性を裏付け、後者は本設計が銅貨(CP)を新設する方針そのものを裏付ける。

## 個人視点(プレイヤーキャラクター)の価格スケール問題(新規確認・優先度上昇)

2026-08-01 に実装された player character travel(`832230f0`、burgTravelHere ボタン)により、**「個人視点での通貨単位」は本ドキュメント冒頭で位置づけていたような将来的な先行投資ではなく、既に目の前の問題になっている**ことが確認された。

- **トリガー**: `src/extensions/nobility/ui/components/PlayerCharacterPanel.tsx:85` が `formatPrice(summary.wealth)` でプレイヤーキャラクター個人の所持金を常時表示する。burg間移動という「一個人としてこの世界を動き回る」体験が実装されたことで、この所持金表示は単なる数値ではなく、**プレイヤーが実際に「これで何が買えるか」を意識する対象**になった。これまでのAboutタブのフレーバーテキスト(読み物)とは異なり、実際のゲームプレイUI上の体験である。
- **確認された具体的な症状1: Boots(耐久財)の価格が個人視点では法外**
  `src/extensions/economy/generators/goods-generator.ts:911-919` — Boots は `value: 7`、`unit: "pair"`。[cost-of-living.md](../analytics/cost-of-living.md)で算出した農民一人の年間最低生存費(約0.3〜0.4🟡)と比較すると、**ブーツ1足で生存費約20年分**に相当する。本設計のフェーズ1レート(1 old🟡=1銀貨)をそのまま適用しても「ブーツ1足=銀貨7枚」であり、桁自体は破綻しないが、農民一人の年間生活費(銀貨0.3〜0.4枚)と並べると依然として非現実的に高価に見える。
  → **これは表示単位(通貨のデノミネーション)の問題ではない。** Goods の `value` はそもそもburg間卸売貿易(`caravans.ts`のロット単位取引)のバランス調整で決まった値であり、個人の購買力を基準に調整されたことが一度もない。フェーズ1(表示レイヤーのみの変更)では解決せず、**Goods の `value` 自体を個人の購買力スケールに合わせて見直す、通貨デノミとは別軸のゲームバランス調査**が必要になる(本ドキュメントのスコープ外、別途の調査・設計が必要)。
- **確認された具体的な症状2: Trade で運ばれるキャラバンの Units が1未満の端数になる**
  `src/extensions/economy/generators/markets-generator.ts:251-252`(`affordableUnits = budget / price` → `units = rn(Math.min(requestedUnits, stock, affordableUnits), 4)`)や `src/extensions/economy/generators/caravans.ts:299`(`units: rn(deal.units, 2)`)で、キャラバンが運ぶ量が例えば `0.5` のような端数になり得ることをコードで確認した。この値は `MarketTradeOpportunitiesDialog.tsx` の "Units" 列、`TradeAnimationDialog.tsx` の "Units" 列にそのまま表示される。
  → Boots(`unit: "pair"`)のような**本来不可分な個数単位**の商品で「0.5足」のような表示になるのは違和感が強い。これは通貨のデノミネーションとは無関係な、**Units表示側の丸め・フォーマット方針の問題**(小数点以下を切り捨てて整数個数のみ表示する、あるいは不可分な `unit` の商品は端数取引自体を禁止する、等)であり、本ドキュメントのスコープには含まれないが、個人視点での「取引しやすさ」を扱う以上、関連課題として記録しておく。

この2点は、本ドキュメントの「[少額決済(外食1食など)についての追加検討](#少額決済外食1食などについての追加検討)」で扱った**下振れ側(1食が硬貨より小さすぎる)**の問題に対して、**上振れ側(耐久財が個人の所持金より大きすぎる)**および**端数取引(不可分な商品が分数個で取引される)**という、性質の異なる2つの追加問題である。いずれもフェーズ1の「🟡→銀貨への表示置き換え」だけでは解決しないため、別タスクとして切り出す必要がある。

## 未確定・要調整事項

1. **アイコン選定**: 🟡(金)は既存流用で問題ないが、⚪(銀)/🟤(銅)が視認性・他UI要素との衝突がないか実装時に確認する。
2. **1銀貨未満の端数の丸め規則**: `Math.round()` を採用し、境界値の挙動をユニットテストで固定した。国庫のような大きい金額では影響が無視できるが、少額の所持金表示には影響する。
3. **フェーズ2(内部単位の再スケール)着手条件**: 硬貨の重量・盗難・インベントリ枠といった、内部保存値が整数銅貨単位であることを前提とする新規メカニクスが具体的に計画されるまでは着手しない。
4. **「1食」フレーバー値の具体的な数字**: 「[少額決済(外食1食など)についての追加検討](#少額決済外食1食などについての追加検討)」で提案した銅貨1〜3枚は暫定値。宿屋・酒場サービス(食事以外に宿泊費等)を将来追加する場合、そのレンジ内でのバリエーション付けが必要になる。
5. **銅貨未満の端数決済の扱い**: 史実では銀貨(ペニー)を物理的に切断してさらに細かい端数を作っていた(farthing = 1/4ペニー)。本設計の銅貨(CP)がゲーム内での最小額面だが、将来「銅貨未満」の端数決済(例: 銅貨の1/4)を表現する必要が出た場合、史実に倣い銅貨をさらに分割する額面(例: ファージング相当)を追加するか、単純に切り捨てるかは未検討。
6. **[個人視点の価格スケール問題](#個人視点プレイヤーキャラクターの価格スケール問題新規確認優先度上昇)で見つかった Goods の `value`・Units端数の問題**: Boots(価値7)のような耐久財が農民の年間生存費の約20年分になる問題、およびTradeキャラバンのUnitsが0.5のような端数になる問題は、いずれも本ドキュメント(通貨の表示レイヤーのデノミ)のスコープ外。別文書 [goods-unit-scale.md](goods-unit-scale.md) として切り出し、「1 unit は実際何個分か」というフレーバー値の追加(内部の`value`・取引量計算は不変)による解決案を設計した。その後の検証で Wine(barrel)にも同様のフレーバー値(酒場での1杯価格)が必要なこと、および Bread(loaf)は体積面の制約からフレーバーだけでは解決できず `Good.value` 自体の変更が必要な唯一の例外であることが判明した(goods-unit-scale.md 参照)。Goods の `value` 自体の再調整が必要になる他のケース(livestock の `head` 等)は依然として本ドキュメント・goods-unit-scale.md いずれのスコープ外であり、別途のゲームバランス調査が必要。
