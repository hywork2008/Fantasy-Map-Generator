# CEの道路網の重複・孤立・折り返しを防ぐ設計

- 作成日: 2026-10-19
- 状態: 初期修正を実装。適用範囲と残る拡張は§8参照。
- 調査対象: revision `a2d32c386` のCE。既定の `mesh-first` を中心に、`skeleton-first` と共通の道路消費側も確認。CGは対象外。
- 関連: [Skeleton-first生成](../city-editor/plan/skeleton-first-generation.md)、[橋の斜交規約](./bridge-skew-policy.md)

## 1. 推奨方針

**道路を一本ずつ独立に完成させて追加する方式から、接続済みの道路網へ必要な区間だけ足す方式へ移す。物理的な道路区間と、その上を通る路線を分ける。道路網を確定してからセルを平滑化する。**

狙うのは道路本数の最少化ではない。門・市場・橋・城・居住街区へのアクセスを満たし、必要な周回路や抜け道を残しながら、新設延長と不要な分岐を減らす。短い道や袋小路にも用途があるため、長さだけで削除しない。

| 症状 | 対応する仕組み |
| --- | --- |
| 複数のroadが同じedgeに重なる | 向きに依存しないedge占有表で物理区間を一元化し、路線はその区間を参照する |
| 長い道路の途中にごく短いroadが重なる | 候補経路の全長ではなく、新設edgeと新しく満たす需要だけを評価する |
| 街中で他のroadにつながらない | 接続済み成分を探索先にして伸ばし、必須地点の到達性を生成の不変条件にする |
| `A-B-C-B-D` と折り返す | 補助経由点を必須通過点にせず、接続要求ごとの単純経路を求める。残存する閉路は平滑化前に検査する |

## 2. 現行コードで確認できたこと

### 2.1 個々の経路の重複判定と道路網の重複判定が異なる

[`streets.ts`](../../src/city-editor/generators/streets.ts) の `buildStreets` は、門→広場に加えて、門間の軸、並行する道、門間の環状路を個別に探索する。

- `sameCorridor` は両端点の近さを比較する。端点の異なる道路が途中を共有する場合や、長い経路に短い経路が包含される場合を判定していない。
- `pathFollowsExisting` は並行路候補に対する近接点数の比率による判定で、全候補に共通するedge占有判定ではない。
- `buildArteries` は既に無向edgeの和集合を作り、交差点・終端で道を分解する。この考え方は再利用できる。ただし返す `arteries` と `vertexShifts` に対する整理であり、最終的な全road groupの一意化にはなっていない。
- [`generateCity.ts`](../../src/city-editor/generators/generation/generateCity.ts) は門→中心の `star` と追加道路 `extras` を構成し、assemblyで道路を改めて探索する。事前の座標ベースの重複判定を通っても、最終メッシュでは同じedgeへ集約され得る。

[`completeRoadRouter.ts`](../../src/city-editor/generators/generation/routing/completeRoadRouter.ts) は水面・壁・堀・城などを避けて経路を求めるが、他の候補が採用済みの道路網を入力に取らない。各道路の探索は独立している。

[`appendGeneratedGroup`](../../src/city-editor/generators/generation/assembly/generatedFeatures.ts) には城壁の重複区間を分割する処理がある一方、roadはそのまま追加する。橋の進入路の区間を `riverRoad` に組み込む処理もあるため、全共有を異常とみなすことはできない。**路線が共有すること自体と、物理的に二重作成・二重描画することを分けて扱う必要がある。**

### 2.2 経由点ごとの最短経路をつなぐと、一つの道路が折り返せる

`completeRoadRouter` はpolylineの補助点をサンプリングしてメッシュ頂点へスナップし、`stitch` で隣り合う経由点間のA*結果を連結する。連続する同一経由点は省くが、連結済み経路に出現した頂点・edgeへの戻りは除去していない。

例えば、候補グラフが次の木で、計画線の経由点が `A, C, D` の場合:

```text
A ---- B ---- D
       |
       C
```

`A→C` の結果 `A-B-C` と `C→D` の結果 `C-B-D` は、それぞれ単純経路でも、連結後は `A-B-C-B-D` になる。単にA*の探索中に直前のedgeへの復帰を禁止しても、探索呼出をまたぐ復帰は解消しない。

[`finishCityGeometry.ts`](../../src/city-editor/generators/finishCityGeometry.ts) は道路edgeを `Set` に集め、次数2の頂点を中心に座標を移動する。`segments` の並びを変更しないので、この頂点列は平滑化後も残る。選択道路の `smoothFeatureGroup` も経路順序を修正しない。したがって、同一頂点IDへ戻る折り返しと、座標だけが近接する幾何学的な折れ曲がりは、別々に診断する。

### 2.3 局所的な接続検査だけでは、道路網全体の到達性を保証しない

[`finalize.ts`](../../src/city-editor/generators/generation/assembly/finalize.ts) などには、門の道路接続、門でない壁頂点への終端の除去、郊外街区の到達判定がある。`generateCity.ts` は外部道路数とFMG由来道路の対応なども検査する。

ただし、道路が門を横切ること、各group内の連続性、外部道路の本数を確認しても、道路網全体が必須の中心・施設につながっているとは限らない。[`mesh.validate`](../../src/city-editor/generators/mesh.ts) はgroup内の隣接区間の連続性を確認するが、道路の頂点再訪、group間の重複、全道路成分の用途までは検査しない。

細街路は [`localInfill.ts`](../../src/city-editor/generators/localInfill.ts) と [`streetGrowth.ts`](../../src/city-editor/generators/streetGrowth.ts) にも存在する。前者には実際の幹道沿いを根とするfaceの到達探索がある。今回の幹道整理はこの接続関係を利用し、細街路まで全て幹道へ昇格させない。

### 2.4 小規模な実測と限界

一時的な診断用Vitestで以下を確認し、診断用ファイルは調査後に削除した。

| 対象 | 結果 |
| --- | --- |
| 上記4頂点・3edgeの分岐グラフに `A,C,D` を入力 | router出力は `A-B-C-B-D`。`finishCityGeometry` 後も同じ頂点列 |
| 既存 `roadEndpoints.test.ts` の都市seed `1o564jj`、グリッドseed `1wnd0y0`、small/evolution、15 patches、organic | road groupは20、使われる一意edgeは97、そのうち49 edgeを複数groupが共有 |
| 同都市の共有例 | `e381` を `gc:road-4`, `gc:road-8`, `gc:road-17`, `gc:road-18` が使用 |
| 同都市の頂点再訪・成分 | 各road内の頂点再訪は0。メッシュroadの和集合は90頂点の1成分 |
| 同都市の1edgeだけの道 | `gc:castle-0:approach`。城への接続なので、短いことだけを理由に削除できない例 |

都市の設定の詳細は既存の [`roadEndpoints.test.ts`](../../src/city-editor/generators/roadEndpoints.test.ts) にある。共有49 edgeはedge数による集計で、道路延長の49/97が重複するという意味ではない。また、共有を除去しても地上の道路長が必ず減るわけではない。

この1都市では孤立と折り返しを再現していない。4頂点モデルは現行routerが折り返しを出せる証拠であり、ユーザーが見た都市の原因箇所を特定したものではない。長区間内の短い重複道・孤立道路の具体例は、実装時に該当文書または再現seedで工程別に追加確認する。多数seedの検証やUIでの見た目の確認は今回実施していない。

## 3. 道路区間と路線を分ける

### 3.1 生成中の共通モデル

まず、保存形式を変えない生成中の索引として次を導入する。

| 要素 | 内容 |
| --- | --- |
| `RoadDemand` | 必須/任意、始点、到達先の集合、用途、優先度、由来、必須portal、補助corridor |
| `RoadEdgeUse` | `edgeId`、利用する路線ID集合、物理的な幅・種類、固定区間か、新設区間か |
| `RoadNetwork` | edge占有表、頂点隣接、接続成分、必須地点の充足状態 |
| `RoadRoute` | 利用区間の順序と方向、FMGのsource、門、終点の用途。複数路線が同じ区間を参照できる |

同じメッシュ内では物理区間のキーを `edgeId` とし、`forward` は経路の通行方向としてのみ保持する。異なるedge IDで同じ幾何区間が存在する場合や、メッシュ外の道路は、交点・重なり端で分割してから別途対応付ける。座標を粗く丸めて近い道を全て結合すると、壁の両側や対岸がつながるため禁止する。

門・橋詰・渡し場・広場への入口は明示的な接続点とする。広場に複数の道路が別々の入口で着く場合は、歩行可能な広場内の移動を表す意味上の接続を置ける。ただし壁・水面・建物で分断されていないことを確認し、その接続を道路として描画しない。各入口を勝手に同一のメッシュ頂点へ押し込まない。

### 3.2 保存・編集への反映は段階的に行う

現行 `EdgeFeatureGroup.sourceRoad` は一つの由来しか持てず、FMG由来道路の一対一対応検査、IDのprefix、配列順序、`beyond`、選択・編集などに依存がある。共有edgeだけを既存groupから削除すると経路が途切れ、groupを単純結合すると由来や門との対応が失われる。

初期段階は既存groupを論理的な路線として維持し、共通の派生 `RoadNetwork` から物理区間を一度だけ消費する。これは保存データ中の参照重複を残す互換段階であり、group数が最少になる段階ではない。SVG、3Dの `collectTownRoads`、幅・clearanceの計算、編集時のヒット判定で同じ区間表を使う。共有区間のクリックは所属路線一覧へ解決する。

最終的に保存形式を整理する場合は、物理道路groupを交差点・属性境界で分割し、別の路線表から参照する。source/beyond/門との対応は路線側へ移す。文書version、旧文書の読込、再保存、既存ID参照の移行を一つの変更単位とする。単なる重複除去のために、先に保存形式の全面変更を必須にはしない。

手動道路とlocked道路は固定の入力とする。自動道路はその接続を利用できるが、手動経路の削除・付け替え・幅変更はしない。固定道路同士に不整合があれば診断し、自動的に片方を消さない。

## 4. 推奨アルゴリズム

### 4.1 制約を確定し、需要を登録する

1. 水面、壁、堀、城、寺院、広場などの通行制約と既存の固定道路を登録する。
2. FMGからの入口、実在する門、橋詰・渡し場、市場・広場、城の入口などを必須需要にする。最寄り頂点へのスナップにも同じ通行制約を適用する。
3. 住宅街区へのアクセス、幹道の軸、環状路は用途別の需要として登録する。既存layoutの形状意図はcorridorや周回路の需要として保つ。
4. 川の両岸、壁の内外など、候補グラフ自体の到達可能な領域を分類する。合法な橋・門などがない領域間の接続は探索の成功扱いにしない。

市場がない都市では、生成済みの都市中心または最優先の幹道を根にする。全域を無条件で一成分にするのではなく、交通手段ごとに、どの入口・中心につながるべきかを定義する。離島や渡し船の対岸の道を、道路edgeだけではつながらないという理由で消さない。

### 4.2 骨格は「最短で接続できる需要」から道路網へ足す

固定道路と中心への入口を初期ネットワーク `N` とする。未接続の必須需要から `N` に到達する合法な経路を求め、優先度が同じなら追加コストの最小なものを採用する。採用するたびにedge占有・到達性・候補評価を更新する。

必須の通過門や認定済み橋などがある需要は、単に最寄り道路へつながった時点で完了としない。指定portalを順序どおり通り、指定中心への接続を満たす必要がある。外部道路は対応する門・入口を終点とする独立の要求を保ち、別の門へ付け替えない。

```text
N = fixed roads + roots
while required demands remain:
    candidates = legal connections from pending demands to N
    if candidates is empty: report unmet required demands
    P = best candidate by priority, incremental cost, stable ID
    validate required portals and normalize P
    register route references on every edge of P
    add only edges(P) minus edges(N) as physical roads
    update N and the satisfied demands
```

初期に根が一つだけの場合も空集合になる場合も明示的に扱う。空なら最優先需要の両端間に一本引いて開始する。この方式は段階的な近似で、道路総延長の大域的最小を保証しない。全端点間の経路を先に大量生成する方式より、現行の生成段階へ組み込みやすい。

### 4.3 探索コストは既存道路の再利用と新設を分ける

経路 `P` の評価を概念的に次とする。係数は未較正で、今回固定しない。

```text
cost(P) = sum(buildCost(e) * isNew(e) + travelWeight * length(e))
          + turnPenalty(P) + corridorDeviation(P)
```

- `buildCost` は新設延長と施工難度を表す。既存edgeでは0になるが、通行距離の項は正のままにする。
- 道路網への接続を短くするだけで、門間の移動が極端な遠回りになることは許さない。需要ごとに合法な最短距離に対する迂回率も評価する。
- 禁止条件は大きな有限penaltyではなく通行不可とする。便利さが禁止条件を打ち消してはならない。
- 曲がりのpenaltyが前のedgeに依存する場合、探索状態を `(vertexId, incomingEdgeId)` にする。頂点だけの距離表へ角度penaltyを足すと、到着方向の違いを正しく比較できない。

**既存の `edgeGraph.aStar` へ単純な「既存道路なら0.2倍」を渡さない。** 同関数の直線距離heuristicはedge costが物理距離以上であることを前提にしている。新routerはまずheuristic 0のDijkstraとし、目標集合と方向状態に対応させる。高速化する場合だけ、全辺コストの下限に合うheuristicを導入する。FMG・河川などの共有A*をこの目的で無断変更しない。

### 4.4 補助経由点を強制しない。折り返しは用途に応じて処理する

一般の街路の計画polylineは、端点と形状の好みを表す。サンプリングした補助点を全て必須通過点にせず、corridorからの偏差で誘導する。門・橋・固定道路の接続点だけは実際に通過を保証する。

開いた通常路線にはstackと頂点位置表を使った線形の再訪検査を行う。`A-B-C-B-D` では、Cが補助点なら閉じた部分 `B-C-B` を取り除き `A-B-D` にする。

- Cが必須の施設入口なら、Cへのアクセスは独立した `B-C` の枝として残す。Dへ行く一本の道に往復を押し込まない。
- 削る部分に必須portalや固定区間が含まれるなら、単純に切らず、要求を分割・再探索する。満たせない場合は生成失敗として診断する。
- 環状路は別の要求とし、始終点の一致を許す単純閉路で表現する。通常路線のloop除去を無条件に適用しない。往復edgeを持つ周回は認めない。
- edgeの集合化だけで頂点列を直さない。路線の順序・方向・連続性を再構成してから登録する。

### 4.5 任意道路は追加利益がある場合だけ採用する

必須の骨格がつながった後に、並行路、横道、環状路、住宅用アクセスを候補として評価する。評価対象の需要は門・施設・街区の代表点などに絞る。

```text
benefit(P) = newlyAccessibleDemand
             + weightedTravelDistanceReduction
             + requiredAlternativeAccess
netGain(P) = benefit(P) - constructionWeight * newPhysicalLength(P)
```

- 完全に既存区間へ包含される候補は、新しい物理道路を作らない。必要なら路線参照だけを追加する。
- 新設部分が少しあっても、需要を満たさず迂回も減らさない候補は棄却する。
- 短い区間でも、城の入口や隣の街区へつながるなら採用する。最小長だけを採否基準にしない。
- 新設区間を除いた経路が複数の小片に分かれても、元の順序付き経路全体で接続を判定する。小片をそれぞれ独立したroadとして追加しない。
- 単純な木で終わらせず、必要な環状路と迂回改善をこの段階で足す。道路一本ごとのMST化や、全閉路削除は採用しない。

既存の `pathFollowsExisting` は安い候補の絞り込みとして残せるが、最後の採否は実際のメッシュedgeと需要で決める。任意道路には都市規模に応じた新設延長の予算と候補数の上限を設ける。

### 4.6 孤立成分と不要な枝を処理する

道路網の成分をBFS/DFSで調べ、各成分の入口・需要・由来を記録する。Union-Findは追加時に利用できるが、削除・分割後は再構築する。

- 必須需要のある成分: 接続先への合法な経路を探索する。無理なら該当候補・工程を失敗にし、需要を消して成功扱いにしない。
- 自動生成の任意成分で需要も接続もないもの: 追加を棄却、または削除する。
- 次数1の端から、必須終端・固定区間・住宅アクセスに到達するまで用途のない枝を段階的に刈る。需要充足と到達性が維持される場合に限る。
- 住宅建設前の整理では、今後の街区へのアクセス需要を使う。まだ家がないことを理由に道路を消さない。建設後に削る場合は区画・建物への到達性を再検査する。

メッシュ外の `frameRoads`、`riverConnections`、固定橋、細街路も境界接続点を介して到達グラフへ含める。中心線が接近しているだけでは接続済みとみなさない。接続判定を描画後の水面clipに任せず、道路幅を含めて合法性を確定する。

## 5. スムージングの順序と守る条件

処理順を次のようにする。壁・河川の事前の境界平滑化は、最終道路探索前に行う現行方針を保つ。

```text
boundary preparation / fixed crossings
→ required road network
→ optional roads with measurable benefit
→ route normalization and connectivity audit
→ physical edge union and junction runs
→ shared mesh smoothing
→ bridge policy / width clearance / connectivity audit
→ local fabric and buildings
```

交差点・終端・固定点・幅や属性の変化点で物理区間の和集合を分解し、共有頂点は一度だけ動かす。`buildArteries` の和集合と `finishCityGeometry.smoothNetwork` の次数判定を活用する。ただし前者は座標キーから最終メッシュのIDへ移し、交差点をまたぐ単純なgroup別平均は行わない。

平滑化は経路の接続順序と所属を変えず、座標だけを改善する。前後で到達性と路線の頂点再訪が変わらないことを確認する。交差・極短edge・面の反転・道路幅の河川侵入も現行の幾何検査で防ぐ。幾何学的な鋭い折れ曲がりが残る場合は、次数2の局所区間を制約内で再探索し、単純な座標平均を強めて解決しようとしない。

橋のデッキ・橋詰・河川接線は保護する。橋は `src/utils/bridgeSkewPolicy.ts` の判定を使い、推奨10°以内、時代・材質・習得技術に応じた上限を厳守する。上限に収まらない場合は道路側の進入区間を変更し、別の合法な渡河点または渡し船を選ぶ。平滑化や孤立成分の接続を理由に、川に沿う橋・川の上で曲がる橋を作らない。

`skeleton-first` の認定済み道路・橋・境界は再スナップや変形をせず初期ネットワークに登録する。既定方式にある再探索をそのまま適用しない。共有区間の索引化・需要充足・描画の一意化は両方式で共通化する。

## 6. 導入順序

| 段階 | 作業 | 完了条件 |
| --- | --- | --- |
| P0 | 読取専用のedge占有・再訪・成分・需要の診断を追加。`road-routing`、shortcuts後、平滑化前後、frame接続後を比較 | 重複が初めて生じた工程と、孤立・短い枝の用途をIDで追える |

## 7. 診断指標と関連テスト

指標は、物理的な一意延長、共有edge長と路線参照数、通常路線の再訪数、未充足の必須需要数、用途のない孤立成分長、用途のない枝の長さ、需要地点間の迂回率、到達可能な居住面積、工程別時間とする。

合格条件は「共有する路線がゼロ」ではなく、**物理区間の重複作成・重複描画がゼロ、通常路線の不要な再訪がゼロ、必須需要の未接続がゼロ**とする。長さは幾何から一度だけ集計し、路線ごとに足して水増ししない。

実装時には、次の振る舞いに絞って回帰テストを追加する。

1. 分岐モデルのCが補助点なら `A-B-D`、必須施設なら幹道と `B-C` の枝になる。
2. 長い経路に包含された短い候補・逆向き候補を足しても、物理延長と描画回数が増えない。
3. 複数の新設小片を既存区間で結ぶ路線が連続性と由来を保つ。
4. 孤立した必須入口は接続されるか、失敗理由が出る。不要な任意成分だけが棄却される。
5. 正当な城の短い進入路、住宅の袋小路、単純環状路、複数入口の広場、固定道路を保つ。
6. 禁止された渡河・壁越えでは接続せず、橋の角度上限とsourceRoadの対応を保つ。

初回調査では既存の `roadEndpoints.test.ts`、`finishCityGeometry.test.ts`、`streets.test.ts` の21テストが成功。一時診断2テストも成功した。診断のconsole出力がtest setupで抑制されたため、一時ファイルへの記録を追加して診断2テストだけ再実行した。全件テスト・多数seedの検証は行っていない。

### 8.9 複数の道路IDに分割された戻り道

共有入力 seed `f0fp2n` では、road-10 の e505 と road-11 の e350 が連続して road-9 へ戻っていた。各道路は1辺なので、道路IDごとの判定では既存網への分岐と合流を同時に検出できなかった。

判定前に、同じ幅員の自動生成道路の端点が道路次数2で接する場合、その連続経路を仮にまとめる。後続道路同士を先に調べ、幹線と戻り道の両端が一致する閉路そのものを結合しない。既存の距離・長さ・保護条件で判定した後、残す辺を元の道路IDへ戻し、所有権と連続区間を正規化する。判定のために道路IDを恒久的に統合しない。

共有入力を `road-loop-multiple-groups.json` に保存し、road-9 の7辺をすべて維持しながら e505・e350 が道路集合から除去されることとmeshの整合性を回帰テストにした。逆向きの道路IDに分割された迂回路の単体テストも追加した。関連5ファイル17テスト、Biome、architecture lintが成功。型チェックは変更外の既存4エラーのみ。
