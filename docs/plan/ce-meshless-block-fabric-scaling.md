# メッシュなしCE 街区構造の大規模化

作成日: 2026-11-08  
状態: S0完了、S1の主要部分（道路グラフ・接続・外周計画の近傍探索）完了（2026-11-08、[S0・S1記録](../analytics/ce-meshless-scaling-20261108.md)）。50,000人の失敗までの時間は100.4→12.6秒、1,000・5,000人の出力は一致。外周計画の切り分けにより、S2の前提としてS1.5（街路の階層）を追加。S1.5（街路の階層）完了。街路街区ごとに独立した処理になり、50,000人の外周計画は19.6→2.0秒、1回の処理は最大約20 ms（生成版`vector-urban-v3`）。  
設計元: [メッシュなしCE設計](ce-meshless-city-editor.md) §8.2・§8.3・§13、[公開基準](ce-meshless-release-acceptance.md)

## 1. 目的

`medieval`の街区構造（既存CEの`buildOrganicBlocks`による外周住宅と内部小路、§8.2）を維持したまま、人口20万人規模の都市まで生成・保存・編集・表示できるようにする。住宅の並び方は既存CEに近いことを優先し、速度のために別の街並みへ置き換えない。

対象は`medieval`の街区構造と、その保存形式・道路グラフ・検証・履歴である。施設モードの施設探索は対象外とするが、本書の保存形式と共通処理の改善は施設モードにも適用する。

## 2. 現状の計測

5,000人のCPUプロファイルでは、`buildOrganicBlocks`（街区内の分割）が約0.54秒で、道路グラフの再構築と検証（主に門の再検証）がそれぞれ0.4〜0.6秒だった。

読み取れること:

- 道路グラフの再構築は小路の数に対して2乗で増える（5,000→50,000人で約140倍）。外周計画も線形より速く増える。主要道路の近傍を全件探索しているためである。
- 小路1本を1つの`VectorPath`と接続ノード・区間、住宅1棟を1つの`VectorPlacement`として保存している。住宅1戸あたり約2.9 KBで、敷地・外形・予約に同じ多角形を3回持つ。
- 20万人（約4.8万戸）をこの形式で保存すると約135 MBになり、道数（2,048）、記録数（10,000）、文書長（8 MB）の上限をすべて超える。
- 履歴（`VectorDocumentHistory`）は確定ごとに文書全体を検証して複製し、参照のたびにも複製する。大規模文書では編集1回ごとの負荷とメモリーが文書の大きさに比例して増える。

## 3. 方針

1. 既存CEの街区構造を正とする。速度のための近似は、§7の比較指標で既存CEとの差が許容範囲にある場合だけ採用する。
2. 採用した生成結果は保存し、読込・描画のたびに解き直さない（§4.1）。圧縮した記録を展開する処理は、保存された値の復号であって配置の探索ではない。
3. 2乗以上で増える処理を先に除く。保存形式の変更は、出力を変えない改善の後に行う。
4. 生成結果は実行環境（Worker数、端末性能）で変わらない。並列化しても同じ入力から同じ文書を作る。
5. 各段階の前後で、変更しない範囲の出力が一致することを直列化文書のSHA-256で確認する。

## 4. 段階

### S0 計測の固定

- 本書§2の手元スクリプトを`scripts/city-editor/meshless/`へ置き、工程別の時間、件数、文書長、ピークメモリーをJSONで出力する。既存の計測スクリプトと同様に、出力先が存在する場合は上書きしない。
- 固定入力は人口で指定する（1,000・5,000・20,000・50,000人と、20万人規模を1件）。成長型の生成（[成長型の都市生成](ce-meshless-growth-generation.md)）では市域が人口から決まるため、半径を入力にしない。成長型の実装前は、壁先行の合成入力で本書§2と同じ半径（150・240・480・760m）を使い、人口との対応を記録する。20万人の合成入力は骨格の分岐数・市域の形が現実的か確認してから決める。
- FMG由来の大都市を1件加える。FMGで作る場合はSettlement patternをStandardにする（AGENTS.md）。
- 2 MBを超える全量出力は`docs/analytics/raw/`へ置き、記録mdにSHA-256を残す。

### S1.5 街路の階層（S2・S3の前提）

S1後の切り分け（[記録](../analytics/ce-meshless-scaling-20261108.md#外周計画の切り分け)）で、外周計画の時間は街区の面積にほぼ比例し、残る増加は街区が大きいことによると分かった。骨格の街区は人口によらず6つ前後で、50,000人では最大44.6 ha・約9,200区画になる。その内部は幅2.4 mの小路だけで、骨格の道路と小路の間の街路がない。既存CEは街路に囲まれたセル（既定の間隔50 m）ごとに`buildOrganicBlocks`を呼ぶので、1回の対象の大きさが100倍以上異なる。

この差は既存CEの街並みとの違いでもあり、S2の記録単位・S3の並列化単位・部分再生成の範囲がすべて45 ha規模になる原因でもある。そこで、`buildOrganicBlocks`の前に街路の層を置く。

- 骨格の街区を、街路（小路より広い道）で街路街区に分ける。街路は既存の道路へ接続ノードで接続し、`VectorPath`として保存する。
- 街路街区の目標の大きさと街路幅は、既存CEのセルの面積分布と、街路・小路の延長比を測って決める（S0の計測に既存CEの固定ケースを加える）。
- `buildOrganicBlocks`は街路街区ごとに呼ぶ。境界のsetbackは既存CEと同じ規則（小路幅の半分＋0.35 m、道路のclearance、水辺6 m）にそろえる。
- 街路の生成は、成長型の生成の「街路を作る」工程（[成長型の都市生成](ce-meshless-growth-generation.md) §3.2の3）と同じ処理を使う。壁先行では骨格の街区に対して、成長型では成長の帯に対して適用する。
- 生成結果が変わるため、アルゴリズム版を上げる。

既存CEには、粗いメッシュのセルの内側に約50 mの街路街区と幅5 mの街路を作る仕組み（`streetCellMeters`）が既にある。前半としてこれを外周計画に使い、setbackと市壁の向きを既存CEにそろえ、生成版を`vector-urban-v2`に上げた（2026-11-08、[記録](../analytics/ce-meshless-scaling-20261108.md#s15-前半既存ceの粗いセル用の街路街区)）。後半として、`buildOrganicBlocks`を「街路街区への分割」と「街路街区ごとの区画・小路・住宅」の2段に分け、街路街区を記録・並列化・部分再生成の単位にする。乱数は街路街区ごとに分けるため、後半でも出力が変わり、生成版を上げる。

完了条件:

- 街路街区の大きさと街路・小路の延長比が、既存CEの固定ケースと§7の許容範囲で一致する。
- 外周計画の時間が面積に比例し、1回の`buildOrganicBlocks`の時間に上限がある（目安は既存CEの1セル相当）。
- 1,000・5,000人で未収容0人を維持する。

### S2 街区単位の記録（native v8）

S1.5で、地区（骨格の街区）を街路街区に分け、街路街区ごとに独立して作れるようになった。S2では、自動生成した街並みを「地区」と「街路街区」の2層の記録として保存する。手動の住宅・施設・固定物は従来どおり`VectorPlacement`で保存する。

#### S2.0 選択を軽くする（形式の変更前に行う）

メッシュありCEのInspectorでは、要素の選択そのものが重くなる場合がある。選択時に地図全体の再描画へ切り替わる経路（`applySelection`で部分更新できない場合の`redrawMap`）や、Inspectorの描画で派生データ（地区の解決等）を求め直す処理があるためである。メッシュなしでも、2026-11-08時点で次の負荷がある。

- 選択の通知で`session.history.document`を読む。この参照は文書全体を`structuredClone`する（5,000人の文書で1回約37 ms）。配置・道・環境の各パネルも選択のたびに同じ参照を読むため、1回の選択で複数回複製する。
- 配置パネルは全配置を`<select>`の選択肢として持つ（5,000人で約1,100件、20万人では4万件を超える）。

選択は次の規則に従う。S2の形式変更より先に、現行のv7文書へ適用する。

1. 選択とInspectorの表示は、文書を複製しない。履歴から読み取り専用の参照を受け取り、複製は編集候補を作るときだけ行う。
2. 選択で文書の検証、生成、街区構造の再計算、地図全体の再描画、3Dシーンの作り直しをしない。強調表示は専用の重ね描きの層に、選択した要素の形だけを描く。
3. 選択で全要素を走査しない。当たり判定は空間索引（2Dは街路街区・配置の外接矩形、3Dはインスタンス番号から論理IDへの表）で行う。
4. Inspectorに出す派生値（住戸数、地区、接道、入口）は選択した要素の分だけ求め、記録のハッシュをキーに保持する。
5. 全要素の一覧を選択肢として描画しない。検索、地図での選択、または表示範囲だけを描く一覧にする。

目標: 選択から強調表示とInspectorの表示まで、50,000人の文書で16 ms以内（1フレーム）。5,000・50,000・200,000人で計測する。

#### S2.1 記録の構成

```ts
interface VectorFabric {
  algorithm: string;                       // fabric algorithm version (vector-urban-vN)
  districts: Record<string, VectorFabricDistrict>;
  cells: Record<string, VectorFabricCell>;
}
interface VectorFabricDistrict {
  id: string;                              // stable district id (S2.2)
  hash: string;                            // content hash; validation and caches key on it
  seed: string;
  parameters: { lotArea: number; laneWidthMeters: number; coverage: number; streetCellMeters: number; streetWidthMeters: number };
  outline: PackedRing;                     // adopted district outline
  boundaries: { feature: boolean; barrier: boolean; setback: number }[]; // per outline edge
  streets: PackedPolylines;                // perimeter and street-block streets, unsplit
  mouths: { street: number; end: 0 | 1; nodeId: string }[]; // explicit joins to the road graph
  cellIds: string[];
  growthStage?: number;                    // growth-first generation
}
interface VectorFabricCell {
  id: string;                              // `${districtId}:cell:${ringHash}`
  hash: string;
  districtId: string;
  ring: PackedRing;
  lanes: PackedPolylines;
  attachments: { lane: number; end: 0 | 1; street: number; t: number }[]; // lane ends on district streets
  houses: {
    rings: PackedRings;                    // site = footprint = reserved; stored once
    storeys: number[];
    dwellings: number[];
    entrances: number[];                   // packed point and target (lane or street) per house
    draws: number[];                       // CE occupancy draw, keeps vacancies spread
  };
  detached: number[];                      // house indices replaced by manual placements
  inside?: boolean;                        // inside the town wall
}
// Packed* = integer centimetres relative to the record's origin, in flat arrays.
```

- 文書の`fabric`に保存する。自動生成の小路は`paths`・`connections`へ登録せず、住宅は`placements`へ登録しない。
- 街路と小路の交点は保存しない。地区の街路は分割せずに保存し、街路街区の小路の端が街路に接する位置を`attachments`で持つ。街路街区を作り直しても地区の記録は変わらない。
- 住宅の論理IDは`<街路街区ID>#<番号>`とする。街路街区を作り直すまで変わらない。

#### S2.2 安定した地区ID

現在の地区IDは`block:${i}`で、骨格の街区の並び順から決まる。街路街区IDと乱数はこのIDから作るため、別の地区が増減すると無関係な地区の中身が変わる。地区IDを、輪郭の正規化ハッシュ（1 cm単位）と接する道路のIDから決める。同じ輪郭・同じ接道なら同じIDになり、生成結果も同じになる。成長型の生成では`growthStage`と市壁の内外区分も保存する（[成長型の都市生成](ce-meshless-growth-generation.md) §5）。

#### S2.3 道路グラフとの関係

- 主要道路・既存道路と接続する街路の端だけを接続ノードとして登録し、`mouths`で参照する（§7.1の「接続は明示する」を維持する）。
- 小路の到達性は、街路と小路の内部グラフ（`attachments`と`mouths`から作る派生データ）で求める。近いだけで接続とは見なさない。
- 利用者が街路・小路を編集する場合は、その線を通常の`VectorPath`へ切り出してから編集する（「道として切り出す」）。切り出しは1回の履歴項目で行い、Undoで記録へ戻る。

#### S2.4 編集・依存更新

- 住宅を移動・削除・固定するときは、その住宅を`VectorPlacement`へ切り出し、街路街区の`detached`へ番号を加える。
- 道路・川・壁の変更（§10.2）では、影響を受けた地区の街路街区への分割から作り直す。影響が街路街区の中に収まる変更（施設の移動など）では、その街路街区だけを作り直す。手動で切り出した住宅・道は保持し、衝突する場合は§10.1に従って候補を示す。
- 人口容量は記録の`dwellings`の合計から求め、`faceId`は使わない。

#### S2.5 保存・検証・共有

- v7→v8の移行では、既存の文書を書き換えない。v7の`urban:perimeter:*`住宅と`urban-lane:*`の道は従来の形式のまま読み込める。v8で生成した都市だけが`fabric`を持つ。
- 検証は記録単位で行う。整数座標の範囲、輪の単純性、住宅が街路街区の輪の中にあること、入口が小路・街路に接すること、`attachments`と`mouths`の位置が一致することを確認する。結果は記録の`hash`をキーに保持し、編集では変更した記録とその依存だけを検証する。読込時・保存時は全記録を検証する。
- 所有権の指紋（`vectorUrbanFingerprint`）は文書全体の`JSON.stringify`をやめ、記録の`hash`とそれ以外の部分の指紋から作る。
- 住宅1戸あたりの保存量の目安を200 B以下とする。20万人（約4.8万戸）で約10 MBになるため、文書長の上限をS2の計測後に決め直す。大きな文書は整形せずに保存する。共有は既存のgzip符号化を使う。

#### S2.6 描画と選択

- 2Dは街路街区ごとに住宅を1つの`<path>`にまとめる。強調表示は重ね描きの層に、選択した住宅だけを描く。
- 3Dは住宅の種類（階数・屋根）ごとにインスタンス描画し、インスタンス番号から論理IDへの表を持つ。
- 当たり判定は、街路街区の外接矩形の空間索引で候補を絞り、その街路街区の住宅だけを復号して判定する。
- 選択・計測・Inspectorは論理IDで行う（M9の論理ID選択を拡張する）。S2.0の規則に従う。

完了条件:

- 20,000人・50,000人が上限エラーなしに生成・保存・再読込できる。
- 1,000人・5,000人で、v7（生成版v3）とv8の住宅数・住戸数・未収容人数・小路の総延長が一致する。
- 住宅・道の切り出しと依存更新の回帰テストに成功する。
- 50,000人の文書で、選択から強調表示とInspectorの表示まで16 ms以内。

### S3 街区単位の並列生成

- S2.2の安定IDにより、街区ごとの生成は他の街区に依存しない。街区をWorkerプールへ分け、結果を街区IDの順で結合する。
- Worker数は`navigator.hardwareConcurrency - 1`を上限に4程度とし、1本でも同じ結果になることを確認する。
- 進捗は完了した街区数で示す。初期生成Workerの60秒の無応答上限は維持し、全体の上限は別に設ける（現状は進捗通知のたびにタイマーが戻るため、全体の上限になっていない）。

完了条件: Worker数1・2・4で直列化文書のSHA-256が一致する。

### S4 履歴の差分化

- 大規模文書では、確定ごとの全体複製・全体検証をやめ、変更した記録（道・街区記録・配置）単位の差分を履歴に持つ。
- 検証は変更した記録とその依存（§10.2の表）に限定する。読込時と保存時は全体を検証する。
- 履歴の総メモリーに上限を設け、古い項目から破棄する。

完了条件: 50,000人の文書で、住宅1棟の移動の確定とUndoがそれぞれ0.5秒以内で終わる。

### S5 必要に応じて検討するもの

S1〜S4の後に目標を満たさない場合だけ、次を比較して採否を決める。

| 案 | 内容 | 懸念 |
| --- | --- | --- |
| 区画種類のカタログ | 「間口×奥行×階数→住戸数」の区画種類を時代・文化ごとに用意し、街区の辺に沿って1次元に詰める | 既存CEの区画分割と見た目・密度が変わる。§7の指標で比較する |
| 需要に応じた打ち切り | 収容が足りた時点で街区の生成を止める | 既存CEの空き地の散らばり（地区ごとの抽選）を崩さない順序が必要 |
| 同じ形の街区の再利用 | 正規化した輪郭のハッシュで生成結果を使い回す | 有機的な市街地ではほとんど一致しない。計画都市の格子状の街区でだけ有効 |

街区の形と建物の組合せを2次元のタイルとして事前に用意してはめ込む方式は採用しない。実際の街区は道路・市壁・河岸に囲まれた不規則な形で、タイルでは隙間や細い余りが大量に出る。はみ出た建物を切ると実寸の住宅ではなくなり、タイルの縁と道路がずれると入口が道に届かない。既存CEの街並みからも離れる。

## 5. 目標値（暫定）

固定入力・開発機での単回計測による暫定値とする。S0の計測後に見直し、合意してから受入値にする。

| 人口 | 骨格＋施設住宅（`medieval`） | 文書長 | 備考 |
| --- | --- | --- | --- |
| 5,000 | 10秒以内（現状2.4秒＋骨格0.9秒で達成） | 現状以下 | S1前後で出力一致 |
| 20,000 | 10秒以内 | 4 MB以下 | S1で道路グラフ1秒以内 |
| 50,000 | 20秒以内 | 10 MB以下 | S2以降 |
| 200,000 | 60秒以内（並列4本） | S2の計測後に決定 | 保存・再読込・編集ができること |

施設モードの時間目標は本書では定めず、公開基準の10秒目標を維持する。

## 6. 影響範囲

- `generators/vector/generation/`（urban.ts、perimeter.ts、pipeline.ts）
- `generators/vector/editing/`（network.ts、dependencies.ts、placements.ts）
- `generators/vector/validation/`（document.ts、urban.ts）
- `generators/organicBlocks.ts`（`Face`への依存を`{ id, ward }`程度の入力型へ絞る。メッシュ方式の出力は変えない）
- `types/vector/`、`services/io/vector/`（v8 codec・移行・共有）
- `renderers/vector/`（街区単位の2D・3D描画、論理ID選択）
- `generators/vector/history.ts`

旧CE（メッシュ方式）の生成順・乱数消費は変えない。`organicBlocks.ts`の入力型の変更では、メッシュ方式の関連テストで出力一致を確認する。

## 7. 既存CEとの比較指標

街区構造を変える変更（S2.2のID変更、S5の案）では、次を既存CEと比較する。

- 住宅の区画面積の分布（中央値・四分位）
- 外周住宅の割合と、接道する住宅の割合
- 小路の総延長／街区面積
- 住戸密度（戸/ha）と未収容人数
- 目視確認用の同一範囲の2D画像

完全一致は求めない。許容範囲はS0の計測時に既存CEどうしのseed違いのばらつきを測って決める。

## 8. テスト

- S1は1,000人・5,000人の直列化SHA-256の一致と、道路グラフ・外周計画の関連テストだけを実行する。
- S2はv8 codec、移行、切り出し、依存更新、描画データの関連テストを追加する。
- 大規模計測は明示実行時だけ有効にし、通常のVitestではskipする（M9と同じ扱い）。
- 多数seed探索・全件テストは行わない。
