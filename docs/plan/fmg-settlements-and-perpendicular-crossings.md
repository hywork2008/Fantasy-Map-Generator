## 1. 設計の結論

**川の両岸を別々の陸地として探索し、事前に成立を確認した直交橋だけを両岸の接続辺として使う。都市・川・橋・道路の物理座標をFMGで確定し、CEへそのまま渡す。**

生成後に道路の交点へ直角の点列を挿入する方式では、渡河地点、橋への進入、重複渡河、都市への到達を同時には保証できない。新方式では渡河の成立を探索グラフの制約にする。

必須条件:

- roads / trailsの橋は、渡河地点の河川中心線の接線に直角な直線とする。橋の前後に短い同軸の乾いた進入区間を確保し、その外側からの接近も急旋回なく接続する。
- 橋以外の陸路辺は河川水域を横断できない。航行不能な小河川にも同じ原則を適用する。
- 幅・深さ・技術・船舶通航条件を満たさない橋、両岸の足場や進入路が成立しない橋は候補から除く。角度条件を緩めて接続しない。
- 水辺の都市は実際の岸近くの乾いた土地に置く。河川沿いとして配置した都市は、CEの範囲内に実際の岸と水面が含まれることを確認する。
- 同じ川の反復横断は、同岸迂回より明確な利益がある場合だけ採用する。
- 新方式ではSVG・WebGL・CE・移動判定が同じ接続と橋位置を使う。旧形式の抽象的な接続を維持する場合は第10節の互換扱いと区別し、新方式の検証済み接続に混ぜない。

### stashから引き継がない構造

差分では、既存の交点を中心に法線方向の制御点を挿入し、点を描画時のスナップから保護している。しかし探索グラフや都市対選定は変更されていない。以下は差分から分かる未解決事項であり、個々の失敗画面の原因を断定するものではない。

- 元の交点が架橋向きか、進入道路が乾いた土地に収まるかを探索時に評価していない。
- 同じ川を何度も跨ぐ経路そのものは残る。
- 制御点の保護だけでは、曲線補間・河岸形状・別rendererまで含む直交性を保証できない。
- `points`へ同一セルの点を増やすと、セルIDを接続点とみなす既存の処理に影響する。
- ロード時に道路形状を変更するため、再生成を要求していない保存地図にも変更が及ぶ。

## 3. 共通の河川形状を先に確定する

新規サービス案: `src/services/riverGeometry.ts`。

河川生成後、蛇行を含む中心線を一度確定し、以後はその形状から接線、川幅、物理的な両岸、水域ポリゴンを導出する。中心線は弧長で参照でき、曲線を採用する場合はその曲線の微分から接線を得る。rendererごとに別の平滑化を加えない。折れ線の不連続な角で架橋候補を作らず、その前後の安定した区間で探す。

- 計算上の幅・距離・橋長はメートルに統一する。現行の`mapUnitMeters`を使い、距離単位とdistanceScaleを一度だけ変換する。
- 世界座標は保存座標とし、局所座標への変換は一様拡大縮小・平行移動・Y反転だけに限定する。この変換なら直角性は保たれる。
- 現行`Rivers.getWidth`の物理幅への変換を初期の基準として再利用する。河川表示の幅と物理幅は別フィールドにする。
- FMGの誇張した河川記号は都市の物理座標を動かす理由にしない。近接表示では物理形状へ移行する。遠景で橋記号を水面記号の縁まで延ばす場合も同じ法線上の表示専用延長とし、橋長・通行距離・CE座標には戻さない。
- 表示専用延長が他の曲がり・支流に触れる場合は、その地点の誇張幅を抑える。橋の方向や実際の河川を曲げて合わせない。
- 河川・湖・海の水域を空間索引で検索可能にし、セルIDが異なっていても線分と水域の衝突を検出する。

洪水位や地盤支持力の精密な資料は現在の地形からは得られない。初期実装では水域外の足場、岸付近の勾配、低地への露出をゲーム用の代理評価とし、精密な治水・土木計算とは位置づけない。

## 4. 都市は食料・気候・取水と乾いた市街地で配置する

都市配置を「地域候補」と「地域内の具体的な敷地」に分ける。

1. 既存のsubsistenceCapacity、気候適性、危険度から居住可能な地域を選ぶ。standardとSettlement Foundationに共通の人間向け評価を用意する。地下都市・巨人など既存の種族固有条件は専用評価を保つ。
2. 既存の局所食料支持力を基礎とし、後背地を評価する場合は距離と候補数を制限した到達性集計にする。川の向こうの食料を橋なしで使える前提にしない。集水・取水可能性は距離で連続的に評価し、流量が大きいだけで無制限に加点しない。淡水湖と塩湖も区別する。
3. 初期実装は食料支持力を都市候補の適性・規模の評価に使い、新たな食料配給・交易均衡計算や街道完成後の人口増加計算は導入しない。将来、到達可能な食料供給を人口へ加算する場合は、同じ供給量の重複計上を防ぐ配分処理が別途必要になる。
4. 河川沿いの敷地では、物理的な岸からの取水距離、乾いた市街地面積、局所勾配、周辺の畑へのアクセスで点を選ぶ。水面・急斜面を避け、政治境界を跨ぐ座標移動で所属を偽装しない。
5. 街道の接続優先度には、既存の食料支持力・都市役割から求める決定的な基礎規模を用意する。未確定の`burg.population`を0として比較しない。初期実装では人口の確定順を大きく組み替えず、`Burgs.specify`の既存人口算出は一度だけ行う。CEの最終frameは人口確定後に決める。
6. 水への近さと安全な敷地を先に決め、その敷地の街区と近岸・水面が収まるようCEのframeを決める。河川沿い属性は物理的な取水距離・岸への到達性から決め、既定frameに入らないという理由で都市を棄却・内陸化しない。

新規配置では物理岸に近い乾いた候補を選び、都市が不当に遠い場合は道路確定前に同じ地域内で敷地を調整する。ただし表示だけを理由に水面・崖・政治境界を越えて中心を引き寄せない。代替敷地が必要なのは、乾いた市街地や取水路が成立しない場合である。

川岸に接するだけでは水面が見えないので、表示余白もメートル単位で持つ。大河では近岸と水面が入ればよく、対岸や中心線を無理に画面へ収めない。都市中心を原点とする現在のCE座標契約を維持し、必要ならframeの広さを調整する。frame中心の移動は、都市中心を原点とみなす多数の処理に影響するため初期案では採用しない。

現在のdescriptorは人口からextentを決めて上限4,500mで丸め、CEの`shareFromDescriptor`は`fitUndersizedTownFrame`で小都市のframeをさらに縮める。両方を更新し、近岸・水面・必要な接続点の`requiredBounds`を渡して、縮小後も保持する。frameを広げても街区密度や都市半径を一緒に拡大しない。遠い川を入れるための無制限な街区生成は避け、細密な市街地範囲と周辺地形の表示範囲を分ける。性能上の限界に達したら表示範囲の問題として診断し、都市や河川沿い属性を黙って変更しない。

`burg.cell`は行政上の所属を維持する必要がある一方、道路接続と取水には実位置が必要になる。敷地データに`physicalCellId`、接続ノードID、最寄り河川・河岸・距離を記録し、`burgWaterAccess.ts`をセルIDだけから決める方式から更新する。現在の「cells.rと一致しないriverPlacementを削除」は新データには適用しない。

## 5. 直交する橋と進入路を候補化する

新規モジュール案: `src/generators/riverCrossingCandidates.ts`。

河川の局所的な狭窄部、平坦な両岸、都市近くの回廊に候補を作り、粗い一定間隔の候補も加える。間隔はワールドのセル数ではなく実距離・曲率から決め、成立する経路が見つからない回廊では局所的に細分化する。

各候補について中心線上の点を`q`、下流方向の単位接線を`t`とし、法線`n=(-t.y,t.x)`を求める。`q + λn`と物理水域境界の交差を計算し、qを含む一つの水域区間の両端を橋台A/Bとする。単純な「中心±代表幅/2」では確定しない。

橋と短い同軸区間を固定し、その外側の進入回廊は地形に合わせて選ぶ:

```text
同岸道路 ～ 緩やかな接近 ～ 進入端A ─ 橋台A ═══ 橋台B ─ 進入端B ～ 緩やかな接近 ～ 同岸道路
                                    河川に直角な一本の直線
```

候補の成立条件:

- 橋軸`B-A`と`t`の内積がゼロ。誤差は浮動小数点計算の許容差だけとし、「85度なら許可」のような緩和はしない。
- 渡る水域区間が一つであり、同じ法線が蛇行の別区間や支流を再横断しない。合流点・急曲率・中洲の複合渡河は初期実装では候補から外す。
- 両岸に橋台を置ける乾いた領域があり、橋台付近では橋軸と同じ方向で接続する。短い直線区間は道路種別・地形に応じて設定範囲内で調整する。長さを川幅へ比例させ続けたり、一律の長い進入路を義務付けたりしない。
- 進入端の外側も含め、乾いた進入回廊内で連続した接線と道路種別ごとの最小曲がり半径・許容勾配を満たす。急な折れを進入端へ移すだけの候補は不採用。幅・橋台が成立しただけの候補は仮候補とし、都市側との進入接続まで成立してから採用する。
- `planRiverCrossing`に実橋長、深さ、時代、技術、必要船舶を渡して方式が成立する。既存の総延長制限と支間長・橋脚深さは混同しない。幅が許容上限以下というだけで建設を採用しない。

**「最短距離」は選んだ渡河地点の局所断面における最短直交渡河であり、川全体の最狭部を探す目標ではない。** 非平行な自然河岸では、両岸間の無制約の最短線と中心線への直角は常に一致するわけではない。直角を必須条件とし、近岸から対岸まで余分な水上区間なく結ぶ。近隣候補の比較は橋長だけでなく進入路・全行程の地形費用を含め、短い橋だけを求める大迂回を避ける。

進入回廊の探索では、橋から離れた位置から方向転換できるよう、直前の辺の方向を状態に含める。橋へ近づくほど法線から外れた進行や急な方向転換に非負のペナルティを与える。岸沿い道路全体を罰せず、その橋への進入区間に限定する。方向の優遇は候補選びの補助であり、直角性と接線連続性は幾何の必須条件として検証する。狭い谷では候補の移動・回廊の拡張・許容範囲内の短い進入区間を比較し、それでも成立しない地点は採用しない。

渡し船は橋と別種の交通辺とする。道路は岸の乗降場で終わり、乗換・待ち時間を持つ。`none`は通行不能であり接続辺を作らない。初期段階で渡し船の移動処理が未対応なら、船が必要な接続を未接続として扱い、水面上に陸路を引かない。

## 6. 河岸を区別する探索グラフ

新規モジュール案: `src/generators/landRouteGraph.ts`。

通常の陸地は既存のセルグラフを利用する。水域に接するセルだけ局所的に精細化し、「セルの陸地から水域を除いた連結成分」ごとにノードを作る。同じセル内の左右岸でも別ノードにする。セル代表点が水中なら、各乾燥成分の内側に代表点を置く。

- 隣接セルの乾いた共有境界に接続口を置き、同じ乾燥成分内で実際に到達できる辺だけ作る。曲がった成分内では代表点同士を直結せず、局所メッシュ・可視グラフなどで乾いた経路を得る。
- 都市、道路交差点、橋の進入端、橋台を明示的なノードとして追加する。
- 渡河は採用した橋辺・渡し辺だけを通る。通常の陸路辺には水域交差を認めない。
- 川岸に沿う乾いた道路は許可する。「同じriverIdのセルを連続して踏んだら禁止」という代替判定は廃止する。
- 橋は進入端Aから進入端Bまで一つの制約付き接続として扱い、中途の橋台から平行方向に道路を接続しない。合流は直線進入区間の外で行う。
- 国境・外交・allowedCellsの条件は、辺の途中も含む実際の通過領域へ適用する。

探索状態は少なくとも`(nodeId, incomingEdgeId, crossingHistory)`とし、進入方向や渡河履歴の違う到達を同じセルの一つの最良費用へ潰さない。橋台での接線は正確な幾何で検査し、粗い方向分類だけで合格させない。初期実装は非負コストのDijkstraでよく、A*へ変えるなら既設路割引も含めて過大評価しない下界を用いる。新状態を扱う専用探索を作り、海路など既存`findPath`の利用側へ不要な変更を波及させない。

セル→橋台→同じセルの別岸、という経路も表現できるため、`Route.cells`だけを接続の正本にはできない。`cells`は検索・フォーカス用の派生索引とし、接続はノードID・辺IDで保持する。

`pack.cells.routes`は同じセル内の分断を表現できない。道路接続・旅行・交易・軍事などの利用箇所を列挙し、正確な到達性が必要な処理には新グラフの問い合わせAPIを渡す。旧索引だけから対岸へ移動可能と推定する互換処理は作らない。ここを移行し終えるまで新方式を既定にしない。

少なくとも`Routes.buildLinks`と接続問い合わせ群、`regimentMovement.ts`、Economyの`trade-animation.ts`、`resample.ts`が移行確認の対象になる。都市の経済指標などで「道路があるセル」を数える用途と、実際の通行経路を求める用途を区別する。道路外のセル移動を使う処理でも、橋なし渡河を道路網の接続と誤認しないよう、水域境界を共通に照会する。

## 7. 道路と橋を「利益がある接続」として選ぶ

初期実装は**少数の接続候補と地形・渡河コストによる決定的な近似**にする。全都市対の需要行列、年換算建設費、償却期間、物流均衡、世界全体の目的関数最適化は必須要件から外す。高度な経済モデルを導入しなくても、接続先の重要度と代替経路との差によって「橋を造る意味」を表せる。

### 接続候補と費用

- 既存の主要都市・港・首都を結ぶroads、そのほかの近隣都市を結ぶtrailsという構成を残す。人口未確定時には第4節の基礎規模を使う。食料や市場の役割は既存データから分かる範囲の優先度とし、詳細な取引量は予測しない。
- Urquhart/Delaunayに各都市の少数の同岸候補を追加する。同岸を優先するが、対岸の重要都市や幹線の接続候補は残す。同岸判定は同じセルや局所的な左右符号ではなく、河川区間・乾燥成分の到達性で行う。
- 候補数に上限を設け、未接続地域だけ到達性探索で候補を補完する。地形を無視した近傍都市対しか試さずに孤立と判断しない。

経路選択には次の非負コストを使う:

```text
探索費用 = 距離・勾配・標高等の費用
         + 新設道路・橋の整備負担
         + 渡河ごとの利用負担
         + 進入方向・曲がりの負担
         + 同一河川の再渡河負担
```

金銭収支ではなく、基準距離などに正規化した生成用スコアとする。幅、深さ、橋脚、方式、進入工事で架橋の整備負担を増やす。既設橋は新設負担を再計上しないが、渡河ごとの正の利用負担は残す。既存道路の割引は陸上部分へ適用し、橋の新設負担まで一律に半減させない。探索用の整備負担・履歴ペナルティを、実際の旅行時間や料金として利用側へ渡さない。

### 候補の採否と共用

1. 現時点の徒歩到達性・既存街道・有効な水運による基準経路と、候補橋を含む新経路を比較する。船種・上り下りの既存制約を維持し、未対応の渡しを基準経路として発明しない。
2. 新経路の移動費用の改善が新設負担と所定の余裕を上回る場合に採用する。接続先の重要度から有限の整備許容スコアを決め、基準経路がない場合や極端な大迂回の場合はこの上限と比較する。未接続を無限の利益と解釈して巨大橋を無条件採用しない。
3. 共有橋の候補では、同じ回廊を使う上限付きの近隣都市対だけ改善をまとめる。橋と両側の道路は一式で評価し、複数橋が揃わないと接続できない経路も丸ごと比較する。施設IDごとの新設負担は一度だけ数える。全都市対の組合せ最適化は行わない。
4. 優先度の高い接続から、経路・進入形状・接続関係を検証して一案ずつ確定する。採用施設に関係する未採用候補だけを、回数上限付きで再評価する。roads / trailsが同じ橋を参照する場合も一施設とする。

橋長の短縮が全行程の費用増を上回らない限り、遠い狭窄部への迂回を採用しない。山越えは高費用として残し、合理的な唯一の峠まで一律禁止しない。道路種別で勾配などの許容条件は変わるが、橋の直交条件は共通とする。

### 無駄な左右岸往復は探索中と確定前に防ぐ

同岸の都市対候補、正の渡河負担に加え、同一経路内で同じ河川を再横断した場合の非負ペナルティを探索状態へ入れる。履歴はriverIdだけでなく対象区間・岸との対応を保持し、同じ橋の即時逆行は許可しない。同じriverIdを一律1回に制限せず、崖・大きな蛇行・対岸の目的都市による必要な複数渡河は有限費用で残す。

履歴依存費用をセルごとの一つの最良費用で処理してはいけない。河川別の横断回数は設定上限で飽和させ、回廊内の履歴を持つ複数の探索ラベルを区別する。状態数の増大に備えてラベル数・探索数に上限を設け、上限による枝刈りは近似であると記録する。探索予算の枯渇を「地形上到達不能」と区別し、より広い回廊などへの回数限定の再試行を行う。

都市間経路をネットワークへ登録する**前**に、A岸→B岸→A岸の部分について同岸の代替案と比較する。ほぼ同価なら橋が少ない案を採る。方向誘導や履歴ペナルティだけを、不要な往復が絶対になくなる保証とはしない。再探索する場合も未確定の経路全体を検証し、確定済みの共用区間や枝道を点列の部分置換で切り替えない。

確定後の検査は監査とし、自動の破壊的な枝刈りを行わない。将来、既設網を置換する機能を追加する場合は、施設の利用参照・分岐ノード・都市到達性を含めて一括検証し、成立した場合だけまとめて切り替える。

## 8. 保存形状・描画・CEの契約

提案する保存情報（名称は実装時に既存スキーマへ合わせる）:

| データ | 主な情報 |
| --- | --- |
| `RiverGeometry` | geometryVersion、中心線、物理幅・両岸、下流方向、空間索引用bounds |
| `BurgSite` | 物理位置、physicalCellId、行政セル、接続ノード、river/lake frontage、取水距離、予想半径 |
| `Crossing`（world共通） | 永続ID、riverId、河川弧長、接線、両橋台、両進入端、幅・深さ・方式・必要船舶・採用理由 |
| `LandRoute` | 接続ノード/辺ID列、crossing ID列、`land/approach/bridge/ferry`の区間列、派生cells |
| CE descriptor | river geometry、都市の接続点、道路区間、crossing IDごとの橋台・進入端・方式、source geometryVersion、frame縮小でも保持するrequiredBounds |

同じ橋を複数のrouteが利用しても橋は一施設とする。河川ごとの代表crossing planで全道路を決めず、渡河IDと道路区間で対応を確定する。

描画:

- 橋・直線進入区間は直線として描画する。通常道路だけを乾いた回廊内で平滑化し、接続位置と接続方向を固定する。
- 平滑化後も水域との交差・曲がり・接続方向を検証する。通常道路で成立しない曲線は乾いた探索結果の折れ線へ戻せるが、橋への進入で急旋回を復活させるfallbackは許さず回廊を再探索する。全routeに一括Catmull–Romを掛けない。
- `collapseRedundantCellPoints` / `snapRoutePointsToCellAnchors`は新形式へ適用しない。ノードIDによる同一地点共有で交差点を一致させる。
- SVGとWebGLは同じ確定済み区間を消費する。低ズームの丸め・簡略化で橋軸を回転させない。
- 道路編集・分割・結合・河川編集・都市移動にも同じ制約検査を適用する。

CE:

- FMG由来の新バージョンでは橋台・進入端・河岸を固定境界として扱う。都市内の道や街区をそこへ接続する。
- CEが川を移動・蛇行し直したり、橋を別の角度に再生成したりしない。水域の粗い街区近似で確定済みの川岸を置き換えない。
- `withRiverPortFallback`などの再構成は旧入力・合成入力に限定する。新入力が不整合なら診断付きで失敗を返し、不正な橋で見かけの生成成功にしない。
- frame境界で橋が切れる場合は同じ施設の部分表示として扱い、境界に新しい橋台を作らない。CEの表示範囲外の橋を町のそばへ移さない。
- `requiredBounds`をframe調整・小都市向け縮小・地形クリップの全段階で尊重する。最終CE表示で岸と水面を確認し、descriptor生成時のextent検査だけで完了しない。

`resolveRiverRouteCrossings`は、最終道路から橋を発明する役割を終え、生成結果の監査・旧形式の診断へ移す。船舶通航要件は橋の候補選別前に収集し、確定後は再検証する。橋を先に作って水運が消えたから橋が正当だった、と判定が循環しないようにする。

## 9. 生成順序と実装分割

目標の順序:

```text
地形・気候・河川
  → 共通の物理河川形状 / 乾いた回廊 / 架橋可能候補
  → 食料支持力・居住適性 / 都市候補・基礎規模
  → 物理的な河岸の敷地と必要表示範囲
  → 政治所属の確定 / 敷地の最終検査
  → 接続優先度・船舶通航要件 / 候補数を限定した道路と橋の選択
  → 形状確定・接続と水運の検証
  → 既存処理による人口・都市属性の一度の確定
  → 描画・CE descriptor / 最終frame検査
```

`src/main.ts`の非standard生成はStates生成前後にRoutes生成を呼ぶ。政治生成が必要とする事前の到達性は、同じ制約を満たす暫定ネットワークとして分離する。前段の橋費用や選択を二重計上せず、境界確定後に本ネットワークを決める。`src/generators/index.ts`の別pipelineと`src/types/pipeline.ts`も依存順をそろえる。標準の経路だけを直して非standardが旧処理を通る状態を残さない。

| 段階 | 実装内容 | 完了条件 |
| --- | --- | --- |
| 0 | 現在の交差・同岸往復・CE座標差を記録する診断、代表fixtureの固定 | 実装前後を同じ入力で比較できる |
| 1 | 共通河川形状、断面候補、短い同軸区間と進入回廊の検証 | 斜め橋候補・水上進入・複合横断・進入端の急旋回を採用しない |
| 2 | 局所的な河岸グラフ、方向・渡河履歴を持つ探索、新route区間、SVG/WebGL、接続利用側の移行 | 固定都市のままでも全roads/trailsが有効な橋だけで渡河し、確定前に不要な往復を検査する |
| 3 | FMG→CEの新descriptor、固定河岸・固定橋の受け渡し、保存読込 | 同じ世界座標でFMG/CEの橋と道路が一致する |
| 4 | 都市の物理河岸配置、食料・気候評価の共用、基礎規模とCE必要範囲 | 河川沿い都市を既定frameで棄却せず、最終CEに実際の水域が入る |
| 5 | 接続優先度と新設負担の校正、少数候補の共有橋評価、探索予算の調整 | 不要な大橋・重複横断を減らし、採用理由を説明できる。新たなマクロ経済モデルを前提にしない |
| 6 | seed群・既存fixture・性能検証、再生成UIと旧形式互換 | 全受入条件を満たしてから新方式を既定化 |

段階2〜3は「生成時から直角にしか渡らない」最小の一貫した実装単位。最終的な都市・街道最適化には段階4〜5も必要。新方式の幾何制約は`legacy/elevationAware`などの地形コスト設定に左右されない。旧コストを選んでも斜め橋を許可しない。

## 10. 再生成・既存地図・性能

- 街道だけの再生成では、都市と河川を固定して道路・橋だけを再計画する。都市移動を伴う新配置は新規生成または明示的な都市再配置に適用する。
- ロードだけでは既存都市・道路の保存座標・接続表を自動修正しない。旧データの診断は読み取り専用とし、新形式への移行は新規生成または明示的な再生成で行う。旧形式の移動・交易は従来の抽象的な接続モデルを維持し、ロード時に橋を接続表から削除して既存シミュレーションを寸断しない。
- ただしAGENTS.mdの「直角に交差しない橋は絶対に描いてはならない」に旧地図の例外はない。斜め橋を含む従来描画の完全維持は採用しない。問題の渡河区間は通常の橋・水上の道路線として描かず、対象地点と修復が必要な状態を橋ではない診断表示で示す。保存された座標、ロック、旧接続は保持するが、その形状を新方式の検証済みの橋と偽らない。これは表示互換に残る制約として明示する。
- 新方式へ移行する際には、ロック路を含む既存渡河を検証する。有効な施設だけを新グラフへ取り込む。無効なロック路があって完全移行できない場合は、結果をプレビューして未解決箇所を報告し、旧ネットワークをそのまま保持する。部分的な新旧混在による対岸接続を作らず、無断のロック解除・都市移動・道路削除はしない。
- 永続IDは座標文字列で作らず、橋・ノードの明示IDを使う。形状変更時はgeometryVersionで依存キャッシュを無効化する。保存・読込・再描画で経路が累積変形しないようにする。
- 水域の空間索引、河川近傍セルだけの細分化、局所回廊ごとの候補絞り込みで規模を抑える。毎都市対で全河川を走査しない。
- 土地の到達性と都市対候補をキャッシュし、採用施設の影響範囲だけ未確定候補を再評価する。各都市の候補数、共有評価の都市対数、進入回廊の候補数、探索状態・ラベル数、再試行回数に明示的な予算を設ける。上限到達は近似・未解決の診断とし、到達不能と混同しない。
- 同じseed・設定で同じ結果を得る。候補の評価順は安定ソートし、形状構築・描画でworld RNGを消費しない。計算時間、ノード・候補数、探索数を記録して現行との差を測る。

## 11. 受入テスト

幾何の保証と「それらしい分布」の評価は分ける。直角性は例外ゼロの制約、都市密度・橋数は比較指標として扱う。

| ケース | 確認する結果 |
| --- | --- |
| 縦・横・斜めの直線河川 | 接線と橋軸の正規化内積が数値誤差内で0。橋台が両岸にあり、進入区間も同じ法線上 |
| 全地形を回転・一様拡大した入力 | 橋の位相と直交性が維持される。単位設定を変えても実距離が同じなら判断が同じ |
| 一つのセルの両岸に二都市 | 橋なしで接続されない。同じcell IDから瞬間移動しない |
| 河川IDを持たないセル間の線分が水域を横切る | 幾何判定で禁止される |
| 狭い直線部と広い蛇行部 | 進入路も成立する狭い断面を優先。急曲率・合流・別の蛇行への再侵入は不採用 |
| 川沿いに並ぶ同岸都市 | 乾いた沿岸路を作り、不必要な左右岸往復をしない |
| 同岸に崖がある蛇行 | 十分な総便益がある必要な複数渡河は残り、採用理由が記録される |
| 広い川と代替路 | 高費用橋より迂回・既設橋・有効な渡しを選ぶ。限界超過・noneは陸路接続にしない |
| 複数都市が利用する橋 | 橋ID・建設費・描画が一つにまとまる。共同需要でのみ採算が合うケースも採用可能 |
| 二つの橋が揃って初めて有益 | 単一橋の貪欲評価だけで見落とさず、経路一式で比較する |
| 平地迂回と高山・峠 | 妥当な低地を優先し、合理的な唯一の峠は通れる |
| 気候・食料・取水条件の比較 | 他条件が同じなら温和で食料支持力のある地域の人口が増え、水際の浸水域は選ばれない |
| 小都市・大河・河口・湖畔 | 都市中心が乾いた土地にあり、河川沿い敷地のCE frameに実際の岸と水面が入る |
| 描画・descriptor往復 | SVG/WebGLの最終線とCEの逆変換後の橋台・進入端が一致。橋区間の平滑化や位置補正がない |
| 固定橋・可動橋・渡しと船舶 | 選定前に必要な航行条件を考慮し、確定後も既存の航行検証に通る |
| 保存再読込・再生成・ロック・手編集 | 勝手な座標変化、重複橋、自己リンク、無効橋の通行・通常描画がない |
| standard / 非standard / 国際trail | 同じ幾何制約が適用され、外交・所属条件を維持する |

既存のKy Cuong river ports、river foldback、河川と城壁のfixtureを利用し、FMGからdescriptorを作るところからCEの最終形状まで検証する。現行テストは探索・渡河方式・descriptor・WebGL adapter・CEそれぞれに追加し、制御点だけの検査で完了にしない。

全seed群で数える必須違反は、非直交橋数、未承認水域横断数、無効な対岸接続数、河川沿い敷地で水域がCEに入らない数。すべて0を受入条件とする。橋本数、総橋長、道路長、移動費用、孤立都市、同岸往復、食料供給達成度、実行時間は比較レポートに残す。橋を全部消して違反だけ0にする実装は、必要な接続が成立するfixtureで失敗させる。

角度の許容差、岸との距離許容差、進入長、候補間隔、費用係数、需要上限は中央設定にまとめる。前二者は数値精度から決める検証用の値、残りはfixtureとseed群で校正するゲーム設計の値として区別する。性能予算も段階0の計測を基準に決め、未計測の数値を達成済みとはしない。
