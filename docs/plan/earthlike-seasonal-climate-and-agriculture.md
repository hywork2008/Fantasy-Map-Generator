# 地球型の季節気温と農業への適用計画

作成日: 2026-10-05  
状態: 一部実装。候補係数による気候基盤・本体月次更新・旧表示値のロード後再構築を実装。観測較正、農業・統計表・REの移行は未完了。[実装記録](../calibration/earthlike-seasonal-climate-v1.md)を参照。

## 1. 目的と境界

地球と同じ大きさ・公転周期・地軸傾斜を基準に、セルの緯度・経度と地図上の海陸配置から年間の気温変動を概算する。画面の気温、栽培可能期間、収穫時期の判断に同じ気候データを使う。

本体と経済拡張の分離を維持する。本体が提供するのは作物に依存しない気候・地理・水資源情報までとする。経済拡張が作物を選び、栽培・収穫量を計算する。本体の食料キャパシティは、拡張をオフラインで実行して得た統計による近似値とし、実行時に拡張のソースコードを参照しない。

対象事例は `temp/000.savdata/Bria 2026-10-05-18-35.fmg` の都市391 Degoryesk、セル1273・1274・1275。セル1275の「年平均4°C、開始時20°C、南半球」という条件は、夏季の栽培可能性を調べる理由になる。ただし、ある日の20°Cだけでは成熟までの積算温度、期間、水量を確定できない。新モデルで必ず20°Cや特定の収穫量を再現することは要求しない。

既存の [季節気温計画](seasonal-temperature-variation.md) の年平均保持・月次更新方針を継承し、緯度だけの振幅計算を更新する。[作物カレンダー計画](seasonal-crop-calendars.md) の地域代表気温と固定月別偏差による栽培判定は、本計画の実セル気候による判定に置き換える。

## 2. 現行実装で分かれている計算

| 箇所 | 現在の動作 | 更新方針 |
| --- | --- | --- |
| `src/main.ts` / `calculateTemperatures` | 緯度と標高から年平均 `grid.cells.temp` を生成 | 初期段階では維持する。標高低下を季節側で二重に適用しない |
| `src/utils/seasonUtils.ts` | 緯度と赤道・極の温度差で季節振幅を決定 | 地球型の振幅・位相の純粋関数に分離する |

| `src/data/cropCalendars.ts` | 気候帯の代表年平均＋固定偏差で生育月を判断 | 実セルの月別気温を入力にする。地域名は表示用途として残せる |
| 経済拡張 `agriculturalLandUse.ts` | 年平均気温で適性・収量を評価。降水量8未満で降水係数0 | 栽培期間の熱量・利用可能水量で評価する |
| 経済拡張 `production-utils.ts` | 地域・気候帯・作物・コホートでカレンダーをキャッシュ | 気候と灌漑状態の変更をキー／無効化に含める |

現行の月次気温は、更新時の「日」を使用する一方で再計算のキーは月だけである。同月でも最初の更新日によって結果が変わるため、新モデルでは正規の月平均値を使う。

既存 [食料気候較正文書](../calibration/food-climate.md) にある誤差は旧経済モデルへの近似誤差であり、現実の農業への妥当性を保証しない。旧モデルで1275の農業寄与が0、非農業分を含むキャパシティが約4.9kになる結果を、新モデルの正解値にはしない。

## 3. 地理・暦の前提

- 地球定数は `src/data/earthConfig.ts` を使用し、既定の地軸傾斜は23.5°、暦は既存のグレゴリオ暦とする。
- セル中心の座標変換は `getEarthCoordinatesAtMapPoint` に集約する。南緯は負、北緯は正とし、経度は距離計算時に正規化する。
- 南北半球の季節は反転する。南半球の栽培期間が12月から翌年へ続く場合も連続期間として扱う。
- 経度だけから年較差や季節の位相は決まらない。架空地図の同じ緯度経度に現実のヨーロッパ等の気候を貼り付けない。海陸配置から海までの距離を計算する際に経度を使う。
- 月平均モデルに地方時は不要なので、経度による時差を季節の位相へ加算しない。
- 年々の異常気象、日較差、山脈による風下効果、海流の熱輸送、積雪の詳細は初期実装の対象外。月平均から推定した生育日数を、観測された無霜日数とは呼ばない。

緯度・標高・海からの距離を主要因とすることは [Met Officeの解説](https://weather.metoffice.gov.uk/learn-about/met-office-for-schools/other-content/other-resources/understanding-weather) に沿う。以下の数式と係数はゲーム用の近似案であり、同資料から得た回帰式ではない。

## 4. 月別気温モデル v1

### 4.1 年平均と海洋性

年平均 `Tannual` は既存 `grid.cells.temp` を正とする。季節モデルは年平均を変更しない。新規生成時の年平均気温自体の高精度化は別作業に分ける。

海岸までの地理的距離 `d`（km）から大陸性 `C` を求める。

```text
C = 1 - exp(-d / L)
L = 300 km（初期候補、観測比較で較正）
```

海岸は海洋に接する境界とし、内陸の小湖を海と同じ扱いにしない。`cells.t` の隣接段数をkmとみなさず、地球座標上の距離を使う。距離場は地形変更時に構築し、月次処理で全セル×全海岸の探索をしない。

部分地図の外縁を海岸と仮定しない。範囲外により最近傍の海岸が不明な場合は `C=0.5` を暫定値とし、`continentalitySource=regionalFallback` を保持する。地図内の海岸が最寄りか不確かな場合も境界までの距離で検出し、信頼度を落とす。海陸情報を持たない旧データにも同じ明示的フォールバックを使う。全周地図だけ経度方向を接続し、地域地図の左右端を接続しない。

### 4.2 振幅

絶対緯度に対して以下を線形補間し、海洋性・大陸性の振幅を混合する。振幅は年較差の半分で、単位は°C。

| 絶対緯度 | 海洋性振幅 `Asea` | 大陸性振幅 `Aland` |
| --- | ---: | ---: |
| 0° | 0 | 0 |
| 15° | 2 | 3 |
| 30° | 4 | 8 |
| 45° | 7 | 14 |
| 60° | 10 | 20 |
| 75° | 12 | 24 |
| 90° | 14 | 26 |

```text
A = ((1-C) * Asea(abs(latitude)) + C * Aland(abs(latitude)))
    * sin(axialTilt) / sin(23.5°)
```

この表は未較正の出発値。初期版は赤道の半年周期を省略し、赤道の年周期振幅を0にする。地球型23.5°を受け入れ対象とし、既存の傾斜設定も有限値・0°での無季節性を維持する。大きな傾斜角の物理的妥当性は保証しない。年平均設定を変更しただけで年較差まで比例して変わる旧挙動は採用しない。

### 4.3 季節の位相と月平均

気温の極大を夏至より遅らせる。初期候補は内陸20日、海洋45日の遅れとする。

```text
lagDays = C * 20 + (1-C) * 45
Y = その年の日数（365 または 366）
peak = 北半球なら6月21日、南半球なら12月21日の通日 + lagDays
r(t) = A * cos(2π * (t - peak) / Y)
```

`t` は1月1日0時を0とする連続日数で、`peak` も同じ原点を使う。年を越えた極大も周期関数で扱う。これは天文暦の厳密計算ではなく固定の至日による近似である。

各月の開始日から翌月開始日まで `r(t)` を積分し、月の日数で割って `r[m]` を得る。丸め誤差も含めて年平均偏差を補正する。

```text
rMean = Σ(days[m] * r[m]) / Y
T[m] = Tannual + r[m] - rMean
```

内部計算は浮動小数点とし、12か月の日数加重平均が `Tannual` に一致することをテストする。表示互換の `grid.cells.seasonalTemp` だけ既存の整数形式に変換する。作物評価は整数表示値を読み戻さない。

年平均4°Cで振幅16°Cという仮の条件なら、曲線の夏の極大は約20°Cになる。この例では基準温度5°Cを超える期間は概算175日あり、年平均4°Cだけでは栽培不可と判断できない。ただし、この振幅を1275に固定せず、その緯度・海岸距離から計算する。月平均、日別の平滑曲線、実際の日々の天候は区別する。

### 4.4 実データとの較正

まず [NOAA NCEIの1991–2020気候平年値](https://www.ncei.noaa.gov/products/land-based-station/us-climate-normals) の月別平均を使い、緯度帯・海岸距離別に振幅と最暖月を比較する。南半球の観測値は各国の気象機関等の一次資料を追加し、米国だけの適合を全球の精度と呼ばない。

観測地点ごとに年平均を引いた偏差を比較し、既存FMGの年平均モデルの誤差と季節振幅の誤差を分離する。地点単位で較正用・未使用の検証用を分け、月別MAE、振幅誤差、最暖月のずれを報告する。採用目安は月別偏差MAE3°C以下、最暖月のずれ1か月以内とし、未達の地域と理由を記録する。達成したという実績はまだない。

## 5. 気候データの責務と更新

本体に作物非依存の `CellClimateNormals` 相当の読み取りAPIを追加する。名前・型の配置は既存の拡張向け契約に合わせる。

```text
CellClimateNormals
  modelVersion / climateRevision
  latitudeDeg / longitudeDeg
  annualMeanTemperatureC
  monthlyMeanTemperatureC[12]
  annualPrecipitationMm
  monthlyPrecipitationMm[12]
  continentality / continentalitySource
  precipitationSeasonalitySource
```

降水量の内部単位からmmへの変換は一か所で定義する。現行の8を800mmと扱う換算について、生成・表示・水配分それぞれの契約を確認してから確定する。

純粋な気温曲線・月平均計算は本体の下位ユーティリティに置く。`seasonUtils.ts` のleaf制約を守り、world context・generator・extensionをimportしない。地形からの距離場生成とデータ更新はgenerator側が担当する。

更新の順序は「地理・年平均 → 気候プロファイル → 当月表示気温 → 拡張の農業計画／本体近似値」とする。全セルの12か月キャッシュはFloat32で約48バイト/セルであり、必要メモリと生成時間を計測して保持方式を決める。丸め前の平均保存テストにはFloat32誤差を考慮した許容差を使う。

キャッシュは月だけでなく地図ID、地理・気候revision、モデル版、暦の年種別も検証する。座標範囲、地形・海岸、年平均気温、傾斜、降水、水資源設定の変更を依存関係に応じて無効化する。同月の設定変更も反映する。農業計画には別途灌漑・作物・土壌・技術のrevisionを含める。

## 6. 農業計算への適用

### 6.1 作物の選択と成熟

経済拡張がセル気候を読み、作物・栽培型ごとに次を評価する。

1. 年間を循環する候補播種窓を探索する。
2. 本体の気温曲線から生育可能期間と積算温度を求める。月平均から日単位を扱う場合も同じ曲線を評価し、乱数による日々の天候は追加しない。
3. 栽培型の最低生育温度、必要積算温度、最低成熟日数、越冬・春化条件を評価する。
4. 同期間の利用可能水量を評価し、成立する作付けと面積を選ぶ。
5. 成熟可能な作付けだけから年収量・収穫月・労働月をまとめて生成する。

春播きと秋播きは同じ商品でも別の栽培型として持つ。既存の冷涼穀物の240日＋休閑30日だけで短い夏の栽培を排除しない。[FAOのオオムギ資料](https://ecocrop.apps.fao.org/ecocrop/srv/en/cropView?id=1232) は春播きと冬作で異なる栽培期間を挙げている。この区別を出発点に、作物ごとの値を一次資料で定義する。

スペルトも栽培型・成熟条件を明示する。クリは多年生樹木として休眠、低温要求、開花から成熟までの熱量、水、樹齢を扱う。穀物の短い生育窓をそのまま転用しない。年平均温度を前提とする既存Crop climate guideの範囲を、生育期平均の閾値にそのまま読み替えず、パラメータの意味と資料を更新する。

年収量とカレンダーを別々のモデルで計算しない。生産可能な場合の月別収穫重みの合計は1、不成立なら年収量も月別収量も0とする。二毛作は各作期の収量を足し、一年分の収量を各作期で重複計上しない。

### 6.2 降水と河川水

年降水量が500mmでも、その全量を栽培期間に使えるとは限らない。一方、年降水量800mm未満を一律0にする判定も採用しない。生育期に温度と水がそろう期間を評価する考え方は [FAOの生育期間の解説](https://www.fao.org/4/x5648e/x5648e0e.htm) を参考にする。

初期版で月別降水情報がない場合は、年降水量を日数比例で12か月に配分し、`precipitationSeasonalitySource=uniformAssumption` と明示する。緯度経度だけで雨季・乾季を決めない。後続版で季節降水を入れる場合も年総量を保存する。

経済拡張側に月次の簡易土壌水収支を導入する。入力は降水、配分された灌漑水、前月の土壌水。出力は蒸発散消費、流出、貯留とし、土壌別貯留上限を設ける。気温・緯度から求める簡易蒸発散は独立した方式・単位・係数を文書化し、寒冷時に負の消費を作らない。積雪融解を省略するv1では寒冷地域の水量に不確実性が残ることを較正結果に記録する。

河川水は既存の本体の水ネットワーク配分を利用し、上下流で二重に消費しない。現在の流量換算係数を物理的なm³/sと断定せず、年水量から月水量への契約を先に確定する。季節流量が不明なら年配分量を日数比例で分け、夏に任意の追加水を発生させない。灌漑面積・到達範囲・効率で実際に届く量を制限し、未灌漑面積に灌漑後の作物適性を適用しない。

## 7. 経済拡張なしの食料キャパシティ

依存方向を次に固定する。

```text
本体の地理・気候・水情報 ──→ 経済拡張の作物・収量計算
            │                        │
            │                  オフラインで条件を変えて実行
            │                        ↓
            └────────────→ 数値統計表を読む本体の近似計算
```

オフラインの較正ツールだけが拡張コードを呼べる。製品の本体から拡張へのimport、動的import、無効化された拡張の起動は行わない。共通化するのは気候などの物理入力であって、作物選択・生産ロジックではない。

既存の `foodClimateCalibration.test.ts` と統計成果物を新モデルで再生成する。年平均気温だけの表をそのまま流用しない。入力候補は年平均、季節振幅、生育期の長さ、年間降水、暖候期の水量、灌漑可能割合・追加水量、土壌とする。生育期の長さは例えば5°C超の日数など作物非依存の定義とし、本体に特定作物の判定を持ち込まない。

標本は年平均−5〜40°C、振幅0〜26°C、乾燥〜多雨、河川水0〜十分、灌漑割合0〜1をカバーする。高地・沿岸・内陸・南北半球・年をまたぐ栽培期を含め、低温年平均でも暖かい夏がある条件を重点化する。降水の季節配分を実装した版では暖候期多雨・寒候期多雨も別条件とする。水の時期と気温の位相の関係を失う単純な年総量への圧縮は検証なしに採用しない。

全軸の直積による標本爆発を避け、境界条件の格子と層化標本を組み合わせる。平均・分位点・選択作物の内訳を保存し、文化による差も別に集計する。本体に持たせない文化差等を平均化した場合はその誤差を報告する。近似形式は少数軸の補間表を第一候補とし、必要な特徴量は未使用標本で決める。

学習に使わない気候条件・地図で、収量のMAE、95パーセンタイル誤差、最大誤差、栽培可否の取り違えを測る。生産量0付近の割合誤差は使わず、絶対誤差も示す。目標は生産可能標本の平均収量に対するMAE5%以下、栽培可否の取り違え2%以下とする。未達なら特徴量を増やすか適用範囲を制限し、未達を隠して表を採用しない。

REの農地配置、本体キャパシティ、経済拡張の実生産では「潜在的に耕作できる面積」「現在の割当農地」「現在の収穫量」を区別する。1275の旧割当面積0を入力にして潜在収量まで常に0にする循環を避ける。REは有効な提供元の農地割当結果を描画し、独自の気温閾値で畑を再選別しない。

## 8. 保存データと互換性

- 年平均気温、人口、在庫、既存農地をロード時に黙って書き換えない。
- 気候モデル版を導入し、旧 `seasonalTemp` と月バケットが残っていても、新モデルの派生値は再構築する。
- 気候・統計表の版を対応付け、不一致の表を最新モデルの近似として使わない。ロード後と拡張切替時の再評価経路を用意する。
- キャパシティ再評価だけで食料在庫や既得収穫を増減しない。実生産への新しい作付け計画の適用時期は次の未確定作期とし、進行中の作期は計画版を保持して二重収穫を防ぐ。
- 気候図・セル情報・暖房などの既存消費者も新しい月平均を使う。描画更新は既存のtopicと再描画方針に従う。

## 10. 受け入れテスト

1. 日数加重した12か月平均は年平均と一致する。Float64計算で誤差1e−9°C以内、Float32格納後で1e−5°C以内を目安とし、閏年・年末年始も検証する。
2. 同じ絶対緯度・海岸距離では南北で暖候期が反転する。月の日数差があるため「6か月シフトした配列の完全一致」は要求しない。
3. 同じ緯度では内陸ほど振幅が大きく、海洋性ほど極大が遅い。経度だけを平行移動した同一地理では季節が変わらない。日付変更線をまたぐ距離、全周と部分地図を検証する。
4. 地軸傾斜0°と赤道のv1モデルでは年周期偏差0。年平均への標高補正が二重適用されない。
5. 同月1日と20日に初回更新した結果が一致する。同月の地図・気候変更後は再計算される。旧セーブの月バケットで更新が抑止されない。
6. 年平均4°C・十分な夏季熱量のケースと、通年4°Cのケースで適した春作の成立が異なる。期間・熱量・水が不足する場合は不成立になる。
7. 年500mmでも栽培期に水が足りる条件を一律0にしない。実際の利用可能水が0なら生産は成立しない。灌漑は河川配分上限を守り、部分灌漑の面積を超えて効果を出さない。
8. 南半球の年越し作期、春作・冬作、スペルト、クリの成熟条件を個別に検証する。収穫重みと年収量の整合、二重収穫の防止を確認する。
9. Briaの3セルについて変更前後の月別気温、成熟可能な作物、水量、潜在面積、割当面積、農業／非農業キャパシティ、RE表示を並べる。1275の正の収量を無条件の合格基準にせず、不成立ならその条件を数値で説明する。
10. 経済拡張を無効にした製品ビルド・実行で、作物計算への実行時依存がないことをアーキテクチャ検査と動作確認で確かめる。較正ツールの依存は製品から除外する。
11. 全セル再生成時間、月次更新時間、キャッシュメモリを代表サイズの地図で測定する。月次に海岸距離を再探索せず、既存の時間進行を大幅に悪化させないことを数値比較で確認する。

## 11. 実装前に確定するパラメータ

- 観測比較後の緯度別振幅、海岸距離の減衰尺度、季節遅れ。上記候補値を較正済みと扱わない。
- 春作・冬作・多年生ごとの熱量、成熟日数、越冬条件と、その一次資料。
- 降水内部単位、河川水単位、蒸発散と土壌保水の換算。全て同じ水収支で比較できるようにする。
- 季節降水・積雪を省略したv1で許容する地域と誤差。精度が足りない地域を年間値の強制補正で隠さない。

これらは実装工程で調査・較正する項目であり、今回の文書作成時点では未測定である。
