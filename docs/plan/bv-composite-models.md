# BVの複合モデルと部品別品質

2026-11-01

## 目的と調査結果

Medieval 33のUrban mendicant friaryを起点に、建物と付属設備を別々に作り、配置の組み合わせで用途・規模の違いを表現する。新しいFriary Highの制作より先に、Lowの負荷原因と部品の境界を整理する。

ユーザー提供のÁvila航空写真は「大きな教会堂＋隣接する回廊＋囲まれた中庭」という配置の参考とする。Salisbury G07にも回廊と参事会室がある。一方、外形が似ていることだけでFriaryをCathedralに分類し直さない。用途分類、建築様式、敷地構成、実在建築の固有再現は別の属性とする。今回、Ávilaの実測再現や歴史考証は行っていない。

固定BVプレビューの実測では、Friaryの旧Lowは350,742三角形。うち樹木4本が336,392（95.9%）だった。建築が精密だったためではなく、`createLandscapeTree`の品質省略で既定のUltraを生成していたためである。`siteVariants.ts`にもUltra樹木への依存が明記されていた。Highの判定は三角形数からの自動推定ではなく、モデル登録の明示的な品質を用いる。Friary自体にはHigh登録がない。

樹木を除いた14,350三角形のうち井戸が11,284。井戸も単独展示用の詳細が敷地の付属物にそのまま入っている。測定値と変更前後の記録は[負荷調査](../analytics/bv-composite-models-20261101.md)を参照。

住宅系はすべて「完成済み住宅の横に物を置くだけ」で成立するわけではない。店舗の大きな開口は外殻の生成入力に渡す必要がある。パン窯・炉の離隔、煙突と屋根の貫通、共用壁の重複除去、庇の支持、入口から中庭への通路も組み合わせ契約に含める。

調査開始時のHighには`house`、`oven`、`lodging`、`stable`、`serviceWing`、`brewingHall`等の関数があるが、多くは非公開で、位置が固定されていた。最後の`compactModel`で材質ごとに結合され、部品の意味も失われていた。この状態から描画後のメッシュ名だけで分割する方法は採用しない。P3のShop Housesでは生成境界を明示し、材質結合後にも台帳と部品範囲を残す方式を導入した。

## 部品生成と配置の契約

次の内容は実装予定であり、現行の保存形式にはまだ追加しない。

1. **部品定義**：安定した部品ID、用途、作者、品質別factory、基準寸法、占有領域、接続点、必要な空地、互換条件を持つ。壁・屋根の切り欠きは部品生成時に指定する。
2. **配置計画**：部品ID、配置、向き、寸法パラメーター、接続関係を保持する。`Monastery`の既存`buildings`・`walk`・`courts`・`trees`等を、まず描画用部品計画に変換する。地面のPointとThree座標の変換は既存`planFrame`を使う。
3. **組み合わせプリセット**：単なる部品の直積ではなく、用途に必要な部品と配置制約を持つ。既存モデルIDは同じプリセットを指す互換入口として残す。例えば共同パン窯は住居棟が不要、宿屋の中庭には通路が必要、Orthodoxの庭に西欧式回廊を自動追加しない。
4. **生成結果**：部品ごとのgroup・pickables・資源所有者・作者と派生元・計測値を保持する。BVでは部品選択／単体表示に用い、CEでは結合前に台帳を保存する。結合メッシュには部品の範囲または対応表を残す。

寸法は幅・奥行・ベイ数・階数等の限定した入力で再生成し、完成した全施設の非等方拡縮で合わせない。教会堂と回廊の接続面や標高は計画から決定する。既存CEの敷地・回廊の開口・門の通路・基礎標高を維持する。

## BVの表示・品質パラメーター

用途のカテゴリは現行のまま、選択モデルに応じて以下を表示する案とする。

| パラメーター | 内容 |
| --- | --- |
| View | 全体／部品単体／分解表示。分解表示の移動はBVの検査専用でCE計画には反映しない |
| Preset | Urban friary、住居併設パン屋等。互換性を満たす登録済み構成から選ぶ |
| Architecture quality | Low／High。High実装のない部品はLowと明記する |
| Vegetation quality | Off／Low／Medium／High／Ultra。建築品質から独立させる |
| Dressing | 井戸、家具・道具、商品、植栽などを部品群ごとに選択する |
| Layout | 回廊側・棟数・設備の接続先等、各プリセットで意味のある選択だけを提示する |
| Complexity | 全体と部品別の三角形・メッシュ・属性バッファ量。単体品質と全体コストを分けて表示する |

Offは生成前に除外し、非表示にするだけで生成負荷やメモリ削減を達成したと扱わない。品質や部品変更時は古い資源を解放する。同じ入力は同じ配置になるようローカルseedを使用する。

樹木Ultraを含むだけで全体をHighとしない。全体Highの可否は主要な建築部品の明示的なHigh対応から判断し、付属物の品質は別に示す。作者・依存元は実際に生成した部品から組み立てる。現在の`basedOn`は既定構成を示すため、任意の植栽品質をUI公開する段階では選択に追従するメタデータが必要になる。

High不足の監査では部品のHigh対応と組み合わせプリセットの対応を分ける。同じ部品の配置違いを独立した新規High資産として水増ししない。既存の全体モデル監査は、部品対応の監査を追加するまでは継続する。

## 負荷を抑える方針

- 植栽品質は必ず明示する。部品の既定値を呼び出し側へ暗黙に流入させない。
- 井戸Lowは開いた井筒、柱、屋根、巻上げ機という輪郭を残し、個別石材80個、屋根板168枚、巻き縄13巻等は単純化する。現在の単独展示用モデルは維持し、軽量部品を別に追加する。
- 部品の再利用は制作の共通化であり、それだけでGPU資源の共有にはならない。同一樹木・樽等の繰り返しはprototype共有またはinstancingを別途検討し、disposeの所有権を明示する。
- 結合は描画回数を減らすが三角形を減らさない。現CEは非index化と頂点色付加でバッファが増える。部品台帳を保ち、植栽のLODを更新できる単位でバッチ化する方向を評価する。
- Lowの固定Friary例は主要建築・外構を約6,000三角形以下、井戸を1,000以下、樹木を明示的Lowとすることを次段階の仮目標にする。メッシュ数も別に管理する。これは計画の規模が異なる全CE施設に一律適用する上限ではない。

P0〜P1を実装した。`ModelPartTracker`は生成中の明示的な境界から役割・品質・作者・依存元・メッシュ数・三角形数を記録する。部品IDは同じ保存計画と配列順に対して決定的で、編集で配列順を変えた前後の永続識別子を保証するものではない。BVでは部品別負荷表を表示し、CEでは非index化した結合メッシュの頂点範囲を部品IDへ対応付ける。井戸は既定Lowと既存の`default`をAPIで独立指定できる。任意指定した植栽・井戸の品質と依存元は台帳へ記録される。

P2で`monasteryComponents.ts`へ建築棟・回廊・壁・地面・植栽・井戸のfactoryを分離した。`monasteryPartFactories`は形状を作らずに部品を列挙し、`createModelAssembly`が選んだfactoryだけを生成して所有する。`createMonastery`の`partIds`は複数部品の部分構成にも対応する。BVは`MedievalModel.parts`のあるモデルへ`View`を表示し、全体／部品単体を切り替える。単体は元の配置を保持し、比較キャッシュへ全体モデルの計測値として登録しない。

P3のShop HousesはLowを5部品、Highを6部品に分け、住宅外殻と店舗開口、戸、カウンター、Highの棚、庇と支持材、商品・道具を区別する。`MedievalModel.parts`は選択variantと構成を受け取り、BVは`Composition`と`View`を組み合わせて表示する。`assembleParts`があるモデルはその結合方法を使う。標準以外の構成と単体の計測値は登録variantの比較キャッシュへ混入させない。`compactModel`は部品台帳と頂点範囲を維持し、明示指定時だけ同じ設定の通常Lambert材質をまとめる。

P3のBakeriesは、住宅棟または共同窯の上屋、窯本体、薪、冷却台、パン、支持台付き道具、捏ね作業台へ分割した。モデルと品質に実在する部品だけを列挙し、「標準」「作業設備なし」「窯と薪」の3構成を提供する。窯は台座・窯口・煙突・作業口の受け台を一つの部品として保持する。道具と支持物、捏ね槽と台を一緒に切り替えることで、構成変更時の支持関係を維持する。

P3のInnsは宿泊棟・中庭・厩舎・大型宿のサービス棟・卓とベンチの組・樽・看板・大型宿の門へ分割した。「標準」「中庭家具なし」「宿泊棟と中庭」を提供する。厩舎は床・柱・仕切り・飼葉設備・屋根を一緒に切り替える。看板は宿泊棟を含む構成で維持する。部品化後の指摘により、蓋に隙間のあるHigh専用樽を削除し、Lowと同じStorage propsの閉じた樽へ共通化した。樽の依存元と品質は両方で共通default（Low扱い）とする。[修正記録](../analytics/bv-inn-shared-barrel-20261101.md)。共通樽の4,940三角形は今後の付属物の軽量版の候補として残る。

P3のBreweriesは醸造棟・上屋・加熱ユニット・仕込み桶・麦芽作業台・貯蔵樽の6部品とし、「標準」「貯蔵樽なし」「醸造庭のみ」に対応した。加熱ユニットには炉・銅釜・煙突・煙道を含め、上屋側には煙突の切り欠きと雨仕舞いを残す。仕込み桶は蛇口・攪拌棒・液面を含む専用設備として保持する。閉じた貯蔵樽3本はHighもStorage propsへ共通化し、部品品質はLow扱いとする。共通化により標準Highの三角形数は増えるため、分割自体の形状維持と樽の置換を別々に計測した。

P4でFriary専用の`friaryDetails.ts`を追加した。壁は厚みを持つ開口付き外殻とし、隣接する棟の共有面を除く。屋根は隣接棟の高い面へ交わる箇所と鐘架の位置を切り欠き、重複する居住棟の床は一度だけ生成する。Highの部品も既存計画から寸法・向き・標高を求め、部品単体で生成・検査できる。登録の`default`と`low`はLow建築に固定し、`high`だけが詳細建築を生成する。CEはModel quality設定を渡し、変更時には修道院レイヤーを再生成する。StandardはLowへフォールバックする。CE画面で実際の対象がAbbeyだったことを確認し、Abbeyも共通の詳細外殻・回廊と専用の開口付き石造交差塔でHigh化した。FriaryとAbbeyの両方を設定で切り替える。[修正記録](../analytics/ce-abbey-quality-20261101.md)。OrthodoxのHighは未対応で、CEでは既存defaultを使い、直接生成APIで未実装のHighを指定すると拒否する。

修道院の植栽・井戸品質はAPI指定でき、BVでは既定Low。CEではModel qualityに追従し、植栽はLow／Medium／High、井戸はHighで既存詳細版default、それ以外でLowを使う。Friary・Abbey・Orthodoxに共通で、実際の依存元IDをCE採用モデル一覧へ記録する。主要建築のHighから付属物の品質を独立させる。住宅系も共通容器の品質は親のHighを継承しない。任意の混在品質を選ぶUI、自由な住宅と設備の交換、分解表示は未実装。P5ではSalisburyを12部品へ分け、全体Highの中でも参事会室は未詳細化のLowと明示した。次は参事会室のHighと他の固有建築の部品検査を進める。その後、監査に残る非樹木High候補の制作を再開する。

26 Civic Hallsと27 Cloth HallのHighにも同じ部品契約を適用した。`exteriorStair.ts`は寸法から階段・踊り場・支持柱・手すりを再生成し、扉接続点と通路の空地を返す。`civicHallParts.ts`が建築本体と共通外階段を独立factoryにし、接続点を実際の上階扉へ合わせる。BVのViewから単体表示でき、結合後も部品台帳と頂点範囲を保持する。入口側の手すりは通路の手前で止め、踊り場の外側・奥側を囲う。Lowの元の生成関数は維持し、Low階段の分割は未対応。[実装・通路検証記録](../analytics/bv-shared-exterior-stair-20261101.md)。

## 会館・ギルドホールの統一契約（2026-11-01）

Highの織物商人会館と職人ギルド会館4種は、`civicHallProfile.ts`の`GUILD_HALL_PROFILE`と共通建築factoryを使う。外形は幅15 m・奥行7 m、2階床高3.32 m、上階壁高3.25 m、屋根の立上り2.2 mで統一する。外階段は東側、扉はZ=-2.3 m、1階は石造アーチ回廊とする。職種によって変えるのは紋章・展示台・見本などの用途部品であり、建物の高さ・階段の面・柱の種類を個別に変えない。

市庁舎の高い上階と鐘楼、市場会館の木柱支持は、職人ギルドの差ではなく用途の異なる名前付き構成として`civicHallProfile`へ明示する。新しい階高・階段位置・支持構造が必要な場合は、既存部品の契約と互換性を確認したうえで構成を定義し、理由を記録する。Low/defaultの互換入口は維持し、古い前面階段を持つLow形状を今回一括変更しない。

[High不足監査](../analytics/bv-non-tree-high-quality-audit-20261031.md)の先頭にもこの設計への参照と制作規則を置く。監査の生成スクリプトにも同じ規則を含め、再生成で失われないようにする。制作開始時に既存の階段・支持部・床・屋根を確認し、部品単体表示、突出と接合の両方、入口通路、屋根貫通、資源所有を関連テストで確認する。
