## 0. 結論

- 描画の単位は四分木タイル（地図ピクセルの正方形）とし、都道府県は描画単位にしない。都道府県は「どこを表示するか」の選択と境界線に使う。
- 毎フレーム（カメラが動いたとき）、四分木を上から辿り、画面外の枝を捨て、画面上の誤差がしきい値を超えるタイルだけ子に割る。タイル数に上限を設け、上限内で誤差の大きい順に割る。これでズームしても画面内の頂点数がほぼ一定になる。
- 画面外・不要になったタイルは `geometry.dispose()` で GPU から外し、LRU で CPU 側のデータも捨てる。three.js の視錐台カリングは描かないだけでメモリは減らない。
- メッシュは Worker で作り、配列は Transferable で受け取る。今の「描き直しのたびに0.3〜0.4秒止まる」をなくす。
- 誇張（Height scale）は頂点シェーダの uniform にし、変えてもタイルを作り直さない。
- 局地戦の窓（[`japan-local-war-terrain.md`](./japan-local-war-terrain.md)）は「読み込み範囲を徒歩3日に絞ったタイル表示」として同じ仕組みに載せる。

## 1. いまの状態と問題

| 項目 | 値 |
| :--- | :--- |
| 地面 | 窓全体を1枚の `campaign-ground` として作り直す（`buildCampaignMesh`） |
| LOD | 窓の中心からの同心の環（`campaignAxis`）。カメラの位置ではなく窓の中心で決まる |
| DEM | 都道府県ごとのラスタ（1km・500mを配布、250m・100mは手元）。窓に掛かる県を丸ごと読む（`ensureLevels`） |
| 負荷（R4〜R8） | 配布の段で窓1つ約6.7万頂点・0.27〜0.31秒。日本全体を1枚で描くと2kmで94万頂点・4.1秒、1kmで376万頂点・12.4秒 |

問題は3つある。

1. 範囲を広げると頂点数と描き直しの時間が面積に比例して増える。全体表示ができない。
2. カメラを寄せても、窓の中心から離れた所は細かくならない（接触モードで窓ごと作り直すしかない）。
3. 都道府県のラスタは大きさが揃わない（北海道1km段で531×462、香川は数十×数十）。県境付近を見るだけで隣県を丸ごと読む。

## 2. 分割の単位

| 用途 | 単位 | 理由 |
| :--- | :--- | :--- |
| 描画・読み込み・破棄 | 四分木タイル | 大きさが揃い、親子で粗密を切り替えられる |
| 表示範囲の選択・境界線・ラベル | 都道府県 | 意味のある範囲で選べる |
| ゲームの判定 | FMG セル | 今のまま |

FMG セル（ボロノイ）は形が不揃いで親子が無いので、LOD の単位にならない。H3 などの六角形の階層は親子が近似でしか入れ子にならず、格子の継ぎ目処理が増えるので採らない。

### 2.1 タイルの座標

- タイルは地図ピクセルの正方形で切る。Japan の地図は経緯度と一次式で対応する（`georefMapToLonLat`）ので、地図ピクセルの正方形は経緯度の矩形と一致し、焼き込みでそのまま経緯度に戻せる。
- 最上位（z=0）のタイルの一辺は `rootKm`（初期値256km）を地図ピクセルに直した長さ。地図全体を `ceil(幅/一辺) × ceil(高さ/一辺)` 枚で覆う。
- z が1増えると一辺は半分。初期値では z=6 で4km。
- タイルの格子は `samples × samples`（初期値65、縁の1列は隣と共有）。格子間隔は z=0 で4km、z=2 で1km、z=3 で500m、z=4 で250m、z=5 で125m。

| z | 一辺 | 格子間隔（65点） | 対応するDEMの段 |
| :--- | :--- | :--- | :--- |
| 0 | 256km | 4km | `japan.bin` |
| 1 | 128km | 2km | `japan.bin` |
| 2 | 64km | 1km | 1km（配布） |
| 3 | 32km | 500m | 500m（配布） |
| 4 | 16km | 250m | 250m（手元・未定） |
| 5 | 8km | 125m | 100m（手元） |

日本の陸地（約37.8万km²）に掛かるタイルは z=2 で約150〜200枚、z=3 で約600〜800枚。海だけのタイルは作らない。

## 3. 選択（`src/renderers/terrainTiles/tileTree.ts`）

純粋関数とし、three.js に依存しない。テストできるようにする。

1. 最上位のタイルを候補にする。
2. `include(tile)` が偽のタイルは子も含めて捨てる。視錐台、表示する都道府県、陸の有無をここで判定する（呼び出し側が渡す）。
3. 各タイルの画面上の誤差を求める。
   - 幾何誤差 = 格子間隔（一辺 ÷ (samples − 1)）。
   - 距離 = カメラからタイルの箱（高さの最小〜最大を含む）までの最短距離。
   - 画面上の誤差 = 幾何誤差 × 投影係数 ÷ 距離。投影係数 = 画面の高さ(px) ÷ (2 tan(fov/2))。
4. 誤差がしきい値（初期値2px）を超え、z が `maxZoom` 未満で、子のデータがある（`hasData`）タイルを、誤差の大きい順に4つの子へ割る。
5. タイル数が上限（初期値256）を超える割り方はしない。
6. 読み込み前のタイルは、読み込めている最も近い祖先で代わりに描く（`resolveDrawable`）。祖先も無ければ描かない。

段の違うタイルの継ぎ目に出る割れ目は、タイルの縁に下向きのスカート（高さの差より長い垂れ壁）を付けて隠す。隣接の段差を1段以内に揃える処理（制限付き四分木）は、スカートで足りないと分かったら足す。

## 4. キャッシュと読み込み（`tileCache.ts`）

- 状態：未読 → 読み込み中 → データ有り → メッシュ有り。
- データ（標高の Int16 配列）は LRU で上限 64MB。メッシュは選択から外れて一定時間（初期値2秒）経ったら dispose する。すぐ戻ったときの作り直しを避けるため（ヒステリシス）。
- 読み込みは近い順に同時4本まで。選択から外れた要求は `AbortController` で取り消す。
- 上限は Playwright で測って決める（頂点数・FPS・`usedJSHeapSize`）。

## 5. メッシュ（`tileMesh.ts` と Worker）

- 入力：タイルの標高格子、陸海の判定、FMG の水域（川幅つき）、誇張なしのメートル単位。
- 出力：位置（y はメートル）、法線か陰影の色、スカート込みの index。
- Worker で作り、`ArrayBuffer` を転送で返す。メインスレッドは `BufferGeometry` に差すだけ。
- 誇張は `onBeforeCompile` で y に uniform を掛ける。陰影は誇張後の法線で決まるので、陰影もシェーダで求める（今の頂点色への焼き込みはやめる）。
- 川の谷寄せと掘り下げ（R8 の `snapRiverToValley`）は、タイルを跨ぐので、タイル作成ではなく地図全体の前処理で1回行い、結果の川の線と幅をタイルへ切り分けて渡す。

## 6. データ（`scripts/bakeJapanTiles.mjs`）

- 既存の都道府県ラスタ（1km・500m）と `japan.bin` から、タイルのピラミッドを焼き直す。新しい取得は要らない。
- 1タイル = 65×65 の Int16（0.5m刻み、−16,000m〜を表せる）＋ヘッダ。約8.5KB。z ごとに1ファイルへまとめ、索引に位置を書く（小ファイル数百枚の配信を避ける）。
- 索引 `index.json`：タイルごとに z/x/y、最低・最高標高、陸の有無、掛かる都道府県の ID。
- 境界線（海岸・県境）はタイルで切り、z ごとに点を間引く。元データは TopoJSON か MVT が良い（県どうしが線を共有し、隙間が出ない）。国土数値情報 N03（行政区域）は詳しいが、W05 と同じく利用条件を先に確かめる。それまでは Natural Earth admin-1 を使う。
- 配布の大きさの見積もり（陸に掛かるタイルだけ）：z=2 約1.7MB、z=3 約6.8MB。今の1km・500m（11.5MB）より小さくなる見込み（県境の重なりが無くなるため）。焼いてから測る。

### 6.1 細かい段の扱い（250m配布の判断に関わる）

国土地理院の標高タイル（dem_png）はそれ自体が XYZ タイルなので、z=4 以降は配布せず実行時に取る案がある。

| 案 | 内容 | 欠点 |
| :--- | :--- | :--- |
| 配布 | z=4 を焼いて配布 | z=4 で約27MB（見積もり） |
| 実行時取得 | Worker で dem_png を取り、メルカトルから地図の座標へ取り直す | オフライン不可。外部への依存。出典表記は Encyclopedia の既存の記載で足りる |
| 手元のみ | 今と同じ | 配布版は500mまで |

決めるのはユーザー。T3 で実行時取得の手間と速さを測ってから判断材料を出す。

## 7. 部分表示

- 表示する都道府県の集合を渡すと、`include` が索引の県 ID で枝を捨てる。
- 境界はタイルと関係ない形なので、シェーダで切る。県 ID のマスクテクスチャ（地図全体で 2048×2048 程度の R8）を作り、選んでいない県の頂点は暗くするか捨てる（`discard`）。
- 局地戦の窓は「中心から徒歩3日の円」を `include` に渡すだけで済む。

## 10. やらないこと

- 他のテンプレート（地理参照の無い地図）への適用。FMG のセル標高だけではタイルにしても細部が無い。
- 地球の曲率。Japan の範囲は正距円筒の平面で扱う。
- 建物・樹木などの立体物。

## 11. T0 の結果（2026-11-17）

- `src/renderers/terrainTiles/tileTree.ts` を追加した。`tilePyramid`（地図の大きさと一辺から最上位の並びを決める）、`tileBounds`、`selectTiles`（誤差の大きい順に割り、上限と `include`・`hasData` を守る）、`resolveDrawable`（読み込み前は祖先で代わりに描く）。
- テストで確かめたこと：近いタイルほど深く割れる、`include` で捨てた枝は子も出ない、上限を超えない、選ばれたタイルが重ならず隙間なく覆う、祖先での代替が重複しない。

## 12. T1 の結果（2026-11-17）

記録: [`../analytics/japan-terrain-tiles-20261117.md`](../analytics/japan-terrain-tiles-20261117.md)。

- `scripts/bakeJapanTiles.mjs` を追加した。既存の `japan.bin` と配布の1km・500mの県ラスタから z=0〜3 を焼く（11秒、取得なし）。
- 索引の各タイルは `[x, y, 位置, 最低m, 最高m, 県の番号]`。県の番号は Natural Earth admin-1 を1km格子に塗って求める。
- z0・z1 は近隣の陸（朝鮮半島など）も持つ。z2 以降は日本の県に掛かるタイルだけ（`--fineFrom`）。
- 大きさ：z0〜3 で 982 枚、8.33MB（gzip 5.36MB）。§6 の見積もり（z2 1.7MB、z3 6.8MB）に対し、z2 1.6MB、z3 4.7MB。
- 調整中は Git 管理外（`.gitignore`）。県ラスタから再生成できるため。配布するなら、同じ段の県ラスタ（11.5MB）を置き換える形にするかを T4 の後で決める。
- 課題：z0・z1 は点で拾うので山頂が低く出る（富士山 z0 2,971m）。全体表示で目立てば面平均か最大値で焼く。

## 13. T2 の結果（2026-11-17）

記録: [`../analytics/japan-terrain-tiles-20261117.md`](../analytics/japan-terrain-tiles-20261117.md)。

- `terrainTileLayer.ts`（選択・読み込み・作成・破棄）と `tileMesh.ts`（格子・陰影・垂れ壁）を追加した。戦争用3Dで `?ltTiles=1` のとき、窓の地面を隠してタイルを描く。川・道・都市・駒は従来の窓のまま重ねる。
- 焼いていない海のタイルは、海面のすぐ下の平面1枚で埋める。
- 日本全体が41万頂点・0.11秒で出る（1枚の2km格子は94万頂点・4.1秒）。局地の斜めは窓（11.5万頂点）より多い82万頂点。窓の外の地平線まで描くため。FPS はどれも60で頭打ちなので、頂点数の差はこの機械では見えない。
- カメラを動かしたときの1回の更新は最大24ms。窓の描き直し（0.3〜0.4秒）の止まりは無くなった。Worker 化（T3）の急ぎは下がった。
- 課題
  1. 接近・地表でも細かさは z3（500m）止まり。250m・100m の段（手元）か実行時取得を z4・z5 として足さないと、接触モード（100m）の代わりにならない。
  2. 高さの誇張と陰影を頂点に焼いているので、Height scale を変えると全タイルを作り直す。
  3. タイルの継ぎ目に陰影の筋がうっすら出る（縁の陰影を片側差分で求めているため）。焼き込みで縁を1点ずつ広く持てば消える。
  4. 地平線まで描くので、斜めの頂点数は窓の7倍。戦争用では `include` に「窓から何km」を足して遠景を z0〜1 に抑えるかを T4 で決める。

## 14. T3 の結果（2026-11-17）

記録: [`../analytics/japan-terrain-tiles-20261117.md`](../analytics/japan-terrain-tiles-20261117.md)。

- 手元の250m・100mから z4（250m）・z5（125m）を焼いた（`--local`）。細かい段は、その細かさのラスタが陸の5割以上を覆うタイルだけ書き、親に `split`（子が揃っているか）を持たせた。100mの無い県では z4 で止まり、穴は開かない。
- 焼き込みで外周に1点ずつ余分に持たせ（`border`）、縁の陰影を隣のタイルと同じ点で求めるようにした。継ぎ目の筋は見えなくなった。
- 高さの誇張は、Height scale 50（×3）で作ったメッシュの群を縦に拡大するだけにした。50→100 で表示中の98%のタイルを作り直さない。陰影は×3のときのまま（誇張を大きくしても陰が濃くならない）。
- 接近の頂点は108万（窓の接触モード17万の6倍）だが FPS は60のまま、1回の更新は最大24ms。z5 が関ヶ原の近くで60枚描かれ、接触モードの100m環の代わりになる。
- Sekigahara の接近では、窓は国の色、タイルは標高の色になる（タイルは地図の塗りを持たない）。地図の塗り（国・文化など）をタイルに載せるかは T4 で決める。
- 課題
  1. 段ごとにファイル全体を読むので、z4 で16.7MBを一度に読む。タイル単位で読む（`Range` 要求か、z4 以降を地域ごとのファイルに分ける）に変える。
  2. z5 の焼き込みは全域を走査するので遅い（413秒）。100m のある範囲だけ走査するよう直す。
  3. 地平線まで描くので、斜めと東京の接近は上限256枚に当たる。遠景の扱いは T4 で決める。

## 16. T4 の結果（2026-11-17）

記録: [`../analytics/japan-terrain-tiles-20261117.md`](../analytics/japan-terrain-tiles-20261117.md)。

- 遠景の制限：戦争の焦点から `farKm` より遠いタイルは `farZoom`（既定1、2km）までしか割らない。既定 `farKm` は100km（徒歩3日の窓の半幅84kmの少し外）。接近では枚数が東京 256→118、関ヶ原 240→163 に減り、斜めでは浮いた枠が窓の近くの細かい段に回る。URL `ltTileFarKm`・`ltTileFarZoom`。
- 都道府県の部分表示：`tiles.prefectures`（URL `ltTilePrefs=JP-21,JP-25`）。選んだ県に掛からないタイルは描かず、掛かるタイルの県外は暗くする（県マスク `prefectures.bin`、1km格子）。部分表示では海の平面を出さない（全面の海が「日本の他は海」に見えるため）。岐阜・滋賀だけなら日本全体で7枚・3.1万頂点。
- 国の色：既定では載せない。`tiles.mapColors: "states"`（URL `ltTileColors=states`）で陸に国の色を55%重ねる。色は地図ピクセル2px格子で一度だけ `findCell` から作り、国の色が変わると作り直す。
- 残り
  1. 部分表示でも、FMG のセル境界・川・道の線は県外まで描かれる。線を県で切るかは未定。
  2. 県マスクは Natural Earth admin-1（粗い）を1km格子に塗ったもの。県境が階段状になる。詳しい県境（国土数値情報 N03 など）は利用条件の確認が先。
  3. 段のファイルを丸ごと読む（z4 で16.7MB）。タイル単位の読み込みは未着手。
  4. タイル表示は `?ltTiles=1` のときだけ。既定にするかは、配布（z4 以降をどうするか）と合わせて決める。

## 17. T5 の結果（2026-11-17）

記録: [`../analytics/japan-terrain-tiles-20261117.md`](../analytics/japan-terrain-tiles-20261117.md)。

- 決定（ユーザー）：タイル表示を既定にする。4段目（250m）以降は配布しない。
- 既定：`tiles.enabled` true、`maxZoom` 5（入っている段で頭打ち）。`?ltTiles=0` で従来の窓の地面に戻る。索引が読めるまで（読めないときも）従来の地面を出す。
- 配布：`index.json`・`z0.bin`〜`z3.bin`・`prefectures.bin`（約13MB、gzip 約6.4MB）をコミットする。500m より細かい段は `index.local.json` に分けて Git 管理外にし、実行時にあれば継ぎ足す。
- タイル単位の読み込み：2MB 以下の段（z0〜z2）は丸ごと、それより大きい段は1枚ずつ HTTP Range で読む（同時8本、48MB までの LRU）。Range が効かない配信では段ごと丸ごとに切り替える。読み込む高さは 30MB から 4〜8MB に減った。
- 焼き込みは、細かい段で1段上に焼いたタイルの子だけを走査するようにし、413秒から27秒になった。
- 残り
  1. 従来の窓の地面（`campaign-ground`）を隠しているだけで、作る処理（0.3秒前後）は毎回走る。タイルが既定になったので、地面の作成を省く。
  2. 川・道・都市・駒の高さは、従来どおり県ラスタ（`japan-local/`）から取る。タイルと同じ高さを読むようにすれば、県ラスタ（11.5MB）の配布を止められる。
  3. 部分表示で線を県で切るか、県境データの精度（N03）は §16 のまま。

## 18. T6 の結果（2026-11-17）

- タイルの索引が読めているときは、窓の地面（`campaign-ground`）を作らない（`CampaignBuildInput.skipGround`）。描き直しは 372ms から 24〜38ms になった。初めて戦争用3Dを開いたときだけ、索引の読み込み前に一度作る。
- 線・都市・駒の高さは、読み込み済みの最も細かいタイルから取る（`TerrainTileLayer.metersAt`）。地面より15m上に載り、地面より下に潜る点は無くなった。細かい高さが届いたら、読み込みが落ち着いたところで線だけ作り直す（400ms 待ち）。
- 接触モード（カメラが近いと窓を100m環で作り直す）は、タイルが細かさを受け持つので止めた。
- 残り
  1. 表示中のタイルが粗い段のとき、細かい段の高さに載せた線が粗い地面に隠れることがある（遠景）。線の高さを表示中の段に合わせるかは見た目で判断する。
  2. 従来の窓は FMG の川を川幅で水色に塗っていたが、タイルは塗らない（線だけ）。タイルに川の塗りを載せるかは未定。
  3. 県ラスタ（`japan-local/`、11.5MB）は、川の谷寄せ・海岸の判定（`createLocalTerrainField`）と、タイルが読めないときの高さにまだ使う。これをタイルの高さに置き換えれば配布を止められる。止めるかはユーザーの判断。
