# CE都市生成の最速化計画（出力を変えてよい場合）

2026-10-15。[ce-generation-failure-speed-plan.md](ce-generation-failure-speed-plan.md) の P3 は「出力を1ビットも変えない」制約下の高速化で、全596都市の合計を 380 s → 271 s にした。本書はその制約を外し、**生成結果が変わってよい**前提で、最速を目指す場合の案をまとめる。

根拠データ: `temp/benchmarks/p3-full1.jsonl`（Triviers 596都市、P3 完了時）と、CPUプロファイル（`node --cpu-prof`）。数値は特記しない限りこの計測による。

## 1. まず押さえる事実

### 1.1 時間はどこに使われているか（全596都市、271 s）

| 区分 | 時間 | 割合 | 内容 |
| --- | --- | --- | --- |
| 建物区画（fabric）の構築 | 約 133 s | 約49% | 下の 1.2 の重複構築が主 |
| 　`generation` 直下の自己時間 | 50.4 s | 18.6% | ほぼ全てが生成後の最初の `buildBlockFabric`（計測されていない） |
| 　`fit-housing` | 82.2 s | 30.3% | 住宅数の調整。区画構築を3〜4回繰り返す |
| 道路・門・壁の組み立て `apply-plan` | 45.7 s | 16.8% | 後述 1.3 |
| 計画 `plan` | 33.3 s | 12.3% | 後述 1.3 |
| 港の船 `harbor-ships` | 20.4 s | 7.5% | 港町157都市で、さらに区画を1回構築する（15.6 s） |
| その他（`finish-geometry` ほか） | 約 30 s | 約11% | |

- 都市の規模（住宅数）に対する時間の増え方は k≈0.43 で、固定費の比重が大きい。上位10%の60都市が全体の39%で、**全体の92%は small 都市**。したがって「重い都市を速くする」より「全都市に共通の工程を減らす」ほうが効く。
- 大きな都市の最大は 4.2 s。体感の遅さを決めるのは港町（`coastal-reservations`、`harbor-fabric`、`harbor-ships`）。

### 1.2 区画（fabric）構築の重複

1都市を生成する間に、同じ文書から区画を作る処理が次のように繰り返される。

| 呼び出し元 | 回数 | 備考 |
| --- | --- | --- |
| `generateCity.ts` の生成後（都市化計画の入力） | 1 | `generation` 直下の未計測の正体 |
| `fit-housing` の `count()` | 3〜4 | 地区の設定を少し変えて数え直す。うち1回は直前と同条件（P3 で省略済み） |
| `harbor-ships`（港町のみ） | 1 | `ship-plan` 内で別に構築 |
| 生成後にUIが表示するとき（アプリ内） | 1 以上 | `ce:perf` の計測には含まれない |

最終的に必要なのは「最後の姿の1回」だけで、残りは**住宅数を数えるための試し作り**。

### 1.3 計画・組み立て段階の内訳（プロファイルの例）

- `plan`: 城の配置（`placeCastleRegion`）と、内壁計画後の再割り当て（`remap`）が大半。12 Dunsbole では `planDefenses` が `plan` の約 70% を占める。
- `apply-plan`: `applyRoads` が大半で、その約6割が `assembleRoads.ts` の「全辺について水面と交差するか」を調べる2か所（辺ごとに水面ポリゴンを取得し直している）。P3 で試した「辺ごとから1回にまとめる」変更が、30都市で約10%速かった。テストが失敗して戻したが、これは**未解決の問題を示唆している**（4.1 を参照）。
- 文書の複製（`structuredClone`）は1都市あたり144〜220回、145〜350 ms で全体の3〜8%。複製の仕組み自体は共有フィールド化済みで、支配的ではない。
- メッシュの O(E) 走査（`incidentEdges` など）は1都市263回・計30万要素で、1〜10 ms 程度。**今は問題ではない**。

### 1.4 計測のバイアス

`ce:perf` は都市ごとに新しいプロセスで測る（`sequential-fresh-process-per-run`）。同じプロセスで6回連続生成すると、2回目以降は1回目より速い。

| 都市 | 1回目 | 2〜6回目 |
| --- | --- | --- |
| 100（small、中央値付近） | 435 ms | 約 255 ms |
| 14（港、small） | 3164 ms | 約 2500 ms |
| 1（Leigh、medium） | 4637 ms | 約 4100 ms |
| 12（港、small） | 2768 ms | 約 2350 ms |

- 小さい都市ほど、JIT とモジュール初期化の影響が大きい。アプリで使うときは暖まった状態なので、**最速化の判断には暖機後の時間を使うべき**。
- 現行の計測は、改善の効果を実際より小さく見せる。

## 2. 方針

1. **重複の削除を最優先にする**（49%を占める fabric 構築を、構築回数の削減で減らす）。
2. その次に、組み立て・計画の個別の無駄を削る。
3. 出力が変わる変更を許す代わりに、**品質を判定する指標を先に整える**。ハッシュ一致は使えなくなるので、「同じ品質か」を測る仕組みが必要。
4. 並列化は、1都市の生成を速くするのではなく**バッチと応答性**に使う。

## 3. 計測と品質ガード（最初にやる）

出力が変わるので、P3 までの「ハッシュ一致」に代わる合格基準を決める。

### 3.1 計測の改善

| 項目 | 内容 |
| --- | --- |
| 暖機計測 | `ce:perf --warm`: 同じ Worker で複数都市を連続生成し、最初の N 件を捨てる。既定は従来どおり新プロセス。速度の判断は `--warm` で行う |
| 並列計測 | `ce:perf --jobs N`: 都市を N プロセスに分けて測る（このマシンは10コア）。計測自体を 1/5〜1/8 に短縮できる。時間の比較は並列度を固定する |
| 未計測部分の可視化 | `generation` 直下を `initial-fabric`、`urban-growth-plan`、`validate` などに分けて計測する |
| 区画構築の回数 | `buildBlockFabric` の呼び出し回数と呼び出し元を JSONL に記録する |

### 3.2 品質ガード（出力が変わってよい範囲の定義）

`ce:perf:query` に `quality` コマンドを追加し、前後のレポートを次の指標で比較する。1つでも悪化したら変更を採用しない。

| 指標 | 基準 |
| --- | --- |
| 生成成功率 | 596/596 を維持。再試行回数・捨てた時間が増えない |
| 住宅数の誤差 | 目標住宅数との差の分布（中央値・p95）が悪化しない（既存の許容は ±10%） |
| 地図の検証 | `crossing-validation`、`road-connection-validation`、`wall-defense-closure` の違反件数が増えない |
| 橋 | [AGENTS.md](../../AGENTS.md) の橋の斜め交差の上限を超える橋が0（`bridgeSkewPolicy.ts` の判定を使う） |
| 区画の量 | 建物数・市街地面積の中央値が ±3% 以内 |
| 目視 | 代表12都市（首都・港・河川・城塞・二重市壁・小さな村）を描画して確認する（`temp/p1dbg/draw.mjs` と同種のツール） |

## 4. 変更案

効果は、全596都市の合計 271 s に対する見積り。出力が変わるものには ★を付ける。見積りは設計上の推定で、各段で実測して確かめる。

### 4.1 重複の削除（出力不変、または不変に近い）

| # | 案 | 見積り |
| --- | --- | --- |
| A1 | **共有キャッシュ**: 生成後の最初の区画構築、`fit-housing` の各回、港の船の計画で、1つの区画キャッシュ（`FabricCache`）と構築結果を共有する。地区の設定が同じ回・同じ地区は再利用する | 区画構築のうち約1/4〜1/3を削減。-10〜15% |
| A2 | `fit-housing` の初回の数え直しを、生成後の最初の構築結果から作る（A1 の一部） | 上に含む |
| A3 | `harbor-fabric` の計画（港の桟橋・広場）を、入力の街路が同じ間は再利用する | 港157都市で 11 s のうち約2/3。-2〜3% |
| A4 | `assembleRoads.ts` の水面判定を1回にまとめる（P3 で一度試して戻した案）。**先に失敗の原因を特定する** | apply-plan の約3割。-5% |
| A5 | `sameCoast`（水面ポリゴンのキャッシュ検証）が水面判定のたびにメッシュ全体を比べている。メッシュに版番号を持たせて O(1) にする | 0.5〜1 s。-0.4% |

A4 の失敗は、「同じ都市を2回生成した結果が一致しない」テストで出た。水面ポリゴンのキャッシュが、呼び出し回数や順序に依存して結果を変えている疑いがある。ここを直さずに他の最適化を重ねると、再現性の問題が表に出にくくなる。A4 の原因調査は、他の変更より先に行う。

### 4.2 区画構築の回数を根本から減らす ★

| # | 案 | 見積り |
| --- | --- | --- |
| B1 | ★ **住宅数の調整を、再構築せずに行う**。現在は占有率を変えて区画を作り直し、数を数えている。最大の占有率で区画を1回だけ作り、各区画に「採用順」の優先度を付けて、目標戸数になるよう上位から採用する。調整は並べ替えと切り捨てだけになる | `fit-housing` の構築を3〜4回から1回に。-20〜25% |
| B2 | ★ 住宅数の調整の途中の数え方を、建物を作らず区画数の見積りで行う（B1 が難しい都市のみ、最後に1回だけ実構築して補正） | B1 の代替。-15〜20% |
| B3 | ★ `harbor-ships` の船の計画で、区画を作らずに桟橋と水際の情報だけを使う。船の位置は建物の詳細に依存しないよう設計を変える | 港157都市で 15.6 s。-5% |

- B1 の注意点: 現在は「占有率を下げる＝密度が下がる」ことで街の見た目が変わる。上位採用では、通り沿いから埋まるなど、見た目が変わる。採用順の決め方（街路への近さ、広場への近さ、区画の面積）を設計して、現行の分布に近づける必要がある。
- B1 の検証: 住宅数の誤差、通りごとの密度分布、目視。

### 4.3 計画・組み立ての個別の無駄

| # | 案 | 見積り |
| --- | --- | --- |
| C1 | ★ 城の配置（`placeCastleRegion`）の候補探索を減らす。候補の評価を空間索引で絞り、評価の順序を打ち切りやすいものにする | `plan` の約3〜5割。-4〜6% |
| C2 | 二重市壁の計画（`planInnerTown`）の再割り当て（`remap`）を、2回目以降は差分だけにする。P2 で2段階の選択を入れたため、計画と構築で同じ処理が繰り返される | 二重市壁の都市のみ。-1% |
| C3 | ★ `applyRoads` の道路の探索で、辺の通行可否（水面・壁・城・川）を最初に1回の配列にして、探索中は参照だけにする | apply-plan の1〜2割。-2〜3% |
| C4 | ★ 計画段階の道路の経路探索に、都市の外側の道を後回しにする遅延評価を入れる（外側の道は他の処理で再計算されることが多い） | 要プロファイル |
| C5 | `moveVertices` のように1頂点ずつ文書全体を複製する経路を、1回の複製にまとめる（バッチ編集） | 港・河川都市で 0.3〜0.4 s/都市。-1〜2% |

### 4.4 データ構造と実装

| # | 案 | 見積り |
| --- | --- | --- |
| D1 | 多角形・線分の幾何関数（`pointInPolygon`、`segmentGap`、`polygonOverlaps` ほか）を、点の配列 `[x, y][]` ではなく `Float64Array` の平坦な配列で扱う。割り当てを減らし GC（現在1都市あたり15〜20%）を下げる | -5〜10% |
| D2 | 空間索引（`BoxIndex`）を各所で別々に作っている。文書ごとに1つ作って共有する | -1〜2% |
| D3 | 区画の構築中に作る小さな配列（`[x, y]` の点、`{a, b}` の線分）の再利用 | D1 と合わせて評価 |
| D4 | `Object.values(mesh.edges).filter(...)` のような走査を、頂点→辺・面の隣接表（メッシュの索引）に置き換える。**現状は 1〜10 ms なので優先度は低い**。ただし将来のメッシュの大型化には効く | 現状 -0.5% |

### 4.5 並列化と非同期

| # | 案 | 効果 |
| --- | --- | --- |
| E1 | **バッチ生成の Worker プール**: FMG の全都市（数百〜数千）を一括で生成するとき、都市を Worker に分配する。都市は互いに独立 | 10コアで 5〜8倍の壁時間短縮。ブラウザ・Node の両方 |
| E2 | 1都市の生成を Web Worker に移す。時間は変わらないが、UIが固まらない | 体感の改善 |
| E3 | 1都市の中で、地区ごとの `local-fabric`（互いに独立）を Worker に分配する | 大きな都市のみ。転送コストがあるため、medium 以上でのみ |
| E4 | 暖機した Worker を使い回す（初回の遅さ 435→255 ms を避ける） | 小都市の初回 -40% |

### 4.6 品質と速度の段階化（下書きモード）★

| # | 案 | 効果 |
| --- | --- | --- |
| F1 | ★ **下書き生成**: 道路・壁・門・街区の骨格だけを先に出し、建物・港の船・風車などの細部は表示時に遅延して作る。FMG からの一括生成では下書きだけを作り、都市を開いたときに細部を作る | 一括生成の時間を約 1/3〜1/2 に（fabric と港の船を省く）。開いたときの待ちは増える |
| F2 | 遅延した細部を、バックグラウンドで先に作る（アイドル時、または隣接する都市を先読み） | 開いたときの待ちを隠す |
| F3 | 表示範囲（ズーム・視野）の外の区画は作らない | 大きな都市。UI側の対応が必要 |

## 5. 実施順序と到達見込み

| 段階 | 内容 | 累積の合計時間（見積り） |
| --- | --- | --- |
| S0 | 3.1 の計測改善と 3.2 の品質ガード、A4 の原因調査 | 271 s（基準を暖機・並列で取り直す） |
| S1 | 4.1（A1〜A5）。出力はほぼ不変 | 約 215〜230 s |
| S2 | 4.2（B1 または B2、B3）★ | 約 150〜170 s |
| S3 | 4.3（C1〜C5）★、4.4（D1〜D3） | 約 120〜140 s |
| S4 | 4.5（E1、E2、E4） | 壁時間は並列度に応じてさらに 1/5〜1/8 |
| S5 | 4.6（F1、F2）★ | 一括生成の壁時間を、下書きのみで約 1/3〜1/2 |

- S1 は P3 と同じく、ハッシュで検証できる範囲（A4 のみ要調査）。S2 以降は 3.2 の品質ガードで検証する。
- 全体では、1都市あたりの CPU 時間を 271 s → 120〜140 s（約半分）、バッチの壁時間を 10 コアで約 1/10 程度まで短縮できる見込み。見積りは各段で更新する。

## 6. 順序の理由

- S0 を最初に置く理由は、暖機計測がなければ、小都市の改善が過小評価され、判断を誤るため。品質ガードがなければ、S2 以降の「速くなったが壊れた」を見逃す。
- S1 を S2 の前に置く理由は、キャッシュ共有（A1）で区画構築のコストが下がると、B1/B2 の効果の見積りが変わるため。また A4 の原因が、キャッシュの設計（版番号の導入）に関係する可能性が高いため。
- 並列化（S4）を最後の方に置く理由は、1都市あたりの CPU 時間を先に減らすほうが、並列化の効果も大きくなるため。ただし E1 は独立しているので、S1 と並行して着手してもよい。
- 下書きモード（S5）は仕様の変更を伴い、FMG と CE の運用に影響する。性能の限界を見極めてから、必要かどうかを判断する。

## 7. リスク

| リスク | 対策 |
| --- | --- |
| 出力が変わって見た目が悪化する | 3.2 の品質ガードと代表都市の目視。悪化したら採用しない |
| 決定性（同じ入力で同じ出力）が崩れる | 同じ都市を2回生成して一致することを、全都市で検査する。A4 の原因調査で見つかる問題の再発防止にもなる |
| 共有キャッシュの古い値（in-place の更新） | キャッシュのキーに内容または版番号を含める。キャッシュした値を変更する箇所を検出する |
| 暖機計測が実際の初回体験と乖離する | 速度の報告には「暖機後」と「初回」の両方を載せる |
| 並列化で結果の順序や乱数が変わる | 都市単位の seed を固定し、都市間で状態を共有しない |
| 品質ガードの指標が足りない | 目視で見つかった問題は、指標として追加していく |

## 8. 未確認事項

- A4 の失敗原因（水面ポリゴンのキャッシュ）。
- `plan` と `apply-plan` の内訳は、少数の都市のプロファイルでしか見ていない。S0 で全都市の内訳を取る。
- B1 の「採用順」で、現行の密度の分布に近い見た目になるか。
- D1 の効果（GC の削減）は推定で、小さな実験で確かめてから全体に広げる。
- アプリ内（UI表示）の区画構築の回数と時間は、`ce:perf` に含まれていない。Playwright で別に計測する。
