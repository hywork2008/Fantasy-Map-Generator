# CE 二重市壁を内側から生成する比較実験の設計

- 作成日: 2026-10-13
- 状態: 内側先行の実験モードを実装済み。既定は外側先行。実装と少数ケースの比較結果は§9。
- 対象: CE。CGは対象外。
- 既存方式: [外側から作る二重市壁](./ce-multi-ring-walls.md)。同文書を履歴として保持する。
- 調査基準: Git `3932b06a3970671bd5f0bc34adc8ee5199a650e7`（調査開始時の作業ツリーに変更なし）。
- 依頼元: `codex://threads/01a1340e-2b3f-7250-b665-8dec87abd1e4`。スレッド本文は参照できておらず、現行コードと既存設計書を根拠とする。

## 1. 結論と検証する仮説

外壁を確定してからその内側に旧市壁を収める方式を残し、旧市街の防御線を先に確定してから、その外側へ市街地と外壁を拡張する方式を追加する。

仮説は「外壁・外門・橋による制約が少ない段階で内壁を作れば、河川沿いの閉鎖可能な経路を選びやすい」。ただし、生成順だけでは欠落を防げない。河川に触れた壁を消す処理が残れば、内側先行でも同じ問題が起きる。したがって、生成順と防御線の閉鎖検証を別の変更として比較する。

この設計における『閉鎖』は、壁・閉鎖できる門・水門・城壁によって防御境界が連続すること。川に接しているだけでは閉鎖と認めない。ゲーム上の戦闘や攻城の再現ではなく、岸沿いに壁端を回り込める幾何的な欠陥を検出する。

## 2. 現行実装で確認した原因

| 箇所 | 現状と影響 |
| --- | --- |
| `core/generate.ts` の `runPlan` / `applyPlan` | 旧市街の仮計画はあるが、実際の内壁は外壁・外門・橋の処理後に作る。街路よりは先に作る（既存設計§15）。 |
| `core/gen/innerTownWall.ts` の `addInnerTownWall` | `outerTownCircuit` が必須。外壁内面積から内壁を選び、壁間不足なら半径を縮める。単に呼出順を交換することはできない。 |
| 同 `build` の `touchesRiver` / `open` | 川と同じ辺、または正しい交差を持たない河川頂点に接する辺を開口にする。正しい交差には既に `riverPassages` を付けているため、『内壁は常に水門を作らない』という古い説明は現状と異なる。 |
| 同 `finish` | 門が存在する等の条件で成功になる。`riverOpenings > 0` でも失敗しない。 |
| `core/castles.ts` の `updateCircuitWalls` | 壁のない境界を `waterfront` / `opening` として登録する。 |
| `core/fortifications.ts` の検証 | 境界が壁または natural barrier に含まれるかを検査するが、開口から侵入できないことは保証しない。 |

既存の `innerTownWall.test.ts` は河川との正しい交差・水門を検査するが、残りの全境界の防御を保証するテストではない。`pacmanWall.test.ts` は外壁の河川境界修復の回帰資料として利用する。ユーザーが見た都市そのものの再現データは未取得なので、特定シードでの原因確定・発生率の実測とは区別する。

## 3. 既存方式の保持と設定

`GenerationSettings` に次を追加した。

```ts
townWallBuildOrder?: "outer-first" | "inner-first";
```

- 省略時は `outer-first`。`townWallRings === "double"` のときだけ適用する。単一壁の結果は変えない。
- 現行 `addInnerTownWall` と現行の外側先行経路を保持する。内側先行は別の計画関数から開始し、比較が済む前に共通化で旧方式の結果を変えない。
- Git参照だけに頼らず、両方式を通常のコードから呼べる状態にする。旧方式の固定シードfixture・設定・結果の指標を保存し、既定値省略と明示 `outer-first` の一致を検証する。
- UIに『生成順: 外側から（従来）／内側から（実験）』を追加。二重のときだけ有効。旧市壁の standing / razed は独立した設定とする。
- 設定の復元・共有・再生成経路（`generate.ts`、`gen/fabricDistricts.ts` の設定検証、`CityEditorPage.ts` のリセットを含む）に通す。未指定の旧データは従来方式。
- 要求した方式、実際の方式、リング数、縮退理由を診断に残す。失敗した内側先行を黙って外側先行へ切り替えない。
- 新しい実験のメタデータは optional とし、文書version 2の既存データを読めることを往復保存で確認する。実行時キャッシュは保存しない。

## 4. 内側先行の生成手順

### 4.1 共通入力と旧市街の規模

地形・河川形状と幅・既存の固定橋・都市中心・目標都市面積を共通入力として確定する。外壁そのものはまだ作らない。外壁用の市街地分類は『利用可能な土地と面積予算』として利用できるが、その境界を内壁の制約にはしない。

旧市街の目標陸地面積を `A_inner_target = A_city_target × innerShare` とする。`innerShare` は既存の `innerWalledAreaShare` と同じ入力意味を維持する。両方式で同じ都市面積予算を使い、最終的な実面積比も別に記録する。旧市街を確定した後、外壁を作って比率を厳密に合わせるために内壁を縮め直すことはしない。

### 4.2 内壁・城・内門を先に確定

1. 中心から陸地セルを連結に拡張し、目標面積に近い旧市街候補を作る。円形への近さは評価値であり、河川沿いの閉鎖性を優先する。
2. 城ありなら候補内または境界に予約し、`innerTownCapacity` の空き面数・面積に加え、広場と内門候補間の道路到達性を検査する。城壁を代用できるのは、実際に連続した城壁と接続する区間だけ。
3. 河川との接触を§5の規則で解決する。必要なら局所的に面・辺を分割して交差点を作る。
4. 外門は未確定なので、内門候補は取込み街道の方向、地形、広場への到達性、固定橋への接続から決める。外門からの計画線を必須にする `arteryGates` はそのまま転用しない。
5. 内門通路を開け、広場までの幹線と、壁間へ出る接続方向を予約する。橋を使う場合は有効な橋経路が存在することを先に確かめる。
6. §6の閉鎖・到達性検証を通した内壁を確定する。内壁だけがある段階で `outerTownCircuit` を参照して役割を推測せず、明示した circuit ID を渡す。

内側先行用の計画は外側 circuit を入力に取らない。例: `planInnerFirstTown(site, areaBudget, settings)` → 旧市街面、境界、門候補、河川処理、城予約、診断。実装時は `gen/innerFirstTownWalls.ts` に分離する。

### 4.3 壁間の市街地と外壁

1. 確定した旧市街から外へ連結に拡張する。河川・海岸・利用不能地を尊重し、内門から外へ伸びる交通方向を成長の重みにする。
2. 内外壁間には既存基準の2セル以上を確保する。分割後の小セルで距離を水増ししないよう、元セルの対応とメートル単位の最小距離も計測する。城が接続を代用する場合はその区間を別に検証する。
3. 目標都市面積に近づいたら外壁を計画する。内壁全体の包含、壁の非共有・非交差、河川での閉鎖を満たすまで外側候補を調整する。
4. 取込み街道の端点と内門への到達性から外門を決め、外門→壁間→内門→広場の経路を作る。内外門を一直線にすることは必須にしない。
5. 橋・幹線・街路・街区・建物を確定する。内壁を横断できるのは内門のみ。壁間は `settlement: "core", wallRing: 1`、旧市街は `wallRing: 0` とし、既存の住宅配分を使う。
6. 平滑化、門の直交化、河川修復などの後処理後に、内外両方を再検証する。

『内壁の確定』は座標と防御上の接続の保持を意味する。外側施工のメッシュ分割でIDが変わることは認めるが、親面→子面・親辺→子辺の対応を全circuit、門、`riverPassages`、区域分類に反映する。内壁を動かす必要が生じたら、内壁計画まで明示的に戻って再試行する。

## 5. 河川との接触を開口にしない規則

河川中心線の辺だけでなく、川幅を持つ水域形状と陸側の岸を使って判定する。

| 状態 | 採用する処理 |
| --- | --- |
| 内壁が川に接するだけ | 内壁を陸側へ退避し、連続した壁線にする。接触した辺を消して成功にしない。 |
| 川沿いに壁を置く必要がある | 岸から離した連続した護岸側の壁を構成する。両端を他の壁に接続し、岸から回り込める隙間を残さない。 |
| 川が旧市街を貫流する | 流入口・流出口を含むすべての横断に水門を計画する。`wall, river, wall, river` の交互接続と、川幅全体を覆う閉鎖範囲を検証する。既存の `riverPassages` 表現を利用し、必要ならデータ表現を拡張する。 |
| 急湾曲・合流・固定橋付近で閉鎖不能 | 別区間へ壁を移すか、旧市街を片岸に収める。それでも成立しなければ候補を棄却する。 |

水門は道路橋ではない。水門ができたことを理由に通行可能な橋を自動追加しない。橋が必要なら `src/utils/bridgeSkewPolicy.ts` に従い、推奨10°以内、時代・材質・技術の上限を守る。条件を満たさない橋は作らず、別地点・渡し船など既存の対応範囲で処理する。平行な橋や川の上で曲がる橋は禁止。

## 6. 防御線の検証と失敗時の扱い

新しい読取り専用検証 `auditTownDefenseClosure` を両方式の出力に適用する。従来の構造検証を置き換えず、その結果が空でも追加の監査を行う。

- 境界区間を壁、閉鎖可能な陸門、水門、接続済み城壁、未防御区間に分類する。`opening` / `waterfront` への登録だけでは合格にしない。
- 河川沿いの未防御区間長、全未防御区間長、壁端の未接続数を計測する。正当な門の幅は未防御長に含めない。
- すべての門を閉じた状態の陸地通行グラフを作り、壁外から旧市街への到達を検査する。内壁単独の検証では壁間を出発側にし、外壁に遮られるため欠陥が隠れることを防ぐ。
- 水域は陸地通行から除外するが、両岸の細い陸地通路は残す。境界頂点の角抜けを扱えるグラフと、幅を含む形状検査を併用する。水門の閉鎖は別途全河川横断で検査する。
- 門を開いた状態では内門→広場、外門→内門、城のアクセスが通ることを検査する。
- 生成完了時の standing 内外壁について、未防御長0・侵入経路0を受入条件とする。浮動小数点の許容誤差は幾何計算用に限定し、可視の開口を許す閾値にはしない。

失敗時は、局所的な壁線修正→内壁候補の位置・形状調整→片岸案→城の縮小・移動→二重断念の順に、固定上限の回数で探索する。各試行は独立した文書で行い、失敗したメッシュ変更を残さない。内壁確定後の外壁失敗は、まず外壁候補を再探索する。

二重断念時は安全な単一壁を改めて生成し、その壁にも閉鎖検証を適用する。単一壁も成立しない場合は明示的な生成失敗とする。内壁を欠落させた二重壁や、自動の razed 化で成功数を増やさない。ユーザー指定の razed は防御評価対象から除外し、環状道路として別集計する。

## 7. 比較検証

生成順の効果と閉鎖処理の効果を混同しないため、ラボでは次の4条件を同じ入力で比較する。Bの不完全な結果は実験資料としてだけ保存し、通常UIの成功した都市として採用しない。

| 条件 | 生成順 | 閉鎖処理 |
| --- | --- | --- |
| A | 外側先行 | 現行を保持。監査のみ追加 |
| B | 内側先行 | 現行相当の接触時開口を許す実験用方針 |
| C | 外側先行 | 新しい閉鎖処理を有効化する実験用分岐 |
| D | 内側先行 | 新しい閉鎖処理。本提案のUI実験モード |

A対B、C対Dで順序の効果を比較し、A対C、B対Dで閉鎖処理の効果を見る。監査の判定は全条件で同じ。Cの追加は旧方式Aを書き換えず、実験用分岐に限定する。

固定するもの: 元メッシュ、河川形状・幅、固定橋、人口・面積予算、時代、城設定、シード。順序変更で乱数消費がずれるため、実験では段階別乱数または地形生成後の共通スナップショットを使う。旧方式Aの既存乱数列は変更しない。

対象は hex / voronoi / evolution、micro〜large、城なし／small／standard、川なし／貫流／接線状／岸沿い／蛇行／合流／広い川／橋付近／海岸付近。小規模な固定fixtureを先に実行し、その後に代表ケース各30シードを初期バッチとする。evolutionは標準設定と拡大率50%・nPatches 400も比較する。circulade・Bramは既存どおり単一限定。

報告する指標:

- 全要求数、二重成立率、単一への縮退率、生成失敗率（失敗・縮退を母数から除かない）。
- 二重成立例の河川沿い未防御長と最大値、侵入経路のある都市の割合、水門成立率。
- 内外面積・目標面積誤差・実面積比、壁間距離、内外門数、門の到達性、城アクセス、住宅充足率。
- 試行数、失敗理由、生成時間。ペアごとの改善／悪化／両方成立せず、を含む。

`wallRingLab.ts` は現状では水域なしの幾何近似なので、それだけで河川問題の改善を結論づけない。実生成を使う監査経路を拡張し、CSV、設定・シードのmanifest、両方式の文書、SVGを保存する。描画では河川幅・水門・壁端・橋頭・城との接続を拡大確認する。

内側先行Dの受入条件は、採用されたstanding二重壁の未防御長・侵入経路が0、門と城の到達性が維持されること。優位性は二重成立率・縮退率・処理時間も含めて判断する。CとDに差がなければ『主因は生成順ではなく閉鎖処理』と報告し、内側先行が有利だと断定しない。

## 8. 実装順と完了条件

1. **従来方式の保存**: 固定fixture、明示 `outer-first` と省略の一致、設定の保存・復元。既存経路は変更しない。
2. **共通監査**: 河川接触で壁が欠けた小fixtureと、正常な水門・陸門・城接続を追加。欠陥を既存構造検証が許しても監査が検出できること。
3. **内側先行の計画**: 外壁なしで内壁を作り、確定した内壁を保持して外側を拡張。まず城なし、次に城・固定橋・取込み都市へ拡張。
4. **閉鎖処理と後処理保護**: 水門・岸沿い壁・局所修復、ID更新、ロールバック、後処理後の再監査。橋の規約違反は0。
5. **比較とUI**: A〜Dの固定入力比較、生成順選択、診断、保存往復。現行の `walls` / `innerWall` 等の段階表示は順序別の工程表へ対応させ、同じ完成文書のチェックポイントから表示する。旧方式の段階意味は保持する。

重点回帰対象は `innerTownWall.test.ts`、`multiRingWalls.test.ts`、`pacmanWall.test.ts`、`generateWallCheckpoints.test.ts`、河川壁の描画テスト、`CityEditorPage.generate.test.ts`。実装時の検証結果は次節。既定方式の切替は比較結果を見て別途判断する。

## 9. 実装記録（2026-10-13）

### 操作と生成経路

生成パネルで「市壁」を二重または二重（旧市壁を撤去し環状道路）にして、「市壁の生成順」を「内側から（実験）」にする。外側先行は「外側から（従来）」として選択でき、省略時も従来方式になる。生成順は共有リンクと evolution の生成レシピで復元できる。

- `gen/innerTownWall.ts` の `addFirstTownWall`: 外壁・外側circuit・生成済み橋が存在しない段階で旧市壁を作る。面積予算から円形候補を選び、河川の横断を分割し、接触回避・城接続・閉鎖検証を行う。失敗候補の分割は破棄する。
- 合格した内壁から元のセル単位で2層外へ拡張し、全市街地の計画範囲を合わせて外壁の範囲を作る。分割セルで壁間距離を水増ししない。内壁を外壁に合わせて選び直さない。
- `generate.ts` の分岐: 内壁→外壁→外門→橋・街路。外壁の囲み面検出と門数・候補位置の検索から内壁を除き、外壁の河川修復中は内壁を保護する。内外区域は外側circuitの登録後に確定する。
- 内壁だけの途中状態では、未登録の外側リング番号を面に付けない。これにより外壁の河川修復・門通路の面分割が構造検証で拒否される問題を避ける。
- 生成スライダーも内側先行では旧市壁・内門通路を外壁の前へ移す。従来方式の工程表は維持する。
- `townDefenseClosure.ts`: 既存の構造検証とは別に、開口長、未接続壁端、岸沿いの陸地侵入、無水門の河川接触、物理水域内の未閉鎖壁、水門が両岸に達するかを調べる。完成時には内外門から広場への道路到達性も調べる。広場内には道路edgeを描かないため、広場の各隅を到達先として扱う。
- 内包された城の保護済み境界は未防御の穴として扱わない。ユーザー指定の razed は防御監査の対象外にし、環状道路として保持する。
- `riverWallPassage.ts`: 描画と監査で水門の両岸への到達経路を共有する。川幅と取込み水域形状を使う。
- `CityDocument.townWallGeneration`: 要求した順序、実際の順序、単一壁への縮退理由を optional で保存する。単一に戻したときはUIに理由を表示する。新方式では、完成後の閉鎖・到達性監査に失敗した都市を採用しない。

現在の候補探索は、既存のセル選択・接触回避と6段階の目標面積調整を使う。任意の位置への中心移動、独立した片岸専用プランナー、渡し船の新設は追加していない。成立しない河川・城配置は明示的な縮退または生成失敗になる。新方式を選んだことを理由に、不適切な橋を追加する処理はない。

### 内壁ステージの失敗時の停止と河川修復（2026-10-13 追記）

再現条件: 都市シード `9u8ta1`、格子シード `1c48bkk`、voronoi small、貫流河川、城なし、内側先行。旧実装では内壁候補をすべて `open-defense` で棄却し、その後「Inner town wall」チェックポイントを通過して単一外壁・橋・街路まで描いていた。

- 不採用・事前計画失敗の場合にも内壁と内門のチェックポイントで停止する。生成順は事前計画の成否から独立して保持する。
- 内壁の失敗通知が最後の「ここまで生成」「すでにこの段階」通知で上書きされないようにする。内側先行のステージ説明も、外壁より先に作る順序に合わせる。
- 河川接触で辺を削除すると、半径を変えても同じ開口を繰り返す場合がある。城のない旧市街では、削除前の連続した試行壁線を既存の `repairRiverWalls` に渡し、岸への迂回・水門を修復してから閉鎖を再検証する。実際の囲み面と分割面の元セル対応を更新し、合格したものだけを外壁の拡張に使う。修復不能な候補の変更は破棄する。
- 不採用候補の閉鎖エラーは非致命的な診断として生成ログに表示する。

同じ `9u8ta1` のまま、ブラウザで内壁ステージは内壁1グループ・街路0・水門2、完全生成は内壁と外壁の2グループ・水門4になることを確認した。再現シード、計画済み内壁の強制不採用、microでの計画失敗、失敗通知の保持を回帰テストに加え、関連29件とTypeScript検査が成功。

  --grid hex,voronoi,evolution --size small \

個別シードは `--seed d1,d2`、格子密度の比較は `--patches 400 --rim-growth 50`。出力は `cases.csv`、`summary.csv`、`manifest.json`、各ケースの入力・設定・完成文書・診断JSONと、通常のエクスポートと同じ自己完結SVG。条件Bの従来閉鎖方針はCLI用であり、UIで内側先行を選んだ場合は閉鎖必須になる。共有リンクにはこのラボ用の閉鎖方針上書きを復元しない。

比較は各条件で同じ元メッシュ・地理シードを使い、最初の案だけを実行する。再試行で別シードに変わった結果を混ぜない。生成失敗と単一壁への縮退も母数に含める。内側先行は外壁の範囲を拡張できるため、二重成立率の比較には生成順に加えて面積変化の影響があり、各ケースの内外面積も合わせて読む。
