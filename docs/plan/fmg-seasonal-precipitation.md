# FMGの月別降水量と雨季・乾季の設計

作成日: 2026-10-31  
状態: 調査・設計。季節降水の実装・係数の較正は未着手。

## 1. 目的と決定

[BV樹木の季節の姿](bv-tree-seasonal-appearance.md) §3.3・X01の前提となる、FMGの雨季・乾季を用意する。**既存の年降水量を保ち、既存の季節風と地形・海陸配置から12か月の降水配分を導く**。月別降水の正本は本体の `CellClimateNormals` とし、CEや経済拡張が別の雨季を作らない。

現実との比較から必要なのは、夏雨・冬雨・二峰性・通年降水の描き分けである。一律の「夏は雨が多い」という正弦波では足りない。季節降水の提供、FMGでの表示、CEへの受け渡し、樹種別の乾季応答を順に実装する。本書を保存した段階ではX01を完了にしない。

[地球型の季節気温と農業](earthlike-seasonal-climate-and-agriculture.md) §6.2の「月別情報がない間は日数比例」「後続で年総量を保存」を具体化し、[季節風計画](wind-aspect-climate-variability.md) §5.9の降水配分を引き継ぐ。

## 3. 現実の気候との比較

### 3.1 観測平年値との数量比較

気象庁TCCの[平年値の説明](https://www.data.jma.go.jp/tcc/tcc/products/climate/explanation/normal.html)に従い、1991–2020年を基準とする月別平年値を使う。地点ごとの欠測条件があり、全地点が30年分の完全な観測を持つという意味ではない。以下は[主要地点の月別平年値](https://www.data.jma.go.jp/tcc/tcc/products/climate/mainstn/nrmlist.php)からの集計。シンガポールは[Changi地点表](https://www.data.jma.go.jp/tcc/tcc/products/climate/normal/parts/NrmMonth_e.php?stn=48698)を使用した。参照日: 2026-10-31。

| 地点 | 月別値の合計 mm/年 | 最少月 mm | 最多月 mm | 雨の多い連続3か月の年量比 |
| --- | ---: | --- | --- | --- |
| ムンバイ | 2,250.7 | 1月: 0.6 | 7月: 790.5 | 6〜8月: 79.5% |
| ダーウィン | 1,827.2 | 7月: 0.0 | 1月: 468.0 | 1〜3月: 65.6% |
| リスボン | 762.6 | 7月: 2.3 | 11月: 132.0 | 10〜12月: 43.5% |
| パース | 690.8 | 12月: 9.3 | 7月: 137.1 | 6〜8月: 55.4% |
| 東京 | 1,598.2 | 2月: 56.5 | 10月: 234.8 | 8〜10月: 38.4% |
| ルクセンブルク | 838.1 | 4月: 49.3 | 12月: 89.4 | 10〜12月: 29.0% |
| クアラルンプール | 2,841.6 | 6月: 141.5 | 11月: 356.5 | 10〜12月: 32.4% |
| シンガポール・チャンギ | 2,122.7 | 2月: 104.9 | 12月: 333.1 | 11〜1月: 38.1% |

集計方法は、`A = Σ P[m]`、`wet3 = max_s(Σ_{j=0..2} P[(s+j)%12]) / A`。年をまたぐ3か月も含め、小数第1位へ丸めた。独立に公表された年平年値ではなく、表示された12値の合計である。

**現行FMGの式へ同じ年総量を入れた反実仮想との比較**: 平年365日なら連続3か月の割合は24.4〜25.2%にしかならない。ムンバイと同じ2,250.7 mm/年でも各月172.7〜191.2 mmとなり、観測のほぼ無降水の月と夏の集中を消してしまう。これは現行の分配式の評価であり、FMGの実地図を地球の各都市へ合わせて生成した実験ではない。

### 3.2 必要な気象過程とFMGでの近似

| 現実の特徴 | 現行との差 | 本設計への採用 |
| --- | --- | --- |
| 熱帯収束帯（ITCZ）が季節移動し、通過の仕方で雨の山が1回にも2回にもなる | 気温の年較差が小さい熱帯でも降水の季節差は大きくなり得る | 既存の気候帯移動から熱帯対流の強さを求める。最暖月だけから雨季を決めない |
| モンスーンは海陸の温度差と循環の変化を伴う | 風向反転はあるが、海からの湿気が雨へ接続されていない | 月別風向と、風上側の海・山脈・陸路長から水分供給を近似する |
| 地中海型は夏乾燥・冬雨となりやすい | 低温ほど雨が少ない式や夏雨一律では位相が逆になる | 亜熱帯下降流による抑制と、寒候期の前線活動を分ける |
| 同じ緯度でも海岸の向き・内陸度・雨陰で異なる | 緯度やバイオーム名だけでは決められない | 海陸配置と風上地形を入力にし、バイオームは入力に使わない |
| 赤道付近でも海洋・循環・地形で雨の山は異なる | 赤道だから必ず春秋に2回、という固定暦は成立しない | 二峰性を許すが強制しない。通年多雨の地域に不要な落葉を作らない |
| 冬の降雪も降水であり、融雪時期と降水時期は違う | 年モデルには寒冷セルでの降水省略があり、雪の貯留もない | 月別値は雨雪合計の水当量mmとして扱う。積雪・融雪と年モデルの修正は後続 |

ITCZと雨季の関係は[NOAAの解説](https://www.noaa.gov/jetstream/tropical/convergence-zone)、季節ごとの前線位置は[NOAAのジェット気流解説](https://www.noaa.gov/jetstream/global/jet-stream)、地中海型と海岸・風の関係は[Met Officeの気候帯解説](https://weather.metoffice.gov.uk/climate/climate-explained/climate-zones)による。上表の「採用」はそれらからの**ゲーム向けの設計上の推論**であり、観測から係数を推定済みという意味ではない。

### 3.3 再現の限界

最初の実装は月別平年配分であり、毎日の雨、梅雨前線の細かな停滞、台風、ENSO、海面水温の年々差を予報しない。東京の秋のピークやシンガポールの年末のピークを、緯度の帯だけで正確に再現できるとは要求しない。一方、二峰性を持てない・全中緯度が夏雨になる、といった構造上の欠点は受け入れない。

年総量が過大・過小なら月別量もその影響を受ける。季節配分の較正はまず `P[m]/A` と日降水率で行い、年proxyの単位・飽和・寒冷時の省略の較正を混ぜない。後者は別の年降水モデル改訂で扱う。

## 4. データ契約と依存関係

### 4.1 本体の正本

既存の `annualPrecipitationMm` と `monthlyPrecipitationMm: Float64Array` を保ち、次を追加・拡張する。以下は実装予定の契約である。

| フィールド | 契約 |
| --- | --- |
| `precipitationModelVersion` | `"seasonal-precipitation-v1"`。気温モデル版と独立に降水の改訂を追跡する |
| `precipitationSeasonalitySource` | `"modeledSeasonality"` / `"uniformFallback"` / 旧来の `"uniformAssumption"`。全利用箇所の型とfixtureも更新する |
| `precipitationSeasonalityConfidence` | 0〜1。地図上の水分供給経路をどこまで確認できるかを示す運用上の信頼度。統計的な予測確率ではない |
| `monthlyPrecipitationMm` | 1月から12月の雨雪合計の水当量。非負・有限、丸め前の12値の和は年総量に一致 |

`climateRevision` は降水配分の変更でも進める。`CLIMATE_MODEL_VERSION` を使った既存の派生キャッシュも監査し、意味が変わった出力を旧版のまま再利用しない。

内部では年に依存しない12か月の**日あたり相対降水率**を保持し、実際の年の日数で月量に変換する。同じ地理・設定なら翌年も同じ雨季であり、うるう年による日数の違いだけが配分へ入る。長周期・火山性の気温異常や経済の干魃ロールは、この平年降水配分に混ぜない。

### 4.2 循環importを先に解く

現在の `cellWindClimate.ts` は `cellClimateNormals.ts` の `ensureClimateGeography` をimportしている。そのままNormalsから風を読むと循環する。実装前に、大陸度・海岸探索とそのキャッシュを `src/generators/cellClimateGeography.ts`（新規）へ移し、呼び出し元を更新する。

依存方向は次に固定する。

```text
cellClimateGeography / terrainAspect / pure climate utilities
    -> cellWindClimate
    -> cellPrecipitationClimate
    -> cellClimateNormals
    -> seasonalClimate / burgSiteDescriptor / extension host readers
```

矢印は下流が上流を読む向き。Normalsは気温計算のため地理も直接読む。降水側は `ensureCellWindClimate` の月平均ベクトル・モンスーン信頼度をバッチで読み、Normalsそのものは読まない。風は年降水proxyを日変化の乾燥度に使っているが、月別降水を風へ戻さない。

## 5. 季節配分の計算

### 5.1 基本方針

年降水の `generateAnnualPrecipitation` を12回実行する方式は採らない。既存の乱数列・生成結果を変え、月別風を扱わない東西南北の処理を繰り返すことになるためである。新しい純粋関数を `src/utils/precipitationSeasonality.ts`、世界の地理探索・キャッシュを `src/generators/cellPrecipitationClimate.ts` に置く。

標準的な地球型配置で夏雨・冬雨・二峰性が生まれるよう、次の独立した成分を連続的に混ぜる。係数・帯幅は初期候補であり、P0〜P1で確定する。都市名・文化・樹種・固定の気候区分から月別表を選ぶ実装にはしない。

### 5.2 気候帯と季節の強制力

月中央日について `getBeltShiftDeg` を共有し、緯度 `phi` と気候帯の北向き移動 `shift[m]` から `effectiveLatitude[m] = phi - shift[m]` を作る。独自に「南半球なら月を6ずらす」分岐を重ねない。

| 成分 | 無次元の強さ0〜1の作り方 | 注意 |
| --- | --- | --- |
| `C[m]` 熱帯対流 | 実効緯度0°から離れるほど小さい滑らかな帯 | 帯の往復で二峰性を許す。温度年較差が0でもこの成分を消さない |
| `F[m]` 前線性降水 | 実効緯度の絶対値が中緯度帯に近いほど大きく、寒候期に強める | 通年の前線活動も残す。亜熱帯の冬の雨を作る |
| `H[m]` 下降流 | 実効緯度の絶対値が亜熱帯帯に近いほど大きい | 海風が吹いていても下降流の強い季節は少雨になり得る |
| `L[m]` 陸上の暖候期対流 | 大陸度と、平年の季節温度偏差の正の成分を使う。熱帯対流との重複を帯の重みで弱める | 内陸の夏雨を許す。月平均気温だけで雨季を確定しない |

初期候補の中心・帯幅は、熱帯0°・8°、前線50°・12°、下降流28°・7°（幅はGaussianの標準偏差）。各成分は `exp(-0.5 × ((latitude-center)/width)^2)` を基礎にする。前線の寒候期強化は0.5〜1倍、陸上対流は温帯側で重くする。これらは物理定数ではなく、地球型の帯を表す少数の調整値である。

地軸傾斜0°では月ごとの強制力を0とし、日降水率を一定にする。**既存の `getSeasonalStrengthFactor` は傾斜と無関係な冬季強化を持つ**ため、その風速をそのまま降水倍率に使わない。既存の風モデル自体の修正をこの作業へ無条件に含めず、降水の季節振幅を傾斜比で減衰させる。極端な傾斜では季節降水の地球型近似として適用範囲外であることを記録する。

### 5.3 海からの供給と地形

月平均の風上を調べて `M[m]`（海洋由来の供給0〜1）と `O[m]`（地形の季節倍率）を得る。ベクトルは **u=東、v=北へ吹いていく方向**。気象表記の「吹いてくる方位」や画面の南向きyと取り違えない。

- 地形構築時に8方位の風上探索を行い、月平均ベクトルの逆向きに対応する隣接2方位から滑らかに補間する。海までの距離・途中の山越え・既知の海上区間を使い、海を遠ざけるほど供給が増す式にしない。
- 初期探索上限は1,500 km、最大96近傍遷移。上限はゲーム係数。上限到達と未知の地図端への到達を区別し、96遷移で距離を調べ切れなかった場合も信頼度へ反映する。内陸への長距離輸送・水分再循環は背景成分で近似する。
- `M` は海岸までの**最短距離だけでは決めない**。夏に海から吹く岸と、冬に海から吹く岸で違う月を湿潤にする。既存の海風用 `coastDistanceKm` は海岸近傍しか有効でないため代用しない。
- 湖は外洋と同量の水分源にしない。v1では外洋のみを主要源にし、湖水蒸発は後続とする。極・地域地図の端を架空の海とみなさない。
- 上り斜面の持ち上げと風上の障壁を使うが、年平均の雨陰は既に年proxyへ入っている。`O[m]` は年内の相対差だけに正規化し、初期は0.5〜2へ制限する。年量を二重に減らさない。
- 無風時は8方位の平均供給を使い、風向の小さな数値誤差で雨の月が飛ばないようにする。日変化の海風24時間分や風配図の描画用集計は入力にしない。

全球地図の経度方向は継ぎ目を接続し、地域地図は接続しない。既存の風の平滑化は端をclampする箇所があるので、継ぎ目で季節風自体が不連続になる場合は共有地理処理の修正と関連テストをP1の前提にする。降水の経路だけwrapして整合したとみなさない。

### 5.4 非負の重みと年総量の保存

日あたりの候補スコアは、次を出発点とする。

```text
score[m] = (b + cC*C[m] + cF*F[m] + cL*L[m])
           * (m0 + (1-m0)*M[m])
           * exp(-cH*H[m]) * O[m]
```

`b > 0` は長距離輸送等の背景、`0 < m0 < 1` は海洋供給を確認できない月の背景。`cC/cF/cL/cH` は非負の較正係数。スコア自体は降水mmでも保存則を満たす湿気でもない。過度に大きな背景はモンスーンの乾季を埋めるため、P0の観測比率を使って決める。気象観測を確認していない具体値を採用済みとして記載しない。

`D[m]` を当該年の月日数、`Y = Σ D[m]`、`A` を既存の年降水mmとする。

```text
modeledShare[m] = D[m] * score[m] / Σ(D[k] * score[k])
share[m] = q * modeledShare[m] + (1-q) * D[m]/Y
P[m] = A * share[m]
```

`q` は水分経路の確認度と季節風の信頼度から決める年内共通の信頼度。月ごとの経路確認度の最小値を基礎にする保守的な方式から始める。小さな地域地図では均等側へ弱まる。未知の風上を無降水扱いして人工の乾季を作らない。地軸傾斜による季節振幅の減衰もここで行う。

守る不変条件:

1. 全月が有限・非負で、`abs(Σ P[m] - A) <= max(1e-8, A*1e-12)`。Float64で計算し、丸め残差は最大配分月へ加える。
2. `A=0` は全月0。配分に使えない地理・非有限スコア・総スコア0の場合は日数比例へfallbackする。元の欠損・不正な年proxyは `invalidAnnualPrecipitation` として診断し、現行の0補完を観測上の無降水と混同しない。
3. `q=0`・季節振幅0・全月同スコアは日数比例。`q=0` は `uniformFallback`。有効な地理で実際に季節差が小さい場合は `modeledSeasonality` のままでよい。
4. 年proxy・乱数消費・地形・河川線形・バイオームをこの処理で書き換えない。同じ年総量に戻すための追加乱数は使わない。

## 6. キャッシュ・保存と表示

### 6.1 構築コストと無効化

地理の8方位探索を `O(N × 8 × K)`、12か月の成分合成を `O(N × 12)` とし、セル1件のReader呼び出しごとに全地図をhashしない。`createCellClimateNormalsReader` と同じバッチReaderを利用する。

キャッシュは地図ID、座標・点・接続、標高、海陸feature、地図の物理縮尺、標高換算、`options.winds`、地軸傾斜、年proxy、降水モデル版で無効化する。温度を入力に使う成分にはその入力revisionも含める。現行Normalsのkeyには風向がないので追加が必要。現行風キャッシュのkeyには全ての点・接続・feature ID配列が含まれないため、共有地理revisionを導入して両方へ渡す。同じ月の地形編集・風向編集でも再計算する。

12か月分の降水量と探索の診断値は実行時派生データとし、巨大な12N配列を保存形式へ足さない。月別率Float32が12Nなら約48N bytes、月量Float64を全セル保持すると約96N bytes。後者はReader時の12値生成を基本にして重複を避ける。初回構築・再利用・編集後を測り、月送りのたびに8方位探索を走らせない。

旧セーブは年降水proxyから新配分を再構築する。派生キャッシュの旧versionは捨てる。旧式保存に月別配列が存在しても現行入力の検証なしに採用しない。新配分で既存製塩の挙動が変わることは変更履歴へ明示する。

### 6.2 FMGでの確認可能性

降水レイヤーに「年合計 / 表示中の月」を用意し、既定の年表示を保つ。月表示は本体の暦を使い、凡例・ツールチップをmm/月へ変更する。月を比較する表示の尺度は全月で固定し、月ごとの最大値への再正規化で雨季・乾季の差を消さない。既存の年降水生成時の風向矢印を月の季節風と誤認させないよう、月モードでは月平均風へ置換するか非表示にする。

セルの診断では12か月の気温・降水、年総量、配分source・confidence、雨の多い3か月、風上供給を同時に読めるようにする。`seasonalClimate.ts` の月更新と描画購読を接続する際、現在は主に気温用の `simulation.cells` 通知であることを確認する。保存する月別セル列を増やすより、表示時に正本Readerから取得する方式を優先する。

## 7. CEと乾季落葉への接続

### 7.1 記述子

`BurgSiteDescriptor.climate` に任意項目 `annualPrecipitationMm`・`monthlyPrecipitationMm`（number[12]）・降水のmodelVersion/source/confidenceを追加する。セルは気温と同じ **burgのpackセル -> `pack.cells.g` -> gridセル**。経済拡張の有効・無効に依存させない。旧記述子との互換のため、降水がない記述子は現在の気温による季節表現を保つ。

正本の値を保ってJSON化し、丸めはUIで行う。気温用の小数1桁丸めを降水の保存へコピーして、少雨月を0や同じ値へ潰さない。version 2/3の任意項目として扱い、import時に12値・有限・非負・sourceを検証する。欠損した月を0補完して乾季と判定しない。

`src/city3d/treeSeason.ts` のキーに降水配列とそのsource/confidence/versionを追加し、月別気温が同じでも降水の編集を反映する。姿を含む既存のprototypeキーとLOD予算は再利用し、毎月別の樹木骨格を作らない。

### 7.2 乾季の検出と樹種の応答を分ける

「降水が少ない月」「植物が水不足の月」「その樹種が落葉する月」は同一ではない。[FAO-56の土壌水収支](https://www.fao.org/4/x0490e/x0490e0e.htm)は降水だけでなく蒸発散、土壌貯留、灌漑等を扱う。本段階はそこまでの水収支を導入せず、**降水に由来する乾季候補**だけを渡す。

初期の表示用候補判定は次とする。閾値は植物学上の普遍則ではなく、X01の試作で較正するゲーム値である。

- `r[m] = P[m]/D[m]` とし、30日換算降水 `30*r[m] < 60 mm` かつ `r[m] < 0.5*(A/Y)` を満たす連続2か月以上を候補にする。日数の短い2月だけで乾季を作らない。
- 12月〜1月を連続として判定する。二峰性では乾いた区間を最大2本まで返せる構造にし、最長の1区間へ潰さない。
- `uniformAssumption`・`uniformFallback`、降水欠損、不正年値、confidence 0.5未満は「判定不能」。有効な入力で候補なしなら「乾季なし」。通年少雨は季節の落葉と別の慢性的乾燥として診断する。
- `A=0` で比率を割らない。気温による休眠と重なる場合の優先順位は樹種側で決める。河畔・灌漑・地下水利用の木を降水だけで自動落葉させない。

気候本体は樹種名や `bare` を知らない。候補区間を入力に、X01でカポックの落葉、アンブレラソーンの疎葉、インドボダイジュの短い落葉と新葉を個別に設計する。3種を同じ2か月の `bare` に一括変換しない。樹種ごとの落葉の遅れ・再展葉・常緑を保つ条件を定め、月の閲覧順に依存しない12か月の循環判定とする。必要な層・配色が実装されて初めてX01を完了にする。

## 9. 検証と受け入れ基準

### 9.1 数学・地理の契約

関連テストに次を加える。式の写しではなく、利用者に意味のある不変条件・反例を固定する。

1. 全月非負・年総量保存、年量0・不正値、平年/うるう年、一定スコアの日数比例、傾斜0°。
2. 地球型の同じ合成大陸の東岸/西岸、内陸、風上/風下の山地で配分が変わる。風向反転・南北反転・経度の平行移動と、年をまたぐ雨季を確認する。
3. 全球の経度継ぎ目で連続し、地域地図の端を海と誤認しない。海が見えない小地図・湖だけの地図・粗い解像度ではsource/confidenceが正しく低下する。
4. 同じ月の風向・標高・地物ID・地図縮尺・年量のin-place編集で必要なキャッシュだけ更新する。返された配列の変更が正本へ漏れない。
5. 降水追加前後で `grid.cells.prec`、乱数消費、生成した河川・バイオームが変わらない。月次更新とReaderの両経路で同じ降水になる。

### 9.2 気候パターンの較正

P0で§3.1の元地点ID・座標・基準期間・12か月値・取得URL・取得日を小さな固定入力として保存する。実地球の標高・海陸配置がない合成大陸へ都市名を貼り、地点別誤差を計算しない。実地球地形を使う場合も地点とモデルセルの標高・海岸距離の差を併記する。

| 固定ケース | 最低限の受け入れ条件（モデルの精度目標ではなく構造の確認） |
| --- | --- |
| 熱帯の夏雨・モンスーン | 湿潤3か月の割合が均等配分より明確に大きく、2か月以上の乾季候補を表現できる。南北で位相が反転する |
| 亜熱帯の西岸・冬雨 | 暖候期より寒候期の降水が多い。海から吹く風があっても下降流の季節は抑制できる |
| 赤道近傍の往復する収束帯 | 2つの雨の山を持つ条件を表現できる。同時に通年多雨条件では乾季を強制しない |
| 弱い季節差・通年降水 | ルクセンブルクのような小さい差を表現でき、全地域を強いモンスーン型にしない |
| 寒冷・乾燥 | 雪水当量として有限値を返し、降水時期と融雪を混同しない。年モデルに由来する不整合を診断する |

正規化月別量のMAE、日降水率の年内変動、湿潤3か月の割合、ピーク月（同率なら複数）、乾季候補区間を旧式と比較する。係数決定用と独立確認用の地域を分ける。具体的な許容誤差はP0の基準記録後に確定し、未較正の候補式を「現実を再現済み」と扱わない。
