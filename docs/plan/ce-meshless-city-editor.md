# CEメッシュなし都市生成・編集の設計

作成日: 2026-11-06  
状態: M0〜M6完了（M6: 2026-11-07）。[M0の調査・計測](../analytics/ce-meshless-m0-20261106.md)、[M1の実装・検証](../analytics/ce-meshless-m1-20261106.md)、[M2の実装・検証](../analytics/ce-meshless-m2-20261106.md)、[M3の実装・検証](../analytics/ce-meshless-m3-20261107.md)、[M4の実装・検証](../analytics/ce-meshless-m4-20261107.md)、[M5の実装・検証](../analytics/ce-meshless-m5-20261107.md)。[M6の実装・検証](../analytics/ce-meshless-m6-20261107.md)。次はM7「2D／3D・出力・保存共有・既存都市の複製変換」。

## 1. 目的と採用方針

道・川・壁・門・橋を、ボロノイやヘックスのセル辺・頂点から独立して配置する。FMGから受け取った形状や利用者が描いた線をセルへ合わせるための分割・統合・変形を不要にする。街区・敷地は道路、河岸、市壁などが作る空間から生成する。

既存CEの画面・資産・入出力・履歴の仕組みを共有し、メッシュなしの正本データ、生成、編集処理を独立して追加する。CE全体を`src/city-editor-2/`へ複製しない。既存のメッシュ前提関数へ`grid === "none"`の分岐を広げる実装にもせず、文書方式を判別する境界から専用処理へ渡す。

既存の`mesh-first`、現行の`skeleton-first`、Freeform、既存保存データの動作を維持する。新方式の仮称は`vector-first`、画面表示名は「Meshless / メッシュなし」とする。既存データの方式を暗黙に切り替えない。

### 1.1 利用者が期待する効果

| 要求 | 設計上の対応 |
| --- | --- |
| 門を市壁上の任意位置へ置き、道を接続する | 曲線上の参照点と道路グラフの接続ノードを共有する |
| 二重市壁間の細い空間へ道を通す | 実際の壁厚・道路幅・離隔から通行可能領域を計算する |
| 橋の角度のためにセルを変形しない | 河川曲線の接線から橋軸と取付道路を直接決める |
| 都心を流れる川の幅を変える | 中心線と位置ごとの川幅から河岸を生成する |
| 川と街道を並行させ、皮なめし施設等を配置する | 河岸に対する距離制約付き道路と河岸用途の区域を扱う |
| 円形市壁を楕円、方形市壁を長方形へ調整する | 市壁プリセットに実寸、縦横比、回転などを持たせる |
| 道・川・壁を自由に描く | 自動、プリセット、折れ線、フリーハンド、ベジェを共通の曲線契約へ接続する |

道路幅を収められない隙間、橋規約に適合しない渡河、施設実寸に足りない土地は生成できない。メッシュ適合処理をなくしても、交差判定、経路選定、ポリゴンの切り取り、接続関係の構築は必要である。

### 1.2 「メッシュなし」の範囲

- 都市の正本に`CityDocument.mesh`、セルの`faceId`、セル境界への道路・川・壁の割当を要求しない。
- 道路の交点で線を分割する処理や、街区ポリゴンの分割は行う。これらは実際の都市形状に必要な処理であり、セル適合とは区別する。
- 3D描画の三角形、地形の高さ場、当たり判定・経路探索用の一時的な空間索引は使用できる。これらの解像度や格子境界によって正本形状を決めない。
- 判定用の近似折れ線も派生物であり、画面倍率や描画品質で都市の接続・施設数・住宅容量を変えない。

Freeformが存在することを、新しい都市生成が既に成立している根拠とはしない。市壁・門・都市街路・街区・人口住宅を一体で扱う契約は別途必要である。`src/city-generator/`は調査・実装・再利用対象に含めない。

## 3. 構成と処理の境界

CEの既存の層構成を維持し、各層の下へ専用処理を置く。以下のファイル名・API名は実装時の案であり、現時点の既存APIではない。

```text
src/city-editor/
  types/vector/                 文書、曲線、接続、領域、生成結果の契約
  generators/vector/
    geometry/                   曲線評価、交差、幅付き領域、領域演算
    topology/                   道路グラフ、門・橋・交点、参照の更新
    generation/                 入力→骨格→領域→施設→住宅
    editing/                    編集コマンドと整合性検証
    validation/                 自動生成と手動編集で共有する制約
  controllers/vector/           描画ツール、選択、操作の調停
  components/                   共通パネルと方式別コントロール
  renderers/vector/             方式固有の線・領域・編集ハンドル
  renderers/                    共有可能な建物・資産・地形の描画部品
  services/io/vector/           codec、共有、旧形式からの変換
  services/                     Worker通信、方式ごとの起動
  state/                        方式判別、履歴、採用、派生結果の所有
```

`EditorDocument`を既存文書と新文書の判別可能なunionとして扱う境界を設ける。既存`CityDocument`の`mesh`を一律にoptional化しない。メッシュ用関数は従来の型のままとし、新文書を渡せない状態を型で維持する。

- controllerが文書方式を判別し、対応する生成・編集・描画を選ぶ。
- generatorはDOM・SVG・UI状態を参照せず、明示的な入力から文書・診断・進捗を返す。
- rendererは都市の存在、接続、用途、住宅容量を決定しない。
- 旧CEの共通化は、旧入力に対する出力を関連テストで維持できる単位で行う。新方式のために旧方式の生成順や乱数消費順を変えない。
- 空メッシュを旧関数へ渡して互換性を装う実装はしない。既存Freeformの投影を使う場合も、その対応範囲だけを明示する。

## 4. 正本と派生データ

### 4.1 文書

新形式は`format: "fmg-vector-city"`。M1〜M3のv1〜v3に続き、M4で入力snapshot・座標系・固定形状・測量水域、生成所有revision・街区候補・接道・診断・段階情報を保存するv4へ更新した。v1〜v3は検証してv4へ移行し、入力や生成結果を勝手に追加しない。単位はメートル、平面は+X東・+Y北、方位は北0度・時計回りとする。SVGのY反転と既存資産の回転表現はadapterで変換する。

| 保存する正本 | 内容 |
| --- | --- |
| `frame`、`context` | 図枠、歴史時代、文明、人口目標、FMGの都市・国家情報 |
| `sources` | FMG入力、合成入力、座標変換、固定交差、入力側の識別子とrevision |
| `paths` | 道・川・壁の形状、幅、作成方式、固定・自動・手動の所有区分 |
| `connections` | 接続ノード、道の区間、門、橋、河川合流、市壁との関連 |
| `districts`、`reservations` | 用途区域、広場・城・港・防御用地・保護地、生成対象範囲 |
| `placements` | 採用済みの施設・住宅・手動資産と敷地、入口、属性、安定ID |
| `landUse`、`terrain` | 森林・農地・公園・墓地、地形recipeと手動造成 |
| `recipe` | アルゴリズム版、設定、seed、入力参照、採用した生成結果のrevision |

自動生成済みの施設・住宅も採用後は保存する。読み込みや描画のたびに配置を解き直さない。再生成は明示した対象だけを置き換える。

曲線から求める河岸、道路面、壁面、街区候補、近似折れ線、描画用の三角形、空間索引はrevision付きの派生データとする。街区から施設を配置した時点で、その敷地と対象区域の対応を保存する。共有のために派生形状を同梱する場合はキャッシュ扱いとし、正本との二重編集は認めない。

### 4.2 曲線の契約

概念型の例:

```ts
type CurveSegment =
  | { id: string; kind: "line"; from: Point; to: Point }
  | { id: string; kind: "cubic"; from: Point; control1: Point; control2: Point; to: Point };

type CurveAnchor = { pathId: string; segmentId: string; t: number };

type PathSource =
  | { kind: "preset"; recipe: PresetRecipe }
  | { kind: "curve"; closed: boolean; segments: CurveSegment[] };

interface VectorPath {
  id: string;
  revision: number;
  role: "road" | "river" | "wall";
  source: PathSource;
  origin: "imported" | "automatic" | "manual";
  editPolicy: "fixed" | "editable";
  width: WidthProfile;
}
```

`Point`、`PresetRecipe`、`WidthProfile`の詳細型はM1で確定する。接続ノードで共有する座標はノードを正本とし、各曲線の端点や途中の拘束点が一致するよう、単一の編集transactionで更新する。独立した端点同士を描画時だけ近づけて接続扱いにしない。

- `line`と`cubic`をv1の基本形とする。円・楕円はプリセットの解析式から評価し、必要に応じて誤差を管理したベジェ・折れ線へ変換する。
- プリセットではrecipeが正本、曲線では制御点が正本であり、両方を同時に編集可能な正本にはしない。
- 曲線ごとに長さ、接線、最近点、交点、領域境界を評価できるAPIを設ける。
- 区間IDを維持し、分割・結合・削除時は`CurveAnchor`、幅の基準点、門、橋の参照変換表を返す。参照できない場合は確定を止め、最寄りの別区間へ黙って付け替えない。
- フリーハンドの生のpointer履歴は永続保存を必須とせず、確定した線と簡略化・近似設定を保存する。

### 4.3 近似精度

計算用と表示用の精度を分離する。計算用の位置誤差・交差判定誤差・接線角度誤差はメートル／角度で設定し、zoomや端末性能に依存させない。低品質描画でも計算用形状と異なる接続や橋判定を採用しない。

M0で、細い壁間道路、狭い支流、急な曲線、接する境界を固定入力として誤差を校正する。数値はこの段階では性能実測済みの保証値として置かない。保護地・水面への侵入判定では近似誤差を考慮した保守的境界を使い、許容誤差で通路を消したり、離れた線を一律に吸着したりしない。上限精度で解けない場合は診断して確定を止める。

## 5. 市壁のプリセットとパラメーター

### 5.1 基本形と変形

| 基本形 | 主なパラメーター | 例 |
| --- | --- | --- |
| 円形 | 中心、寸法の指定方式、縦横比、回転 | 縦横比1で円、比率変更で楕円 |
| 四角形 | 中心、幅・高さ、回転、角の丸め | 正方形、長方形、角丸長方形 |
| 正多角形 | 辺数、寸法、回転、縦横比、角の丸め | 六角形、横長の六角形 |
| 地形追従・有機形 | 基準領域、離隔、平滑化量、揺らぎ、seed | 河岸・丘・既存市街地に沿う市壁 |
| 稜堡式 | 幕壁数、囲繞寸法、稜堡の張出し・幅、回転 | 時代・技術条件を満たす場合のみ |

円形から楕円形、四角形から長方形への調整を、別の都市生成のやり直しなしでプレビューできる。既存の`round`・`oval`等との対応は入力adapterに限定し、旧設定の意味を変更しない。

寸法は次の排他的な指定方式を持つ。

1. **幅・高さ指定**: 外接寸法をメートルで入力する。縦横比は結果として表示する。
2. **囲繞面積・縦横比指定**: 面積を固定し、縦横比から幅・高さを求める。楕円なら`a = sqrt(A * r / pi)`、`b = sqrt(A / (pi * r))`、幅`2a`・高さ`2b`とする。

比率`r`は回転前のローカルX方向寸法／Y方向寸法と定義する。比率を変えたとき面積を保持するかは上記の寸法方式で決まり、入力欄同士が相互に上書きし合わない。幅・高さ・面積・角丸半径は実際の外形から検証する。

回転は位置・寸法調整後に適用する。壁厚、門の幅、塔の実寸は縦横比に合わせて伸縮させない。稜堡式の縦横比変更は単純な描画の伸縮ではなく、変形した基準多角形上で稜堡寸法・接続角を再計算して検証する。

### 5.2 二重市壁

- 外壁と内壁は独立ID・独立した形状源を持ち、同じ中心・形を強制しない。
- 内外の関係は`parentCircuitId`で保持する。円・楕円・任意曲線の組合せを許す。
- 補助操作として「外壁から指定距離で内壁候補を作成」を用意する。単純な縮尺変更では一定距離にならないため、実際のoffset領域を計算する。
- 凹部等でoffsetが分裂する場合、勝手に一つへ結ばず、候補を提示して採用を確定する。
- 市壁間道路は壁の実体領域と離隔を除いた自由空間を探索し、道路幅が収まる連結経路を求める。中心線だけが通る結果を採用しない。
- 道路を通すためのセル分割は行わない。幅不足は必要幅・不足箇所を示し、壁間隔の変更、道路幅の変更、別経路の選択へつなぐ。

### 5.3 プリセットから直接編集への移行

位置・回転・寸法・比率・角丸などの操作中はプリセットを維持する。任意の制御点編集を始めるときは、その時点の輪郭を曲線へ変換し、曲線を新しい正本とする。操作名を「曲線に変換」とし、Undoで元のプリセットへ戻せるようにする。元プリセット情報は由来として残せるが、後から数値を変えて手動形状を上書きしない。

## 6. 川・道・壁の作成と編集

### 6.1 作成方法

| 方法 | 入力・操作 | 確定時の扱い |
| --- | --- | --- |
| 自動 | FMG入力・地形・都市設定・制約 | 決定論的なrecipeと採用形状を記録 |
| プリセット | 形状選択と数値パラメーター | recipeを正本として保持 |
| 折れ線 | 点を順に配置 | 直線区間と安定した区間ID |
| フリーハンド | pointerで線を描く | メートル単位の許容誤差で簡略化し、交差・接続・急曲率を検証 |
| ベジェ | アンカーとハンドルの配置・調整 | 三次ベジェ区間、角／接線連続／滑らかなハンドルを保存 |

共通ツールとして移動、回転、数値座標、制御点挿入・削除、区間分割・結合、開閉、反転、幅変更、固定を扱う。壁には閉じた市壁と開いた防壁の両方を許す。閉曲線の終端は始点と同じノードで閉じ、見た目だけ重ねない。

端点・曲線上・門への吸着は編集補助であり、候補が見えるときに明示的な接続を作る。画面上の吸着距離はpointerの操作性に使い、保存時の幾何誤差や無関係な線の接続条件には使わない。

### 6.2 道路

- 中心線、区間ごとの幅、路面、用途、通行種別、必要なら縦断・階段・踊り場を保持する。
- 分岐・合流・行止まりを道路グラフで表現し、交差点の路面を幅付き領域として結合する。
- 線の交差が接続か立体交差かは明示する。交点が近いだけで橋・地下通路・道路接続を作らない。
- 手描き道路も門・橋・河川・固定施設との検証を通す。接続を要求した門に届かない状態を完成扱いにしない。

### 6.3 河川と幅

- 河川は流向付き中心線、左右の幅プロファイル、合流関係、必要な水面高を持つ。両岸は中心線からの派生形状とする。
- 幅の基準点は曲線上の参照で保存する。幅の補間方式を保存し、負幅や不自然な飛び、急曲率での折返しを検証する。
- 合流部は水域を結合する。中心線が交差するだけの自動的な接続は行わず、流向と合流の意味を保持する。
- 河岸の直接編集は将来拡張できるが、v1は中心線＋幅を正本とする。中心線方式と独立した河岸方式を同時に正本にしない。
- 幅変更では橋長、壁の水門、河岸道路、施設の水辺条件、港・護岸、住宅・土地利用への影響をプレビューする。

### 6.4 川沿いの道と用途区域

補助操作「河岸に沿う道路候補」を設け、対象河川、左右岸、開始・終了、河岸から道路端までの距離、道路幅を指定する。近似曲線の局所的な法線を評価し、曲率・合流・水面を考慮して経路を作る。道路中心線までの距離と河岸までの距離を混同しない。

採用時に「追従する道路」と「独立した道路」を選べる。追従する場合は河川への参照と距離条件を保存し、河川編集時に道路変更も同じtransactionで提案する。独立した場合はその時点の形状を保持し、河川変更時に衝突のみ通知する。自動追従が固定入力や施設用地へ侵入する結果は採用しない。

皮なめし等の配置は、河岸距離、接道、必要な作業用地、用途ごとの立地条件を同時に満たす候補域から行う。河岸に近いだけ、または道路が近いだけで配置可能としない。既存の施設需要・BV実寸・人口住宅の契約を維持する。

## 7. 門・交差点・橋の接続契約

### 7.1 接続の正本

道路はノードと区間からなるグラフを持ち、各区間は曲線上の範囲を参照する。門は市壁上のアンカー、開口幅、城壁回路ID、道路の接続ノードIDを持つ。水門と人・車両の通行門は用途を区別する。

不変条件:

1. 門の開口中心と道路の通過ノードは同じ確定位置を使う。
2. 道路の分岐は共通ノードを参照する。近い別座標を同一接続と推定しない。
3. 道路・川・壁が同じ座標で交わる場合も、それぞれの用途と接続関係を分ける。
4. 門を移動した場合は壁上の参照、道路の取付、必要な開口を一括検証する。
5. 壁の編集で門の参照が消える場合、削除・再接続の対象を提示し、ぶら下がった参照を保存しない。
6. 接続を変更しない曲線の表示精度変更で、グラフのノード数を変えない。

### 7.2 橋

- 河川上の橋軸は直線とし、河岸外の乾いた取付位置まで確保する。川の上の屈曲、川と平行に近い橋を禁止する。
- 中心線の交点だけで判定せず、橋が通る区間の河岸・幅・河川接線を確認する。急曲率や複数流路で単一の適法な軸を確保できない候補は棄却する。
- 取付道路は河岸の外で曲げる。固定された橋・道路を勝手に回転・短縮しない。
- 自動生成・手動描画・FMG入力・再読込の検証は`src/utils/bridgeSkewPolicy.ts`の共通値と関数を使い、別の角度上限表を作らない。
- 直角からのずれ10度以内を推奨し、古代・中世は石15度／木20度、近世25度、斜めアーチ以降30度の上限を守る。Historical periodを開始時の下限、国家技術による引上げを扱う。
- 共通APIが返す既存の明示値とプロジェクト規約の適合性をM0で監査し、M3で明示値と判定の絶対上限を30度へ修正した。FMG・RE・既存CE・Freeformへの影響と関連検証は[M3記録](../analytics/ce-meshless-m3-20261107.md)に記載する。局所実装だけで上限を緩めない。
- 手描き中の不正候補は赤い操作線と理由で示し、橋として確定・描画しない。読み込んだ不正な交差も有効な橋として描かない。
- 適法な橋が置けなければ、取付道路変更、別地点、渡し船を候補とし、施設や住宅を先に生成して失敗を隠さない。

## 8. 領域・街区・施設・住宅の生成

### 8.1 セルの代わりになるもの

都市全体を均等なセルへ分割する代わりに、用途を持つ領域、幅付き道路・河川・壁の占有領域、その残地を用いる。領域は穴・複数の連結成分を許す。単一の凸多角形へ無理に変換しない。

```text
FMG入力／合成入力／手動曲線
  → 河岸・市域・用途制約
  → 市壁・門・橋・道路グラフの確定
  → 道路面・水面・防御用地・保護地の領域
  → 建築可能領域と接道区間
  → 街区・小路
  → 職業施設の敷地とアクセス予約
  → 残地の住宅・店舗・庭
  → 住宅容量・人口割当
  → 農地・森林・景観・2D／3D表示
```

道路が閉じた輪を作らない郊外や、市壁と道路の間の土地も対象にする。道路グラフの閉路だけを街区と見なさず、市域・用途境界・水域・防御区域で残地を閉じ、道路への入口を別に評価する。

### 8.2 街区・小路

- 主要道路の路面、河川、水域、市壁・堀、防御用地、保護対象を都市領域から差し引く。
- 残地ごとに用途・接道区間・入口・通行可能な小路候補を付ける。土地の隣接関係は実際の共有境界から求める。
- 小路は道路へつながるネットワークとして生成する。地図上の近さだけで到達可能とせず、河川・壁を越える接続は門・橋等を要求する。
- `buildOrganicBlocks`等から、輪郭、境界条件、用途パラメーター、seedを受ける部分を抽出する。`Face`を模した仮セルを大量に作るadapterにはしない。
- 狭い残地は道、庭、作業場、空地として扱い、不適法な建物を詰めない。

### 8.3 施設と住宅

`medieval-facilities`は需要計算→施設配置→残地住宅の順を守る。施設敷地、必要な作業場、入口通路を予約し、その後の住宅生成が予約を削除しない。BV資産の寸法・入口・住戸容量を共有し、予約と実際の表示を一致させる。

人口不足時の面積拡張は、自動生成に属する可変領域だけを対象にする。手動市壁、固定入力、手動建物を無断で拡張・移動しない。拡張不能なら不足人数・住戸数と制約を報告する。橋や門を動かす必要がある場合は変更候補を示して採用する。

通常の`medieval`は職業施設工程を持たず、同じ街区入力から住宅・店舗・庭を構成する。人口容量計算は`faceId`ではなく敷地の用途・内外区分・建物属性を読む契約へ分離する。

## 9. 生成ステージと再生成

新方式専用のステージ定義を持ち、IDで扱う。旧CEの18／19等の番号や内部の`processStep`へ合わせるためのダミーステージは作らない。

| 順 | ステージID案 | 表示内容 |
| --- | --- | --- |
| 1 | `inputs` | FMG／合成入力、固定線・水域 |
| 2 | `cityDomain` | 都市核・市域・用途条件 |
| 3 | `wallCircuits` | 市壁の形、内外壁、防御用地 |
| 4 | `connections` | 門、橋、水門と接続条件 |
| 5 | `roadNetwork` | 接続を持つ主要道路・壁間道路・河岸道路 |
| 6 | `domains` | 通行可能領域と建築可能領域 |
| 7 | `blocksAndLanes` | 街区、小路、接道・到達性 |
| 8 | `facilities` | 職業施設と入口通路。施設モードのみ |
| 9 | `housing` | 施設予約後の住宅・店舗・人口容量 |
| 10 | `landscape` | 農地、森林、公園等の仕上げ |
| 11 | `presentation` | 道路線等を隠す表示仕上げ |

機能に該当しない工程は省略し、総数と番号を再計算する。河岸・橋の幾何を確定する平滑化は街区より前に行い、見た目の仕上げで形状を変えない。

生成run内にrevisionとチェックポイントを保持し、施設工程では住宅を生成・表示済みと扱わない。面積拡張などで上流が変わった場合はチェックポイントをそのrunの採用済み形状から作り直し、ステージを戻した際に別の都市が混ざらないようにする。描画用の表示フラグだけで未実行工程を実行済みに見せない。

手動編集後は該当runのチェックポイントを無効化し、編集済み文書を表示する。再生成対象・変更範囲を選んで新runを開始する。旧runを参照する場合は「前回の生成結果」と分かる履歴表示にし、現編集を上書きしない。

## 10. 編集と依存更新

### 10.1 確定手順

すべての編集を「候補作成→影響範囲算出→制約検証→関連参照の更新→履歴へ一括確定」とする。ドラッグ中は別のプレビュー状態を使い、pointerイベントごとに住宅や森林を全生成しない。

- Undo／Redoは曲線、接続、施設・住宅、recipe、採用revisionを一括で戻す。
- 不正候補は操作プレビューとして残せるが、有効な完成都市には採用しない。
- 施設・建物に衝突する川幅変更等は、衝突箇所と対象を表示する。「取消」「該当する自動配置だけ再配置」等の具体的な選択を用意し、手動・固定物を自動削除しない。
- 固定要素があるため解けない変更は理由を返す。既存形状を保ったまま解決不能の要求を黙って無視しない。

### 10.2 依存関係

| 変更 | 再評価する主な対象 |
| --- | --- |
| 道路曲線・幅 | 交差点、門の取付、橋、路面、接道、小路、施設入口、影響街区・敷地 |
| 河川曲線・幅 | 河岸、合流、橋、水門、追従道路、河岸施設、港、影響土地利用 |
| 市壁形状・厚さ | 門、水門、内外関係、壁間道路、堀、塔、防御用地、影響街区 |
| 門の位置・幅 | 壁の開口、取付道路、道路到達性、門前の予約用地 |
| 施設の移動・寸法 | 敷地と入口、隣接する残地、住宅容量、施設レポート |
| 外観・表示品質 | 描画キャッシュ。接続・敷地・住宅容量は再生成しない |

固定・手動・自動の所有権を別に持つ。入力がimportedでも利用者が明示的に編集可能へ変更できるが、その後はFMGの固定入力を忠実に再現しているとは扱わず、overrideを保存する。

## 11. FMG連携、保存、変換

### 11.1 FMG入力

FMGの都市descriptor、地域道路、河川、水域、固定交差、地形・気候・国家技術等を新しい入力adapterで読む。座標系とメートル換算を入口で統一し、元ID・revisionを残す。入力側がセルから作られていても、CE側でそのセルを再現する必要はない。

固定道路・橋の位置、両岸の取付、共有する交差、外部道路との接続を保持する。FMG入力に不整合がある場合は該当入力を診断し、別位置へのスナップや調査済みの橋の回転で補わない。都市内の自動道路は固定された取付点へ接続する。

都市位置や入口が水域内、入力範囲が不足、橋規約に不適合等の場合は生成前に検出する。必要な範囲拡張ができなければ理由を表示する。既存のFMG右クリックからのCE起動経路は維持し、方式選択を受け渡せるようにする。

### 11.2 保存と共有

- ファイル形式の判別は`format`と`version`による。旧文書とFreeformのcodecを維持する。
- ベジェの制御点、プリセットの数値、幅プロファイル、接続ID、固定・手動区分、採用配置を保存する。
- 共有は「入力＋recipeで再現」と「手動編集を含む文書」の違いを明示する。手動曲線を落としてrecipeだけ共有しない。
- アルゴリズム版が異なる場合も保存済み形状を表示できるようにし、自動的に新しい生成結果へ差し替えない。
- 読込時は曲線・ID・参照・幅・接続・橋・閉領域を検証する。修復が必要な場合は修復候補を元文書と分けて提示する。

### 11.3 既存都市からの変換

元文書を残して「メッシュなし文書として複製」を行う。道路・河川・壁の辺列をメートル座標の曲線へ、門・橋を接続へ、用途・保護対象・建物を領域と配置へ写す。元のメッシュ由来の折れ線を最初から勝手に平滑化しない。

変換対象と対象外の一覧・件数を確定前に表示する。変換できない城・市場・堀等を黙って捨てない。完全に変換できない場合は元のCEで開ける状態を維持する。メッシュなしからメッシュ方式へ戻すための架空のセル生成は標準操作にせず、元文書または明示的な変換に委ねる。

## 12. 既存CEの機能維持

「旧方式が継続して使えること」と「新方式でも同等機能を使えること」を別々の受入条件として管理する。新方式の基本生成が動いた時点で、CE全機能への対応完了とはしない。

| 機能 | 共有・維持するもの | 新方式で必要な対応 |
| --- | --- | --- |
| 新規・FMG起動・生成設定 | CE入口、人口・時代・外観等の入力 | 専用入力adapter、方式選択、未対応項目の表示 |
| 都市生成・ステージ | 進捗・診断・キャンセルのUI | 専用工程と正確なチェックポイント |
| 道・川・壁・門・橋 | 共通の歴史・角度等の規約 | 曲線、グラフ、実寸領域、編集ツール |
| 地区・土地利用 | 用途・密度・高さ等の設定 | セル塗りから領域の描画・分割・結合へ対応 |
| 施設・住宅・人口 | BV資産、需要、容量の意味 | セル非依存の用地割当・接道・人口適合 |
| 城・二重市壁・堀・稜堡 | 外観部品、用途・技術条件 | 複数回路、防御領域、門と道路の接続 |
| 港・護岸・船・市場 | 資産、交易・荷役・活動の属性 | 河岸・海岸・敷地を参照する配置とアクセス |
| 寺院・墓地・公園・農地・森林 | 資産・文化・景観・農地設定 | 面領域、生成予約、道路との到達性 |
| 地形・高低差・造成 | 高さ場、Freeformの敷地・道の処理 | 曲線の高さ・勾配・橋面・敷地への投影 |
| 2D・3D・選択・計測 | 資産描画、カメラ、外観、計測部品 | 完成形状の共有入力、曲線・区域IDの選択 |
| Undo／Redo・保存・共有・出力 | 操作体系、ファイル操作、SVG等 | 専用文書codec、履歴・出力の方式分岐 |
| レイヤー・固定・手動調整 | 操作の意味、既存UI部品 | セルIDに依存しない対象参照・所有権 |

初期公開は試験モードとし、対応表で未対応の項目を設定から選べないようにして理由を表示する。旧CEを削除・自動移行しない。全機能維持を要する正式切替はM9の受入後とする。

## 13. 描画と性能

### 13.1 完成形状を渡す

`TownRenderData`等の契約を設け、建物ポリゴン・資産配置、小路、農地、公園、港湾、用途属性、選択IDを渡す。`faceId`を描画時の必須キーにしない。既存の`renderTownFabric()`から再利用可能なSVG組立を抽出し、旧文書側はadapterで同じ描画契約へ写す。

旧CEへの影響を小さくするため、初期は新rendererから共有描画部品を使ってよい。旧描画を丸ごと置き換えることを最初の工程にしない。新方式の2D・3D・出力は同じ採用配置・幅付き形状を参照し、片方だけ橋・河岸・敷地を解き直さない。

### 13.2 計算の単位

- 曲線revision・依存要素ID・計算精度・アルゴリズム版をキャッシュキーに含める。
- 既存の空間索引を再利用候補にし、曲線区間や領域の境界箱で交差候補を絞る。新ライブラリの採用はM0で精度・穴付き領域・bundle負荷を比較して決める。
- ドラッグ中は影響領域のプレビューだけを更新し、確定後に重い領域演算・配置をWorkerで行う。
- 生成jobは入力revisionとjob IDを持ち、キャンセル・Undo・別編集の後に届く古い結果を採用しない。
- キャッシュは容量上限を持ち、文書を閉じた際に索引、Worker、3D資源を解放する。
- 性能目標はM0の固定入力で基準値を測って決める。メッシュをなくせば必ず高速になるとはしない。曲線交差・領域演算が新たな負荷になる点を測定する。

## 14. 実装段階と受入条件

M0〜M9の実装・検証・判断を完了。M9の公開判断は試験運用継続で、正式移行は保留。M4でFMG／合成／手動入力から固定交差を保つ骨格と、穴・複数成分・接道を持つ街区候補まで実装した。M5で小路・用途・施設先行・残地住宅・人口不足の集計と同一生成の段階表示を接続した。生成は候補の確認と採用を分け、手動変更済みの生成形状は再生成で上書きしない。複雑なoffsetの分裂に対する複数候補の選択や、大都市・全空地の配置最適化は後続とする。各段階で変更範囲に関係するテストだけを実行し、成功後の再実行・範囲拡大は新しい変更や懸念がある場合に限る。

## 15. 固定ケースと検証

大量seed探索ではなく、問題を分離した少数の固定形状を使う。

| ケース | 確認する条件 |
| --- | --- |
| 円形→楕円、正方形→長方形 | 寸法方式、面積保持、回転、壁厚・門幅の実寸、保存、Undo |
| ベジェ市壁とフリーハンド河川 | 制御点・閉路・接線・自己交差・参照変換、2D／3Dの一致 |
| 狭い二重市壁 | 必要幅が収まる場合の道路生成、収まらない場合の明示的失敗 |
| 中心部の可変幅河川 | 河岸、橋長、住宅・施設・港への影響、固定物の保護 |
| 直角橋と限界角の橋 | 共通規約、河岸外の取付、河川内での無屈曲、時代・技術・材質 |
| 河岸道路と皮なめし施設 | 川幅を含めた離隔、施設の河岸条件、実寸敷地、短い入口接続 |
| FMGの共有橋・固定街道 | 位置と共有ID、外部接続、不適合入力の診断、勝手な補正なし |
| 島・港・穴付き領域・開いた道路 | 領域の穴、複数成分、閉路がなくても街区候補が得られること |
| 施設付き都市の段階表示 | 街区→施設だけ→住宅追加、前後移動で配置が変わらないこと |
| 手動修正後の再生成 | 固定物と編集の保持、影響領域、Undo／Redo、キャンセルと遅延結果 |
| 旧文書・新文書・Freeform | 方式判別、再読込、共有、変換時の機能欠落の検出 |

幾何検証は共有ノードの一致、参照の有効性、幅付き領域の侵入、到達性、接道、面積と容量、描画品質による非変化を対象にする。旧方式と新方式の建物ポリゴンの完全一致は要求せず、入力保護・必要機能・幾何制約・容量を比較する。

十分な人口を要するFMG連携の確認ではSettlement patternをStandardにする。全量観測JSON等の再生成可能な2 MB超の出力は`docs/analytics/raw/`へ置き、Git管理には記録md・固定入力・派生比較・SHA-256一覧を残す。

## 16. 決定事項と次に進める作業

本書での設計上の決定:

1. CEを複製せず、共通UIと独立したメッシュなし処理系を作る。
2. 初期セルもK6の適合メッシュも生成しない。道・川・壁の曲線と接続、実寸領域を正本とする。
3. 市壁はプリセット＋寸法・縦横比等で調整でき、曲線へ変換して直接編集できる。
4. 川・道・壁は自動・プリセット・フリーハンド・ベジェを扱い、同じ接続・幾何検証を通す。
5. 職業施設を先に予約し、残地へ住宅を配置する。生成ステージもこの順で示す。
6. 旧CEの動作維持と、新方式の機能充足を別々に確認する。
