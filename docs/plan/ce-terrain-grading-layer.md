# CEの造成レイヤー: 段・坂・崖を持つ地形と自動生成の統合

作成日: 2026-10-23
状態: 設計。P0（地形モデルの導入とFortSiteの移植）、P1（城のセルの台地）、P2（道路の縦断と回廊の造成）、P3（崖の台地への登城路）、G1（生成後の城の地盤）、P4（段々の町と階段）、セル標高の段と土手（§7.18）は実装済み。段を街路生成の前に決める統合（§5の4）は未実施。

## 1. 目的

崖の上の城塞、外周を巻いて登る登城路、段々に重なる街区のように、平らな面と上り・下りの坂を組み合わせた立体構造をCEで自動生成し、3Dで自然に描けるようにする。

受入例: citadelのセル群を周囲より12 m高い平らな台地にしたとき、次の4点を満たす。

- 台地の縁は崖か擁壁として鉛直に描かれる
- 台地の上の道は水平に通る
- 城門から台地の門までは勾配が上限以内の坂道で登る
- 段の境界の上を道が通って凸凹になることはない

## 2. 現状と問題の所在

関連実装:

- `src/city-editor/generators/terrainElevation.ts`: `cityTerrain()` は `FaceProperties.elevation` をセル中心に置き、セル間で共有する頂点には隣接する陸セルの平均を与えて、中心から扇形の三角形で地面を作る。
- `src/city3d/three/roadMeshes.ts`: 道路メッシュの各頂点を後から `heightAt` で持ち上げる。道路は自分の高さを持たない。
- `src/city-editor/renderers/terrainMassing.ts` と `cityView.ts`: 建物・区画は `foundationAt` で水平な基礎の高さを得る。

この持ち方では次の問題が起きる。

1. **セルの境界は常に両隣の中間の高さになる。** セル全体を平らなまま持ち上げることも、境界に崖を作ることもできない。
2. **道はセルの辺の上にあり、辺の高さは両隣のセルで決まる。** 高さの違うセルにまたがると、道は坂ではなく凸凹になる。
3. **道の高さは地形の結果でしかない。** 勾配の上限や交差点で高さを揃える条件を課す場所がない。

いずれも、高さをセル（face）の属性として持っていることから生じる。CEの生成器を部分的に直しても解消しない。

一方、FortSite（`types/fortSite.ts`、`generators/fortSiteGeometry.ts`）はすでに正しい方向の作りになっている。

- 高さを墳丘・郭・堀というプリミティブから関数として評価する（`fortHeight`）
- 道（routes）は `elevationsMeters` で地形と独立した設計高を持つ
- 描画用の細かいメッシュは編集用のトポロジーとは別に作る

本設計は、これを城塞専用の仕組みから都市全体の地形モデルへ一般化する。

## 3. 地形モデル: 3層

ゲームエンジンの「ランドスケープ＋地形を変形させるスプライン道路」と同じ考え方を採る。

### 3.1 基盤地形（base）

造成前の地面。

- `cells`: 各陸セルが自分の標高の水平面になり、隣のセルとの高低差は、2つのセルの間に収まれば土手、収まらなければ擁壁でつなぐ（§7.18、`generators/cellRelief.ts`）。P0〜P4では、セル中心の標高と隣接セルの平均で頂点の高さを決める扇形三角形（円錐）だった。
- `flat`: 一様な地面。FortSiteが使う。

### 3.2 造成フィーチャー（features）

ベクターで表し、高さは絶対値（m）で持つ。

| 種類 | 形 | 用途 | 段階 |
| --- | --- | --- | --- |
| `platform` | 頂面（円、またはセルの集まり）＋水平な頂面高＋縁（`cliff` / `slope`）。段々の町の段は `role: "terrace"` | 墳丘、郭、城塞の台地、段々の街区 | P0（円）、P1（セル）、P4（段） |
| `ringCut` | 環状の軸＋幅・深さ・縁高・法面の比率・水位 | 堀 | P0 |
| `ramp` | 中心線＋各点の甲板の高さ＋幅（`CityTerrainLayer.ramps`） | 崖の台地への登城路 | P3 |
| 階段 | 道の縦断から導く（保存しない）。中心線＋各点の高さ＋幅 | 擁壁や急坂を越える路地・段のある街路 | P4 |
| `corridor` | 道路の中心線＋縦断の高さ列＋幅 | 道路に合わせた切土・盛土 | P2 |

### 3.3 合成規則

`generators/terrainModel.ts` の `evaluateTerrainFeatures` で評価する。

1. 基盤の高さから始める。
2. `platform` は max で持ち上げる。`slope` の縁は、頂面から `runMeters` の距離で基盤の高さまで直線的に下る。
3. どれかの `platform` の足元（頂面＋斜面）の内側の点は、そこで評価を終える。郭の上を堀が削ることはない。
4. 残りの点では切土（`ringCut`、後の `corridor` の切土側）を min で下げる。堀の底は、縁高から深さを引いた水平面になる。
5. 道路の回廊（P2）は、1〜4の結果の上にかける。回廊の幅の中では道路の設計高で上書きし、その外では 1:1.5 の法面の範囲に地形を収める（盛土側は下げ、切土側は上げる）。回廊は自分が通る段だけを造成し、崖の帯と崖で隔てた別の段には触れない。

FortSiteの `fortHeight` はこの評価をそのまま使う（`fortSiteTerrainFeatures` → `evaluateTerrainFeatures`）。

### 3.4 道路の縦断プロファイル（P2）

街路グラフの辺ごとに高さの列を持つ。**道が地形に従うのではなく、地形が道に合わせて造成される**ようにする。

- 交差点で高さが一致すること、勾配が上限以下であることを条件に、地形に近く滑らかな高さを解く（§7.6）。
- 解いた道は回廊になり、回廊の幅の中の地形を設計高に揃える。回廊は保存しない派生物で、文書側のフィーチャーにはしない。
- 勾配の上限は道の種類（`RoadRibbon.gradeClass`）ごとに次のとおりとする。

| 種類 | 対象 | 上限 | 根拠 |
| --- | --- | --- | --- |
| `cart` | メッシュの道路、地図の枠から来る道、川沿いの接続 | 10% | 荷を積んだ車は5%を超える勾配をほとんど扱えなかった（Lawton 2004）、ヒスパニアの道で実用は6〜8%（Moreno 2006）。アルプス越えの道では6.7〜10%の区間に轍が残る。望ましい値ではなく、車が通れた上限として10%を採る |
| `lane` | 街区の路地（fabric lanes） | 15% | 車両を前提としない徒歩・荷駄の路地。史料の数値は未確認で、`cart` と `path` の間に置いた暫定値 |
| `path` | 郊外の小道（`trail`） | 25% | ハドリアヌスの長城の Military Way は25%（短区間33%）の勾配を持ち、車両用ではなかったと考えられている |

5〜8%を守るには道筋を変える必要がある。これは道の網を作り直すP3の範囲とし、P2では上限だけを課す。

出典:

- [Land transport in mountainous regions of the Roman Empire（2019、Lawton 2004・Moreno 2006 とアルプスの轍の勾配を引用）](https://recercat.cat//bitstream/2072/369267/1/2019-Land-transport-mountainous-regions-roman-empire-Postprint.pdf)
- [Military Way (Hadrian's Wall)](https://en.wikipedia.org/wiki/Military_Way_(Hadrian%27s_Wall))

## 4. 描画

- 地面は基盤の種子三角形を出発点とし、フィーチャーの近くで細分化し、フィーチャーの折れ線（breakline）で分割する。各頂点の高さは `heightAt` から取る。P0の処理は、FortSiteの既存の細分化と分割をそのまま一般化したものである。
- セルの台地は、縁が編集メッシュの辺に一致するので、地面の三角形が縁をまたがない。任意の多角形の切り抜き（CDT）は要らない。
- 崖の縁は、台地の内側に幅0.25 m（`CLIFF_BAND_METERS`）の帯として表す。帯の外側の縁で基盤の高さ、内側の縁で頂面の高さになる。高さは場所ごとに1つに決まり、`heightAt` は連続のまま使える。三角形は、各縁の辺から0.25 m内側の平行線で分け、帯の三角形に `escarpment` の印を付ける。3Dではこれを地面ではなく石の色のメッシュ（`ce-escarpment`）で描く。
- 帯は幅を持つので、凹んだ角のごく近く（0.25 m以内）では頂面がわずかに下がる。見た目の影響はない。
- 斜面の縁（`slope`）は台地の外側に `runMeters` の幅で下る。三角形は、縁から `runMeters` 外側の平行線（法尻）でも分ける。
- 登城路は地面ではなく石造の構造物として描く（§7.9）。地面の三角形を登城路の形に合わせる必要がないので、P3でもCDTは使っていない。任意の多角形の台地が必要になった時点で導入する。
- `CityTerrain` の `heightAt` / `foundationAt` / `triangles` というインターフェースは維持する。道路・建物・水面・農地・公園の各描画は変更しなくてよい。
- `foundationAt` は、足元の多角形の内側にある地形の最高点（輪郭の頂点、内側にある三角形の頂点、輪郭と三角形の辺の交点）を返す。P0で `cells` と `flat` の両方をこの方式に揃えた（§7）。

## 5. 自動生成との統合

高さの境界を街路生成の前に決め、ネットワークの制約にする。skeleton-first パイプラインに次の順で差し込む。

1. **段の計画**: 城塞・街区ごとに段（level）を割り当てる。FMGから取り込んだ実標高で高所を選ぶか、指定に応じて台地を造成する。
2. **段の境界を確定する**: `platform` の縁を「越えられない辺」にする。城壁はこの縁の上に載せる。崖の上の城壁は史実の配置と一致する。
3. **アクセス路を生成する**: 城門から城塞の門まで、勾配の上限付きの経路探索で `ramp` を作る。台地の外周を巻く道やつづら折りになる。攻め手が盾を持たない右側を城壁に向けて登る配置もここで規則にできる。坂の頂部に城塞の門を置く。
4. **街路を生成する**: 段の境界をまたぐ辺は「ランプがある」「階段（歩行者のみ）」「つながない」のいずれかにする。段の境界の上に道を引いて凸凹になる状態は、トポロジーの上で起きなくなる。
5. **縦断を平滑化する**: §3.4 の最小二乗で解く。解けない辺はステップ4に戻して迂回させる。
6. **区画・建物を置く**: 既存の `foundationAt` で基礎の高さを決める。

## 6. 保存

- P0のフィーチャーは文書から毎回導出し、保存しない。FortSiteは従来どおり `document.fortSite` が正本である。
- P1から、造成を `CityDocument.terrain = { version: 1, features }` として保存する。保存できるのはセルの台地だけである。セルは ID で持つので、メッシュの縮尺の変更に追従する。生成器が作った派生のメッシュと縦断の解は保存しない。
- 台地は `ownerId` で作った城を指す。城を削除すると台地も消える。
- 読み込み時は形だけを検査する。メッシュ編集で無くなったセルは評価のときに飛ばす。
- 旧文書は `terrain` を持たず、`cells` 基盤だけで今と同じ地面になる。

### 7.2 P0の同一性の確認

変更前後で、FortSite（`generateFortOnDocument` の micro hex）、丘上の城塞の確認用サンプル（`createFortressStudy`）、平坦なグリッドの3文書について、次を比較した。

- 地面の三角形（座標・高さ）
- 6,068点の `heightAt`
- `fortHeight`
- 構造物・区画の `foundationAt`

結果は次のとおり。

- 三角形・`heightAt`・`fortHeight` は、3文書すべてで差が 4e-15 m 以下（浮動小数の丸めのみ）だった。
- 3文書のうち `cells` の2文書は、`foundationAt` も完全に一致した。
- FortSiteでは、684個中85個の `foundationAt` が最大0.09 m上がった。以前のFortSite専用の実装は、輪郭の頂点と重心しか調べていなかった。そのため、墳丘の斜面にかかる足元では、内側の高い地点を見落としていた。共通の実装はインターフェースの約束（足元のすべての地形より上）を満たしている。この差は見落としの修正として受け入れた。

### 7.3 P1の実装内容

- `types/terrain.ts`: 台地の頂面を `TerrainShape`（円、またはセルの集まり `faces`）にし、`ownerId` と保存用の `CityTerrainLayer` を追加。`TerrainPatch.escarpment` を追加。
- `generators/terrainModel.ts`: セルの頂面を縁の線分（内向きの法線付き）に解決する `resolveTerrainFeatures`。内外の判定（偶奇）と縁からの距離で、崖の帯・斜面を評価する。三角形を分ける平行線（`terrainFeatureCreases`）と、帯の判定（`onTerrainEscarpment`）を提供する。
- `generators/terrainElevation.ts`: セルの集まりの縁の線分をメッシュから作り、平行線で三角形を分ける。`cityTerrainStamp` に `document.terrain` を含める。
- `generators/terrainEditing.ts`（新規）: `setCastlePlatform`、城の削除時に消す `removeOwnedTerrain`、読み込み時の検査 `validateTerrainLayer`（`validate` から呼ぶ）。
- `controllers/inspector.ts`: 城の検査欄に「地盤」（自然地形 / 平らな台地・崖の縁 / 平らな台地・土の斜面）、台地の標高、斜面の水平長を追加。初期値は城のセルの最高標高＋10 m。
- `city3d/three/waterMeshes.ts`: 崖の帯を `ce-escarpment` として石の色で描く。

城の城壁は台地の縁（セルの辺）に載る。既存の `groundStructures` が城壁の足元から基礎を下ろすので、崖の縁の城壁は擁壁の上に立つ姿になる。

### 7.4 P1の確認

- 単体テスト（`generators/terrainEditing.test.ts`）で次を確かめた。
  - 崖の縁: 台地の面の三角形がすべて頂面の高さにそろう。縁の1 m内側は頂面の高さ、1 m外側は5 m以上低い。足元の基礎の高さは頂面の高さ。崖の帯のメッシュが作られる。
  - 斜面の縁: 縁の上では頂面の高さ、10 m外側では1 m以上低い。崖の帯は作られない。
  - 保存して読み直しても同じ内容になる。不正な台地を含む文書は読み込まない。「自然地形」に戻すと消える。城を削除すると消える。
  - 2つのセルの台地では、セル間の共有辺は頂面の高さのまま、外周だけが崖になる。
- P0で取った変更前の値（FortSite、丘上城塞のサンプル、平坦なグリッド）とも再び比べた。差はP0と同じ（FortSiteの基礎の高さだけ）だった。
- CEをブラウザで開き、次の3点を3Dの画面で確かめた。
  - 検査欄で城の地盤を「平らな台地・崖の縁」に変えると、台地が持ち上がる。
  - 城のない2つのセルの崖の台地では、上面が平らで、縁が石の色の鉛直な面になる。
  - 土の斜面の台地では、外へ下る斜面ができ、外から来る道が坂になって門へ上がる。

### 7.5 P1で残した課題

- セルの辺に沿う道は、崖の縁では段差になる。段の境界を道の網の制約にするのはP2で行う。
- 崖の台地の城門には登る道がない。外へ下る `ramp` の自動生成はP3で行う。それまで、門から入れる見た目が必要な場合は斜面の縁を使う。（P3で対応、§7.9）
- 任意の多角形の台地とCDTは、P3で必要になってから入れる。（P3では不要だった、§4）

### 7.6 P2の実装内容

- `utils/roadSurface.ts`: `RoadRibbon.gradeClass`（`cart` / `lane` / `path`）を追加。`generators/townRoads.ts` で、街区の路地を `lane`、郊外の小道を `path`、それ以外を `cart` にする。
- `generators/roadGrading.ts`（新規）: 道路の縦断を解き、回廊を評価する。
  1. 道の中心線を4 mごとの節点に分ける。座標が一致する節点は同じ節点とし、交差点の高さはそこで一致する。
  2. 他の道の幅の中で終わる路地の端は、その道の最寄りの節点につなぐ。
  3. 崖で隔てた段をまたぐ区間（崖の帯の上、または両端の段が違う区間）は切り離し、道をそこで止める。止めた地点は `cliffBreaks` に残す。段の判定は `terrainModel.ts` の `terrainLevelAt` を使う。崖の縁の上に沿う道も、この判定で止まる。
  4. 地形の高さを目標に、8 mの長さで滑らかにする（Gauss-Seidel、60回）。
  5. 勾配の上限を必ず守らせる。上から押さえる関数（上限付きの最大の関数）と下から押さえる関数（最小の関数）を、多始点 Dijkstra で求める。辺の重みは「勾配×長さ」とする。その中点を採ると、勾配の上限を満たし、滑らかにした縦断からのずれも最も小さい。初めは逐次の補正で実装したが、節点の多い道では収束が遅く、上限を約1割超えたため、この方式に替えた。
  6. 台地の頂面にある節点は固定する（`onPlatformSummit`）。このため、斜面の縁の台地へ登る道は頂面を掘り下げず、台地の外側の盛土の坂になる。
- `generators/terrainElevation.ts`: `cityTerrain(document, { roads })` で道を受け取ると、上の結果で `heightAt` を造成する。結果の `roads` には、描く道（崖で切った後の道）と `cliffBreaks` が入る。地面からのずれが5 cmを超える回廊の近くは、三角形を辺2 mまで細かく分ける。
- `renderers/cityView.ts`: fabric を先に作り、道を集めてから地形を作る。地形の更新判定に道の更新判定を含める。道路メッシュは `terrain.roads.ribbons` を描く。道路メッシュは各頂点で `heightAt` を引き続き引くが、回廊の中の `heightAt` が設計高になるので、道は幅方向に水平になり、縦断のとおりに上り下りする。
- 道を渡さない呼び出し（BV、水面メッシュの既定値、テスト）は従来どおり造成しない地形になる。

- 3D: `renderers/terrainMassing.ts` の `rampStructures`。区間ごとに、地面の0.3 m下から甲板までの石の塊を作り、折れ目の外側を三角形で埋め、両側に高さ1 m・幅0.4 mのパラペットを載せる。最初は折れ目の左右の点を角度に応じて外へ延ばして（マイター）つないだ。しかし折り返しでは点が台地の上まで延び、塊が裏返ったため、区間ごとの直方体と三角形の継ぎ目に替えた。

### 7.15 P4の実装内容

丘の上の町を、擁壁で区切った水平な段に造成する。段の間は、路地も街路も階段で越える。

- 段の計画: `generators/terracePlanning.ts` の `planTerraces`。
  - 各陸セルの中心で敷地の標高を引き、最も低いセルから段の高さ（既定4 m）ごとに番号を付ける。
  - k 番目の段は、番号 k 以上のセルの集まりで、高さは「セルの標高の最高値＋k×段の高さ」とする。これを入れ子の台地（`role: "terrace"`、縁は崖＝擁壁、`ownerId: "terraces"`）にする。
  - 段は地面を持ち上げるだけで、掘らない。段の数は最大40。
- 標高の出所: FMGの記述子（`descriptor.terrain` の高さ場）か、記述子のない生成では合成敷地（`synthSite`）の高さ場。生成した都市のセルの標高は、どちらでも都市の中で一様である（§7.7）。起伏は高さ場にしかないので、そこから段を作る。合成敷地の「丘の上」は、都市の半径を幅とする高さ60 mの山になる。
- 生成: `GenerationSettings.terraces = { stepMeters }`。`generateCityOnDocument` が、城の地盤（G1）の前に段を置く（計測名 `terraces`）。城の台地の高さは、城のセルが載る段の高さから測る。生成パネルの合成敷地の設定に「斜面」（自然の斜面 / 擁壁で区切った段々）と「段の高さ (m)」を追加し、共有リンクにも載せる。
- 段の扱い:
  - `terrainLevelAt` は段の擁壁を、道を止める崖として扱わない。道は段を越えてよい。
  - `onPlatformSummit` は段の上を固定しない。段の上で道を水平に固定すると、段を越える坂が作れなくなるため。
- 階段: `roadGrading.ts`。
  - 路地と小道の勾配の上限を、階段の勾配 `STAIR_GRADE`（0.5）に上げた。ブロンデルの式（蹴上げ2つと踏面1つで約63 cm）から、蹴上げ16 cm・踏面31 cmとした値である。
  - 歩いて上れる勾配（路地15%、小道25%）を超える区間を階段にし、道の帯はそこで切る。
  - 段のある町（文書に段があるとき）では、荷車の道も同じく階段で段を越える（段のある街路）。
  - 段のある町では地面を道に合わせて削らない。道の縦断は、地形以上で勾配上限を満たす最も低い縦断とする（多始点Dijkstraの上側の包絡）。階段と坂は、擁壁から下の段へ張り出して築く。地面の三角形も細分しないので、三角形の数は造成しない地形と同じになる。
  - 道の帯は、段のある町では `CityTerrain.surfaceAt`（新設の `RoadGrading.roadAt`）で縦断の高さに載る。
- 3D: `renderers/terrainMassing.ts` の `stairStructures`。区間ごとに16 cm以下の蹴上げで踏面を切り、各踏面を地面から立ち上がる石の塊として置く。
- 2D: 段の擁壁は、城の崖より細い線と短いケバで描く。階段は2Dには描かない。
- 高速化: 段は入れ子で数が多く、縁の線分も多い。そこで2点を高速化した。
  - 縁の線分を格子に入れて、近い線分だけを調べる（`TerrainOutline.bins`）。
  - 内外の判定を、点を含むセルの検索で行う（`faceLocator`）。セルの辺や頂点の上でどのセルにも入らない点は、従来の偶奇判定で決める。

### 7.16 P4の確認

- 実装の途中で、次の2つの不具合を見つけて直した。
  - **台地の内側にある頂点の高さが0になっていた。** セルの頂点は、点を含むセルの検索でどのセルにも入らない。そのため、台地の内側にある頂点が「外」と判定され、高さが0になっていた。上の偶奇判定への切り替えで直した。
  - **段々の町で畑が減っていた。** 農地の判定（`ruralSuitability`）が、擁壁の面を急斜面として数えていた。擁壁の面と、凹んだ角で擁壁の帯に頂点だけ入る小さな三角形を、擁壁の面として扱うようにした。直した後の小さな町（tiny）では、畑の数が段を作らない場合と同じ153区画になった。
- 最初は、P2と同じく地面を道に合わせて切土・盛土し、三角形を道の回廊に合わせて細分した。合成の丘の上の小さな町では、三角形が97万個、地形の計算が15 sになった。誤差で細分を止めても、道の両側を擁壁にしても、5万〜11万個から下がらなかった。そこで、段のある町では地面を削らず、階段と坂を構造物として築く方式に替えた。

| --- | --- | --- | --- | --- |
| tiny | 14 | 6,805 → 6,805 | 119 → 181 ms | 404 か所 |
| small | 14 | 18,791 → 18,791 | 313 → 570 ms | 1,426 か所 |

### 7.17 P4で残した課題

- 階段を2Dに描いていない。階段は道の縦断から導くので、2Dの描画で地形と道の縦断を計算する必要がある。
- 段のある町の荷車の道は、つづら折りに付け替えずに階段で段を越える。荷車が通れる坂道にする道筋の変更は扱っていない。
- 段は図枠の中のすべての陸セルに作る（郊外の畑も段畑になる）。川は段の擁壁を越えて流れる（滝や堰は描かない）。
- 段の擁壁の上に建つ町の城壁は、低い側の段まで基礎が下りるので、高い擁壁の上の城壁に見える。
- 段を街路生成の制約にすること（§5の4）はしていない。街路は段を知らずに作られ、その後で段と階段が付く。

### 7.18 セルの標高：水平なセルを土手と擁壁でつなぐ

#### 報告された不具合と原因

既定の設定で生成した都市（small）で、templeのあるセルの標高を100にした。すると、セル中心に templeより高い尖った物体が現れ、templeは地面に埋もれた。標高を50にすると、隣のセル（標高1）の噴水がtempleの中ほどの高さに見えた。原因は次の3つだった。

1. **地面が円錐になっていた。** セル中心だけが指定の標高で、縁の頂点の高さは隣接セルとの平均だった（§2の問題）。標高50のセルでは、中心から40 m離れると高さが4〜6 mになる。
2. **道路の造成が円錐を削っていた。** P2の道路の造成が荷車の道を10%に収めるため、円錐を深く削った。法面が削り残したセル中心だけが尖塔として残った。標高100では、中心から10〜25 mの地面が59〜86 mから24〜31 mまで削られていた。
3. **templeが部品ごとに別の高さに置かれていた。** 部品がそれぞれの足元で接地し（24〜99 m）、詳細なバシリカのモデルは、その最低値に置かれて埋もれた。

#### 決定

方式の候補は3つあった。セル全体を水平な段にして境目をすべて擁壁にする方式は、`flat-top` ブランチに保存した。ユーザーの決定により、標高差の大きさで境目の作りを使い分ける方式を採った。

- 各陸セルは、セル全体が自分の標高の水平面になる。
- 隣のセルとの境目は、標高差が小さければ土手、大きければ擁壁にする。
- 境目は、土手の勾配と、土手を置ける幅で決める。
  - 土手の勾配は1:3（`BANK_GRADE`）とした。芝を張った土手を人が歩き、草を刈れる、ほぼ最も急な勾配である。
  - 土手は共有する辺を中心に、両側のセルへ同じ幅だけ入る。片側の幅は「標高差 ÷ 勾配 ÷ 2」になる。
  - 片側の幅が、辺から両側のセルの中心までの距離の短い方の半分（`BANK_SHARE` = 0.5）以下なら土手にし、超えれば擁壁にする。
  - したがって閾値はセルの大きさで変わる。辺から中心まで25 mのセル（約50 mのセル）では、標高差8 m以下が土手になる。辺から中心まで10 mのセルでは、3 m以下が土手になる。

#### 実装

- `generators/cellRelief.ts`（新規）
  - `cellRelief` は、標高の違う陸セルの間の辺を「段差」として集め、土手と擁壁に分ける。
  - 高さは、点を含むセルの標高を基本にする。その点に最も深く入り込んでいる段差で次のように決める。
    - 土手：辺の上で2つの標高の中間になり、片側の幅の位置で自分のセルの標高に戻る、一次の斜面にする。
    - 擁壁：高い側のセルの内側0.25 mの帯で、低い側の標高から高い側の標高まで立ち上げる。
  - 辺や頂点の上でどのセルにも入らない点は、1 cmずらしてセルを探す。どちら側のセルでも、辺の上の高さは同じになる。
  - 土手の両端と擁壁の上端を、地面の三角形を分ける線（折れ目）として返す。
  - `faceLocator` は `terrainElevation.ts` からここへ移した。
- `generators/terrainElevation.ts`
  - セルの種子三角形は高さを持たず、高さは `cellRelief` から取る。
  - 起伏がある文書では、地面の三角形を必ず段差の折れ目で分ける。
  - 擁壁の帯は、擁壁の面として石の色で描く。帯のうち、より高い台地に覆われて高低差が0.01 m以下の部分は、擁壁の面として扱わない。
- 道路
  - 擁壁が1つでもある文書は、段々の町（P4）と同じ扱いにする。地面は削らず、道は階段や坂で擁壁を越える。
  - 土手だけの文書では、P2の地面の造成（荷車の道の切土・盛土）がそのまま働く。
- `renderers/terrainMassing.ts`: templeは1つの建物として接地する。すべての部品の床を、部品の中で最も高い接地面にそろえ、低い部品には基礎を下ろす。
- `generators/rampPlanning.ts`: 登城路を、段差のある地面に合わせて決め直す方式にした。
  - 以前は、裾の地面の高さから必要な長さを決め、裾から頂部まで一様に上げていた。この方式では、水平なセルと土手の上を通るときに、途中で地面より低くなって候補がすべて捨てられた。丘上城塞のサンプルでは、登城路が置けなくなっていた。
  - 新しい方式では、経路を町の最も低い地面まで届く長さで敷く。着地点から勾配8%で下げた甲板が、道幅全体で初めて地面に届いた所を裾にする。

## 8. 採用しない案

- **高さ場だけで表す**: 鉛直の崖・橋・門のトンネルを表せず、§2 の問題が残る。
- **完全な3Dメッシュ / ボクセル**: 自動生成と2Dの編集UIのどちらとも噛み合わない。
- **セル標高のまま、生成器の側で補正する**: セル境界が中間の高さになることは変わらず、改善が限られる。
