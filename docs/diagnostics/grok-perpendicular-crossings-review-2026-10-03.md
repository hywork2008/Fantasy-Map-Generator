# Grokの直交渡河レビューの検証

2026-10-03。対象は[レビュー本文](../temp/reviews/perpendicular-crossings-review-1-9.md)と[HTML図解](../temp/reviews/perpendicular-crossings-review-1-9.html)。現行FMG・CEのソースを確認し、図1・3・4・6・9はHTMLをブラウザーで描画して検査した。橋床の頂点間横断は実関数への最小入力でも確認した。

今回は採否の判断を記録する。既存の[設計書](../plan/fmg-settlements-and-perpendicular-crossings.md)の未コミット変更は保持し、設計本文・ソースコード・レビュー原文・図解は変更していない。

## 結論

レビューはCEの一部の実装を読んでいる。特に`bridgeDecks`の二つの生成経路を指摘した点は正しい。ただし、FMGとCEの異なる河川表現を十分に区別しておらず、図の誤り、コードの数値の誤読、設計書に既にある制約の見落としがある。全体をそのまま設計へ取り込むべきではない。

実質的に優先して取り込むべきなのは、**有限の渡河区間と局所断面の検証（4）、水際・橋床端・進入端の区別（5）、CEの実際の橋床描画まで含む契約（6）**。1・2・3・7・9は、既存方針を変える理由ではなく、検証条件や用語を明確にする補足として扱う。8は通常生成に存在する不具合の根拠としては採用しない。

## 1. 現在の河川表現は同じではない

| 対象 | コードで確認した表現 | レビューを読む際の注意 |
| --- | --- | --- |
| FMG / SVG | `draw-rivers.ts` → `addMeandering` → `getRiverBanks` → `getRiverPath`。流量等に応じた幅で左右岸を作り、左右岸をそれぞれCatmull–Romで描く | 角張った中心折れ線に一定幅のstrokeを置く図と同一ではない |

| CE / 大河の道路接続 | `render/svg.ts`が`document.riverConnections[].banks`を別に描画する | `bridgeDecks`だけ直しても全種類の河川橋は統一されない |

## 2. 各指摘の採否

### 1 — 内積だけではqを通ることを保証しない

**検証条件の補強として採用。ただし「図の赤い橋は河川と直角でない」という根拠にはならない。**

内積ゼロだけで通過位置が固定されないことは正しい。一方、設計第5節は既に`q + λn`と水域境界の交点から橋を作ると指定しているため、生成定義そのものにqが欠けているわけではない。

図1は中心線が水平で、赤も緑も鉛直である。赤は指定したqを通らないが、別の中心線上の交点q'では正しく直交する。「採用した候補の位置を保存しているか」と「その地点の流向に直角か」は別の検査である。

取り込む補足は、保存した河川弧長sから`q=C(s)`と`t`を再評価し、橋の全軸点Pについて`(P-q)·t≈0`、両水際点の法線方向の符号が反対、qが渡河区間内部にあることを検査すること。候補選定中に別のq'を評価することは許し、確定後にqだけを置き去りにして橋を平行移動することを禁止する。

無限に延長した法線と中心線の交点が世界全体でqだけであることは要求しない。第4項の範囲制限と整合させる。

### 2 — 河川接線と道路接線の混同

**用語の明確化として採用。現設計が道路を川と平行にせよと要求しているわけではない。**

`tRiver`を河川接線、`nCrossing`を橋軸、`tRoad`を道路の接近方向として区別するとよい。橋台付近では道路の接線が橋軸に平行で、進行方向も連続することを要求する。双方向の道なので符号は経路の向きに合わせる。河川接線へ道路を合わせるものではない。

### 3 — 最短弦と局所法線上の幅

**定義の明確化として採用。新しい最短弦探索は導入しない。図3は実装の再現例には使わない。**

設計は既に局所断面を定義し、無制約の両岸最短線との違いを述べている。確定したqではqを含む法線上の水域区間を渡る、と検証文にも明記すれば足りる。

図3の片岸だけの三角形の張り出しと水平中心線は、CE通常河川の一定幅ribbonや、FMGの直線中心線から左右へ幅を振り分ける単純区間の形状を再現していない。一般的な非対称ポリゴンの概念図としては使えるが、現行描画でこの現象が生じた証拠ではない。また、赤い斜め線より短い鉛直の横断も左側に存在するため、赤を「両岸間の最短線」の例とは扱えない。

### 4 — 無限法線の再交差と、長すぎる単一水域区間

**採用優先度が高い。ただし図4Bの緑を正解として採用しない。**

設計の「同じ法線が別の蛇行へ再横断しない」は検査範囲が曖昧である。対象は橋床・必要な直線進入部・進入回廊の有限な占有範囲とする。遠くの別の曲がりと延長線が交わるだけでは棄却しない。

一方、qを含む水域区間が一つでも、曲がった先の水域へ入り込み、局所的な両岸間横断でない場合はある。両交点が同じ局所河川区間の反対岸に由来すること、岸の生成元の弧長・区間IDがq近傍にあることを検査する。中心線・幅の変化に合わせた局所窓を使い、単純な「代表幅の何倍」という値だけを正しさの根拠にしない。判定に使う水域は共通の物理形状とする。

**図4Bの緑は`(778,80)→(778,180)`だが、終点は水際でない。** 図の水域ポリゴンは`760<x<900`で`y=180`より下にも続くため、終点から先も水中である。図のq=`(800,130)`も通らない。これは新しい有効橋の例にできない。この地点を棄却して別の断面を選ぶか、別地点の有効な両岸交点を再計算する必要がある。

### 5 — 水際・橋床・進入端の区別

**役割の分離は採用。レビューの延長量と現行実装への保証は訂正する。**

水際での交点、橋床の岸への乗り、乾いた道路の進入端は区別すべきである。特に「橋台」を水際交点と同義に使うと構造物と幾何点が混ざる。保存情報または一意に再計算できる情報として、qと河川参照、水際点、橋床端、進入端、形状versionを扱う。

`src/city-editor/core/bridgeDeck.ts:11`では`BRIDGE_BANK_SEAT=1.4`。両端はそれぞれ`BRIDGE_BANK_SEAT/2=0.7m`延長する。レビューの「/2（1.4m）」は誤り。`passages.ts`の`straightenRiverCrossing`には別途`half+1.4`という進入頂点の補正があり、この値と橋床の延長を混同しない。

また`straightenRiverCrossing`はロック・門・壁などの頂点を動かさず、移動にも位相上の制約がある。実装が常に両腕を完全に法線へ移す保証はない。「現在のCEでも全点が必ず法線上」という前提ではなく、新方式で満たす契約とする。

単なる描画の岸への乗りと構造上の橋長も区別し、通行距離は経路軸全体から一度だけ積算する。q・t・nを重複保存する場合は相互検証し、不整合な別々の正本を増やさない。

### 6 — CEの橋床が別の向きで生成される

**採用優先度が最も高い。実コードと最小実行で確認できる。**

`bridgeDecks`は共有河川頂点では前後方向の平均から法線を求める。一方、共有頂点がない横断では、水面で切った道路の両端を結ぶ方向をそのまま延長する。後者には直角性の検証がない。

実関数へ、幅10mの河川`(0,-30)→(0,30)`と道路`(-40,-10)→(40,10)`を入力した結果:

```text
橋床端 = (-5.6790997501, -1.4197749375)
       → ( 5.6790997501,  1.4197749375)
河川方向と橋軸の正規化内積 = 0.2425356250（0ではない）
```

これは斜めの道路から斜めの橋床が生成される再現であり、画面全体やすべての生成地図で発生する頻度を測ったものではない。

新形式では、検証済みCrossingから橋床・水域外の道路・進入部を同じ形状として生成する。`bridgeDecks`の再推定や弦方向fallbackだけでなく、`riverConnections[].banks`の別描画経路も対象にする。同時に河川の形状を保持する必要があり、**橋床端だけ固定してCEの川が変わる状態では解決しない。**

図6Aの緑は保存した元形状の法線として描かれているが、現在のV字中心線の頂点には一意な接線がなく、緑をそのまま「現在の川に対する正しい橋」とは言えない。図6Bの斜めの橋床は上記の実行結果に対応する。

### 7 — 必須条件と確定後の監査が矛盾する

**矛盾という指摘は不採用。処理段階とノード接続の明記は採用できる。**

現設計は第5節で幾何を必須条件とし、第7節で登録前の検証を要求している。確定後に共有道路を破壊しないことと、確定前に不正な候補を採用しないことは両立する。費用を払えば直交条件を破ってよいという記述はない。

補足するなら「断面候補→進入接続の検証→有効辺→経路全体の検証→登録」の段階を明示する。探索中に進入形状を解く場合も、未検証候補を通行可能な確定辺として公開しない。橋台付近の物理的な道路接続は軸方向の前後だけとし、複数routeの共有参照と道路の分岐は区別する。分岐は進入区間外で行う。

### 8 — 中心線のない小河川

**通常生成の不具合という前提は不採用。欠損入力・適用範囲の説明だけ追加する。**

FMGは河川を`river.cells`列から生成し、描画時は`river.points`がなくても`getRiverPoints`がセル座標列を取り出し、`addMeandering`で点列を作る。任意のpointsフィールドがないことは中心線がないことではない。航行可否の流量判定とも別である。短すぎる流路は`MIN_RIVER_CELLS`でriver登録前に除外され、独立した水域として描かれる「中心線のない細流」にはならない。

CEの通常river featureも頂点列を持つ。大河ポリゴンの近岸だけがframe内にある場合はあり得るが、それは世界側の河川参照が不要という意味ではない。新形式では必要な断面参照を維持する。

破損した旧入力や独立編集の水域ポリゴンで河川軸を復元できない場合は、橋を推測せず未解決とする。今回の依頼を、地図に存在しない全細流の新規生成へ広げる必要はない。

### 9 — 折れ線頂点の平均接線

**本当に折れた中心線の角に対する方針として条件付き採用。FMG全体へ一律適用しない。**

角のある数学的な折れ線では、頂点で一意な接線はない。現設計もその点で候補を作らず、前後の安定区間へ移すとしている。CEの前後方向を平均するコードの指摘は正しいが、それは局所方向の近似規約であり、「隣接する二つの線分のどちらとも直角でない」というだけで全形状の不正を判定することはできない。

FMGのSVG河岸は曲線で、WebGLも中心点列をサンプリングする。共通RiverGeometryが滑らかな曲線なら、実際の曲線の微分で接線を求める。左右のサンプル弦の両方に直角であることは要求しない。真の折れ線の場合だけ、区間内部の方向を使い、橋床と進入に必要な局所窓が角や折返しへ掛からないことを確認する。「区間内部なら角のすぐ近くでも安全」とはしない。

設計上の補足は、曲線と折れ線の表現を区別し、曲率・幅変化・局所窓に基づく安定性を検証すること。粗い頂点配置への依存で橋向きが変わらないよう、同じ曲線を再サンプリングしても結果が一致するテストを加えるとよい。

## 3. レビューの版に関する注意

末尾の「文書は第11節で終わる」は現在の設計書には当てはまらない。第12節は存在し、Geminiの「ペナルティだけへの置換」と「旧図の斜め橋の互換描画」を採用しない理由も記載済みである。レビューは更新途中の版を見た可能性があるため、現在の欠落として再修正する必要はない。

## 4. 次に設計へ反映するなら

1. 共通の物理中心線・水域を正本とし、qと法線上の位置まで検証する。図1のような別の有効地点との違いを明記する。
2. 水際点・橋床端・進入端を区別し、検査範囲を有限な橋・進入区間へ限定する。遠方の蛇行交差では棄却せず、局所断面を逸脱する長い横断は棄却する。
3. CEの通常河川と大河の両描画経路で、確定した河岸と橋を保つ。斜め弦fallbackを新形式へ適用しない。
4. 用語と確定前の検証段階を明記する。曲線には曲線の接線、真の折れ線には区間方向を用いる。

この補強で十分であり、道路探索や都市配置の基本方針をGrokレビューに合わせて再設計する必要はない。
