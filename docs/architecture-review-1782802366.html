1. LAYER VIOLATION: Generators Doing SVG DOM Manipulation

Strong Priority
Files Involved src/generators/routes-generator.ts:820 src/generators/burgs-generator.ts:778-779
Type Layer Violation
Problem

Generator layer directly calls viewContext.viewbox.select(...).remove() instead of delegating to controller/renderer. This violates the strict 4-layer architecture: Generators must NOT mutate SVG or DOM.

Current Impact
  • Breaks generator testability
  • Dual element management (generator + renderer)
  • Inconsistent SVG state
Root Cause

Legacy coupling; routes/burgs deletion refactored partially but generator still reaches across layers.

❌ Current (Violates Architecture) 
Generator (routes)
  ├─ worldContext.pack (✓ OK)
  ├─ Call viewContext.viewbox.select()
  ├─ .remove() SVG elements (❌ WRONG)
  └─ DOM side effect

Renderer
  └─ Tries to render removed elements
✅ Desired (Layered) 
Generator (routes)
  ├─ worldContext.pack (✓ OK)
  └─ Return deletion set

Editor (controller)
  ├─ Receive deletion set
  ├─ Call RouteRenderer.remove()
  └─ Renderer handles SVG mutation
Solution: Extract route deletion logic into an Editor-owned function. Generators return data; controllers coordinate renderer operations.

3. DIRECT ViewContext/WorldContext FIELD ACCESS (No Accessor Layer)

Strong Priority
Scope

47 controller files, 6 ViewContext layer groups scattered

Type Large (Coupling Hotspot)
Problem

Controllers directly access viewContext.ocean.select(), viewContext.biomes.attr(), etc. without validation or caching layer. 47 files reach into 6 layer groups independently. Any change to ViewContext structure ripples across all 47 files.

Why This Matters
  • Cannot refactor rendering backend
  • Hard to add caching/memoization
  • No consistency enforcement
  • Breaking changes cascade
Example Breaking Change

If SVG layer structure changes (e.g., nesting groups), all 47 files must update selectors.

❌ Direct Access (Brittle) 
Controller A: viewContext.ocean.select()
Controller B: viewContext.biomes.attr()
Controller C: viewContext.routes.classed()
...× 47 files

Change ViewContext → Update all 47
✅ Accessor API (Stable) 
viewService.getOceanLayer()
  └─ Returns SVGGElement (typed)
viewService.getBiomesLayer()
  └─ Handles structure changes internally

Controllers call viewService.*
1 change = 1 place to fix
Solution: Create ViewLayerService with getter methods for each layer group. Controllers call viewService.getLayer('biomes'). Centralizes mutation logic.

5. TIGHTLY-COUPLED GENERATOR CALLS (33 files, 6-12 imports each)

Worth Exploring
Pattern: import { Cultures, Religions, Routes, ... } from src/generators/ then direct calls like Cultures.generate()
Problem: 33 controller files import 6-12 generators each. Adding a new generator requires updating 33+ call sites. No explicit dependency graph or call order.
Solution sketch: Introduce GenerationPipeline facade. Controllers call one method; pipeline controls order, dependencies, and lifecycle.

🎯 Top Recommendation: Phased Attack Plan

Phase 1 (Weeks 1-2): Fix Critical Layer Violations

Target: Issues #1 (generator SVG mutations) and extract a single concern from #2 (style.ts)
Effort: Small, high-leverage. Unblocks testing and downstream refactors.
Result: Strict layer enforcement restored. Builds ground for Phase 2.

Phase 2 (Weeks 3-5): Break Monoliths Into Facades

Target: Extract ViewLayerService accessor API (Issue #3). Create GenerationPipeline facade (Issue #5).
Impact: Reduce coupling, enable independent testing, create seams for future refactors.
Payoff: 47 controller files now depend on stable interface, not brittle structure.

Phase 3 (Weeks 6+): Finish DOM Migration & Dialog Consolidation

Target: Complete 30% remaining DOM queries (Issue #4). Consolidate dialog state management.
Foundation: By now, ViewLayerService + GenerationPipeline are in place, unblocking React refactors.

Why This Order?

  • Phase 1 removes layer violations — architectural foundation must be solid before refactoring above it.
  • Phase 2 introduces seams (accessor APIs, facades) that unblock downstream work. Controllers become testable.
  • Phase 3 leverages the seams built in Phase 2. React refactors become safe because interfaces are stable.
