# Beerの物量増加と価格・レシピ・生産配分の切り分け(T15)

2026-10-22。[元の設計 §29・§30](../plan/goods-physical-units.md)の追加調査。[計測JSON](beer-supply-causal-observation-20261022.json)に入力・観測コード・生サンプルのSHA-256、契約、月次集計、条件試験のソース差分を保存した。通常の経済モデルは変更していない。

## 1. 結論

Beerの増加は単なる表示差ではない。ただし、「安くなったので家計が多く買った」という説明は棄却する。家計需要と消費量の決定処理は価格を参照せず、今回の価格だけの比較でも、**高い価格の方が製造・供給・消費が多い**。

§29は価格の再校正に加え、穀物の投入効率と、1 lotに対応する出力量・労働量・利益の尺度を同時に変えていた。安くした200 Lのままでは生産配分を失うが、1,000 Lにすると1 lotあたりの利益と出力量を確保できる。今回の条件試験では、この生産側の変化が値下げによる供給減を上回った。レシピの影響は価格水準によって向きも変わり、変更ごとの増減を単純に加算する説明にはできない。

同一入力での§29前後の実製造量は71.830→94.470 kL(+31.5%)、市場からの家計消費は82.078→99.340 kL(+21.0%)。§29に記載された61.2→104.1 kLの1.7倍という**過去の数値そのものは再現していない**。過去計測の生サンプル・実行条件との対応を確定できないため、1.7倍の各要因への厳密な配分は主張しない。表示差と実物増の区別、価格仮説の検証、生産側の変更の切り分けというT15の完了条件は満たした。

## 2. 条件と数え方

- 入力: `province-101.fmg`、SHA-256 `c4e2d3bae09117d9f9be2a3bcc88456a52d72228fcda579dfa9c39adfeebfb10`。§30と同一。seed=101、Settlement pattern=Standard、populationRate=1000。
- §29直前 `25670636c` と§29実装 `00e0c91d2`。各条件は別プロセスで同じ保存済み乱数状態から36か月、1か月刻み。長距離交易あり・隊商襲撃なし。他の設定は保存入力を維持する。多数シードの比較は行っていない。
- 価格試験は読込・移行後のBeerのカタログ値と既存の市場提示単価を同じ比率で変更。穀物試験はBeerの4原料経路の穀物量だけ変更。市場在庫・人口・労働・国庫は注入しない。月ごとに条件が上書きされていないことを検査する。
- 実製造量は `recordBeerCaskFilling` が完成量に比例して加算する `cumulativeBeerCaskReplacement` の期首差から求める。`差分 / レシピのBarrels係数 × L/lot`。係数は旧caskで0.08、tunで0.4。この台帳は完成量に対する名目修繕材の記録であり、実購入した樽材料の量ではない。
- 製造レコードは各都市の最新サイクルを示し、月内の複数サイクルや生産を休んだ都市の古い記録を含み得る。月末値を足して期間製造量にしない。生サンプルには診断用として残したが、集計JSONの製造量には使わない。
- `source:burgCraft` は都市から市場への**直接搬入**で、全製造量ではない。都市から輸送された荷は `source:importArrival` で到着する。市場消費は `sink:householdFood`。全条件・全月で「期首市場在庫＋source－sink＝期末市場在庫」と家計台帳の消費差分を照合した。
- 市場外・移動中の在庫は今回の在庫集計に含まない。製造期間と配送期間も異なるため、家計消費と同期間の製造を同量と仮定しない。保存済みの荷の単位互換性全体はT21の範囲に残す。

§30のBeer「都市生産」70.226→89.730 kLは直接搬入の値だった。今回の実製造量と区別して読む。

Beerは専用の労働校正表に載らず、今回の全条件で `applyCalibration=true`、`laborPointsForLots("Beer", 1, 1000)=1`。tunへの変更で労働点を5倍にしていない。実出力には文化・生産性等の倍率が掛かるため、表は実際の全労働の測定値ではなく契約の比較である。

表示だけの換算なら旧lot数を1/5にして1,000 Lを掛けるので、L数は保存される。一方、§29では同じ穀物1 wain・名目労働1点からの基準出力が200→1,000 Lになる。これは効率の変更を含む。単位だけの移行で実物量を保存するT18の基準とは区別する。

## 4. 同じ入力での7条件

数量は36か月累計、kL。単価はカタログ値/L。全条件で期首・期末の市場在庫は0だが、途中の全サンプルが0という意味ではない。

| 条件(JSONのrun名) | L/lot | 単価/L | 穀物wain/L | 実製造 | 家計消費 | 需要充足率 |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: |
| §29直前(`before`) | 200 | 0.0200 | 0.005 | 71.830 | 82.078 | 0.00942% |
| 直前版、Beerの単価・穀物だけ新値(`cask-new`) | 200 | 0.0024 | 0.001 | 5.954 | 5.594 | 0.00064% |
| 直前版、Beerだけtun化・新値(`beer-only`) | 1,000 | 0.0024 | 0.001 | 87.880 | 91.580 | 0.01051% |
| §29実装(`after`) | 1,000 | 0.0024 | 0.001 | 94.470 | 99.340 | 0.01140% |
| §29実装、Beerの単価/Lだけ旧値(`old-price`) | 1,000 | 0.0200 | 0.001 | 1,041.520 | 1,342.110 | 0.15408% |
| §29実装、Beerの穀物/Lだけ旧値(`old-grain`) | 1,000 | 0.0024 | 0.005 | 156.760 | 187.130 | 0.02148% |
| §29実装、Beerの単価・穀物/Lを旧値(`old-both`) | 1,000 | 0.0200 | 0.005 | 919.570 | 1,151.190 | 0.13216% |

`beer-only` は直前版のBeerのL定数・単位ラベル・市場在庫の1/5移行・物量定義・移行レシピの樽係数だけをtunに変更し、単価を観測スクリプトで設定した条件。Wine・果物等は旧仕様。再現可能なソース差分をJSONの `beerOnlySourcePatch` に保存した。

読み取れること:

1. **家計の直接の価格反応ではない。** `calculateAleDemand` は人口・成人比率0.65・年48 L/成人・水リスクで需要を求め、`drawHouseholdDemand` は需要残と在庫の小さい方を消費する。関連テストでは市場価格0.01と100を比較し、在庫不足・在庫十分の双方で需要・消費・未充足・残在庫が一致した。フローのvalueは在庫評価額で、家計の現金支出ではない。
2. **安いcaskは生産配分を失う。** `cask-new`→`beer-only` は同じLあたり単価・穀物量・修繕材量だが、製造5.954→87.880 kL。1 lotの利益・労働と出力量を変えるtun化は、表示の読み替えを超える。両者の差には輸送枠・価格平滑化・丸め等の単位依存も含むので、全量を労働効率だけに帰属させない。
3. **価格低下は供給を抑える側。** `old-price`→`after` は同じtun・レシピで単価だけを下げ、製造1,041.520→94.470 kL。生産者の採算・選択と、その後の配送・供給が変わった結果であり、需要が安さに反応した結果ではない。家計需要は全条件で大幅に未充足。
4. **歩留まり改善だけで供給増とは言えない。** 新価格では穀物を減らすと製造156.760→94.470 kLだが、旧価格では919.570→1,041.520 kLと逆になる。市場価格は原料費と付加価値から更新され、生産候補は売価・原料費・税・需要倍率から選ばれる。原料削減が提示価格と相対的な生産順位も変えるため、効果は条件に依存する。
5. **Beer以外の§29変更も影響する。** `beer-only`→`after` は製造87.880→94.470 kL。これは他の酒・果実・価格移行等の変更を含む比較で、品別の寄与率は分解していない。単一入力の差から一般的な増加率は定めない。

期末の市場提示単価の単純平均/Lは旧0.021541、新0.002314。家計消費フローの評価額/Lは旧0.023821、新0.003011。この違いは期末の提示単価と期間中の在庫評価の違いで、どちらも実際の家計支出の測定値ではない。

## 5. 再現と検証

観測器: `scripts/observeBeerSupply.mts`。指定リビジョンのソースツリーへ同じ観測器をコピーし、依存関係を用意して実行する。今回のNode 22/tsxで歴史版を実行するため、一時ツリーの `package.json` に `"type": "module"` を追加した。これは全条件共通の実行設定。

```sh
node --import tsx scripts/observeBeerSupply.mts province-101.fmg before.json --revision 25670636c
node --import tsx scripts/observeBeerSupply.mts province-101.fmg after.json --revision 00e0c91d2
# In the section-29 source tree:
node --import tsx scripts/observeBeerSupply.mts province-101.fmg old-price.json --revision 00e0c91d2 --price-per-liter 0.02
node --import tsx scripts/observeBeerSupply.mts province-101.fmg old-grain.json --revision 00e0c91d2 --grain-per-liter 0.005
node --import tsx scripts/observeBeerSupply.mts province-101.fmg old-both.json --revision 00e0c91d2 --price-per-liter 0.02 --grain-per-liter 0.005
# In the pre-section-29 tree, then in its beerOnlySourcePatch copy:
node --import tsx scripts/observeBeerSupply.mts province-101.fmg cask-new.json --revision 25670636c --price-per-liter 0.0024 --grain-per-liter 0.001
node --import tsx scripts/observeBeerSupply.mts province-101.fmg beer-only.json --revision 25670636c+beer-unit-patch --price-per-liter 0.0024
```

7条件×36か月を完走。全条件の入力・観測器のハッシュ一致、全252月の市場在庫収支と家計台帳を照合した。現在版の観測器は1か月の実行も確認。`npx vitest run src/extensions/economy/generators/foodProcessingLedger.test.ts` は12件成功(追加した価格比較2件を含む)。変更テストのBiomeチェックも成功。

今回、通常モデルの価格・レシピ・労働配分は変更していない。Beerの単位に依存する労働・価格処理の解消はT18・T19、移行中の荷はT21で扱う。
