# CE森林 F0：固定入力・既存負荷・樹木規模の計測

実施日：2026-10-28（JST）

対象計画：[ce-forest-surroundings.md](../plan/ce-forest-surroundings.md)

## 1. 結論

F0の固定3入力による計測と接続先の確認を実施した。F1へ進める条件として、以下を採用する。

1. **2Dは面＋林縁を既定にする。** 全域の木を林縁だけにすると、今回の森林用SVG要素数は約79〜85%減った。ただし林縁にも上限が必要。
2. **既存の詳細樹木を森林全域へ使わない。** シナノキ相当の `garden_parkland` は1本84,098三角形。16本でも約135万三角形になる。樹種・色の選択は再利用し、森林用の形状は軽量な別LODを作る。
3. **立木のインスタンス化だけでは不足する。** 80三角形の樹冠でも、小都市の全域で約87万、中都市で約353万三角形。遠景の内部を連続した粗い樹冠メッシュへまとめる。
4. **近景は128 mチャンク、遠景は256 m単位でまとめる。** 64 mでは俯瞰のdraw call見積もりが増え、256 mだけでは近景で不要な木を多く送る。寸法は構造的な比較からの初版の選択であり、GPU時間の最適値とは主張しない。
5. **森林用地の解決を農地候補の選定前へ入れる。** 表示後に畑を隠す方式では、畝・小屋・Workerの古い結果が残る。F1では既存のfingerprintと結果採用判定を拡張する。

**実GPUでの33 ms目標は未検証。** この環境のChromiumはSwiftShaderを使用し、`render()`＋`gl.finish()`の値も0〜0.1 msへ丸められた。これらからFPSやGPUの余裕を推定しない。F0で決めるのは実装の構造・初版の総量制限までとし、フレーム時間による品質の校正はF3〜F5で実GPU上にて行う。

## 2. 再現方法と計測範囲

```sh
node --import tsx scripts/benchmarkCeForest.mts
node --import tsx scripts/analyzeCeForestChunks.mts
```

- 固定レシピ：[ce-forest-f0-v1.json](fixtures/ce-forest-f0-v1.json)。固定3都市のみ。seed探索・多数seedの試験は行っていない。
- 全数値と各サンプル：[results.json](ce-forest-f0/results.json)。実行時のGit HEAD、実際の生成設定、seed、入力ファイルのSHA-256、生成文書のSHA-256も収録した。Git HEADは実行時の基点であり、今回追加した未コミットの計測コードを含むコミットではない。
- チャンクの構造比較：[chunk-analysis.json](ce-forest-f0/chunk-analysis.json)。入力レポートのSHA-256を含む。
- 環境：Apple M4 / arm64 / macOS、Node v22.23.1、Headless Chromium 151、Three.js r185、1000×720、DPR 1。プロジェクトの推奨Nodeは24以上だが、今回の実測環境は22。
- Nodeの農地再生成、ブラウザーのSVG・農地メッシュ構築は、ウォームアップ1回＋3回の中央値。都市生成、fabricの初回構築、3D mount、3Dの計測用表現の構築は各1回。
- 実際の `mountCity3d()` で既存の都市全体も計測した。俯瞰と郊外への接近の各姿勢で3回を除外後24回のCPU submit時間を収録。これはGPU完了時間や操作全体のフレーム時間ではない。
- 別の描画専用シーンでは同じ都市の簡略建物に、既存農地／全域の簡略樹冠／箱状の樹冠／詳細樹木16本を切り替えた。影は1024²で有無を比較し、実CEの4096²・オンデマンド更新とは条件を分けた。
- 森林の配置は、**生成済みの農地区画内にある8 m格子の中心**を使う計測専用の近似。林縁は4近傍の欠けた点。正式なセル単位の森林用地、ポリゴンunion、樹冠分の余白、揺らぎ、LOD、施設の最終保護判定はまだ実装していない。
- SVGのforest overlay構築時間は、共通の都市SVGのclone・農地削除を除く。attach/layout時間には共通の都市も含まれる。2D・3Dの画像は負荷比較の試作であり、完成した森林表現の見本ではない。

固定入力の成立も確認した。平坦な2件は陸セル標高1 m・河川なし。谷の1件は陸セル標高2.3〜50 m・河川1本である。すべて単独CE生成のためFMGのSettlement patternや経済シミュレーションは介在しない。

実CEのdraw calls・三角形数は `renderer.info` から取得し、既存の影等も含む。geometryを一度だけ数えた常駐量とは異なる。農地3D構築の計測では地形モデルの準備時間を別に取り、上表の値へ含めていない。

既存の景観が非常に少ないのは、森林バイオームを指定しても農地区域を森にする処理がないため。`landscape.ts` は `ward` が空でないセル等を景観配置から除く。散布確率を上げるだけでは耕作地を森林化できない。

中都市は既存のSVG構築だけでも約2.2秒かかっている。森林追加の時間と既存市街の時間を分けて扱い、森林の品質切替で都市全体のfabricやSVGを毎回作り直さない。

## 5. 3Dのモデル規模と表現

### 既存樹木

geometryのバッファは共有前の1モデル分の配列バイト数で、GPUメモリ実測ではない。すべて同じ幾何をインスタンス化できても、描画三角形数は本数倍になる。

| 樹種モデル | 三角形/本 | 材質数 | 配列バイト数 | 構築中央値 |
| --- | ---: | ---: | ---: | ---: |
| garden_parkland | 84,098 | 2 | 8,696,808 | 29.61 ms |
| norway_spruce | 44,246 | 2 | 4,778,568 | 11.31 ms |
| silver_birch | 51,320 | 2 | 5,542,560 | 13.22 ms |
| sacred_yew | 33,428 | 2 | 2,989,176 | 10.31 ms |
| mediterranean_cypress | 280 | 2 | 11,056 | 0.44 ms |
| oriental_evergreen | 136 | 2 | 8,912 | 0.27 ms |
| sacred_bodhi_and_fig | 1,424 | 2 | 56,704 | 0.51 ms |
| peaceful_willow | 1,104 | 2 | 38,784 | 0.44 ms |

`garden_parkland`を小都市の10,815点へそのまま配置すると計算上909,519,870三角形になる。森林用のLODを必須とする根拠として十分大きい。

### 森林の計測用表現

下表は森林部分だけの三角形数。80三角形は幹なしのicosahedron樹冠、12三角形は8 m格子ごとの箱。完成モデルの外観・遮蔽・地形への連続的な追従は評価していない。

| 表現 | 平坦な小都市 | 平坦な中都市 | 川と谷の小都市 |
| --- | ---: | ---: | ---: |
| 全域の80三角形樹冠 | 865,200 | 3,525,120 | 908,240 |
| 全域の12三角形の箱 | 129,780 | 528,768 | 136,236 |
| 詳細な既存樹木16本 | 1,345,568 | 1,345,568 | 1,345,568 |

箱の樹冠でも中都市の標準予算30万を超える。内部を16〜32 m程度の粗いメッシュへまとめ、林縁と穴の近くのみ細かくする。粗くする際にも正本の森林境界を越えて水域や道路を埋めない。画像の[簡略樹冠を全域配置](ce-forest-f0/small-flat-3d-low-poly-all.png)と[箱状の樹冠](ce-forest-f0/small-flat-3d-canopy-tiles.png)は見え方の差の確認用で、後者の水平な格子状の外観はF3で起伏・輪郭・色を改善する。

影なしでは森林1バッチを足しても都市の簡略建物と合わせて3 draw callsだが、三角形数は上表のまま。小都市の80三角形樹冠は、影を毎フレーム描く試験でシーン全体894,766→1,759,966三角形になった。全森林の影は既定にしない。

## 6. チャンク寸法と初版の制限

全サンプルを同一樹種・材質2種類で描く場合のAABB/視錐台による構造見積もり。LOD・遮蔽・影は含まず、実GPUのdraw時間ではない。

| 中都市のチャンク幅 | 俯瞰・可視チャンク | 俯瞰・提出樹木数 | 俯瞰・draw calls見積もり | 接近・提出樹木数 | 接近・draw calls見積もり |
| --- | ---: | ---: | ---: | ---: | ---: |
| 64 m | 577 | 31,210 | 1,154 | 1,409 | 60 |
| 128 m | 175 | 33,467 | 350 | 2,157 | 24 |
| 256 m | 56 | 36,284 | 112 | 4,567 | 12 |

128 mなら、64 mに比べ俯瞰で提出する木が約7%増える代わりにdraw callsは約70%減る。256 mは接近時に128 mの約2.1倍の木を提出する。したがって個別の立木は128 m、遠景の樹冠は256 mへ集約する。128 mを全域のまま使うだけでも350 callsなので、距離による表現の切替が必要。

初版の制限を次のように置く。品質保証値ではなく、超えたら簡略化する打切り条件である。

| 森林品質 | 可視個別樹木の絶対上限 | 森林の可視三角形上限（主描画） | 主描画draw calls上限 | 森林の影 |
| --- | ---: | ---: | ---: | --- |
| 軽量 | 2,000 | 100,000 | 64 | 投影しない |
| 標準 | 8,000 | 300,000 | 128 | 近景のみ、投影三角形50,000まで |
| 高品質 | 20,000 | 800,000 | 256 | 近景のみ、投影三角形150,000まで |

近景の森林用モデルは幹込み256三角形以下、中景は64以下を実装の初期目標とする。個体数より三角形・draw callsが先に上限へ達したら内部を先に簡略化する。既存の詳細樹木は既定で森林に使わず、後に目立つ少数へ使う場合も全予算へ含める。遠景は原則1材質とし、樹種差は色・輪郭へまとめる。

自動品質は、実GPUで初期品質と上下の判定を校正するまで軽量へ落とせる手動設定を必ず残す。今回の丸められたフレーム時間を閾値の校正へ使用しない。

## 7. F1で変更する接続先

| 接続先 | 必要な変更 |
| --- | --- |
| `types/document.ts`、`types/generationSettings.ts`と保存・共有入力 | 都市・セルの森林指定を正本として伝播。未指定は従来動作 |
| `generators/generation/generateCity.ts`の最終`farmland`ステージ | 施設・防御・道路を確定した都市に森林指定を渡し、農地ステージ前から有効にする |
| `generators/ruralFieldStage.ts`の`regenerateRuralLand()`後、農地区画生成前 | 農地候補と森林用地を排他にする。`createLotPads`も含む既存ステージの責務を維持 |
| `generators/ruralFields.ts`の陸地・`ward: farm`候補の選択 | 森林指定と保護領域を除外。`applyRuralFields()`を直接呼ぶ経路にも効かせる |
| `generators/blockInfill.ts`の旧農地経路・`overlayFabric()`・fingerprint | 旧経路とoverlay適用後も排他を守り、forest設定・セル指定の変更で無効化する |
| `controllers/mapDisplay.ts`の`generateFarmland()` | 現在あるrequest・document・fingerprintの採用判定を再利用。森林化後の古いWorker結果を棄却する。新しい並行ジョブ管理を一から作らない |
| `generators/ruralFieldOverlay.ts`、`services/ruralFieldWorker*.ts` | 森林入力込みの同じキーでsnapshot・overlay・Workerを扱う |
| `renderers/editorSvg.ts`の`landscapeSlot` | 施設のkeep-out収集後に森林を描き、森林の範囲では従来の散布を止める |
| `renderers/townFabricSvg.ts`の`farmSheds()`等 | 農地配列から派生するものを森林化後の配列にそろえる |
| `renderers/cityView.ts`の農地更新判定と`dispose()` | 森林のdirty判定と資源破棄を追加。品質・カメラだけの変更で市街を再構築しない |

省略したパスの起点は `src/city-editor/`。共通の森林用地解決は `buildBlockFabric()`を内部で呼ばない設計にする。そうしないと農地生成→森林解決→fabric生成という再帰が起こり得る。用地の判定と、建物・予約計画を受け取って作る描画用の輪郭を分ける。
