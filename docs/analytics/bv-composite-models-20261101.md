# BV複合モデルの負荷調査

2026-11-01。対象はUrban mendicant friaryと、住宅・施設を組み合わせたMedieval 08 / 10 / 12 / 15。

## 結果

Friaryの旧Lowに含まれる樹木4本が336,392三角形、全体350,742の95.9%を占めた。`createMonastery`が`createLandscapeTree("garden_parkland")`と品質を省略しており、単独樹木factoryの既定値Ultraが採用されていた。`siteVariants.ts`の`basedOn`も明示的にUltraを指していた。修道院の建築にHigh登録があるわけではない。

植栽品質を独立した`MonasteryRenderOptions.vegetationQuality`として追加し、既定をLowに変更した。Friary・Abbey・Orthodox共通の生成経路と既定構成の依存元を修正。旧Ultraは同じ計画に`{ vegetationQuality: "ultra" }`を指定して再現できる。BVのUIへこの選択肢を追加する作業は後続とする。

| 固定プレビュー | 変更前の三角形 | 変更後の三角形 | 樹木なし | 変更後メッシュ数 |
| --- | ---: | ---: | ---: | ---: |
| Friary（樹木4本） | 350,742 | 14,914 | 14,350 | 497 |
| Abbey（樹木3本） | 267,348 | 15,477 | 15,054 | 524 |
| Orthodox（樹木2本） | 181,652 | 13,738 | 13,456 | 486 |
| Salisbury Low | 11,754 | 変更なし | — | 364 |
| Salisbury High | 295,432 | 変更なし | — | 58 |

Friaryの三角形数は95.75%減。樹木を含むメッシュ数は変わらないため、BVでの描画回数の問題が解決したことを意味しない。

## Friaryの部品内訳

旧構成のトップレベル部品を集計した。頂点・材質は部品間で共有する場合があるので、ユニーク資源数は部品の値を単純合算できない。

| 部品群 | メッシュ数 | 三角形 |
| --- | ---: | ---: |
| 樹木4本（旧Ultra） | 8 | 336,392 |
| 井戸 | 319 | 11,284 |
| 回廊の柱 | 20 | 1,280 |
| 窓の暗色オーバーレイ | 100 | 1,200 |
| それ以外の教会堂・居住棟・回廊屋根・庭・壁等 | 50 | 586 |
| 合計 | 497 | 350,742 |

樹木なしの14,350三角形の78.6%を井戸が占める。樹木と井戸を生成前に除くと、建築・外構は170メッシュ、3,066三角形。これらを隠すだけでなく、計画から除外した対照生成で確認した。

井戸の主な内訳は井筒の石64個が3,328三角形、笠石16個が832、巻き縄13巻が3,120、屋根板168枚が2,016。全体の輪郭に比べて細部に多く配分されている。井戸を消すのでなく、敷地の付属物としてのLow部品を別途用意するのが適切である。

単木`garden_parkland`はLow 141、Medium 2,043、High 21,626、Ultra 84,098三角形。FriaryのLow樹木4本は564三角形になる。各木を別々にfactoryで生成する現方式では、同形でもバッファ・材質は別に作られる。

## メモリ・結合経路

| Friary構成 | メッシュ数 | 三角形 | 属性・index配列のバイト数 |
| --- | ---: | ---: | ---: |
| BV 変更前 | 497 | 350,742 | 34,943,456 |
| BV 変更後 | 497 | 14,914 | 210,368 |
| CE 変更前 | 1 | 350,742 | 37,880,136 |
| CE 変更後 | 1 | 14,914 | 1,610,712 |
| CE 樹木なし | 1 | 14,350 | 1,549,800 |

CEの`createTownMonasteries`は全pickablesをclone・ワールド変換・非index化し、色属性を追加して一つに結合する。描画メッシュは減るが三角形数は変わらず、共有形状も展開される。上表は最終的に保持するCPUの配列だけで、構築中のclone、JSオブジェクト、GPU・ドライバの確保は含まない。ピークメモリやFPSの実測値とは扱わない。

Highは最後に`compactModel`で材質別に結合するため、三角形が多くてもメッシュ数が小さい。Low/Highの処理負荷は三角形だけで一列に比較できない。今回、これらのモデルのFPSや部品別負荷は測定していない。

Highの生成関数には建築棟・窯・厩舎などの境界が既にあるが、共有kitに固定座標で生成し、最後に一体化している。再利用可能な部品factoryと配置計画に分ければ、意味のあるバリエーションを作れる。住宅への店舗開口等は外殻の生成入力も変更する必要がある。分割・分類・パラメーター・実施順序は[設計書](../plan/bv-composite-models.md)に記載した。

## 検証と再現

- `node --import tsx scripts/profileBvCompositeModels.mts`：固定プレビュー、修正前Ultraの明示再現、修正後Low、樹木除外、井戸除外、単木4品質、井戸部品、Salisbury、住宅系9モデルのLow/Highを生成し、数えた後にdisposeする。
- [変更前JSON](bv-composite-profile-before-20261101.json)：修正前に取得。CEの旧結合結果を含む。
- [変更後・部品内訳JSON](bv-composite-profile-20261101.json)：P0時点の記録。`BV-legacy-ultra`は旧植栽品質の明示再現。P1以降のスクリプトは井戸Lowも扱い、別名のJSONへ出力する。
- 時間はNode v22の単発観測で、順序・JIT・キャッシュの条件は揃えていない。速度改善率やFPSの根拠には使わない。変更前JSONの`cold observation`というmethod表記も、厳密なcold計測を保証するものではない。
- `npx vitest run src/city3d/three/friaryMeshes.test.ts src/city-editor/generators/monasteryLayout.test.ts`：23件成功。追加した回帰テストでBV・CEの明示的Low、固定例20,000三角形未満、植栽Ultraの独立指定を検証。既存の回廊の空洞・門の通路・回転／標高・資源解放も成功。
- `npx vitest run src/city3d/adoption.test.ts`：3件成功。既存のモデルID・CE採用を確認。
- 実BV：Urban mendicant friaryの全体・平面図を目視。回廊の中庭、菜園、樹木、教会堂、居住棟を確認。インスペクターはLowのみ、497メッシュ・14,914三角形でNode計測と一致。CEの対話操作とGPU FPSは今回測定していない。
