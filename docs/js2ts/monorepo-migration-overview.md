# JS2TS Monorepo Migration Overview

## 背景
Fantasy Map Generator は長年の運用で `public` 配下にレガシーな JavaScript が蓄積され、以下の課題がありました。

- 型安全性が低く、変更時の破壊的影響を検知しづらい
- 依存関係が暗黙的で、モジュール境界が不明確
- グローバル変数の利用が多く、保守時の回帰リスクが高い
- ビルドとテストの統合が弱く、段階的移行の足場が不足

## モノリポジトリ化の主目的
**主目的は `public` 内のレガシーな JavaScript ファイルを TypeScript へ段階的に移植すること**です。

この主目的を実現するために、モノリポジトリ化では次を狙いました。

- 共有型・共有ユーティリティ・生成ロジック・UI の責務分離
- TS 移行中でも既存 `.map` 互換を維持できる移行導線の確立
- 既存 runtime を壊さない互換レイヤー（compatibility layer）構築
- CI/ローカル双方で再現可能なビルド・E2E テスト基盤の整備

## 新しい構成（概要）
ワークスペース構成を導入し、段階的移植を進められる形に整理しました。

- `@fmg/types`: グローバル宣言・共通型
- `@fmg/shared`: 共通ユーティリティ
- `@fmg/core`: 生成アルゴリズムとコアモジュール
- `@fmg/legacy-ui`: 既存 UI/編集系の互換レイヤー

ルート側では npm workspaces + TypeScript + Vite の連携を前提に、
既存コードを急激に壊さず移行できる設定（path alias / build alias）を整備しています。

## 今回の移行で整備した要点

1. ワークスペース境界を定義し、責務を package 単位で分離
2. `src/modules/index.ts` などの互換レイヤーで既存参照を吸収
3. 型定義とグローバル宣言を `@fmg/types` に集約
4. ユーティリティ群を `@fmg/shared` として再利用可能化
5. Vite/tsconfig の alias 解決を統一し、ビルド時解決エラーを抑制
6. build パイプライン（`tsc` → `vite build`）を通る状態に復旧

## なぜモノリポジトリが有効か
`public` 配下の JS を TS 化する際、既存コードと新コードが長期間共存します。
モノリポジトリ化により、以下が可能になります。

- 共通型を横断利用して移植品質を均一化
- 段階移行（ファイル単位/機能単位）でも依存の見通しを維持
- 旧実装と新実装の共存期間における回帰影響を局所化
- package 単位で変更範囲を限定し、レビューとテストをしやすくする

## 直近の移植方針（public JS → TS）

- `public` の高利用モジュールから優先移植（影響範囲と効果で優先度付け）
- 1ファイル移植ごとに型定義を `@fmg/types` へ寄せる
- 汎用処理は `@fmg/shared` に吸い上げ、重複ロジックを削減
- UI 依存は `@fmg/legacy-ui` で段階吸収し、最終的に整理
- 各段階で `npm run build` と E2E を通し、回帰を早期検知

## 成果指標（Definition of Done の例）

- `public` 配下の対象 JS が TS に置換され、型エラーなし
- 既存 `.map` データのロード・生成・編集の互換が維持される
- 本番ビルド（`npm run build`）が安定して成功する
- 主要操作の E2E がグリーンを維持する
